Конспект к собеседованию по аннотациям типов и по тому, во что оформлять данные: что проверяет mypy и чего не проверяет интерпретатор, отложенные аннотации (PEP 649), generics и `Protocol`, а также `dataclass`, `NamedTuple` и pydantic — когда какой, как валидировать вход и читать настройки из окружения.
Рядом: [[Типы и изменяемость]] (изменяемый default в `dataclass` — тот же корень, что и в аргументах функций) · [[Атрибуты и дескрипторы]] (что делает `slots=True`) · [[Деньги и числа]] (`Decimal`, который лежит в этих моделях).
Разделы: [[#Аннотации в рантайме и в mypy]] · [[#Отложенные аннотации (PEP 649)]] · [[#Generics: PEP 695]] · [[#Protocol и ABC]] · [[#Мелкие конструкции typing]] · [[#dataclass, NamedTuple, BaseModel]] · [[#Кортеж в возврате против dataclass]] · [[#pydantic v2]] · [[#pydantic-settings]] · [[#Что спросят дальше]]

Примеры запускались на Python 3.15.0, pydantic 2.14, mypy 2.4 (`--python-version 3.14`; вывод mypy сокращён до нужных строк).

**Суть.** Аннотации — метаданные: интерпретатор их запоминает и не проверяет, проверяют внешние инструменты (mypy, pyright) и библиотеки, которые читают аннотации сами (pydantic, FastAPI). Поэтому «типизированный» код без mypy в CI ничем не защищён, а граница с внешним миром (JSON, окружение) закрывается не mypy, а валидацией на входе.

## Аннотации в рантайме и в mypy

```python
def add(a: int, b: int) -> int:
    return a + b

print(add("x", "y"))
print(add.__annotations__)
```

```text title="Вывод"
xy
{'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

Код отработал: `"x" + "y"` — валидный Python. Та же программа под mypy:

```text title="mypy"
a1.py:3: error: Argument 1 to "add" has incompatible type "str"; expected "int"  [arg-type]
a1.py:3: error: Argument 2 to "add" has incompatible type "str"; expected "int"  [arg-type]
```

mypy проверяет статически, по исходнику, и только то, что аннотировано; неаннотированные функции по умолчанию пропускает. Он не видит, что реально пришло из `json.loads` или `os.environ`: там тип `Any` или `str`, и пока значение не прошло валидацию, аннотация — обещание, а не гарантия.

## Отложенные аннотации (PEP 649)

До 3.14 аннотации вычислялись в момент определения функции, поэтому ссылка на ещё не объявленный класс падала с `NameError`; обходились строками или `from __future__ import annotations`. С 3.14 (PEP 649/749) аннотации вычисляются лениво — при первом обращении к `__annotations__`. Модуль `annotationlib` умеет получить их в разных форматах:

```python
import annotationlib
from annotationlib import Format

def f(x: Later) -> int: ...

try:
    f.__annotations__
except NameError as e:
    print("NameError:", e)

print(annotationlib.get_annotations(f, format=Format.FORWARDREF))

class Later: ...
print(f.__annotations__)
```

```text title="Вывод"
NameError: name 'Later' is not defined
{'x': ForwardRef('Later', owner=<function f at ...>), 'return': <class 'int'>}
{'x': <class '__main__.Later'>, 'return': <class 'int'>}
```

Само определение `def f(x: Later)` не упало: имя разрешается только при обращении. Пока `Later` не существует, `__annotations__` кидает `NameError`, а `FORWARDREF` даёт `ForwardRef` вместо ошибки (есть ещё `STRING`). После определения класса обычное чтение работает.

А `from __future__ import annotations` по-прежнему делает все аннотации строками (`f.__annotations__` даёт `{'x': 'Later', 'return': 'int'}` и без определения `Later`), вычислить их можно только вручную.

На 3.14+ `__future__` для forward-ссылок больше не нужен, а сам он остаётся (его пока не удаляют). Для кода, который читает аннотации в рантайме (pydantic, FastAPI, `dataclasses`), вместо `typing.get_type_hints` на новых версиях лучше `annotationlib.get_annotations`.

## Generics: PEP 695

С 3.12 типовые параметры объявляются в самой сигнатуре: без `TypeVar` на уровне модуля.

```python
from typing import Hashable

def first[T](xs: list[T]) -> T:
    return xs[0]

class Box[T]:
    def __init__(self, item: T) -> None:
        self.item = item

type Pair[K] = tuple[K, K]

def longest[S: Hashable](a: S, b: S) -> S:     # bound: всё, что Hashable
    return a

p: Pair[int] = (1, "x")
longest([1], [2])
print(Pair, Pair.__value__, first.__type_params__, Box.__type_params__)
```

```text title="mypy"
g3.py:15: error: Incompatible types in assignment (expression has type "tuple[int, str]", variable has type "tuple[int, int]")  [assignment]
g3.py:16: error: Value of type variable "S" of "longest" cannot be "list[int]"  [type-var]
```

```text title="Вывод"
Pair tuple[K, K] (T,) (T,)
```

`type Pair[K] = ...` создаёт `TypeAliasType`, правая часть вычисляется лениво (`__value__`). `S: Hashable` — верхняя граница (bound): подойдёт любой хэшируемый тип, `list` mypy отвергает; `[N: (int, float)]` — перечисление допустимых типов (constraints), на каждом вызове выбирается один. Старый стиль `T = TypeVar("T")` работает по-прежнему и нужен только для версий < 3.12.

`ParamSpec` (`def logged[**P, R](func: Callable[P, R]) -> Callable[P, R]`) нужен декораторам, чтобы обёртка сохраняла сигнатуру исходной функции; подробнее про декораторы — [[Декораторы]]. Проверено в mypy: после `@logged` над `pay(amount: int, *, currency: str = "RUB")` вызов `pay("1")` даёт `Argument 1 to "pay" has incompatible type "str"; expected "int"`, а `pay(1, currency=5)` — ошибку про `currency`. С `Callable[..., Any]` обёртка стёрла бы сигнатуру, и обе ошибки пропали бы.

## Protocol и ABC

ABC — номинальная типизация: класс должен явно унаследоваться. `Protocol` — структурная: подходит любой объект с нужными методами, без наследования и без импорта протокола.

```python
from typing import Protocol

class Closer(Protocol):
    def close(self) -> None: ...

class File:
    def close(self) -> None: ...

class Bad:
    def close(self, force: bool) -> int:
        return 1

def shutdown(x: Closer) -> None:
    x.close()

shutdown(File())
shutdown(Bad())
```

```text title="mypy"
p1.py:19: error: Argument 1 to "shutdown" has incompatible type "Bad"; expected "Closer"  [arg-type]
p1.py:19: note: Following member(s) of "Bad" have conflicts: ...
```

`File` подошёл без наследования, `Bad` — нет: mypy сравнивает сигнатуры. ABC же проверяется в рантайме при создании экземпляра: `Base()` с абстрактным `close` даёт `TypeError: Can't instantiate abstract class Base without an implementation for abstract method 'close'`, а структурно подходящий `File` не наследник: `issubclass(File, Base)` — `False`.

`@runtime_checkable` разрешает `isinstance` по протоколу, но проверяет только **наличие** атрибутов, не сигнатуры и не типы:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Closer(Protocol):
    def close(self) -> None: ...

class Bad:
    def close(self, force: bool, other: int) -> int:
        return 1

print(isinstance(Bad(), Closer), isinstance(42, Closer))
```

```text title="Вывод"
True False
```

`Bad` с несовместимой сигнатурой для `isinstance` — «закрывалка»; без декоратора `isinstance` на протоколе запрещён (`TypeError: Instance and class checks can only be used with @runtime_checkable protocols`), а `issubclass` не работает для протоколов с данными. Выбор: `Protocol` — для границ между слоями и тестовых дублей, ABC — когда нужна общая реализация в базе и принудительное переопределение абстрактных методов в рантайме.

## Мелкие конструкции typing

- `TypedDict` — форма словаря с известными ключами.
- `Literal["auto", "manual"]` — только перечисленные значения; опечатку ловит mypy.
- `NewType("UserId", int)` — отдельный тип для mypy; в рантайме вызов возвращает исходный `int`.
- `Final` — имя нельзя переприсвоить (проверяет mypy, не интерпретатор).
- `Self` — метод возвращает тип того класса, у которого вызван (цепочки, наследование).
- `TypeIs[str]` (3.13) — функция-предикат сужает тип в обеих ветках; старый `TypeGuard` сужает только в положительной.

```python
from typing import Final, Literal, NewType, TypedDict, TypeIs

class Payment(TypedDict):
    id: int
    currency: str

UserId = NewType("UserId", int)
MAX: Final = 3

def is_str(x: object) -> TypeIs[str]:
    return isinstance(x, str)

def run(mode: Literal["auto", "manual"], uid: UserId, v: int | str) -> None:
    if is_str(v):
        reveal_type(v)
    else:
        reveal_type(v)

p: Payment = {"id": 1, "curency": "RUB"}
run("autp", 5, 1)
MAX = 4
```

```text title="mypy"
t2.py:15: note: Revealed type is "str"
t2.py:17: note: Revealed type is "int"
t2.py:19: error: Missing key "currency" for TypedDict "Payment"  [typeddict-item]
t2.py:19: error: Extra key "curency" for TypedDict "Payment"  [typeddict-unknown-key]
t2.py:20: error: Argument 1 to "run" has incompatible type "Literal['autp']"; expected "Literal['auto', 'manual']"  [arg-type]
t2.py:20: error: Argument 2 to "run" has incompatible type "int"; expected "UserId"  [arg-type]
t2.py:21: error: Cannot assign to final name "MAX"  [misc]
```

В рантайме `NewType(5)` возвращает обычный `int`, а `TypedDict` — обычный `dict` без проверок.

## dataclass, NamedTuple, BaseModel

`@dataclass` генерирует `__init__`, `__repr__`, `__eq__`; полезные параметры: `frozen=True` (неизменяемый, получается хэшируемым), `slots=True` (без `__dict__`, меньше памяти, нельзя добавить чужой атрибут), `kw_only=True` (поля только по имени — новое поле в середине не ломает позиционные вызовы).

```python
from dataclasses import dataclass, field, FrozenInstanceError

@dataclass(frozen=True, slots=True, kw_only=True)
class Fee:
    amount: int
    currency: str = "RUB"
    tags: list[str] = field(default_factory=list)

f = Fee(amount=100)
print(f)
try:
    f.amount = 5
except FrozenInstanceError as e:
    print("FrozenInstanceError:", e)
```

```text title="Вывод"
Fee(amount=100, currency='RUB', tags=[])
FrozenInstanceError: cannot assign to field 'amount'
```

`kw_only` не даёт вызвать `Fee(100)` (`TypeError`), `slots` и `frozen` закрывают и новые атрибуты, а неизменяемость поверхностная: `f.tags.append(...)` пройдёт. Изменяемый default (`tags: list[str] = []`) dataclass отвергает при определении класса: `ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory` (та же ловушка, что с аргументом по умолчанию, — [[Типы и изменяемость]]).

| | `dataclass` | `NamedTuple` | pydantic `BaseModel` |
|---|---|---|---|
| Проверка типов на входе | нет | нет | да, с приведением |
| Изменяемость | по умолчанию да, `frozen=True` — нет | нет | по умолчанию да, `frozen=True` в конфиге |
| Это кортеж (индексы, распаковка, `==` с кортежем) | нет | да | нет |
| Где использовать | внутренние данные между слоями | когда форму задаёт чужой кортежный контракт | граница системы: HTTP, очередь, конфиг |

## Кортеж в возврате против dataclass

Функция, которая возвращает `tuple[Decimal, Decimal]`, не говорит, где сумма, а где комиссия. Перепутанный порядок — валидный код, mypy его пропустит: типы одинаковые.

```python
from dataclasses import dataclass
from decimal import Decimal
from typing import NamedTuple

class Split(NamedTuple):
    amount: Decimal
    fee: Decimal

@dataclass(frozen=True, slots=True)
class SplitDC:
    amount: Decimal
    fee: Decimal

s = Split(Decimal("100"), Decimal("3"))
print(s == (Decimal("100"), Decimal("3")), s[0], s.fee)

def split_tuple() -> tuple[Decimal, Decimal]:
    return Decimal("3"), Decimal("100")   # перепутан порядок

amount, fee = split_tuple()
print(amount, fee)
d = SplitDC(Decimal("100"), Decimal("3"))
print(d == (Decimal("100"), Decimal("3")))
```

```text title="Вывод"
True 100 3
3 100
False
```

`NamedTuple` называет поля, но остаётся кортежем: равен обычному кортежу, индексируется, распаковывается позиционно. Значит, добавленное поле сломает всех, кто распаковывал в два имени, а `Split(...) == (a, b)` не отличит модель от случайного кортежа. Frozen dataclass от кортежа отделён: доступ только по имени, равенство только со своим типом, новое поле не ломает вызывающих. Поэтому правило: несколько связанных значений — frozen dataclass с доменным именем; кортеж — только там, где форму задаёт чужой контракт (`asyncio.gather`, `(body, status)` во Flask, `select(A, B)`), и `tuple[X, ...]` как однородная коллекция. Ошибку вторым элементом кортежа не возвращают, её выбрасывают исключением.

## pydantic v2

`BaseModel` разбирает вход: приводит типы (в нестрогом режиме) и собирает **все** ошибки сразу.

```python
from decimal import Decimal
from pydantic import BaseModel, ValidationError

class Money(BaseModel):
    amount: Decimal
    currency_code: str

m = Money.model_validate({"amount": "10.50", "currency_code": "rub"})
print(repr(m))
print(m.model_dump_json())
try:
    Money.model_validate({"amount": "abc"})
except ValidationError as e:
    print(e)
```

```text title="Вывод"
Money(amount=Decimal('10.50'), currency_code='rub')
{"amount":"10.50","currency_code":"rub"}
2 validation errors for Money
amount
  Input should be a valid decimal [type=decimal_parsing, input_value='abc', input_type=str]
    For further information visit https://errors.pydantic.dev/2.14/v/decimal_parsing
currency_code
  Field required [type=missing, input_value={'amount': 'abc'}, input_type=dict]
  ...
```

Строка `"10.50"` стала `Decimal`; `model_dump()` отдаёт словарь Python-объектов (с `Decimal`), `model_dump_json()` — готовую JSON-строку (`Decimal` в ней — строка). `model_validate` для dict, `model_validate_json` для строки JSON.

Нормализацию входа держат в самой модели, а не в обработчиках: `field_validator` правит одно поле, `model_validator(mode="after")` проверяет согласованность полей. Так `currency_code` приходит в сервис уже в верхнем регистре, и «забыть `.upper()`» в новом эндпоинте нельзя.

```python
from pydantic import BaseModel, ConfigDict, ValidationError, field_validator, model_validator

class Payment(BaseModel):
    model_config = ConfigDict(extra="forbid")
    amount: int
    currency_code: str

    @field_validator("currency_code")
    @classmethod
    def normalize(cls, v: str) -> str:
        v = v.strip().upper()
        if len(v) != 3:
            raise ValueError("нужен трёхбуквенный код")
        return v

    @model_validator(mode="after")
    def check(self) -> "Payment":
        if self.currency_code == "RUB" and self.amount < 0:
            raise ValueError("отрицательная сумма в RUB")
        return self

print(Payment(amount="5", currency_code=" rub "))
for data in ({"amount": 1, "currency_code": "rubl"},
             {"amount": -1, "currency_code": "rub"},
             {"amount": 1, "currency_code": "usd", "x": 1}):
    try:
        Payment.model_validate(data)
    except ValidationError as e:
        for err in e.errors():
            print(err["loc"], err["type"], err["msg"])
```

```text title="Вывод"
amount=5 currency_code='RUB'
('currency_code',) value_error Value error, нужен трёхбуквенный код
() value_error Value error, отрицательная сумма в RUB
('x',) extra_forbidden Extra inputs are not permitted
```

`amount="5"` стал `5`, `" rub "` — `"RUB"`; `extra="forbid"` ловит опечатку в имени поля вместо молчаливого игнора. Ошибка `model_validator` имеет пустой `loc` — она относится ко всей модели.

`strict=True` (в `ConfigDict` или на поле) отключает приведение: модель `Strict` с полем `amount: int` на входе `{"amount": "5"}` даёт `int_type: Input should be a valid integer`, а `{"amount": 5}` проходит.

## pydantic-settings

`BaseSettings` читает значения из переменных окружения (имя поля, `env_prefix`, регистр не важен); вложенные модели заполняются через `env_nested_delimiter`.

```python
import os
from pydantic import BaseModel
from pydantic_settings import BaseSettings, SettingsConfigDict

class Db(BaseModel):
    host: str = "localhost"
    port: int = 5432

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_", env_nested_delimiter="__")
    debug: bool = False
    db: Db = Db()
    product_ids: list[str] = []

os.environ.update({"APP_DEBUG": "yes", "APP_DB__PORT": "6432", "APP_DB__HOST": "pg"})
print(Settings())
```

```text title="Вывод"
debug=True db=Db(host='pg', port=6432) product_ids=[]
```

`"yes"` приведено к `True`, `"6432"` — к `int`, `APP_DB__PORT` попал во вложенную модель.

Ловушка: поле-список. Для сложных типов (`list`, `dict`) pydantic-settings сначала пытается разобрать строку из окружения как JSON, и `a1,b2,c3` ломается ещё до валидаторов модели. Чтобы читать список через запятую, поле помечают `Annotated[list[str], NoDecode]` и разбивают строку своим `field_validator(mode="before")`:

```python
import os
from typing import Annotated
from pydantic import field_validator
from pydantic_settings import BaseSettings, NoDecode, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_")
    product_ids: list[str] = []

os.environ["APP_PRODUCT_IDS"] = "a1,b2, c3"
try:
    Settings()
except Exception as e:
    print(type(e).__name__, e)

class Fixed(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_")
    product_ids: Annotated[list[str], NoDecode] = []

    @field_validator("product_ids", mode="before")
    @classmethod
    def split(cls, v):
        if isinstance(v, str):
            return [p.strip() for p in v.split(",") if p.strip()]
        return v

print(Fixed())
```

```text title="Вывод"
SettingsError error parsing value for field "product_ids" from source "EnvSettingsSource"
product_ids=['a1', 'b2', 'c3']
```

Без `NoDecode` сервис падает на старте с `SettingsError`, хотя значение в окружении «выглядит правильно»; `NoDecode` отключает JSON-разбор, и строка доходит до валидатора.

## Что спросят дальше

- **Проверяет ли Python аннотации?** Нет, он только хранит их в `__annotations__`. Проверяют mypy/pyright статически, а pydantic и подобные читают аннотации и валидируют сами.
- **Что изменилось с аннотациями в 3.14?** Они вычисляются лениво (PEP 649/749): определение с ещё не объявленным именем не падает, `NameError` возникает при чтении `__annotations__`; читать в разных форматах — `annotationlib.get_annotations`. `from __future__ import annotations` делает аннотации строками и остаётся, но для forward-ссылок больше не нужен.
- **`Protocol` или ABC?** `Protocol` — структурный, подходит любой объект с нужными методами, проверяет mypy; ABC — номинальный, проверка при создании экземпляра и общая реализация в базе. `runtime_checkable` проверяет лишь наличие атрибутов, не сигнатуры.
- **`dataclass`, `NamedTuple` или pydantic?** Внутренние данные — `dataclass(frozen=True, slots=True)`; граница системы с приведением и проверкой — pydantic; `NamedTuple` — когда нужна совместимость с кортежем, при этом `==` с обычным кортежем и распаковка по позиции остаются.
- **Почему `tuple[Decimal, Decimal]` в возврате — плохо?** Поля без имён, порядок можно перепутать, и mypy не заметит; новое поле ломает всех вызывающих. Возвращают frozen dataclass.
- **Список из переменной окружения через запятую в pydantic-settings?** `Annotated[list[str], NoDecode]` плюс `field_validator(mode="before")`; без `NoDecode` сервис падает с `SettingsError` до валидатора, потому что строку сначала разбирают как JSON.
