Конспект к собеседованию по исключениям в Python: иерархия `BaseException` и почему `except Exception` не ловит `KeyboardInterrupt`, три способа связать исключения (`from err`, неявный контекст, `from None`), порядок `try`/`except`/`else`/`finally` и его ловушки, свои исключения с `add_note`, `ExceptionGroup` и типичные ошибки при перехвате. Все выводы получены запуском на Python 3.15.

**Суть.** Исключение (exception) — объект, который прерывает обычный ход выполнения и поднимается по стеку вызовов до первого подходящего `except`. Все исключения наследуют `BaseException`; прикладные ошибки живут под `Exception`, а то, что управляет самим процессом (выход, Ctrl+C, отмена задачи), стоит рядом, в обход `Exception`. Поэтому правило: ловить узкие типы, широкое `except Exception` — только на границе (обработчик запроса, воркер), а `raise ... from err` — чтобы не терять причину.

## Иерархия

`BaseException` — корень. Под ним `Exception` с прикладными ошибками и несколько исключений вне `Exception`:

- `KeyboardInterrupt` — Ctrl+C;
- `SystemExit` — его поднимает `sys.exit()`;
- `GeneratorExit` — поднимается внутри генератора при `close()`;
- `asyncio.CancelledError` — отмена задачи; с Python 3.8 наследует `BaseException`, а не `Exception`.

```python
import asyncio
for c in (KeyError, ZeroDivisionError, TimeoutError, ExceptionGroup,
          KeyboardInterrupt, SystemExit, asyncio.CancelledError):
    print(" -> ".join(k.__name__ for k in c.__mro__[:-1]))
```

```text title="Вывод"
KeyError -> LookupError -> Exception -> BaseException
ZeroDivisionError -> ArithmeticError -> Exception -> BaseException
TimeoutError -> OSError -> Exception -> BaseException
ExceptionGroup -> BaseExceptionGroup -> Exception -> BaseException
KeyboardInterrupt -> BaseException
SystemExit -> BaseException
CancelledError -> BaseException
```

Зачем так: `except Exception` на границе сервиса не должен проглотить Ctrl+C, выход из программы и отмену задачи. Голый `except:` равен `except BaseException:` и ловит всё.

```python
import asyncio
def ex(exc):
    try:
        raise exc
    except Exception:
        return "поймал except Exception"
    except BaseException:
        return "пролетело мимо Exception"
for e in (ValueError(), KeyboardInterrupt(), SystemExit(1), GeneratorExit(), asyncio.CancelledError()):
    print(f"{type(e).__name__:18}", ex(e))
```

```text title="Вывод"
ValueError         поймал except Exception
KeyboardInterrupt  пролетело мимо Exception
SystemExit         пролетело мимо Exception
GeneratorExit      пролетело мимо Exception
CancelledError     пролетело мимо Exception
```

Голый `except:` опасен тем, что глушит и `sys.exit()`, и программа не выходит. Если всё же нужно перехватить `BaseException` (очистка), в конце делай `raise`: отмену `CancelledError` нельзя проглатывать, иначе задача не отменится (см. [[Ошибки и отмена в asyncio]]).

## Цепочки исключений

Если во время обработки одного исключения поднимается другое, Python хранит связь. Есть три варианта, и трейсбек у каждого свой.

**Явная причина: `raise ... from err`.** Кладёт `err` в `__cause__`. Трейсбек: «The above exception was the direct cause of the following exception».

```python
def parse(s):
    try:
        return int(s)
    except ValueError as err:
        raise RuntimeError("bad config") from err
parse("x")
```

```text title="Вывод"
Traceback (most recent call last):
  File "c1.py", line 3, in parse
    return int(s)
ValueError: invalid literal for int() with base 10: 'x'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
  File "c1.py", line 5, in parse
    raise RuntimeError("bad config") from err
RuntimeError: bad config
```

**Неявный контекст.** `raise` внутри `except` без `from` сам кладёт обработанное исключение в `__context__`. Для читателя это выглядит как «ошибка в обработчике»: «During handling of the above exception, another exception occurred».

```python
def parse(s):
    try:
        return int(s)
    except ValueError:
        raise RuntimeError("bad config")
parse("x")
```

```text title="Вывод"
Traceback (most recent call last):
  File "c2.py", line 3, in parse
    return int(s)
ValueError: invalid literal for int() with base 10: 'x'

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  ...
RuntimeError: bad config
```

**`from None`.** Выставляет `__suppress_context__ = True`: `__context__` остаётся в объекте, но в трейсбеке не печатается. Нужно, когда исходная ошибка — деталь реализации (например, `KeyError` из внутреннего словаря превращается в `NotFound`).

```python
def parse(s):
    try:
        return int(s)
    except ValueError:
        raise RuntimeError("bad config") from None
try:
    parse("x")
except RuntimeError as e:
    print(repr(e.__cause__), repr(e.__context__), e.__suppress_context__)
parse("x")
```

```text title="Вывод"
None ValueError("invalid literal for int() with base 10: 'x'") True
Traceback (most recent call last):
  File "c3.py", line 10, in <module>
    parse("x")
  ...
RuntimeError: bad config
```

`__cause__` ставит только `from`; `__context__` Python ставит сам; трейсбек сначала смотрит `__cause__`, а `__context__` показывает, если нет `__suppress_context__`. Чтобы пробросить то же исключение дальше, пиши голый `raise`, а не `raise e`: стек сохранится без лишней строки.

## try, except, else, finally

Порядок: `try`; если исключения нет — `else`; если есть и подошёл `except` — он; `finally` — всегда, и после `return` тоже. `else` нужен, чтобы в `try` стояло только то, что может упасть, а остальное не ловилось тем же `except`.

```python
def f():
    try:
        print("try")
        return "из try"
    except Exception:
        print("except")
    else:
        print("else")
    finally:
        print("finally")
print(f())
```

```text title="Вывод"
try
finally
из try
```

`return` в `try` не даёт сработать `else`: он выполняется, только если `try` завершился без исключения и без выхода. Значение для `return` вычисляется до `finally`, а сам `finally` выполняется перед возвратом из функции.

**`return` (а также `break`, `continue`) в `finally` глотает исключение**, в том числе `KeyboardInterrupt`, и подменяет возвращаемое значение. С Python 3.14 (PEP 765) компилятор предупреждает `SyntaxWarning`; в будущих версиях обещают сделать это ошибкой.

```python
def f():
    try:
        1 / 0
    finally:
        return "проглочено"
print(f())
```

```text title="Вывод"
t2.py:5: SyntaxWarning: 'return' in a 'finally' block
  return "проглочено"
проглочено
```

Ошибка `ZeroDivisionError` исчезла без следа. В `finally` делай только очистку; а лучше — контекстный менеджер (`with`), который закрывает ресурс сам.

## Свои исключения и add_note

Своё исключение наследуют от `Exception`, а не от `BaseException`. Для приложения заводят общую базу (`AppError`), под ней — ошибки домена: тогда обработчик на границе ловит `AppError`, а чужие баги (`KeyError`, `TypeError`) остаются «непредвиденными» и идут в Sentry. Данные кладут в атрибуты, а читаемое сообщение — в `__str__`.

```python
class AppError(Exception):
    """База всех ошибок приложения."""

class NotFound(AppError):
    def __init__(self, entity, key):
        super().__init__(entity, key)
        self.entity, self.key = entity, key
    def __str__(self):
        return f"{self.entity} {self.key!r} не найден"

class PaymentError(AppError):
    pass

try:
    raise NotFound("user", 42)
except AppError as e:
    print(str(e), "|", repr(e), "|", e.args, e.key)
```

```text title="Вывод"
user 42 не найден | NotFound('user', 42) | ('user', 42) 42
```

`super().__init__(entity, key)` важен: он заполняет `args`, а по `args` исключение копируется и сериализуется (например, при передаче между процессами через pickle). Если `__init__` принимает свои аргументы и не передаёт их в `super()`, `pickle` падает при восстановлении.

**`add_note` (3.11+).** Добавляет к уже пойманному исключению пояснение, не создавая новое и не ломая тип. Заметки лежат в `__notes__` и печатаются в трейсбеке после строки с ошибкой.

```python
def load(path):
    try:
        return open(path).read()
    except OSError as e:
        e.add_note(f"путь: {path}")
        e.add_note("проверьте переменную CONFIG_DIR")
        raise
try:
    load("/nope/cfg.toml")
except OSError as e:
    print(e.__notes__)
load("/nope/cfg.toml")
```

```text title="Вывод"
['путь: /nope/cfg.toml', 'проверьте переменную CONFIG_DIR']
Traceback (most recent call last):
  ...
FileNotFoundError: [Errno 2] No such file or directory: '/nope/cfg.toml'
путь: /nope/cfg.toml
проверьте переменную CONFIG_DIR
```

Это удобнее, чем оборачивать в новое исключение, когда нужно только добавить контекст.

## ExceptionGroup и except*

`ExceptionGroup` (3.11+) собирает несколько исключений в одно: так падает `asyncio.TaskGroup`, если упали несколько задач. `except*` разбирает группу по типам, и каждый блок получает подгруппу своего типа; несколько блоков могут сработать за один `try`.

```python
try:
    raise ExceptionGroup("batch", [ValueError("a"), TypeError("b")])
except* ValueError as eg:
    print("ValueError:", eg.exceptions)
except* TypeError as eg:
    print("TypeError:", eg.exceptions)
```

```text title="Вывод"
ValueError: (ValueError('a'),)
TypeError: (TypeError('b'),)
```

Обычный `except ValueError` группу не поймает: она не `ValueError`. Подробно — вложенные группы, отмена, `TaskGroup` — в [[Ошибки и отмена в asyncio]].

## Ловушки

**`except (A, B)` и `except A, B`.** В Python 3 и до 3.13 запятая без скобок — `SyntaxError` (в Python 2 это означало «ловить A и положить в B»). С 3.14 (PEP 758) скобки можно опускать, если нет `as`; проверено на 3.15:

```python
try:
    int("x")
except ValueError, TypeError:
    print("ловит оба без скобок")
```

```text title="Вывод"
ловит оба без скобок
```

С `as` скобки по-прежнему обязательны:

```python
try:
    int("x")
except ValueError, TypeError as e:
    print(e)
```

```text title="Вывод"
SyntaxError: multiple exception types must be parenthesized when using 'as'
```

Раз код может читаться и на старых версиях, в проектах до 3.14 пиши скобки всегда: `except (ValueError, TypeError)`.

**Переменная `e` удаляется после `except`.** Python делает неявный `del e` в конце блока, чтобы разорвать цикл «исключение → трейсбек → фрейм → переменная». Поэтому `e` нельзя использовать после блока; нужно — копируй в другое имя внутри.

```python
try:
    1/0
except ZeroDivisionError as e:
    pass
print(e)
```

```text title="Вывод"
NameError: name 'e' is not defined
```

**Логирование и проглатывание.** `except Exception: pass` скрывает баг: программа идёт дальше с неверным состоянием, а причину никто не увидит. Если ловишь широко, то либо логируй с трейсбеком, либо пробрасывай. `log.error("...: %s", e)` печатает только текст, `log.exception(...)` (только внутри `except`) добавляет трейсбек (проверено запуском: во втором случае после строки `ERROR плохо` идёт `Traceback`).

Ещё две частые ошибки: ловить исключение и поднимать новое без `from` (теряется ясность, кто причина) и использовать исключения как обычный поток управления в горячем цикле (EAFP хорош, но `try` с частым срабатыванием `except` заметно дороже проверки `if`).

## Что спросят дальше

- **Чем `except Exception` отличается от голого `except:`?** Голый ловит `BaseException`: `KeyboardInterrupt`, `SystemExit`, `GeneratorExit`, `CancelledError`. Это мешает остановить программу и отменить задачу. `except Exception` их пропускает.
- **Чем `raise X from Y` отличается от `raise X` в `except`?** В первом случае причина явная (`__cause__`), трейсбек пишет «direct cause»; во втором Python сам кладёт `__context__` и пишет «During handling...». `from None` прячет контекст из трейсбека.
- **Что выполнится: `else` или `finally`, если в `try` стоит `return`?** `finally` выполнится всегда, `else` — нет: он только после `try` без исключения и без выхода.
- **Что случится с исключением, если в `finally` стоит `return`?** Оно исчезнет. С 3.14 это `SyntaxWarning` (PEP 765).
- **Почему `CancelledError` нельзя глотать?** Это механизм отмены задач в asyncio: если поймать и не пробросить, задача продолжит работать и таймауты перестанут срабатывать. С 3.8 он под `BaseException` поэтому.
- **Зачем `add_note` и когда `ExceptionGroup`?** `add_note` добавляет контекст к пойманной ошибке, не создавая новую. `ExceptionGroup` нужен, когда одновременно упало несколько независимых задач; разбирают группу через `except*`.
