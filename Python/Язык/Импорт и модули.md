Конспект к собеседованию по импортам в Python: что происходит при `import` (кэш `sys.modules`, выполнение один раз), чем `python -m pkg.mod` отличается от `python pkg/mod.py`, как устроены пакеты и `__all__`, откуда берётся циклический импорт и чем его лечат, почему `from x import y` «застывает» и как импортировать лениво (включая `lazy import` из 3.15). Все выводы получены запуском на Python 3.15 на пакете из нескольких файлов.

**Суть.** `import` — это поиск модуля, его выполнение сверху вниз и сохранение объекта модуля в `sys.modules`. Повторный `import` не выполняет файл заново, а берёт готовый объект из кэша. Из этого вытекают почти все ловушки: побочные эффекты на уровне модуля срабатывают один раз и в момент первого импорта, циклический импорт видит «наполовину выполненный» модуль, а `from x import y` копирует ссылку на объект в момент импорта.

## Что делает import

Алгоритм: смотрим в `sys.modules`; если модуля нет — ищем по `sys.path`, создаём объект модуля, кладём в `sys.modules` **до** выполнения кода и только потом выполняем файл. Родительские пакеты импортируются первыми (`__init__.py` пакета выполняется раньше модуля внутри).

```python
# pkg/__init__.py: print("pkg/__init__ выполнен")
# pkg/util.py:     print("util выполнен, __name__ =", __name__)
import sys
import pkg.util
import pkg.util
import pkg.util as u2
print("в sys.modules:", "pkg.util" in sys.modules, sys.modules["pkg.util"] is u2)
del sys.modules["pkg.util"]
import pkg.util
```

```text title="Вывод"
pkg/__init__ выполнен
util выполнен, __name__ = pkg.util
в sys.modules: True True
util выполнен, __name__ = pkg.util
```

Три `import` выполнили файл один раз; после удаления из кэша модуль выполнился снова (и стал новым объектом). Практический вывод: код на уровне модуля (подключение к базе, чтение конфига, `print`) выполняется при первом импорте, поэтому тяжёлые действия прячут в функции, а в `if __name__ == "__main__":` кладут то, что должно срабатывать только при запуске как программы.

## Запуск: -m или скрипт

`__name__` равен `"__main__"` у модуля, который запущен как программа, и полному имени (`pkg.util`) у импортированного. Но способ запуска меняет ещё два важных параметра.

```python
# pkg/where.py
import sys, os
print("sys.path[0] =", os.path.relpath(sys.path[0], os.getcwd()), "| __package__ =", repr(__package__))
```

```text title="Вывод"
$ python pkg/where.py
sys.path[0] = pkg | __package__ = None

$ python -m pkg.where
pkg/__init__ выполнен
sys.path[0] = . | __package__ = 'pkg'
```

- `python pkg/mod.py`: `sys.path[0]` — каталог самого файла (`pkg/`), пакета нет, `__init__.py` не выполняется. Соседние модули импортируются как `import util`, а не `pkg.util`.
- `python -m pkg.mod`: `sys.path[0]` — текущий каталог, файл запускается как часть пакета `pkg`.

Из-за этого относительные импорты работают только при `-m`:

```python
# pkg/mod.py
from . import util
```

```text title="Вывод"
$ python pkg/mod.py
ImportError: attempted relative import with no known parent package
```

Ещё ловушка скрипта: его каталог первый в `sys.path`, и файл `random.py` рядом подменит стандартную библиотеку. Код пакета запускай через `-m`.

## Пакеты и список экспорта

Пакет — каталог, который импортируется как модуль; его `__init__.py` выполняется при первом импорте любого модуля внутри. С Python 3.3 каталог без `__init__.py` тоже работает (namespace package), но для обычных пакетов файл оставляют: он явно задаёт границу пакета и место для публичного API.

- **Абсолютный импорт** — `from pkg.util import helper`: от корня из `sys.path`, предпочтителен.
- **Относительный** — `from . import util`, `from .util import helper`, `from ..other import x`: от текущего пакета; работает только внутри пакета (см. выше про `-m`).

`from x import *` берёт имена, перечисленные в `__all__`; если `__all__` нет — все имена без ведущего подчёркивания. `__all__` задаёт публичный API для `*` и подсказку для линтеров; на обычный `from x import other` он не влияет.

```python
# pkg/api.py: __all__ = ["public"]; функции public, _private, other
from pkg.api import *
print(sorted(n for n in dir() if not n.startswith("__")))
```

```text title="Вывод"
pkg/__init__ выполнен
['public']
```

Звёздочку в рабочем коде не используют: непонятно, откуда имя, и она засоряет пространство имён. Годится для `__init__.py`, который явно реэкспортирует API пакета.

## Циклический импорт

Модули `orders` и `users` импортируют друг друга. Первый начал выполняться, дошёл до `import` второго, а тот просит у первого имя, которое ещё не определено: `orders` в `sys.modules` уже есть, но выполнен только до строки импорта.

```python
# shop/orders.py
from shop.users import get_user
def make_order(uid): return (get_user(uid), "order")

# shop/users.py
from shop.orders import make_order
def get_user(uid): return f"user{uid}"
```

```text title="Вывод"
ImportError: cannot import name 'make_order' from partially initialized module 'shop.orders' (most likely due to a circular import) (shop/orders.py)
```

Вариант с `import module` вместо `from`: импорт проходит, но если имя нужно сразу, на уровне модуля, падает так (`X = orders2.make_order` в `users2.py`):

```text title="Вывод"
AttributeError: partially initialized module 'shop.orders2' from 'shop/orders2.py' has no attribute 'make_order' (most likely due to a circular import)
```

Способы лечения, от лучшего к худшему:

1. **Вынести общее** в третий модуль, от которого зависят оба: цикл исчезает. Обычно это значит, что границы модулей проведены неверно.
2. **`import module` вместо `from module import name`** и обращение к имени только при вызове, а не при импорте: к моменту вызова оба модуля уже выполнены.

   ```python
   # orders4: import shop.users4 as users4; make_order вызывает users4.get_user(uid)
   # users4:  import shop.orders4 as orders4; both вызывает orders4.make_order(uid)
   print(o.make_order(1), u.both(2))
   ```

   ```text title="Вывод"
   ('user1', 'order') ('user2', 'order')
   ```

3. **Импорт внутри функции**: выполняется при первом вызове, когда модули уже загружены. Дешёвый приём, но скрывает зависимость и добавляет проверку `sys.modules` на каждый вызов.

   Проверено запуском: `make_order(7)` возвращает `('user7', 'order')`.

4. **`TYPE_CHECKING` для аннотаций**: если модуль нужен только ради типов, импортируют его под `if TYPE_CHECKING:` (выполняется только для mypy/pyright), а аннотации превращают в строки через `from __future__ import annotations` (в 3.14+ отложенные аннотации и так по умолчанию, PEP 649).

   ```python
   # shop/models.py
   from __future__ import annotations
   from typing import TYPE_CHECKING
   if TYPE_CHECKING:
       from shop.models_b import B      # shop/models_b.py импортирует models.A
   class A:
       def link(self, b: B) -> B: return b

   print(A.link.__annotations__)
   ```

   ```text title="Вывод"
   {'b': 'B', 'return': 'B'}
   ```

   Здесь рантайм ничего не импортирует, поэтому цикла нет.

## from x import y фиксирует объект

`from cfg import DEBUG` создаёт в текущем модуле новое имя, указывающее на тот же объект. Если потом перезаписать `cfg.DEBUG`, имя `DEBUG` в этом модуле не изменится: оно указывает на старый объект.

```python
# cfg.py: DEBUG = False
import cfg
from cfg import DEBUG
cfg.DEBUG = True
print("from-импорт:", DEBUG, "| атрибут модуля:", cfg.DEBUG)
```

```text title="Вывод"
from-импорт: False | атрибут модуля: True
```

Это же причина, почему моки «не срабатывают»: патчить нужно имя там, где оно используется, а не там, где определено (подробно — [[pytest и моки]]).

```python
# mk/svc.py: def send(): return "real"
# mk/use.py:
#   from mk.svc import send
#   import mk.svc as svc
#   def a(): return send()
#   def b(): return svc.send()
from unittest.mock import patch
import mk.use as use
with patch("mk.svc.send", return_value="mock"):
    print("from-импорт:", use.a(), "| через модуль:", use.b())
with patch("mk.use.send", return_value="mock"):
    print("патч там, где используется:", use.a())
```

```text title="Вывод"
from-импорт: real | через модуль: mock
патч там, где используется: mock
```

## reload

`importlib.reload(module)` выполняет код модуля заново **в том же объекте модуля**: старые имена перезаписываются новыми значениями. Но всё, что успело сохранить ссылку на старое, остаётся со старым.

```python
import importlib, settings
from settings import LEVEL
obj = settings.Conf()
old_conf = settings.conf
# файл settings.py переписали: LEVEL = "debug", класс Conf и conf создаются заново
importlib.reload(settings)
print("settings.LEVEL:", settings.LEVEL, "| from-импорт LEVEL:", LEVEL)
print("тот же объект модуля:", importlib.import_module("settings") is settings)
print("старый obj — экземпляр нового класса?", isinstance(obj, settings.Conf))
print("conf тот же объект:", old_conf is settings.conf)
```

```text title="Вывод"
settings.LEVEL: debug | from-импорт LEVEL: info
тот же объект модуля: True
старый obj — экземпляр нового класса? False
conf тот же объект: False
```

Ловушки: `from`-имена не обновляются; старые экземпляры принадлежат старому классу (`isinstance` ложен, патчи по старому классу не видны); перезагрузка не трогает зависимые модули; удалённые из файла имена остаются в модуле. Поэтому `reload` — инструмент для REPL и отладки, в рабочем коде конфиг перечитывают явно.

## Ленивый импорт

Зачем: ускорить старт (CLI, где нужен один из двадцати тяжёлых модулей) и убрать циклы.

**`importlib.import_module(name)`** — импорт по строке в момент вызова; возвращает тот же объект, что и `import`. Так работают плагины и динамический выбор бэкенда.

**Модульный `__getattr__` (PEP 562, 3.7+)** — функция `__getattr__(name)` в модуле вызывается, когда имя не найдено; так пакет подгружает подмодули при первом обращении.

```python
# lazy/__init__.py
import importlib
print("lazy/__init__ загружен")
_lazy = {"heavy": "lazy.heavy"}
def __getattr__(name):
    if name in _lazy:
        print(f"  подгружаю {name}")
        mod = importlib.import_module(_lazy[name])
        globals()[name] = mod          # закэшировать: второй раз __getattr__ не вызовется
        return mod
    raise AttributeError(f"module {__name__!r} has no attribute {name!r}")
# lazy/heavy.py: print("  heavy выполнен"); def f(): return "тяжёлое"

import lazy
print("после import lazy")
print(lazy.heavy.f())
print(lazy.heavy.f())
```

```text title="Вывод"
lazy/__init__ загружен
после import lazy
  подгружаю heavy
  heavy выполнен
тяжёлое
тяжёлое
```

**`lazy import` (PEP 810) — в Python 3.15 есть синтаксис.** Модуль не загружается в момент `lazy import`, а при первом обращении к имени.

```python
import sys
lazy import json
lazy from lazy import heavy
print("json загружен:", "json" in sys.modules, "| lazy.heavy:", "lazy.heavy" in sys.modules)
print(type(globals()["json"]).__name__)
print(json.dumps({"a": 1}))
print("json загружен:", "json" in sys.modules, type(globals()["json"]).__name__)
```

```text title="Вывод"
json загружен: False | lazy.heavy: False
lazy_import
{"a": 1}
json загружен: True module
```

До первого использования в глобальных переменных лежит заглушка `lazy_import`, после — настоящий модуль. Ошибки импорта (`ModuleNotFoundError`) тоже откладываются до первого обращения. Ограничения, проверенные запуском:

```text title="Вывод"
SyntaxError: lazy import not allowed inside functions
SyntaxError: lazy import not allowed inside try/except blocks
```

То есть `lazy import` — только на уровне модуля и вне `try`. Побочные эффекты импортируемого модуля сдвигаются на момент первого обращения, и это нужно помнить при отладке.

## Что спросят дальше

- **Что такое `sys.modules` и что будет, если импортировать модуль дважды?** Кэш уже загруженных модулей по имени. Второй `import` берёт объект из кэша, файл не выполняется. Удалишь запись — модуль выполнится заново и будет новым объектом.
- **Чем `python -m pkg.mod` отличается от `python pkg/mod.py`?** Для `-m` `sys.path[0]` — текущий каталог и модуль запускается внутри пакета (работают относительные импорты); для скрипта `sys.path[0]` — каталог файла, `__package__` пустой, `from . import x` падает.
- **Откуда циклический импорт и как его лечить?** Два модуля импортируют друг друга, и один видит другой недовыполненным. Лечат: вынести общее в третий модуль, использовать `import module` и обращаться при вызове, импортировать внутри функции, `TYPE_CHECKING` для типов.
- **Почему `patch` не подменяет функцию?** `from mod import f` скопировал ссылку на объект. Патчить нужно `use.f` (где используется), а не `mod.f` (где определена).
- **Что делает `__all__`?** Определяет, какие имена вернёт `from x import *`; на явный `from x import name` не влияет. Служит и описанием публичного API.
- **Как отложить дорогой импорт?** Импорт внутри функции, `importlib.import_module`, `__getattr__` на уровне модуля или `lazy import` (3.15, только на уровне модуля).
