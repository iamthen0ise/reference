**Суть.** В Python всё — объекты, включая классы и функции. Класс — это объект типа `type` (или другого метакласса), поэтому `MyClass()` — это обычный вызов объекта: срабатывает `type.__call__`, который сначала создаёт пустой объект через `__new__`, а потом заполняет его через `__init__`. Методы и атрибуты ищутся по цепочке классов в порядке MRO (method resolution order, порядок разрешения методов), который Python вычисляет алгоритмом C3. `super()` идёт не к «родителю», а к следующему классу в этой цепочке. Атрибуты объекта по умолчанию лежат в словаре `__dict__`; `__slots__` заменяет его на фиксированный набор полей и экономит память.

## Как создаётся объект

### __new__, __init__ и кто их вызывает

`Point(1, 2)` — вызов объекта `Point`. Вызов любого объекта ищет метод `__call__` у его типа, а тип класса — `type`. Поэтому на самом деле выполняется `type.__call__(Point, 1, 2)`, и он устроен примерно так:

```python
def type_call(cls, *args, **kwargs):
    obj = cls.__new__(cls, *args, **kwargs)  # 1. создать объект
    if isinstance(obj, cls):
        obj.__init__(*args, **kwargs)        # 2. инициализировать его
    return obj
```

- **`__new__(cls, ...)`** создаёт и возвращает новый объект. Первым аргументом получает класс, а не экземпляр: объекта ещё нет. Это статический метод, хотя `@staticmethod` писать не нужно, Python делает это сам. Внутри почти всегда вызывают `super().__new__(cls)`, и в итоге память выделяет `object.__new__`.
- **`__init__(self, ...)`** получает уже созданный объект и заполняет его атрибутами. Должен вернуть `None`; если вернуть что-то другое — `TypeError`.
- Если `__new__` вернул объект **не этого класса** (например, кэшированный объект другого типа или `None`), `__init__` не вызывается.

Переопределять `__new__` нужно редко. Типичные случаи:

- **Наследование от неизменяемого типа** (`int`, `float`, `str`, `tuple`, `frozenset`). Значение такого объекта задаётся в момент создания, и в `__init__` его уже не поменять.

```python
class Celsius(float):
    def __new__(cls, value: float):
        if value < -273.15:
            raise ValueError("ниже абсолютного нуля")
        return super().__new__(cls, value)


class Upper(str):
    def __new__(cls, value: str):
        return super().__new__(cls, value.upper())


print(Celsius(36.6) + 1, Upper("usd"))  # 37.6 USD
```

- **Контроль количества экземпляров**: одиночка (singleton) или кэш одинаковых объектов (`Currency("USD") is Currency("USD")`).
- **Фабрика**, которая по аргументам возвращает объект подходящего подкласса. Обычно понятнее сделать это через `@classmethod` (`Payment.from_dict(data)`), а не через `__new__`.

Подвох с аргументами: если переопределён `__new__`, но не `__init__` (или наоборот), лишние аргументы конструктора `object` молча проигнорирует. Если переопределены оба, а в `object.__new__` передали аргументы (`super().__new__(cls, *args)`), будет `TypeError`. Правильно — `super().__new__(cls)` без аргументов.

### Одиночка (singleton) через __new__ и его ловушка

```python
class Settings:
    _instance = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self, env: str = "prod") -> None:
        self.env = env  # выполняется при КАЖДОМ вызове Settings(...)


a = Settings("prod")
b = Settings("test")
print(a is b, a.env)  # True test — первый объект тихо перезаписан
```

`__new__` возвращает тот же объект, он того же класса, значит `type.__call__` каждый раз заново вызывает `__init__` и сбрасывает состояние. Варианты лучше:

- **метакласс с `__call__`**: он перехватывает весь вызов `Settings(...)` целиком, и `__init__` выполняется только при первом создании;

```python
class SingletonMeta(type):
    _instances: dict[type, object] = {}

    def __call__(cls, *args, **kwargs):
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class Settings(metaclass=SingletonMeta):
    def __init__(self, env: str = "prod") -> None:
        self.env = env


print(Settings("prod") is Settings("test"), Settings().env)  # True prod
```

- **проще и чаще в реальном коде** — объект на уровне модуля (`settings = Settings()`; модуль импортируется один раз, и все получают один объект) или функция-фабрика с `@functools.cache`, как `get_settings()` во FastAPI. Такой объект легко подменить в тесте.

Все три варианта не потокобезопасны в строгом смысле: «проверить, что объекта нет, и создать» — две операции, и два потока могут создать по объекту. Если создание дорогое или с побочными эффектами — защищать блокировкой, см. [[Python-конкурентность#Синхронизация потоков]].

### __call__: вызываемый объект

`obj(...)` превращается в `type(obj).__call__(obj, ...)`. Объект с `__call__` ведёт себя как функция, но может хранить состояние и настройки в атрибутах.

```python
class Multiplier:
    def __init__(self, k: int) -> None:
        self.k = k

    def __call__(self, x: int) -> int:
        return x * self.k


double = Multiplier(2)
print(double(21), callable(double))  # 42 True
```

Где встречается:

- **функция с настройками, заданными заранее**: зависимость во FastAPI вида `Depends(RequireRole("admin"))` — экземпляр запоминает роль, а FastAPI вызывает его на каждый запрос;
- **класс-декоратор** со счётчиком или кэшем (см. [[Python-протоколы#Класс как декоратор и декоратор класса]] и пример с `__get__` ниже);
- **стратегия** — объект, который передают как функцию (`key=`, `callback=`), но с конфигурацией;
- `torch.nn.Module`: `model(x)` вызывает `__call__`, а тот — `forward` плюс хуки.

Специальные методы Python ищет **у типа, а не у экземпляра**. `a.__call__ = lambda: "hi"` на обычном объекте ничего не даст: `a()` всё равно упадёт с `TypeError: 'A' object is not callable`. То же верно для `__len__`, `__enter__`, `__iter__` и остальных.

### __init_subclass__: реакция на создание подкласса

Если нужно что-то сделать в момент объявления подкласса (зарегистрировать его, проверить, что нужные атрибуты заданы), метакласс не нужен: с Python 3.6 есть `__init_subclass__`.

```python
class Handler:
    registry: dict[str, type["Handler"]] = {}

    def __init_subclass__(cls, *, event: str, **kwargs):
        super().__init_subclass__(**kwargs)
        Handler.registry[event] = cls


class PaymentCreated(Handler, event="payment.created"):
    pass


print(Handler.registry)  # {'payment.created': <class 'PaymentCreated'>}
```

| Метод | Чей | Когда вызывается | Что возвращает |
| --- | --- | --- | --- |
| `__new__(cls, ...)` | класса | при `C(...)`, первым | новый объект |
| `__init__(self, ...)` | класса | при `C(...)`, если `__new__` вернул экземпляр `C` | `None` |
| `__call__(self, ...)` | класса объекта | при `obj(...)` | что угодно |
| `type.__call__` / метакласса `__call__` | метакласса | при `C(...)`, вызывает `__new__` и `__init__` | готовый объект |
| `__init_subclass__(cls, ...)` | родителя | при объявлении подкласса | `None` |

## Порядок разрешения методов (MRO)

**MRO** — список классов, в котором Python ищет атрибут или метод: сначала сам класс, потом его родители в определённом порядке, в конце `object`. Посмотреть: `C.__mro__` или `C.mro()`. При одиночном наследовании всё очевидно: потомок, родитель, дед. Интересно становится при множественном наследовании, особенно в «ромбе» (diamond):

```python
class A:
    def hello(self) -> str:
        return "A"


class B(A):
    pass


class C(A):
    def hello(self) -> str:
        return "C"


class D(B, C):
    pass


print([k.__name__ for k in D.__mro__])  # ['D', 'B', 'C', 'A', 'object']
print(D().hello())                      # C
```

Если бы поиск шёл простым обходом в глубину слева направо, порядок был бы `D, B, A, C, A`: метод нашёлся бы в `A` раньше, чем в `C`, и переопределение в `C` никогда бы не сработало. Так было у «классических» классов в Python 2. С Python 2.3 MRO вычисляется **C3-линеаризацией**, которая гарантирует три свойства:

1. **Потомок раньше родителей**: класс всегда стоит перед своими базовыми классами.
2. **Порядок родителей сохраняется**: в `class D(B, C)` класс `B` всегда раньше `C`.
3. **Монотонность**: если в MRO родителя `X` стоит раньше `Y`, то и в MRO любого потомка `X` стоит раньше `Y`. Порядок, который был у родителя, потомок не ломает.

### Как считать C3 вручную

Формула: MRO класса = сам класс + слияние (merge) MRO всех его родителей и списка самих родителей в порядке объявления.

```text
L[C] = C + merge(L[P1], L[P2], ..., L[Pn], [P1, P2, ..., Pn])
```

Слияние: смотрим на первые элементы (головы) списков слева направо и берём первую голову, которая **не встречается в хвосте** (во всех позициях, кроме первой) ни одного из списков. Берём её в результат, вычёркиваем из всех списков и повторяем. Если ни одна голова не подходит — непротиворечивого порядка не существует, Python бросает `TypeError`.

Ромб выше, `O` — это `object`:

```text
L[A] = [A, O]
L[B] = [B, A, O]
L[C] = [C, A, O]
L[D] = D + merge([B, A, O], [C, A, O], [B, C])

1. Голова B: в хвостах [A, O], [A, O], [C] её нет → берём B.
   Остались [A, O], [C, A, O], [C]
2. Голова A: есть в хвосте [C, A, O] → пропускаем.
   Голова C: в хвостах нет → берём C.
   Остались [A, O], [A, O], []
3. Берём A, затем O.

L[D] = [D, B, C, A, O]
```

Пример, где порядок невозможен:

```python
class A: pass
class B(A): pass

try:
    class C(A, B): pass  # A объявлен раньше B, но B — потомок A и должен быть раньше
except TypeError as e:
    print(e)  # Cannot create a consistent method resolution order (MRO) for bases A, B
```

`merge([A, O], [B, A, O], [A, B])`: голова `A` есть в хвосте `[B, A, O]`, голова `B` — в хвосте `[A, B]`, третий список снова начинается с `A`. Подходящей головы нет. Та же ошибка будет, если `X(A, B)` и `Y(B, A)` наследуются вместе: `class Z(X, Y)`.

### C3 своими руками

Иногда просят написать алгоритм. Он короткий:

```python
def c3_mro(cls: type) -> list[type]:
    bases = list(cls.__bases__)
    return [cls] + c3_merge([c3_mro(base) for base in bases] + [bases])


def c3_merge(seqs: list[list[type]]) -> list[type]:
    seqs = [list(s) for s in seqs if s]
    result = []
    while seqs:
        for seq in seqs:
            head = seq[0]
            if not any(head in other[1:] for other in seqs):
                break
        else:
            raise TypeError("Cannot create a consistent MRO")
        result.append(head)
        # подходящая голова не встречается в хвостах, значит, она может быть только в начале списков
        seqs = [s[1:] if s[0] is head else s for s in seqs]
        seqs = [s for s in seqs if s]
    return result


class O: pass
class A(O): pass
class B(O): pass
class C(O): pass
class D(O): pass
class E(O): pass
class K1(A, B, C): pass
class K2(D, B, E): pass
class K3(D, A): pass
class Z(K1, K2, K3): pass

print([k.__name__ for k in c3_mro(Z)][:-1])
# ['Z', 'K1', 'K2', 'K3', 'D', 'A', 'B', 'C', 'E', 'O']
assert c3_mro(Z) == list(Z.__mro__)
```

Сложность — O(n²) и выше по числу классов, но иерархии маленькие, а MRO вычисляется один раз при создании класса и хранится в `__mro__`.

## super() и кооперативное наследование

`super()` возвращает объект-посредник, который ищет атрибут в MRO **типа объекта `self`**, начиная со следующего класса после текущего. Не «у родителя», а «у следующего в цепочке». В ромбе `super()` внутри `B` ведёт в `C`, хотя `B` про `C` ничего не знает:

```python
class A:
    def hello(self) -> list[str]:
        return ["A"]


class B(A):
    def hello(self) -> list[str]:
        return ["B", *super().hello()]


class C(A):
    def hello(self) -> list[str]:
        return ["C", *super().hello()]


class D(B, C):
    def hello(self) -> list[str]:
        return ["D", *super().hello()]


print(D().hello())  # ['D', 'B', 'C', 'A'] — A ровно один раз
print(B().hello())  # ['B', 'A'] — у объекта B другой MRO, и super() в B ведёт в A
```

Благодаря этому каждый метод выполняется ровно один раз, даже если до класса можно дойти несколькими путями. Если бы `B` вызывал `A.hello(self)` напрямую, `C.hello` был бы пропущен, а в более сложной иерархии `A` вызвался бы дважды.

Чтобы цепочка работала, классы должны **кооперироваться**:

- каждый класс в иерархии вызывает `super().method(...)`; один забыл — все классы после него в MRO не вызовутся;
- сигнатуры совместимы. Для `__init__` это значит: каждый забирает свои именованные аргументы и передаёт остальное дальше через `**kwargs`, а до `object.__init__` должно дойти пусто.

```python
class Storage:
    def __init__(self, *, dsn: str, **kwargs) -> None:
        super().__init__(**kwargs)
        self.dsn = dsn


class LoggingMixin:
    def __init__(self, *, logger_name: str = "app", **kwargs) -> None:
        super().__init__(**kwargs)
        self.logger_name = logger_name


class CacheMixin:
    def __init__(self, *, ttl: int = 60, **kwargs) -> None:
        super().__init__(**kwargs)
        self.ttl = ttl


class UserRepo(LoggingMixin, CacheMixin, Storage):
    pass


repo = UserRepo(dsn="postgresql://localhost/app", ttl=30)
print([k.__name__ for k in UserRepo.__mro__])  # UserRepo, LoggingMixin, CacheMixin, Storage, object
print(repo.dsn, repo.ttl, repo.logger_name)
```

**Миксин** (mixin, «примесь») — маленький класс, который добавляет одну возможность и сам по себе не используется. Миксины ставят **левее** основного класса: тогда их методы оказываются раньше в MRO и могут обернуть метод основного класса через `super()`. Так устроены class-based views в Django (`LoginRequiredMixin, ListView`).

`super()` без аргументов работает благодаря скрытой ячейке `__class__`, которую компилятор создаёт для каждого метода, где упомянуты `super` или `__class__`. Поэтому он не работает в функции, которую объявили вне класса и потом присвоили атрибуту класса. Там пишут `super(Класс, self)` явно.

## Как Python ищет атрибут

Эта схема объясняет, почему методы получают `self`, почему `property` нельзя перезаписать через экземпляр и почему `__slots__` и `cached_property` несовместимы. Ключевое понятие — **дескриптор**: атрибут класса, у которого есть `__get__` (и, возможно, `__set__` или `__delete__`). Дескриптор с `__set__` или `__delete__` называется **дескриптором данных** (data descriptor), только с `__get__` — **дескриптором не-данных** (non-data descriptor).

`obj.attr` вызывает `type(obj).__getattribute__(obj, "attr")`, по умолчанию это `object.__getattribute__`:

1. Ищем `attr` в классах по MRO `type(obj)`. Нашли **дескриптор данных** — возвращаем результат его `__get__`, словарь экземпляра даже не смотрим.
2. Иначе ищем в `obj.__dict__` — нашли, возвращаем.
3. Иначе, если на шаге 1 нашёлся **дескриптор не-данных**, вызываем его `__get__`; если нашёлся обычный атрибут класса — возвращаем его.
4. Ничего нет — вызываем `__getattr__`, если он определён, иначе `AttributeError`.

Что из этого следует:

- **Функция — дескриптор не-данных.** `obj.method` находит функцию в классе и вызывает её `__get__`, который возвращает связанный метод (bound method) с уже подставленным `self`. Поэтому методы получают `self`, а `staticmethod` и `classmethod` — это дескрипторы, которые подставляют ничего или класс.
- **`property` — дескриптор данных**, поэтому `obj.__dict__["x"] = 1` не перекроет свойство `x`.
- **`functools.cached_property` — дескриптор не-данных.** При первом обращении он вычисляет значение и кладёт его в `obj.__dict__`, и дальше шаг 2 находит значение раньше шага 3, дескриптор больше не вызывается. Поэтому ему нужен `__dict__`, и со `__slots__` он не работает.
- **`__getattr__` вызывается только для отсутствующих атрибутов**, а `__getattribute__` — для всех обращений; переопределять последний опасно, легко уйти в бесконечную рекурсию.

Отсюда же решение для класса-декоратора на методе из [[Python-протоколы#Класс как декоратор и декоратор класса]]: экземпляр класса без `__get__` не привязывается к объекту, и `self` теряется. Добавляем `__get__`, как у функций:

```python
import functools
import types


class CountCalls:
    def __init__(self, func) -> None:
        functools.update_wrapper(self, func)
        self.func = func
        self.calls = 0

    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.func(*args, **kwargs)

    def __get__(self, instance, owner=None):
        if instance is None:  # обращение через класс: Service.run
            return self
        return types.MethodType(self, instance)  # привязать, как обычный метод


class Service:
    @CountCalls
    def run(self, x: int) -> int:
        return x * 2


print(Service().run(3), Service.run.calls)  # 6 1
```

## Слоты

По умолчанию атрибуты экземпляра хранятся в словаре `obj.__dict__`: можно добавить любой атрибут в любой момент, но словарь занимает память. Если в классе объявить `__slots__`, Python создаёт для каждого имени дескриптор данных, а значения хранит прямо в объекте, в массиве фиксированного размера. Словаря `__dict__` (и слабых ссылок `__weakref__`) у экземпляров больше нет.

```python
class Point:
    __slots__ = ("x", "y")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


p = Point(1, 2)
try:
    p.z = 3
except AttributeError as e:
    print(e)  # 'Point' object has no attribute 'z' and no __dict__ for setting new attributes
```

Что даёт:

- **Память.** Замер на 64-битном CPython, объект с тремя атрибутами, без учёта самих значений:

| Версия | Обычный класс | Со `__slots__` |
| --- | --- | --- |
| 3.8 | ~150 байт | ~56 байт |
| 3.11 и новее | ~96 байт | ~56 байт |
| 3.11 и новее, если `__dict__` объекта затронули (`vars(obj)`, `obj.__dict__`) | ~160 байт | — |

С Python 3.11 значения атрибутов обычного объекта тоже хранятся компактно, без отдельного словаря, пока к `__dict__` никто не обращается. Поэтому старые статьи про экономию «в три раза» устарели. Сейчас выигрыш около 40%, он заметен на миллионах объектов и не важен на тысячах.

- **Защита от опечаток**: `p.lenght = 5` упадёт сразу, а не создаст тихо новый атрибут.
- **Чуть быстрее доступ к атрибутам**, но разница маленькая, и ради скорости слоты не ставят.

Ловушки:

- **Наследование.** Подкласс без своего `__slots__` снова получает `__dict__`, и вся экономия пропадает. В каждом классе иерархии объявляют `__slots__` только с новыми полями: повторять поля родителя не нужно, это только тратит память.
- **Множественное наследование.** Два родителя с непустыми `__slots__` несовместимы: `TypeError: multiple bases have instance lay-out conflict`. Поэтому у миксинов делают `__slots__ = ()`.
- **Нельзя задать значение по умолчанию атрибутом класса** с тем же именем: `x = 0` рядом с `__slots__ = ("x",)` даёт `ValueError: 'x' in __slots__ conflicts with class variable`. Значения по умолчанию — в `__init__` (или через `dataclass`, он это делает сам).
- **Нет `__dict__`**, а значит, не работают `cached_property`, `vars(obj)` и библиотеки, которые пишут в `__dict__`. Нет слабых ссылок, пока `"__weakref__"` не добавлен в слоты, а слабые ссылки нужны, например, `WeakValueDictionary` и некоторым кэшам.
- **Обычный способ сегодня — `@dataclass(slots=True)`** (Python 3.10+): поля и значения по умолчанию пишутся как обычно, а слоты dataclass создаёт сам. Учтите, что декоратор при этом создаёт новый класс вместо исходного.

Когда ставить: миллионы маленьких объектов (точки, события, узлы дерева, строки отчёта в памяти). Обычным сервисным классам, моделям и репозиториям слоты не нужны. Если объектов очень много и они однородны, ещё экономнее кортеж или `NamedTuple`, `array` или numpy.

## Что спросят дальше

- **Что такое метакласс?** Класс, экземплярами которого являются классы; по умолчанию это `type`. Метакласс может менять класс при создании (`__new__`, `__init__` метакласса) и перехватывать создание экземпляров (`__call__`). Примеры: `ABCMeta`, `EnumType`, декларативные модели SQLAlchemy и Django. В своём коде почти всегда хватает `__init_subclass__` или декоратора класса.
- **`__del__` — это деструктор?** Нет, это финализатор: вызывается, когда объект собирается сборщиком мусора, и момент не гарантирован (в PyPy и при циклических ссылках — когда-нибудь потом). Ресурсы освобождают через контекстные менеджеры, см. [[Python-протоколы#Контекстные менеджеры]].
- **`classmethod` или `staticmethod`?** `classmethod` получает класс и подходит для альтернативных конструкторов (`User.from_row(row)`): в подклассе он создаст подкласс. `staticmethod` ничего не получает, это просто функция в пространстве имён класса.
- **Почему объект с `__eq__` нельзя положить в set?** Если в классе определён `__eq__`, Python ставит `__hash__ = None`: равные объекты обязаны иметь одинаковый хэш, а Python не знает, как вы его считаете. Нужно определить `__hash__` по тем же полям (и только для неизменяемых объектов) или взять `@dataclass(frozen=True)`.
- **`ABC` или `Protocol`?** `ABC` — номинальная типизация: класс обязан явно наследоваться, и проверка идёт при создании экземпляра (нельзя создать объект с нереализованными абстрактными методами). `Protocol` — структурная: подходит любой класс с нужными методами, проверяет только тайпчекер (или `isinstance` с `@runtime_checkable`, но только по наличию имён).
- **Как сравнить `dataclass`, `NamedTuple` и pydantic?** `NamedTuple` неизменяемый, это кортеж, его можно распаковать и сравнить с кортежем. `dataclass` — обычный класс без проверок типов в рантайме. pydantic проверяет и приводит данные при создании объекта; его место — на границе с внешним миром (API, конфиг), а не внутри логики.
- **Почему `super().__init__()` нужно вызывать даже в миксине без родителей?** Родитель миксина — `object`, но в MRO итогового класса после миксина могут стоять другие классы. Не вызвал `super()` — их `__init__` не выполнится.
