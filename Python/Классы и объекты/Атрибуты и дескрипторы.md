Как Python находит атрибут (`__getattribute__`, дескрипторы данных и не данных, `__dict__`, `__getattr__`) и когда `__slots__` заменяет словарь атрибутов фиксированным набором полей.
Рядом: [[Создание объектов]] (`__new__`, `__init__`, метаклассы) · [[MRO и super]] (порядок поиска по классам).
Разделы: [[#Как Python ищет атрибут]] · [[#Слоты]] · [[#Что спросят дальше]]

**Суть.** Атрибуты объекта по умолчанию лежат в словаре `__dict__`; `__slots__` заменяет его на фиксированный набор полей и экономит память.

## Как Python ищет атрибут

Эта схема объясняет, почему методы получают `self`, почему `property` нельзя перезаписать через экземпляр и почему `__slots__` и `cached_property` несовместимы. Ключевое понятие — **дескриптор**: атрибут класса, у которого есть `__get__` (и, возможно, `__set__` или `__delete__`). Дескриптор с `__set__` или `__delete__` называется **дескриптором данных** (data descriptor), только с `__get__` — **дескриптором не-данных** (non-data descriptor).

`obj.attr` вызывает `type(obj).__getattribute__(obj, "attr")`, по умолчанию это `object.__getattribute__`:

1. Ищем `attr` в классах по MRO `type(obj)`. Нашли **дескриптор данных** — возвращаем результат его `__get__`, словарь экземпляра даже не смотрим.
2. Иначе ищем в `obj.__dict__` — нашли, возвращаем.
3. Иначе, если на шаге 1 нашёлся **дескриптор не-данных**, вызываем его `__get__`; если нашёлся обычный атрибут класса — возвращаем его.
4. Ничего нет — вызываем `__getattr__`, если он определён, иначе `AttributeError`.

Приоритеты на деле: в `__dict__` экземпляра вручную положены значения под теми же именами, что у дескриптора данных, дескриптора не-данных и обычного метода.

```python
class Data:
    def __get__(self, obj, owner=None):
        return "дескриптор данных"

    def __set__(self, obj, value):
        print("__set__", value)


class NonData:
    def __get__(self, obj, owner=None):
        return "дескриптор не-данных"


class T:
    d = Data()
    n = NonData()

    def method(self):
        return "метод"


t = T()
t.__dict__.update(d="из __dict__", n="из __dict__", method="из __dict__")
print(t.d)       # дескриптор данных выигрывает у __dict__
print(t.n)       # __dict__ выигрывает у не-данных
print(t.method)  # функция — тоже не-данных, метод затенён
t.d = 5          # присваивание тоже уходит в __set__
print(t.__dict__["d"])
```

```text title="Вывод"
дескриптор данных
из __dict__
из __dict__
__set__ 5
из __dict__
```

Что из этого следует:

- **Функция — дескриптор не-данных.** `obj.method` находит функцию в классе и вызывает её `__get__`, который возвращает связанный метод (bound method) с уже подставленным `self`. Поэтому методы получают `self`, а `staticmethod` и `classmethod` — это дескрипторы, которые подставляют ничего или класс.
- **`property` — дескриптор данных**, поэтому `obj.__dict__["x"] = 1` не перекроет свойство `x`.
- **`functools.cached_property` — дескриптор не-данных.** При первом обращении он вычисляет значение и кладёт его в `obj.__dict__`, и дальше шаг 2 находит значение раньше шага 3, дескриптор больше не вызывается. Поэтому ему нужен `__dict__`, и со `__slots__` он не работает.
- Разницу `property` и `cached_property` видно по `__dict__`:

```python
import functools


class U:
    @property
    def p(self):
        return "property"

    @functools.cached_property
    def c(self):
        print("считаем")
        return "cached"


u = U()
u.__dict__["p"] = "из __dict__"
print(u.p)
print(u.c, u.c)
print(u.__dict__)
try:
    u.p = 1
except AttributeError as e:
    print(e)
```

```text title="Вывод"
property
считаем
cached cached
{'p': 'из __dict__', 'c': 'cached'}
property 'p' of 'U' object has no setter
```

- **`__getattr__` вызывается только для отсутствующих атрибутов**, а `__getattribute__` — для всех обращений; переопределять последний опасно, легко уйти в бесконечную рекурсию.

Отсюда же решение для класса-декоратора на методе из [[Декораторы#Класс как декоратор и декоратор класса]]: экземпляр класса без `__get__` не привязывается к объекту, и `self` теряется. Добавляем `__get__`, как у функций:

```python
import functools
import types


class CountCalls:
    def __init__(self, func) -> None:
        functools.update_wrapper(self, func)
        self.func = func
        self.calls = 0

    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.func(*args, **kwargs)

    def __get__(self, instance, owner=None):
        if instance is None:  # обращение через класс: Service.run
            return self
        return types.MethodType(self, instance)  # привязать, как обычный метод


class Service:
    @CountCalls
    def run(self, x: int) -> int:
        return x * 2


print(Service().run(3), Service.run.calls)  # 6 1
```

## Слоты

По умолчанию атрибуты экземпляра хранятся в словаре `obj.__dict__`: можно добавить любой атрибут в любой момент, но словарь занимает память. Если в классе объявить `__slots__`, Python создаёт для каждого имени дескриптор данных, а значения хранит прямо в объекте, в массиве фиксированного размера. Словаря `__dict__` (и слабых ссылок `__weakref__`) у экземпляров больше нет.

```python
class Point:
    __slots__ = ("x", "y")

    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y


p = Point(1, 2)
try:
    p.z = 3
except AttributeError as e:
    print(e)
```

```text title="Вывод"
'Point' object has no attribute 'z' and no __dict__ for setting new attributes
```

Что даёт:

- **Память.** Замер на 64-битном CPython, объект с тремя атрибутами, без учёта самих значений:

| Версия | Обычный класс | Со `__slots__` |
| --- | --- | --- |
| 3.8 | ~150 байт | ~56 байт |
| 3.11 и новее | ~96 байт | ~56 байт |
| 3.11 и новее, если `__dict__` объекта затронули (`vars(obj)`, `obj.__dict__`) | ~160 байт | — |

С Python 3.11 значения атрибутов обычного объекта тоже хранятся компактно, без отдельного словаря, пока к `__dict__` никто не обращается. Поэтому старые статьи про экономию «в три раза» устарели. Сейчас выигрыш около 40%, он заметен на миллионах объектов и не важен на тысячах.

- **Защита от опечаток**: `p.lenght = 5` упадёт сразу, а не создаст тихо новый атрибут.
- **Чуть быстрее доступ к атрибутам**, но разница маленькая, и ради скорости слоты не ставят.

Замер `tracemalloc` на Python 3.15: 100 000 объектов с тремя атрибутами, средний размер объекта в байтах. `Sub` — подкласс без своего `__slots__`.

```python
import tracemalloc


class Plain:
    def __init__(self):
        self.a = self.b = self.c = 1


class Slots:
    __slots__ = ("a", "b", "c")

    def __init__(self):
        self.a = self.b = self.c = 1


class Sub(Slots):  # своего __slots__ нет
    pass


def measure(cls, n=100_000):
    tracemalloc.start()
    objs = [cls() for _ in range(n)]
    current, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return current // n


print(measure(Plain), measure(Slots), measure(Sub))
print(hasattr(Slots(), "__dict__"), hasattr(Sub(), "__dict__"))

sub = Sub()
sub.anything = 1  # у подкласса словарь вернулся
print(sub.__dict__)
```

```text title="Вывод"
104 64 112
False True
{'anything': 1}
```

`sys.getsizeof` для такого сравнения не годится: он меряет только сам объект, без отдельно выделенного хранилища атрибутов (`__dict__`, а с 3.11 — массива значений атрибутов), и показывает для `Plain` меньше, чем реально занято. `tracemalloc` считает все выделения; в число на объект входят и 8 байт его указателя в списке `objs`.

Ловушки:

- **Наследование.** Подкласс без своего `__slots__` снова получает `__dict__`, и вся экономия пропадает. В каждом классе иерархии объявляют `__slots__` только с новыми полями: повторять поля родителя не нужно, это только тратит память.
- **Множественное наследование.** Два родителя с непустыми `__slots__` несовместимы: `TypeError: multiple bases have instance lay-out conflict`. Поэтому у миксинов делают `__slots__ = ()`.
- **Нельзя задать значение по умолчанию атрибутом класса** с тем же именем: `x = 0` рядом с `__slots__ = ("x",)` даёт `ValueError` (`'x' in __slots__ conflicts with class variable`). Значения по умолчанию — в `__init__` (или через `dataclass`, он это делает сам).
- **Нет `__dict__`**, а значит, не работают `cached_property`, `vars(obj)` и библиотеки, которые пишут в `__dict__`. Нет слабых ссылок, пока `"__weakref__"` не добавлен в слоты, а слабые ссылки нужны, например, `WeakValueDictionary` и некоторым кэшам.
- **Обычный способ сегодня — `@dataclass(slots=True)`** (Python 3.10+): поля и значения по умолчанию пишутся как обычно, а слоты dataclass создаёт сам. При этом декоратор создаёт новый класс вместо исходного.

Когда ставить: миллионы маленьких объектов (точки, события, узлы дерева, строки отчёта в памяти). Обычным сервисным классам, моделям и репозиториям слоты не нужны. Если объектов очень много и они однородны, ещё экономнее кортеж или `NamedTuple`, `array` или numpy.

## Что спросят дальше

- **Почему объект с `__eq__` нельзя положить в set?** Если в классе определён `__eq__`, Python ставит `__hash__ = None`: равные объекты обязаны иметь одинаковый хэш, а Python не знает, как хэш считать. Нужно определить `__hash__` по тем же полям (и только для неизменяемых объектов) или взять `@dataclass(frozen=True)`.
