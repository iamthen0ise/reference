title: Блокировки
---

**Суть.** Благодаря MVCC читатели и писатели в Postgres друг друга не блокируют. Конфликтуют запись с записью одной и той же строки и DDL-команды (изменения схемы вроде `ALTER TABLE`) со всем остальным. Блокировки бывают пессимистичные (захватываем заранее, на случай конфликта) и оптимистичные (не блокируем, а проверяем конфликт в момент записи).

## Общие понятия (для любой БД)

- **Shared (S, разделяемая)** — блокировку могут держать много читателей одновременно. **Exclusive (X, исключительная)** — держит один писатель, остальные ждут.
- **Гранулярность** — на что ставится блокировка: строка, страница или вся таблица. SQL Server умеет lock escalation (повышение: когда строчных блокировок много, они заменяются одной табличной). Postgres так не делает: строчные блокировки хранятся прямо в самой строке (в поле `xmax`, см. [[Транзакции и уровни изоляции]]), и их количество памятью не ограничено.
- **Intent locks (блокировки намерения, IS и IX)** — пометка на таблице «внутри кто-то держит блокировки строк», чтобы не проверять каждую строку отдельно.
- **2PL (two-phase locking, двухфазная блокировка)** — правило: транзакция сначала только захватывает блокировки, а после первого освобождения уже ничего не захватывает. Так получается сериализуемость, но читатели ждут писателей, а писатели читателей. Postgres пошёл другим путём, через MVCC, поэтому чтение у него не блокируется.
- **Gap locks и next-key locks (InnoDB)** — блокируют «промежутки» между значениями индекса, чтобы никто не вставил туда фантом.
- **Распределённые блокировки** — когда нужно взаимное исключение между разными сервисами: Redis (Redlock, с оговорками, см. [[Распределённая блокировка в Redis]]), ZooKeeper или etcd (службы координации кластера), либо advisory locks в Postgres (ниже). Всегда с TTL (Time To Live, время жизни: блокировка сама сгорит, если владелец умер) и fencing token (монотонно растущий номер блокировки, по которому хранилище отвергает запись от владельца, потерявшего блокировку, но не заметившего этого).

## Строчные блокировки Postgres

| Режим | Кто берёт | Блокирует |
| --- | --- | --- |
| `FOR UPDATE` | `DELETE`, `UPDATE` ключевых полей, явный `SELECT ... FOR UPDATE` | все другие строчные режимы |
| `FOR NO KEY UPDATE` | обычный `UPDATE` | всё, кроме `KEY SHARE` (поэтому проверки внешних ключей не ждут обычных обновлений) |
| `FOR SHARE` | явный `SELECT ... FOR SHARE` | изменения строки |
| `FOR KEY SHARE` | проверка внешнего ключа при вставке в дочернюю таблицу | `DELETE` и смену ключа |

Ждать, пока строка освободится, нужно не всегда. С `NOWAIT` запрос сразу падает с ошибкой, если строка занята: это удобно, когда лучше ответить пользователю «попробуйте позже», чем держать его в ожидании. С `SKIP LOCKED` запрос пропускает занятые строки и берёт свободные. На этом построены очереди задач (ниже).

Третий вариант — `lock_timeout`: ждать можно, но не дольше заданного. Сессия A держит строку (`UPDATE wallet SET balance = balance - 10 WHERE id = 1` без `COMMIT`), сессия B пробует взять ту же строку:

```sql
-- сессия B
BEGIN;
SET LOCAL lock_timeout = '500ms';
UPDATE wallet SET balance = balance - 5 WHERE id = 1;
```

```text title="Вывод"
ERROR:  canceling statement due to lock timeout
```

```sql
-- сессия B, строка всё ещё занята сессией A
SELECT * FROM wallet WHERE id = 1 FOR UPDATE NOWAIT;
```

```text title="Вывод"
ERROR:  could not obtain lock on row in relation "wallet"
```

У обоих ошибок один SQLSTATE `55P03` (`lock_not_available`), так что приложение ловит их одним `except`. `SET LOCAL` действует до конца транзакции; таймаут нужен и в миграциях ([[Миграции без простоя#Почему lock_timeout обязателен]]).

## Табличные блокировки Postgres (основные)

Кроме строк, Postgres блокирует и таблицы целиком. Эти блокировки каждая команда берёт сама, и знать их нужно, чтобы понимать, какая команда кого заставит ждать.

| Режим | Кто берёт | Конфликтует с |
| --- | --- | --- |
| ACCESS SHARE | `SELECT` | только с ACCESS EXCLUSIVE |
| ROW EXCLUSIVE | `INSERT`, `UPDATE`, `DELETE` | SHARE и всеми более сильными |
| SHARE UPDATE EXCLUSIVE | VACUUM, ANALYZE, `CREATE INDEX CONCURRENTLY`, `VALIDATE CONSTRAINT` | сама с собой и более сильными |
| SHARE | обычный `CREATE INDEX` | любой записью |
| ACCESS EXCLUSIVE | большинство `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL` | всем, включая `SELECT` |

Из таблицы следует неприятная цепочка. Сессия A открыла транзакцию и прочитала таблицу `t` (ACCESS SHARE держится до конца транзакции, даже если A больше ничего не делает). Сессия B запускает `ALTER TABLE t ADD COLUMN x int`: ей нужен ACCESS EXCLUSIVE, она ждёт A. Сессия C просто делает `SELECT * FROM t` и встаёт в очередь за B, хотя с A она не конфликтует: очередь блокировок честная, и мимо ждущего ACCESS EXCLUSIVE новые читатели не проходят.

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state, wait_event_type, wait_event, left(query, 40) AS query
FROM pg_stat_activity
WHERE datname = 'pg_examples' AND state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY pid;
```

| pid | blocked_by | state | wait_event_type | wait_event | query |
| --- | --- | --- | --- | --- | --- |
| 260 | {} | idle in transaction | Client | ClientRead | SELECT * FROM t |
| 261 | {260} | active | Lock | relation | ALTER TABLE t ADD COLUMN x int |
| 262 | {261} | active | Lock | relation | SELECT * FROM t |

```sql
SELECT pid, mode, granted FROM pg_locks WHERE relation = 't'::regclass ORDER BY granted DESC, pid;
```

| pid | mode | granted |
| --- | --- | --- |
| 260 | AccessShareLock | t |
| 261 | AccessExclusiveLock | f |
| 262 | AccessShareLock | f |

Читатель C заблокирован не долгой транзакцией A, а ждущим `ALTER` (`blocked_by` = 261). Пока A не завершится, таблица `t` для всех новых запросов недоступна. Поэтому перед DDL ставят `lock_timeout`, а долгие транзакции не держат.

## Техника: очередь задач на SKIP LOCKED

```sql
-- Несколько воркеров берут разные задачи, не конкурируя и не дублируя друг друга
WITH next AS (
  SELECT id FROM jobs
  WHERE status = 'new' AND run_at <= now()
  ORDER BY run_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'processing', locked_at = now(), attempts = attempts + 1
FROM next WHERE jobs.id = next.id
RETURNING jobs.*;
-- индекс: CREATE INDEX ON jobs (run_at) WHERE status = 'new';
```

В таблице шесть новых задач. Два воркера берут по две, каждый в своей транзакции, и второй не ждёт первого:

```sql
-- воркер A и воркер B, обе транзакции открыты
SELECT id FROM jobs WHERE status = 'new' ORDER BY id LIMIT 2 FOR UPDATE SKIP LOCKED;
```

| Воркер | Что вернулось |
| --- | --- |
| A (первым) | `id` 1, 2 |
| B (пока A не закончил) | `id` 3, 4 |

Тот же запрос без `SKIP LOCKED` в третьей сессии C повисает, пока A не закоммитит или не откатится, и потом возвращает те же `id` 1, 2: до строк B запрос не доходит.

Так устроены релеи outbox ([[Когда двигать offset#Смежное: transactional outbox (таблица исходящих событий)]]) и готовые очереди задач на Postgres: pg-boss, graphile-worker, River, procrastinate. У такой очереди есть две особенности. Во-первых, `SKIP LOCKED` не гарантирует строгий порядок: два воркера одновременно берут соседние пачки и обрабатывают их параллельно. Во-вторых, воркер может взять задачу и умереть, не закончив её, и тогда она навсегда останется в статусе `processing`. Поэтому нужен ещё «сборщик» зависших задач: он периодически находит записи с `status = 'processing' AND locked_at < now() - interval '5 min'` и возвращает их в статус `new`.

## Техника: advisory-блокировки и взаимная блокировка (deadlock)

Advisory lock («консультативная» блокировка) — блокировка с числовым ключом, который выбирает приложение: Postgres сам ничего не защищает, а просто следит, чтобы один и тот же номер не взяли двое сразу.

```sql
-- Только один экземпляр сервиса выполняет ночной расчёт (без таблицы-флага)
SELECT pg_try_advisory_lock(hashtext('nightly_billing'));   -- true = мы главные
-- ... работа ...
SELECT pg_advisory_unlock(hashtext('nightly_billing'));
-- pg_advisory_xact_lock сама отпустится по окончании транзакции
-- Осторожно: сессионные advisory-блокировки ломаются с PgBouncer (прокси, который переиспользует соединения с базой) в режиме transaction (подробнее — в разделе про пулы соединений)

-- Deadlock (взаимная блокировка): T1 блокирует A, потом B; T2 — B, потом A, и обе ждут друг друга вечно.
-- Postgres через deadlock_timeout (1 секунда) находит такой цикл и отменяет одну транзакцию (SQLSTATE 40P01).
-- Профилактика — единый порядок захвата:
SELECT * FROM accounts WHERE id IN (:a, :b) ORDER BY id FOR UPDATE;

-- Кто кого блокирует
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, state, left(query, 80)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Как выглядит ожидание. Сессия A сделала `UPDATE wallet SET balance = balance - 10 WHERE id = 1` и не закоммитила, сессия B пытается обновить ту же строку. Запрос к `pg_stat_activity` из раздела про табличные блокировки:

| pid | blocked_by | state | wait_event_type | wait_event | query |
| --- | --- | --- | --- | --- | --- |
| 260 | {} | idle in transaction | Client | ClientRead | UPDATE wallet SET balance=balance-10 WHE |
| 261 | {260} | active | Lock | transactionid | UPDATE wallet SET balance=balance-5 WHER |

B ждёт завершения транзакции A (`transactionid`), а A ничего не делает: `idle in transaction`. В `pg_locks` это видно как невыданный `ShareLock` на чужой транзакции:

| pid | locktype | mode | granted |
| --- | --- | --- | --- |
| 260 | transactionid | ExclusiveLock | t |
| 261 | transactionid | ExclusiveLock | t |
| 261 | transactionid | ShareLock | f |
| 261 | tuple | ExclusiveLock | t |

`ExclusiveLock` на `transactionid` каждая транзакция держит на собственном номере, `ShareLock` с `granted = f` — это ожидание номера чужой транзакции. `tuple` — очередь за строку: B стоит в ней первым.

Deadlock на двух строках: `wallet` с `id` 1 и 2. Сессия A обновляет строку 1, сессия B обновляет строку 2, затем A тянется к строке 2, а B к строке 1 (цикл ожидания):

```sql
-- A: UPDATE wallet SET balance = balance - 1 WHERE id = 1;
-- B: UPDATE wallet SET balance = balance - 1 WHERE id = 2;
-- A: UPDATE wallet SET balance = balance + 1 WHERE id = 2;   -- ждёт B
-- B: UPDATE wallet SET balance = balance + 1 WHERE id = 1;   -- замкнули цикл
```

Через секунду (`deadlock_timeout`) Postgres отменяет одну из транзакций, в этом прогоне A. Остальные продолжают. Из лога сервера:

```text title="Вывод"
ERROR:  deadlock detected
DETAIL:  Process 227 waits for ShareLock on transaction 826; blocked by process 228.
	Process 228 waits for ShareLock on transaction 825; blocked by process 227.
	Process 227: UPDATE wallet SET balance=balance+1 WHERE id=2
	Process 228: UPDATE wallet SET balance=balance+1 WHERE id=1
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "wallet"
```

Клиенту приходит то же сообщение без строк с текстами запросов, SQLSTATE `40P01`; жертву не выбрать заранее, поэтому приложение повторяет транзакцию. Номера процессов и транзакций от запуска к запуску другие.

## Пессимистичная и оптимистичная блокировки

|  | Пессимистичная (`FOR UPDATE`) | Оптимистичная (колонка `version`) |
| --- | --- | --- |
| Когда | высокая конкуренция за одну строку, короткая транзакция | конфликты редки, долгое «размышление» между чтением и записью (форма в интерфейсе) |
| Цена | ожидания, риск deadlock, держится соединение | повтор или ошибка пользователю |
| Пример | списание с баланса | редактирование карточки товара двумя менеджерами |

## Бизнес-кейс: флеш-распродажа

«100 телефонов по акции, 50 000 человек жмут кнопку одновременно». Все покупки списывают остаток из одной и той же строки `stock` — это горячая строка (hot row). Блокировку на ней в каждый момент держит одна транзакция, остальные ждут в очереди и всё это время занимают соединения. Пул соединений быстро кончается, и таймауты получает уже весь сайт, а не только страница акции.

Варианты решения, от простого к сложному:

1. Атомарный `UPDATE stock SET qty = qty - 1 WHERE sku = :s AND qty > 0`: блокировка короткая, чтение в приложение не нужно.
2. Разбить остаток на N строк-«вёдер» (например, 10 по 10 штук) и списывать из случайного: конкуренция делится на N.
3. Заранее создать 100 строк-«талонов» и раздавать их через `FOR UPDATE SKIP LOCKED LIMIT 1`.
4. Вынести счётчик в [[Redis]] (команда `DECR`, атомарное уменьшение), а в базу писать только выигравших; перед всем этим поставить виртуальную очередь на фронтенде.

Продуктовый вопрос, который надо задать: нужен ли строгий лимит, или допустим небольшой оверсейл (продано больше, чем есть) с последующей отменой и извинением? От ответа зависит архитектура.

## Что спросят дальше

- **Что такое lock queue и почему «быстрый» `ALTER` положил боевую систему?** Очередь блокировок: пока `ALTER` ждёт долгий запрос, все новые запросы выстраиваются за ним, см. [[Миграции без простоя#Почему lock_timeout обязателен]].
- **Блокирует ли `SELECT` обычный `UPDATE` в Postgres?** Нет. А `VACUUM FULL`? Да, и полностью: он берёт ACCESS EXCLUSIVE.
- **Почему вставка в дочернюю таблицу ждёт родителя?** Внешний ключ берёт на строку родителя блокировку `FOR KEY SHARE`, а она конфликтует с `DELETE` и с изменением первичного ключа родителя.
- **Как найти, кто кого блокирует, и не усугубить пожар?** Порядок действий на воспроизведении: [[Пожар в PostgreSQL#Кто кого блокирует]].
