---
title: Миграции без простоя
---

**Суть.** Zero-downtime — «без остановки сервиса». Трудность в том, что многие изменения схемы на большой таблице останавливают работу с ней. Например, `ALTER COLUMN TYPE` переписывает таблицу целиком и всё это время держит блокировку ACCESS EXCLUSIVE, которая не пускает в таблицу даже читателей. На таблице в сотни гигабайт это минуты или часы полной недоступности. Поэтому опасные изменения делают по паттерну **expand, migrate, contract** («расширить, перенести, сжать»): сначала добавляют новое рядом со старым, потом фоном переносят данные, затем переключаются за одну короткую блокировку и только после этого удаляют старое.

## Что дёшево, а что переписывает таблицу

Прежде чем писать миграцию, нужно понять, к какому виду относится операция. Одни меняют только описание таблицы в системном каталоге и проходят мгновенно. Другие читают или переписывают всю таблицу, и тогда важно, какую блокировку они держат всё это время.

| Операция | Стоимость |
| --- | --- |
| `ADD COLUMN` без значения (nullable) или с константным `DEFAULT` (PostgreSQL 11+) | мгновенно, меняется только каталог |
| `varchar(50)` → `varchar(100)`, `varchar` → `text` | мгновенно (типы бинарно совместимы) |
| `int` → `bigint`, `text` → `int` | **перезапись таблицы и всех индексов** |
| `timestamp` → `timestamptz` | перезапись; начиная с PostgreSQL 12 без неё, если в сессии `timezone = 'UTC'` |
| `SET NOT NULL` | полный скан таблицы под ACCESS EXCLUSIVE (если нет уже проверенного `CHECK`) |
| `ADD FOREIGN KEY` / `ADD CHECK` | скан таблицы; вариант с `NOT VALID` и последующим `VALIDATE` обходится без долгой блокировки |
| `CREATE INDEX` | блокирует запись; `CONCURRENTLY` — не блокирует |
| `DROP COLUMN` | мгновенно (колонка помечается удалённой), но под коротким ACCESS EXCLUSIVE |
| `ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` | перезапись таблицы (в PostgreSQL 18 появился вариант `VIRTUAL`: перезаписи нет, значение вычисляется при чтении) |

Что означают `NOT VALID` и `VALIDATE`. Ограничение, добавленное с `NOT VALID`, создаётся мгновенно: оно сразу начинает проверять все новые и изменённые строки, но старые строки не проверяет, поэтому длинного скана и тяжёлой блокировки нет. Потом отдельной командой `VALIDATE CONSTRAINT` база проверяет старые строки. Эта команда долго читает таблицу, но берёт лёгкую блокировку, которая не мешает чтению и записи.

Как это выглядит на практике. `ADD COLUMN` с константным `DEFAULT` на таблице `orders` в миллион строк проходит за миллисекунды и не трогает файл таблицы, а со значением по умолчанию `random()` (оно разное для каждой строки, поэтому таблицу придётся переписать) занимает секунды, и файл таблицы меняется (`pg_relation_filenode` показывает номер файла на диске):

```sql
SELECT pg_relation_filenode('orders') AS before \gset
ALTER TABLE orders ADD COLUMN source text NOT NULL DEFAULT 'web';
SELECT pg_relation_filenode('orders') = :before AS same_file;
```

```text title="Вывод"
ALTER TABLE
Time: 4.009 ms
 same_file
-----------
 t
(1 row)
```

```sql
ALTER TABLE orders ADD COLUMN rnd double precision NOT NULL DEFAULT random();
SELECT pg_relation_filenode('orders') = :before AS same_file;
```

```text title="Вывод"
ALTER TABLE
Time: 2840.337 ms (00:02.840)
 same_file
-----------
 f
(1 row)
```

`NOT VALID` и `VALIDATE` на таблице `payments` (1 млн строк, `amount` от -4 до 999 995, то есть часть старых строк нарушает будущее правило `amount > 0`):

```sql
ALTER TABLE payments ADD CONSTRAINT amount_positive CHECK (amount > 0) NOT VALID;   -- мгновенно
INSERT INTO payments VALUES (2000000, -1);
```

```text title="Вывод"
ERROR:  new row for relation "payments" violates check constraint "amount_positive"
DETAIL:  Failing row contains (2000000, -1).
```

Новые строки уже проверяются, а старые нарушители остаются, и `convalidated` в `pg_constraint` равен `false`. Проверка старых строк находит их:

```sql
ALTER TABLE payments VALIDATE CONSTRAINT amount_positive;
```

```text title="Вывод"
ERROR:  check constraint "amount_positive" of relation "payments" is violated by some row
```

После исправления данных (`UPDATE payments SET amount = 1 WHERE amount <= 0`) та же команда проходит, а пока она идёт, в `pg_locks` на таблице видна только лёгкая блокировка:

| mode | granted |
| --- | --- |
| ShareUpdateExclusiveLock | t |

Она не мешает `SELECT`, `INSERT` и `UPDATE`. После `VALIDATE` `convalidated` становится `true`.

## Техника: `orders.id int → bigint` пошагово

```sql
-- Шаг 0. Защита от очереди блокировок (lock queue, см. раздел «Почему lock_timeout обязателен») во всех DDL-командах (командах изменения схемы)
SET lock_timeout = '3s';
SET statement_timeout = '30s';

-- Шаг 1. Expand: добавляем новую колонку (мгновенно)
ALTER TABLE orders ADD COLUMN id_new bigint;

-- Шаг 2. Двойная запись триггером: новые и изменённые строки сразу получают значение в обеих колонках
CREATE FUNCTION orders_sync_id() RETURNS trigger AS $$
BEGIN NEW.id_new := NEW.id; RETURN NEW; END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_orders_sync BEFORE INSERT OR UPDATE ON orders
FOR EACH ROW EXECUTE FUNCTION orders_sync_id();

-- Шаг 3. Заполнение старых строк батчами (скриптом в цикле, с паузами и контролем отставания реплик)
UPDATE orders SET id_new = id
WHERE id BETWEEN :from AND :from + 10000 AND id_new IS NULL;
-- между батчами: проверить replay lag (отставание реплики в применении журнала), дать отработать автовакууму

-- Шаг 4. Уникальный индекс под будущий PK — без блокировки записи
CREATE UNIQUE INDEX CONCURRENTLY orders_id_new_uq ON orders (id_new);

-- Шаг 5. NOT NULL без долгого скана под эксклюзивной блокировкой
ALTER TABLE orders ADD CONSTRAINT id_new_nn CHECK (id_new IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT id_new_nn;   -- скан есть, но под лёгкой блокировкой

-- Шаг 6. Переключение — одна короткая транзакция (с повтором при срабатывании lock_timeout)
BEGIN;
ALTER TABLE orders ALTER COLUMN id_new SET NOT NULL;  -- PostgreSQL 12+: скан пропускается благодаря готовому CHECK
ALTER TABLE order_items DROP CONSTRAINT order_items_order_id_fkey;  -- внешний ключ на старый PK (их колонки уже bigint)
ALTER TABLE orders DROP CONSTRAINT orders_pkey;
ALTER TABLE orders ADD CONSTRAINT orders_pkey PRIMARY KEY USING INDEX orders_id_new_uq;
ALTER TABLE orders ALTER COLUMN id DROP DEFAULT,        -- иначе каждая вставка возьмёт два nextval,
                   ALTER COLUMN id DROP NOT NULL;      -- а старая int-колонка всё равно переполнится
ALTER SEQUENCE orders_id_seq AS bigint OWNED BY orders.id_new;  -- иначе sequence упрётся в лимит int
ALTER TABLE orders ALTER COLUMN id_new SET DEFAULT nextval('orders_id_seq');
ALTER TABLE orders RENAME COLUMN id TO id_old;
ALTER TABLE orders RENAME COLUMN id_new TO id;
DROP TRIGGER trg_orders_sync ON orders;
ALTER TABLE order_items ADD CONSTRAINT order_items_order_id_fkey
  FOREIGN KEY (order_id) REFERENCES orders (id) NOT VALID;  -- без скана
COMMIT;
ALTER TABLE order_items VALIDATE CONSTRAINT order_items_order_id_fkey;  -- скан под лёгкой блокировкой

-- Шаг 7. Contract: удаляем старое через релиз, когда убедились, что всё работает
ALTER TABLE orders DROP COLUMN id_old;
ALTER TABLE orders DROP CONSTRAINT id_new_nn;
```

Внешние ключи из других таблиц (`order_items.order_id`) нужно перевести на `bigint` тем же путём **до** переключения. `DROP CONSTRAINT orders_pkey` без предварительного удаления внешних ключей упадёт, а с `CASCADE` молча снесёт их все. Поэтому внешние ключи удаляют и создают заново явно, через `NOT VALID` и `VALIDATE`. Между `COMMIT` и `VALIDATE` новые строки уже проверяются, а старые — ещё нет.

## Техника: `CREATE INDEX CONCURRENTLY` и неисправный индекс

`CONCURRENTLY` строит индекс без блокировки записи, но при ошибке не откатывается чисто: объект индекса остаётся в каталоге со статусом `INVALID`. Пример: уникальный индекс на колонке, где уже есть дубли.

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_accounts_email ON accounts (email);
\d accounts
```

```text title="Вывод"
ERROR:  could not create unique index "uq_accounts_email"
DETAIL:  Key (email)=(u4@example.com) is duplicated.

              Table "public.accounts"
 Column |  Type   | Collation | Nullable | Default
--------+---------+-----------+----------+---------
 id     | integer |           | not null |
 email  | text    |           | not null |
Indexes:
    "accounts_pkey" PRIMARY KEY, btree (id)
    "uq_accounts_email" UNIQUE, btree (email) INVALID
```

Индекс `INVALID` не используется в запросах, но продолжает обновляться при каждой записи и занимает место, а повторная команда `CREATE INDEX CONCURRENTLY` с тем же именем упадёт: имя занято. Нужно исправить причину (убрать дубли), удалить мёртвый индекс и построить заново:

```sql
DELETE FROM accounts WHERE id > 100000;   -- убрали дубли
DROP INDEX uq_accounts_email;             -- в проде: DROP INDEX CONCURRENTLY
CREATE UNIQUE INDEX CONCURRENTLY uq_accounts_email ON accounts (email);
```

После этого `\d accounts` показывает `"uq_accounts_email" UNIQUE, btree (email)` без пометки `INVALID`. Найти такие индексы по всей базе: `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid`.

## Почему lock_timeout обязателен

Даже «мгновенный» `ALTER` должен сначала получить блокировку ACCESS EXCLUSIVE. Если на таблице идёт долгий `SELECT`, `ALTER` ждёт его окончания, а все новые запросы встают в очередь блокировок (lock queue) **за `ALTER`**: Postgres не пропускает их вперёд, чтобы не заморить ожидающую эксклюзивную блокировку. Сервис лежит, хотя сама операция заняла бы миллисекунды. С `lock_timeout` `ALTER` не дожидается и сдаётся с ошибкой, очередь расходится, и операцию можно повторить позже.

Сессия B открыла транзакцию и прочитала `payments` (ACCESS SHARE висит до её конца). Миграция с `lock_timeout` сдаётся через две секунды вместо того, чтобы встать в очередь и заблокировать таблицу для всех:

```sql
SET lock_timeout = '2s';
ALTER TABLE payments ADD COLUMN note text;
```

```text title="Вывод"
ERROR:  canceling statement due to lock timeout
```

Когда B завершила транзакцию, та же команда проходит сразу: `ALTER TABLE`. Поэтому миграционный скрипт оборачивают в повтор: поймать `55P03`, подождать и попробовать снова.

## Смежное: совместимость кода и схемы

Схему и код не получится обновить в один момент. Во время rolling-деплоя (поэтапного обновления, когда часть серверов уже на новой версии, а часть ещё на старой) работают обе версии приложения сразу, и схема должна подходить им обеим.

Отсюда следует, что колонку нельзя переименовать одним релизом: как только пройдёт `RENAME`, старая версия приложения начнёт обращаться к колонке, которой больше нет, и сломается. Переименование делают тем же expand/contract: добавляют новую колонку, пишут в обе, переводят чтение на новую и только потом убирают старую.

Часть этой работы берут на себя инструменты. Flyway и Liquibase ведут версии миграций и помнят, какие уже применены. pg_repack перестраивает таблицу без долгих блокировок. pgroll и reshape автоматизируют expand/contract целиком. В самых тяжёлых случаях данные переносят логической репликацией в новую таблицу или новый кластер и переключаются на него.

## Бизнес-кейс: кончаются id

Тип `int4` заканчивается на 2 147 483 647. Если в таблицу вставляют 10 млн строк в день, этого хватит примерно на 214 дней, а потом каждый `INSERT` начнёт падать с ошибкой `integer out of range`, и продажи остановятся. Быстро перевести колонку на `bigint` не выйдет: миграция из предыдущего раздела на большой таблице идёт неделями. Поэтому начинать её нужно заранее, примерно когда последовательность заполнена наполовину. Продукту это объясняют выбором: либо сейчас плановая задача на спринт, либо потом инцидент, остановка продаж и неделя авральной работы. А чтобы не возвращаться к этому, новые таблицы сразу создают с `bigint`, `bigserial` или UUIDv7.

Заполненность `int`-последовательностей стоит держать на мониторинге:

```sql
-- Мониторинг заполнения int-последовательностей
SELECT sequencename, last_value, round(100.0 * last_value / 2147483647, 1) AS pct_used
FROM pg_sequences WHERE data_type = 'integer'::regtype ORDER BY pct_used DESC;
```
