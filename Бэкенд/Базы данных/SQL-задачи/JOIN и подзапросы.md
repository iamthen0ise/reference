## Виды JOIN

JOIN берёт строки двух таблиц и составляет из них пары по условию в `ON`. Виды соединений различаются тем, что происходит со строками, которым пары не нашлось. Разницу проще всего увидеть на двух крошечных наборах: в `a` числа 1, 2, 3, в `b` — 2, 3, 4. Совпадают только 2 и 3.

```sql
WITH a(x) AS (VALUES (1), (2), (3)),
     b(x) AS (VALUES (2), (3), (4))
SELECT a.x AS a_x, b.x AS b_x
FROM a
LEFT JOIN b ON a.x = b.x;   -- подставь INNER, RIGHT, FULL; у CROSS JOIN условия ON нет
```

`WITH a(x) AS (VALUES ...)` создаёт временную таблицу прямо в запросе: так удобно пробовать идеи без `CREATE TABLE`.

| Вид | Пары `a_x`, `b_x` | Что происходит со строками без пары |
| --- | --- | --- |
| `INNER JOIN` | (2, 2), (3, 3) | отбрасываются с обеих сторон |
| `LEFT JOIN` | (1, NULL), (2, 2), (3, 3) | строки `a` остаются, вместо `b` — `NULL` |
| `RIGHT JOIN` | (2, 2), (3, 3), (NULL, 4) | строки `b` остаются, вместо `a` — `NULL` |
| `FULL JOIN` | (1, NULL), (2, 2), (3, 3), (NULL, 4) | остаются с обеих сторон |
| `CROSS JOIN` | все 9 сочетаний | условия нет, каждая строка `a` встаёт в пару с каждой строкой `b` |

**INNER JOIN** — вид по умолчанию: просто `JOIN` означает именно его. Его берут, когда строка без пары по смыслу не нужна: заказ без клиента в отчёте о заказах не интересен.

**LEFT JOIN** нужен, когда левая таблица главная и каждая её строка должна попасть в результат, даже если справа ничего нет. Типичный пример — отчёт «все отделы и число сотрудников», где пустой отдел должен показать ноль, а не исчезнуть:

```sql
SELECT d.name, count(e.id) AS staff
FROM departments d
LEFT JOIN employees e ON e.department_id = d.id
GROUP BY d.id, d.name
ORDER BY d.id;   -- Backend 4, Data 3, Ops 2, Design 0
```

Считать здесь нужно `count(e.id)`, а не `count(*)`: у Design после `LEFT JOIN` есть одна строка, в которой справа `NULL`, и `count(*)` насчитал бы единицу. А условие на правую таблицу кладут в `ON`, а не в `WHERE`, иначе `LEFT JOIN` превращается в `INNER` ([[#Условие на правую таблицу в WHERE]]).

**RIGHT JOIN** — то же самое, только главная таблица справа. На практике его почти не пишут: проще поменять таблицы местами и написать `LEFT JOIN`, тогда запрос читается слева направо.

**FULL JOIN** нужен, когда главной стороны нет и важны расхождения с обеих сторон. Классический случай — сверка: платежи из выписки банка сравнивают с платежами в своей базе и ищут те, что есть только у одной стороны или отличаются суммой.

```sql
WITH bank(payment_id, amount) AS (VALUES (1, 100), (2, 50), (4, 70)),
     ours(payment_id, amount) AS (VALUES (1, 100), (2, 55), (3, 30))
SELECT payment_id, b.amount AS bank_amount, o.amount AS our_amount
FROM bank b
FULL JOIN ours o USING (payment_id)
WHERE b.amount IS DISTINCT FROM o.amount
ORDER BY payment_id;
-- 2: суммы расходятся (50 и 55), 3: нет в банке, 4: нет у нас
```

`USING (payment_id)` здесь не просто короче, чем `ON b.payment_id = o.payment_id`. В результате остаётся один столбец `payment_id`, и в `FULL JOIN` он заполнен, даже когда строки нет с одной из сторон. `IS DISTINCT FROM` сравнивает с учётом `NULL` (подробнее — в [[CASE COALESCE NULLIF]]): обычное `<>` с `NULL` дало бы «неизвестно», и платежи 3 и 4 пропали бы из результата.

**CROSS JOIN** строит все сочетания строк, поэтому размер результата — произведение размеров таблиц. Случайно это получается, когда забыли условие соединения, и тогда запрос по двум таблицам на миллион строк пытается выдать триллион. Намеренно его используют, чтобы построить сетку: например, все клиенты на все месяцы, к которой потом через `LEFT JOIN` подтягивают реальные данные и получают нули там, где ничего не было (похожий приём — в [[Классические SQL-задачи#Выручка по месяцам с пустыми месяцами]]).

Таблицу можно соединить и саму с собой (self-join): одна копия играет сотрудника, другая — его менеджера ([[#Сотрудники, получающие больше своего менеджера]]). А «есть пара» и «нет пары» без размножения строк (semi-join и anti-join) пишут не через JOIN, а через `EXISTS` и `NOT EXISTS`, см. задачи ниже.

Ещё одно свойство, о котором легко забыть: JOIN не ищет одно подходящее значение, а строит все пары. Если у ключа слева две строки, а справа три, в результате будет шесть строк. На этом построена ловушка из задачи [[#Размножение строк при JOIN двух «один-ко-многим»]].

## ON, USING и NATURAL

Условие соединения можно записать тремя способами.

- `ON` — любое условие: равенство столбцов, попадание в диапазон (`o.created_at BETWEEN p.starts_at AND p.ends_at`), несколько условий через `AND`. Это основной способ.
- `USING (col)` — сокращение для случая, когда столбец называется одинаково в обеих таблицах: `JOIN order_items USING (order_id)`. В результате этот столбец появляется один раз, а не дважды.
- `NATURAL JOIN` соединяет по всем столбцам с одинаковыми именами, и именно поэтому его избегают. В нашей схеме и у `customers`, и у `departments` есть `id` и `name`, так что `customers NATURAL JOIN departments` молча соединит по обоим столбцам и вернёт пустоту. Хуже того, если через год в обе таблицы добавят столбец `created_at`, запрос, который раньше работал, начнёт соединять и по нему.

## Как база выполняет JOIN

То, как JOIN записан в запросе, не определяет, как база его выполнит. Для каждого соединения планировщик выбирает один из трёх алгоритмов. Nested Loop для каждой строки слева ищет пары справа; он хорош, когда слева мало строк, а справа есть индекс. Hash Join строит хеш-таблицу по меньшей стороне и проходит по большей; он хорош для больших наборов с условием на равенство. Merge Join сливает две уже отсортированные последовательности. Порядок соединения таблиц планировщик тоже выбирает сам, поэтому порядок `JOIN` в тексте запроса на скорость обычно не влияет (пока таблиц не больше восьми — это параметр `join_collapse_limit`). Как эти алгоритмы выглядят в плане запроса — в [[EXPLAIN#Узлы плана]].

## Виды подзапросов

Подзапрос — `SELECT` внутри другого запроса. Его можно поставить в разные места, и от места зависит, что он должен вернуть.

**Скалярный подзапрос** стоит там, где ожидается одно значение: в `SELECT` или в сравнении в `WHERE`. Он обязан вернуть не больше одной строки с одним столбцом. Если строк ноль, получится `NULL`. Если больше одной, запрос упадёт с ошибкой `more than one row returned by a subquery used as an expression`.

```sql
SELECT name, salary, (SELECT max(salary) FROM employees) - salary AS gap_to_max
FROM employees
WHERE department_id = 3
ORDER BY id;   -- Kira 75, Ivan 100
```

**Подзапрос в FROM** (производная таблица, derived table) возвращает целый набор строк, и внешний запрос работает с ним как с таблицей. Такие подзапросы уже встречались в [[SQL-задачи#Оконная функция в WHERE]] и [[#Размножение строк при JOIN двух «один-ко-многим»]]. До PostgreSQL 16 ему обязательно давать псевдоним (`) t`). Начиная с 16-й версии можно и без него, но с псевдонимом запрос переносимее.

**Подзапрос-список в `IN`, `ANY` и `ALL`** возвращает один столбец, и значение сравнивают с каждым его элементом. `x IN (подзапрос)` истинно, если `x` равен хотя бы одному элементу; это то же самое, что `x = ANY (подзапрос)`. `ANY` работает и с другими операторами, а `ALL` требует, чтобы условие выполнилось для всех элементов сразу:

```sql
-- кто получает больше любого сотрудника отдела Data
SELECT name, salary FROM employees
WHERE salary > ALL (SELECT salary FROM employees WHERE department_id = 2);   -- Anna 300
```

С `ALL` есть две ловушки. Если подзапрос пуст, условие истинно для всех строк: в отделе Design сотрудников нет, и «больше всех в Design» получают все девять человек. А если в списке есть `NULL`, условие никогда не станет истинным — та же история, что с [[Ловушки SQL#NOT IN с NULL]].

**Коррелированный подзапрос** ссылается на столбцы внешнего запроса, поэтому по смыслу выполняется заново для каждой его строки. Пример — сотрудники, которые получают больше среднего по своему отделу:

```sql
SELECT e.name, e.department_id, e.salary
FROM employees e
WHERE e.salary > (SELECT avg(s.salary) FROM employees s WHERE s.department_id = e.department_id)
ORDER BY e.id;   -- Anna, Dina, Egor, Kira
```

Подзапрос считает среднее по отделу `e.department_id`, то есть по отделу той строки, которую сейчас проверяет внешний запрос. Звучит дорого, и иногда так и есть. Но `EXISTS` и `IN` планировщик обычно превращает в semi-join и выполняет за один проход, а скалярный подзапрос с индексом по условию (`employees (department_id)`) для каждой строки отрабатывает быстро. Эту же задачу можно решить окном и прочитать таблицу один раз: посчитать `avg(salary) OVER (PARTITION BY department_id)` во вложенном запросе и отфильтровать снаружи.

## Условие на правую таблицу в WHERE

Условие: вывести клиентов с их оплаченными заказами. Типичная ошибка — написать условие на правую таблицу в `WHERE`.

```sql
-- Ловушка: Cat исчезла, LEFT JOIN стал INNER
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';
```

У Cat заказов нет, поэтому после `LEFT JOIN` её `o.status` равен `NULL`. Условие `NULL = 'paid'` не истинно, и `WHERE` выбрасывает строку. Получилось, что `LEFT JOIN` повёл себя как `INNER JOIN`. Чтобы условие не убивало строки без пары, кладут его в `ON`: тогда оно участвует в поиске пары, а не в фильтрации готового результата.

```sql
SELECT c.name, count(o.id) AS paid_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
GROUP BY c.id, c.name
ORDER BY c.id;   -- Ann 2, Bob 2, Cat 0, Dan 2
```

Для `INNER JOIN` разницы между `ON` и `WHERE` нет. Для `LEFT JOIN` она принципиальная.

## Клиенты без заказов

Условие: клиенты, у которых нет ни одного заказа. Это anti-join.

Идея: для каждого клиента проверить, существует ли хотя бы один его заказ, и оставить тех, у кого такого нет.

```sql
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);   -- Cat
```

`NOT EXISTS (подзапрос)` истинно, когда подзапрос не вернул ни одной строки. Что именно выбирается в подзапросе (`SELECT 1`), неважно: проверяется только наличие строк.

Альтернатива — `LEFT JOIN ... WHERE o.id IS NULL`: присоединить заказы и оставить клиентов, к которым ничего не присоединилось. Планировщик строит из обоих вариантов один и тот же план (Anti Join), результат одинаков. `NOT EXISTS` читается как условие на человеческом языке, а не как трюк с `NULL`.

> [!warning] NOT IN и NULL
> `x NOT IN (подзапрос)` возвращает пустой результат, если в подзапросе есть хотя бы один `NULL`. Причина: `x <> NULL` даёт «неизвестно», и условие для всех строк оказывается не истинным.
> ```sql
> -- сотрудники, которые не являются менеджерами; у Anna manager_id IS NULL
> SELECT name FROM employees WHERE id NOT IN (SELECT manager_id FROM employees);   -- 0 строк
>
> SELECT name FROM employees e
> WHERE NOT EXISTS (SELECT 1 FROM employees s WHERE s.manager_id = e.id);          -- Vera, Gleb, Egor, Zoya, Ivan
> ```
> Для клиентов без заказов `NOT IN` случайно работает, пока на `orders.customer_id` стоит `NOT NULL`. Это хрупко: через год колонку сделают допускающей `NULL`, и запрос молча начнёт возвращать пустой результат. Поэтому всегда `NOT EXISTS`.

Индекс: `orders (customer_id)`. Без него `NOT EXISTS` для каждого клиента сканирует всю таблицу `orders`.

## Клиенты с оплаченным заказом (semi-join)

Условие: клиенты, у которых есть хотя бы один оплаченный заказ, каждый клиент один раз.

```sql
SELECT c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'paid');
-- Ann, Bob, Dan по одному разу
```

Обычный `JOIN orders` вернул бы Ann дважды, по числу её оплаченных заказов. `EXISTS` останавливается на первом найденном совпадении и не размножает строки клиента. Вариант с `DISTINCT` после `JOIN` даёт тот же ответ, но работает хуже: сначала строит все пары, потом убирает повторы.

## Сотрудники, получающие больше своего менеджера

Условие: найти сотрудников, чья зарплата больше зарплаты их непосредственного менеджера.

Идея: self-join (самосоединение). Таблица `employees` присоединяется сама к себе: одна копия (`e`) играет сотрудника, вторая (`m`) — его менеджера; пары находятся по условию `m.id = e.manager_id`.

```sql
SELECT e.name, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;   -- Egor 260 > Dina 250
```

`INNER JOIN` сам отбрасывает топ-менеджеров: у них `manager_id` равен `NULL`, и пары не находится. Если в условии сказано «вывести всех сотрудников и имя менеджера (если он есть)», нужен `LEFT JOIN`.

## Размножение строк при JOIN двух «один-ко-многим»

Условие: суммарная выручка и число дней активности по каждому клиенту. И у `orders`, и у `logins` связь с клиентом «один-ко-многим»: у одного клиента много заказов и много дней входа.

```sql
-- Ловушка: Ann получает 1100 вместо 220
SELECT c.name, sum(o.amount) AS total, count(l.day) AS days
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN logins l ON l.user_id = c.id
GROUP BY c.id, c.name ORDER BY c.id;
-- сумма / число дней: Ann 1100.00 / 15, Bob 800.00 / 6, Dan 1800.00 / 12
```

Что произошло: у Ann 3 заказа и 5 входов. `JOIN` строит все сочетания заказа и входа, то есть 15 строк, и каждый заказ повторяется 5 раз. Сумма и количество считаются по размноженным строкам, поэтому оба числа завышены.

Решение: свернуть каждую сторону до одной строки на клиента ещё до соединения, и тогда соединяются по одной строке с каждой стороны.

```sql
SELECT c.name, o.total, l.days
FROM customers c
JOIN (SELECT customer_id, sum(amount) AS total FROM orders GROUP BY customer_id) o ON o.customer_id = c.id
JOIN (SELECT user_id, count(*) AS days FROM logins GROUP BY user_id) l ON l.user_id = c.id
ORDER BY c.id;
-- сумма / число дней: Ann 220.00 / 5, Bob 400.00 / 2, Dan 450.00 / 4
```

Альтернатива — коррелированные подзапросы в `SELECT` (подзапрос, который ссылается на строку внешнего запроса). Писать проще, но подзапрос выполняется заново для каждой строки внешнего запроса. Признак этого бага: итоги получаются во столько раз больше ожидаемых, во сколько размножились строки.
