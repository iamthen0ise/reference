## Найти дубли и удалить

Условие: в таблице `emails` повторяются адреса. Найти повторы и оставить по одной строке на адрес, с наименьшим `id`.

Идея: внутри каждой группы одинаковых адресов пронумеровать строки по `id`. Строка с номером 1 остаётся, все строки с номером больше 1 — дубли, их и удаляем.

```sql
SELECT email, count(*) FROM emails GROUP BY email HAVING count(*) > 1;   -- a@x.io 3, b@x.io 2

DELETE FROM emails
WHERE id IN (
    SELECT id FROM (
        SELECT id, row_number() OVER (PARTITION BY email ORDER BY id) AS rn
        FROM emails
    ) t
    WHERE rn > 1
);   -- DELETE 3, остаются id 1, 2, 4
```

Первый запрос только показывает дубли. Второй удаляет: внутренний подзапрос выбирает `id` всех строк с номером больше 1 внутри своего адреса, внешний `DELETE` удаляет их.

Альтернатива — `DELETE ... USING`: `DELETE FROM emails a USING emails b WHERE a.email = b.email AND a.id > b.id;`. Результат тот же (удаляется строка, если есть строка с таким же адресом и меньшим `id`), но самосоединение квадратично растёт с размером группы дублей, и на больших группах оно медленнее.

Если нет уникального ключа, строку можно идентифицировать по `ctid` — физическому адресу строки в таблице:

```sql
DELETE FROM t
WHERE ctid IN (
    SELECT ctid FROM (
        SELECT ctid, row_number() OVER (PARTITION BY email) AS rn FROM t
    ) s WHERE rn > 1
);
```

> [!warning] ctid
> `ctid` меняется при `UPDATE` и при `VACUUM FULL` (полной перезаписи таблицы), поэтому это не идентификатор, а адрес. Используй его только внутри одного оператора. После очистки добавь ограничение `UNIQUE (email)`, иначе дубли вернутся. На больших таблицах удаляй пачками (по диапазонам `ctid` или `id`): одна долгая транзакция раздувает таблицу мёртвыми версиями строк и мешает работе `VACUUM` (фоновой очистке этих версий).

## Дни подряд

Условие: найти пользователей, которые входили три дня подряд и больше. Это задача типа gaps and islands.

Идея. Внутри каждого пользователя пронумеруем дни по возрастанию: 1, 2, 3 и так далее. У подряд идущих дней разность «дата минус номер» одинакова: например, 1 марта минус 1, 2 марта минус 2 и 3 марта минус 3 дают одну и ту же дату, 28 февраля. Когда в датах появляется пропуск, номер растёт на 1, а дата на 2 и более, поэтому разность сдвигается и начинается новая серия. Эта разность и служит идентификатором серии. Остаётся сгруппировать по пользователю и идентификатору серии, взять первый и последний день серии и их количество.

```sql
SELECT user_id, min(day) AS from_day, max(day) AS to_day, count(*) AS days
FROM (
    SELECT user_id, day,
           day - (row_number() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
    FROM logins
) t
GROUP BY user_id, grp
ORDER BY user_id, from_day;
-- пользователь: период (число дней).  1: 03-01..03-03 (3)   1: 03-05..03-06 (2)   2: 03-01..03-02 (2)   4: 03-10..03-13 (4)
```

Для условия «не меньше 3 дней» замени внешний `SELECT` на `SELECT DISTINCT user_id ... GROUP BY user_id, grp HAVING count(*) >= 3`: в ответе пользователи 1 и 4. Выражение `date - int` даёт `date` (число отнимается как количество дней). Вариант `day - row_number() * interval '1 day'` тоже работает (получится `timestamp`) и нужен, когда ключ сам имеет тип `timestamp`.

Если длина серии известна заранее, короче решается через `LEAD`: берём дату, стоящую на две строки впереди, и проверяем, что она ровно на 2 дня позже текущей.

```sql
SELECT DISTINCT user_id
FROM (SELECT user_id, day, lead(day, 2) OVER (PARTITION BY user_id ORDER BY day) AS d2 FROM logins) t
WHERE d2 - day = 2;   -- 1 и 4
```

Этот способ работает, пока в `(user_id, day)` нет дублей: `lead` смотрит на строку, а не на значение. Для серии переменной длины или для поиска самой длинной серии подходит только способ с `row_number`. Если дубли дней возможны, сначала сделай `SELECT DISTINCT user_id, day`. Индекс: первичный ключ `(user_id, day)` уже отдаёт данные в нужном порядке.

## Пропуски в последовательности id

Условие: какие `id` пропущены в `tickets`, где лежат 1, 2, 3, 6, 7, 10.

Есть два способа: найти диапазоны пропусков или перечислить каждое отсутствующее значение.

```sql
-- диапазоны пропусков
SELECT id + 1 AS gap_from, next_id - 1 AS gap_to
FROM (SELECT id, lead(id) OVER (ORDER BY id) AS next_id FROM tickets) t
WHERE next_id - id > 1;       -- 4..5, 8..9

-- каждое отсутствующее значение
SELECT g AS missing
FROM generate_series((SELECT min(id) FROM tickets), (SELECT max(id) FROM tickets)) g
LEFT JOIN tickets t ON t.id = g
WHERE t.id IS NULL;            -- 4, 5, 8, 9
```

Первый способ: для каждого `id` смотрим следующий (`lead`); если разница больше 1, между ними дыра, и её границы — `id + 1` и `next_id - 1`. Второй способ: `generate_series` создаёт ряд всех чисел от минимума до максимума, `LEFT JOIN` присоединяет существующие `id`, и там, где пары нет (`t.id IS NULL`), число отсутствует в таблице.

Первый способ быстрее на разреженных данных: `generate_series` порождает строку на каждое возможное значение. Оба способа видят только пропуски внутри диапазона; пропуск в начале (например, нет `id = 1`) придётся добавить отдельно. Пропуски в значениях `serial` (автоувеличиваемый счётчик) — норма: счётчик не откатывается вместе с откатом транзакции. Это не баг данных.

## Выручка по месяцам с пустыми месяцами

Условие: оплаченная выручка по месяцам за январь–апрель, при этом март должен быть в результате с нулём.

Идея: обычная группировка по месяцу вернёт только месяцы, в которых есть заказы. Поэтому сначала строим календарь из всех нужных месяцев (`generate_series`), а заказы присоединяем к нему через `LEFT JOIN`. Месяц без заказов остаётся в результате, потому что календарь стоит слева.

```sql
SELECT m::date AS month,
       coalesce(sum(o.amount), 0) AS revenue,
       count(o.id) AS orders
FROM generate_series('2025-01-01'::date, '2025-04-01'::date, interval '1 month') AS m
LEFT JOIN orders o
       ON o.status = 'paid'
      AND o.created_at >= m
      AND o.created_at <  m + interval '1 month'
GROUP BY m
ORDER BY m;
-- месяц: выручка / число заказов:  01: 350.00/3   02: 420.00/2   03: 0/0   04: 150.00/1
```

Почему работает и где подвохи:

- Без календаря `GROUP BY date_trunc('month', created_at)` вернёт три строки: марта в результате нет вовсе.
- Календарь стоит слева, а все условия на `orders` лежат в `ON`. Иначе `LEFT JOIN` превратится в `INNER` ([[JOIN и подзапросы#Условие на правую таблицу в WHERE]]).
- Условие `>= m AND < m + interval` — диапазон по столбцу, он использует индекс `orders (created_at)`. Запись `date_trunc('month', created_at) = m` индекс не использует, потому что функция применена к столбцу.
- `count(o.id)`, а не `count(*)`: иначе в пустом месяце будет 1.
- `sum` для пустого месяца даёт `NULL`, поэтому он обёрнут в `coalesce(..., 0)`.

## Медиана

Условие: медиана зарплат по компании и по отделам. Медиана — значение посередине упорядоченного набора, в отличие от среднего её не искажают выбросы.

```sql
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY salary) AS median,   -- 200
       percentile_disc(0.5) WITHIN GROUP (ORDER BY salary) AS disc,     -- 200
       avg(salary) AS avg                                                -- 209.44
FROM employees;

SELECT department_id, percentile_cont(0.5) WITHIN GROUP (ORDER BY salary)
FROM employees GROUP BY department_id;   -- 1: 200, 2: 250, 3: 212.5
```

`percentile_cont(0.5)` — непрерывный перцентиль 50%: если посередине два значения, он интерполирует между ними (в отделе 3 из 200 и 225 получилось 212.5). `percentile_disc(0.5)` — дискретный: возвращает реально существующее значение из набора. Запись `WITHIN GROUP (ORDER BY ...)` указывает, по какому порядку искать.

Агрегат сортирует всю группу, поэтому на больших таблицах он дорогой. Приближённая медиана для больших данных — отдельная тема (структура `tdigest` в расширениях). Вручную через `row_number` медиану пишут только на СУБД, где нет `percentile_cont`.

## Удержание (retention) и когорты

Условие: доля клиентов, сделавших заказ в месяц, следующий за месяцем их первого заказа. Когорта — группа клиентов, сделавших первый заказ в одном месяце. Удержание (retention) — какая часть когорты вернулась в следующий период.

Идея в три шага:

1. Для каждого клиента найти месяц первого заказа: это его когорта.
2. Составить список пар «клиент и месяц, в котором он делал заказы».
3. Для каждой когорты посчитать, сколько её клиентов есть в этом списке в месяце «когорта плюс один месяц».

```sql
WITH first_month AS (
    SELECT customer_id, min(date_trunc('month', created_at)) AS cohort
    FROM orders GROUP BY customer_id
), active AS (
    SELECT DISTINCT customer_id, date_trunc('month', created_at) AS month
    FROM orders
)
SELECT f.cohort::date,
       count(*) AS size,
       count(a.customer_id) AS returned,
       round(100.0 * count(a.customer_id) / count(*), 1) AS retention_pct
FROM first_month f
LEFT JOIN active a
       ON a.customer_id = f.customer_id
      AND a.month = f.cohort + interval '1 month'
GROUP BY f.cohort
ORDER BY f.cohort;
-- 2025-01: size 2, returned 2, 100.0   2025-02: size 1, returned 0, 0.0
```

Почему так:

- В `active` стоит `DISTINCT`: иначе два заказа клиента в одном месяце дали бы две строки и клиент посчитался бы дважды.
- `LEFT JOIN` сохраняет когорты, в которых никто не вернулся (получаем ноль, а не пропажу строки).
- `count(a.customer_id)`, а не `count(*)`, по той же причине, что в разделе про `COUNT`: строка без пары не должна считаться вернувшимся клиентом.
- Для кривой по нескольким месяцам добавь столбец «сдвиг в месяцах» (`month_offset`) и группируй по `cohort, offset`.

## Отдел с максимальной средней зарплатой

Условие: отдел (или отделы) с максимальной средней зарплатой. Средние: Backend 212.5, Ops 212.5, Data 203.3, то есть у двух отделов ничья.

Идея: посчитать среднюю зарплату по отделам, пронумеровать отделы по ней через `RANK` и оставить тех, у кого ранг 1. `RANK` даёт обеим ничьим первый ранг.

```sql
SELECT name, avg_salary
FROM (
    SELECT d.name, avg(e.salary) AS avg_salary,
           rank() OVER (ORDER BY avg(e.salary) DESC) AS rnk
    FROM departments d
    JOIN employees e ON e.department_id = d.id
    GROUP BY d.id, d.name
) t
WHERE rnk = 1;   -- Backend и Ops
```

Подвохи:

- `ORDER BY avg DESC LIMIT 1` вернёт одного из двух (какого именно, зависит от плана запроса) и тихо потеряет ничью.
- Оконная функция над агрегатом допустима: сначала выполняется `GROUP BY`, затем окно считается по получившимся группам.
- Отдел без сотрудников (Design) выпал из-за `INNER JOIN`. Если он нужен в результате с нулём, используй `LEFT JOIN` и `coalesce(avg(...), 0)`.
