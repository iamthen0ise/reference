## Как читать страницу

- Запросы идут на `small`. Планы и замеры — только на `big` (1 024 052 выдачи, 20 052 открытых, после `VACUUM ANALYZE`), у них подпись «набор big»: на малой таблице `Seq Scan` выигрывает при любом индексе.
- «Без индекса» — индекс убран внутри транзакции, которая откатывается. В планах оставлены корень и узлы чтения с условиями; `Buffers` — страницы по 8 КБ.
- Замеры: PostgreSQL 17 в Docker на ноутбуке, тёплый кэш, время на сервере. Три прогона, публикуется медиана; в пределах 20 % — «разницы нет».
- Прогоны делает служебная функция `bench` (не часть схемы): четыре запуска, первый (прогрев) отбрасывается, каждый откатывается.

```sql title="bench-helper.sql"
CREATE FUNCTION bench(q text)
RETURNS TABLE (run1 numeric, run2 numeric, run3 numeric, median numeric)
LANGUAGE plpgsql AS $$
DECLARE t timestamptz; r numeric[] := '{}';
BEGIN
    FOR i IN 0..3 LOOP  -- нулевой прогон прогревает кэш и не считается
        BEGIN
            t := clock_timestamp();
            EXECUTE q;
            IF i > 0 THEN
                r := r || round(extract(epoch FROM clock_timestamp() - t) * 1000, 2);
            END IF;
            RAISE EXCEPTION 'откат' USING ERRCODE = 'P0001';  -- запись не остаётся
        EXCEPTION WHEN raise_exception THEN NULL;
        END;
    END LOOP;
    RETURN QUERY SELECT r[1], r[2], r[3],
        (SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY x)::numeric(10,2) FROM unnest(r) AS x);
END $$;
```

## Сценарий 1. У кого какие книги на руках

Условие: читатель, книга, даты выдачи и срока. На руках — пока `returned_at IS NULL`.

```sql title="q-on-hands.sql"
SELECT r.name AS reader, b.title, l.issued_at, l.due_at
FROM loans AS l
JOIN readers AS r ON r.id = l.reader_id
JOIN books   AS b ON b.id = l.book_id
WHERE l.returned_at IS NULL
ORDER BY r.name, b.title;
```

```text title="Вывод"
 reader |       title       | issued_at  |   due_at
--------+-------------------+------------+------------
 Вера   | Властелин колец   | 2026-10-25 | 2026-11-08
 Вера   | Хоббит            | 2026-11-10 | 2026-12-01
 Глеб   | Основание         | 2026-11-12 | 2026-11-26
 Глеб   | Сильмариллион     | 2026-11-05 | 2026-11-26
 Дарья  | Пикник на обочине | 2026-11-15 | 2026-11-29
 Егор   | Хищные вещи века  | 2026-08-15 | 2026-09-01
(6 rows)
```

Анны (нет выдач) и Бориса (всё возвращено) нет: `JOIN` оставляет читателей с открытой выдачей.

```sql title="plan-on-hands.sql"
\pset tuples_only on
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT r.name AS reader, b.title, l.issued_at, l.due_at
FROM loans AS l
JOIN readers AS r ON r.id = l.reader_id
JOIN books   AS b ON b.id = l.book_id
WHERE l.returned_at IS NULL
ORDER BY r.name, b.title;
```

```text title="Вывод"

               ->  Bitmap Heap Scan on loans l (actual rows=20052 loops=1)

                     ->  Bitmap Index Scan on loans_one_open_per_book (actual rows=20052 loops=1)
```

Набор big, новых индексов нет. Частичный `loans_one_open_per_book` (`returned_at IS NULL`) совпадает с условием: прочитано 188 страниц таблицы вместо 7,5 тысяч. Остальное — хеш по 50 000 читателям и 100 000 книгам, индекс по `loans` на него не влияет. Новый индекс не нужен, цена записи — ноль. Для одного читателя индекс ограничения не годится (он упорядочен по `book_id`): нужен ведущий `reader_id`, это сценарий 2.

## Сценарий 2. Последние K книг каждого читателя

Условие: три последние выдачи каждого читателя; `LATERAL` с `LIMIT` против `ROW_NUMBER`. Ниже читатель 6.

```sql title="q-last-lateral.sql"
SELECT r.id AS reader_id, l.book_id, l.issued_at
FROM readers AS r
CROSS JOIN LATERAL (
    SELECT x.book_id, x.issued_at FROM loans AS x
    WHERE x.reader_id = r.id ORDER BY x.issued_at DESC, x.id DESC LIMIT 3
) AS l
WHERE r.id = 6
ORDER BY r.id, l.issued_at DESC;
```

```text title="Вывод"
 reader_id | book_id | issued_at
-----------+---------+------------
         6 |      10 | 2026-08-15
         6 |       4 | 2026-05-01
         6 |       5 | 2026-04-01
(3 rows)
```

```sql title="q-last-rownumber.sql"
SELECT t.reader_id, t.book_id, t.issued_at
FROM (
    SELECT x.reader_id, x.book_id, x.issued_at, row_number() OVER (
        PARTITION BY x.reader_id ORDER BY x.issued_at DESC, x.id DESC) AS n
    FROM loans AS x WHERE x.reader_id = 6
) AS t
WHERE t.n <= 3
ORDER BY t.reader_id, t.issued_at DESC;
```

```text title="Вывод"
 reader_id | book_id | issued_at
-----------+---------+------------
         6 |      10 | 2026-08-15
         6 |       4 | 2026-05-01
         6 |       5 | 2026-04-01
(3 rows)
```

Результаты одинаковы. Читатель без выдач (Анна) выпадает: `CROSS JOIN LATERAL` отбрасывает пустой подзапрос, оставить его — `LEFT JOIN LATERAL … ON true`. Сортировка кончается уникальным `id`, иначе при равных датах порядок плавает. Теория: [[CTE и LATERAL#LATERAL как топ-N в группе]], [[Оконные функции#Топ-N в каждом отделе]]. Индекс:

```sql title="idx-loans-reader-history.sql"
CREATE INDEX ix_loans_reader_history
    ON loans (reader_id, issued_at DESC, id DESC) INCLUDE (book_id);
```

- **`reader_id` первым, индекс не частичный:** равенство, по нему находится группа читателя; нужна вся история.
- **`issued_at DESC, id DESC`:** внутри группы строки уже по порядку, `Sort` исчезает, `LIMIT 3` читает три записи; `id` нужен и постраничному выводу (сценарий 3).
- **`INCLUDE (book_id)`:** нужна запросу, не порядку; лежит в листьях, таблицу читать не надо (`Index Only Scan`, `Heap Fetches: 0` после `VACUUM`).

План и замер на наборе big, K = 3: план `LATERAL` для 100 читателей без индекса и с ним, затем три прогона и медиана (мс) `LATERAL` и `ROW_NUMBER`:

```sql title="lab-last-k.sql"

       format(w, 100) AS rn100, format(w, 50000) AS rnall

    CROSS JOIN LATERAL (SELECT x.book_id, x.issued_at FROM loans AS x
        WHERE x.reader_id = r.id ORDER BY x.issued_at DESC, x.id DESC LIMIT 3) AS l
    WHERE r.id <= %s $q$, $q$
    SELECT t.reader_id, t.book_id, t.issued_at FROM (
        SELECT x.reader_id, x.book_id, x.issued_at, row_number() OVER (
            PARTITION BY x.reader_id ORDER BY x.issued_at DESC, x.id DESC) AS rn
        FROM loans AS x WHERE x.reader_id <= %s) AS t WHERE t.rn <= 3 $q$)
) AS v(l, w) \gset
\pset tuples_only on
\echo === без индекса
BEGIN;
DROP INDEX ix_loans_reader_history;
DROP INDEX ix_loans_issued_book;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) :lat100;
\echo вариант | прогон 1 | прогон 2 | прогон 3 | медиана, мс
SELECT 'LATERAL, 100' AS вариант, * FROM bench(:'lat100')

ROLLBACK;
\echo === с индексом
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) :lat100;
\echo вариант | прогон 1 | прогон 2 | прогон 3 | медиана, мс
SELECT 'LATERAL, 100' AS вариант, * FROM bench(:'lat100')
UNION ALL SELECT 'ROW_NUMBER, 100', * FROM bench(:'rn100')
UNION ALL SELECT 'LATERAL, все', * FROM bench(:'latall')
UNION ALL SELECT 'ROW_NUMBER, все', * FROM bench(:'rnall');
```

Набор big, медианы, мс:
- Страниц: 751 тысяча без индекса (сто сканов таблицы) и около 300 с ним.

## Сценарий 3. История читателя постранично

Условие: страницы по `LIMIT`; `OFFSET` против keyset (запомнить ключ последней строки). Читатель 6, по две строки, вторая страница:

```sql title="q-history-pages.sql"
(SELECT 'OFFSET' AS how, l.id, l.book_id, l.issued_at FROM loans AS l
 WHERE l.reader_id = 6 ORDER BY l.issued_at DESC, l.id DESC LIMIT 2 OFFSET 2)
UNION ALL
(SELECT 'keyset', l.id, l.book_id, l.issued_at FROM loans AS l
 WHERE l.reader_id = 6 AND (l.issued_at, l.id) < (DATE '2026-05-01', 9)
 ORDER BY l.issued_at DESC, l.id DESC LIMIT 2);
```

```text title="Вывод"
  how   | id | book_id | issued_at
--------+----+---------+------------
 OFFSET |  8 |       5 | 2026-04-01
 OFFSET |  7 |       5 | 2026-01-12
 keyset |  8 |       5 | 2026-04-01
 keyset |  7 |       5 | 2026-01-12
(4 rows)
```

Одинаково. Курсор — `(issued_at, id)` последней строки первой страницы, у читателя 6 это `(2026-05-01, 9)`; кортеж сравнивается верно, потому что обе колонки идут в одном направлении. Теория: [[Ловушки SQL#OFFSET на больших смещениях]]. Индекс тот же, что в сценарии 2: по `reader_id` находится история, порядок совпадает с курсором, условие по кортежу становится условием индекса. История читателя коротка (17 строк на big), и глубокий `OFFSET` на ней ничего не стоит. Чтобы увидеть, где он мешает, взята лента всей библиотеки (`ORDER BY issued_at DESC, id DESC`). Её индекс создаётся только на время замера и в сводку не входит; `ix_loans_issued_book` на время замера убран, иначе он подменяет «без индекса».

```sql title="m-pagination.sql"
CREATE TEMP TABLE cases AS
SELECT label, format($q$SELECT l.id, l.reader_id, l.book_id, l.issued_at FROM loans AS l %s
    ORDER BY l.issued_at DESC, l.id DESC %s LIMIT 10$q$, w, o) AS q
FROM (VALUES ('первая страница', '', ''), ('OFFSET 100000', '', 'OFFSET 100000'),
    ('OFFSET 500000', '', 'OFFSET 500000'), ('OFFSET 1000000', '', 'OFFSET 1000000'),
    ('keyset после 500000-й', $w$WHERE (l.issued_at, l.id) < (DATE '2025-05-30', 557088)$w$, '')
) AS v(label, w, o);
\pset footer off
BEGIN;
DROP INDEX ix_loans_issued_book;
\echo === лента без индекса
SELECT c.label, b.* FROM cases AS c CROSS JOIN LATERAL bench(c.q) AS b;
CREATE INDEX ix_loans_feed ON loans (issued_at DESC, id DESC);
\echo === лента с индексом, создан только для замера
SELECT c.label, b.* FROM cases AS c CROSS JOIN LATERAL bench(c.q) AS b;
ROLLBACK;
```

```text title="Вывод"

-----------------------+--------+--------+--------+--------
```

Набор big, медианы, мс:
- Без индекса `OFFSET` растёт с глубиной: 100 000 строк — 79, 500 000 — 111, 1 000 000 — 228. Keyset 25: в 4,4 раза быстрее `OFFSET 500000`, но это скан таблицы.

## Сценарий 4. Должники

Условие: книга на руках дольше 21 дня. Записано как `issued_at <= DATE '2026-11-20' - 21`: колонка слева, константа справа. Запись `DATE '2026-11-20' - issued_at > 21` оборачивает колонку и отключает индекс ([[Индексы#Когда индекс НЕ используется]]).

```sql title="q-debtors.sql"
SELECT r.name AS reader, b.title, DATE '2026-11-20' - l.issued_at AS days_on_hand
FROM loans AS l
JOIN readers AS r ON r.id = l.reader_id
JOIN books   AS b ON b.id = l.book_id
WHERE l.returned_at IS NULL
  AND l.issued_at <= DATE '2026-11-20' - 21
ORDER BY days_on_hand DESC, r.name;
```

```text title="Вывод"
 reader |      title       | days_on_hand
--------+------------------+--------------
 Егор   | Хищные вещи века |           97
 Вера   | Властелин колец  |           26
(2 rows)
```

На `small` двое: Егор (97 дней) и Вера (26). Индекс только над открытыми:

```sql title="idx-loans-open-by-issued.sql"
CREATE INDEX ix_loans_open_issued ON loans (issued_at) INCLUDE (reader_id, book_id)
    WHERE returned_at IS NULL;
```

- **`issued_at` ключом:** диапазон по дате. **`INCLUDE (reader_id, book_id)`:** нужны запросу, таблицу читать не надо.
- **Частичный `WHERE returned_at IS NULL`:** должники только среди открытых (2 % таблицы). Цена записи: 632 КБ, а не десятки мегабайт, запись только при выдаче и возврате.

План и замер на наборе big, без индекса и с ним:

```sql title="lab-debtors.sql"

    WHERE l.returned_at IS NULL AND l.issued_at <= DATE '2026-11-20' - 21 $q$ AS only_loans,
  $q$
    SELECT r.name, b.title, DATE '2026-11-20' - l.issued_at AS d FROM loans AS l
    JOIN readers AS r ON r.id = l.reader_id JOIN books AS b ON b.id = l.book_id
    WHERE l.returned_at IS NULL AND l.issued_at <= DATE '2026-11-20' - 21
    ORDER BY d DESC, r.name $q$ AS with_names \gset
\pset tuples_only on
\echo === без индекса
BEGIN;
DROP INDEX ix_loans_open_issued;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) :only_loans;
\echo вариант | прогон 1 | прогон 2 | прогон 3 | медиана, мс
SELECT 'только loans' AS вариант, * FROM bench(:'only_loans')

\echo === с индексом
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF, SUMMARY OFF) :only_loans;
\echo вариант | прогон 1 | прогон 2 | прогон 3 | медиана, мс
SELECT 'только loans' AS вариант, * FROM bench(:'only_loans')

```

## Сценарий 5. Топ-K популярных книг за период

Условие: десять самых выдаваемых книг за последние 30 дней. На `small` проверяем форму запроса: период с 1 января, K = 3.

```sql title="q-top-books.sql"
SELECT b.title, t.loans
FROM (SELECT l.book_id, count(*) AS loans FROM loans AS l
      WHERE l.issued_at >= DATE '2026-01-01' AND l.issued_at < DATE '2026-11-21'
      GROUP BY l.book_id ORDER BY loans DESC, l.book_id LIMIT 3) AS t
JOIN books AS b ON b.id = t.book_id
ORDER BY t.loans DESC, b.id;
```

```text title="Вывод"
      title      | loans
-----------------+-------
 Властелин колец |     3
 Хоббит          |     3
 Основание       |     3
(3 rows)
```

Три книги по три выдачи; порядок при равенстве задан вторым ключом `book_id`. Название подтягивается `JOIN`-ом после `LIMIT`. Индекс:

```sql title="idx-loans-issued-book.sql"
CREATE INDEX ix_loans_issued_book ON loans (issued_at) INCLUDE (book_id);
```

- **`issued_at` ключом:** диапазон по дате. **`INCLUDE (book_id)`:** для группировки нужен только он, таблица не читается.
- **Не частичный:** нужны и закрытые выдачи, в периоде их большинство. Группировка и сортировка остаются: индекс убирает чтение таблицы, а не агрегацию.

## Сводка сценарий и индекс

| Сценарий | Индекс | Эффект |
| --- | --- | --- |
| 1. На руках | нет, хватает `loans_one_open_per_book` | время в `JOIN` |
| 2 и 3. Последние K, история | `ix_loans_reader_history (reader_id, issued_at DESC, id DESC) INCLUDE (book_id)` | `LATERAL` 1 460 → 0,12 мс; keyset по `(issued_at, id)` |
| 4. Должники | `ix_loans_open_issued (issued_at) INCLUDE (reader_id, book_id) WHERE returned_at IS NULL`, условный | `loans` 1,24 → 0,36 мс; с именами разницы нет |
| 5. Топ-K | `ix_loans_issued_book (issued_at) INCLUDE (book_id)` | 13,7 → 2,9 мс |

Три индекса, один условный; индекса на каждую колонку нет.

Размеры индексов и цена записи, набор big: три индекса вместе около 63 МБ при таблице 59 МБ. Ниже вставка 10 000 закрытых выдач с индексами сценариев и без них.

```sql title="index-cost.sql"
WHERE relname = 'loans' OR relname LIKE 'ix\_loans%' ORDER BY pg_relation_size(oid) DESC;
SELECT $q$
    INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
    SELECT 1 + (g * 7919) % 50000, 1 + (g * 104729) % 100000,
           DATE '2026-11-20' - 1 - g % 365, DATE '2026-11-20' + 13 - g % 365,
           DATE '2026-11-20' + 2 - g % 365
    FROM generate_series(1, 10000) AS g $q$ AS ins \gset
```

## Что спросят дальше

- **Зачем `INCLUDE`.** Колонка лежит в листьях индекса, не влияет на порядок и отдаётся без захода в таблицу; работает, пока таблица вакуумируется (карта видимости). Цена — размер индекса.
- **Почему планировщик не взял индекс.** Условие отбирает слишком много строк, оборачивает колонку функцией или индекс упорядочен не так (в сценарии 1 `book_id` вместо `reader_id`). Разбор — [[Индексы#Когда индекс НЕ используется]], чтение плана — [[EXPLAIN#Как читать план]]. `enable_seqscan = off` — приём отладки, а не лечение.
- **А если несколько экземпляров.** Таблица `copies`, у выдачи `copy_id`; индекс истории и частичный уникальный переезжают на `copy_id`, «последние книги читателя» получают лишний `JOIN`.
- **А если миллион книг.** Индексы растут вместе с `loans`, а не с `books`. Первыми болят `OFFSET` на длинных списках и агрегация за широкий период.
