Сквозная задача «Библиотека»: читатели, книги, авторы и выдачи. Эта страница — единственный источник схемы и данных для остальных рецептов. Команды `make sql-up`, `make sql-block` берут блоки `schema.sql`, `seed-small.sql` и `seed-big.sql` отсюда.

Рядом: [[Нормализация]], [[Индексы]], [[Транзакции и уровни изоляции]], [[JOIN и подзапросы]].

## Как запустить

Нужен только запущенный Docker. Образ `postgres:17-alpine`, в нём есть `pg_stat_statements`. База `library`, контейнер `reference-pg`, пользователь `postgres`. Порт наружу не публикуется: к базе подключаются через `docker exec`, не из DBeaver и не локальным `psql`.

### Из репозитория

Команды запускаются из корня репозитория.

```bash
make sql-up SEED=small      # 7 читателей и 20 выдач, вывод читается глазами
make sql-up SEED=big        # около 1,02 млн выдач, для планов и замеров (15–20 с)
make sql-block PAGE="Бэкенд/Базы данных/SQL-рецепты/Схема библиотеки.md" TITLE="demo-open-twice.sql"
make sql-psql               # psql внутри контейнера, выход — \q
make sql-down
```

`sql-up` пересоздаёт контейнер, загружает схему и данные, создаёт расширение и выполняет `VACUUM ANALYZE`, чтобы планы на `big` строились по свежей статистике. Последняя строка вывода — `ready: reference-pg (small)`. `sql-block` прогоняет блок любой страницы рецептов по его `title`. `psql` запускается с `ON_ERROR_STOP=1`: ошибка SQL даёт ненулевой код выхода.

### Без репозитория

То же руками. Поднять контейнер и через пару секунд зайти в `psql`:

```bash
docker run -d --name reference-pg \
  -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=library \
  postgres:17-alpine -c shared_preload_libraries=pg_stat_statements -c track_io_timing=on
docker exec -it reference-pg psql -U postgres -d library
```

В `psql` вставить по очереди блок `schema.sql`, блок `seed-small.sql` или `seed-big.sql` (оба — ниже на этой странице) и в конце:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
VACUUM ANALYZE;
```

Дальше блоки с других страниц вставляются так же. Убрать контейнер — `docker rm -f reference-pg`. `trust` пускает без пароля, это допустимо только для локальной песочницы без опубликованного порта.

## Сущности и связи

```text
readers 1 ──< loans >── 1 books >──< book_authors >──< authors
```

| Таблица | Что хранит |
| --- | --- |
| `readers(id, name, registered_at)` | читатели |
| `authors(id, name)` | авторы |
| `books(id, title, published_year)` | книги |
| `book_authors(book_id, author_id)` | связь книга и автор, многие ко многим |
| `loans(id, reader_id, book_id, issued_at, due_at, returned_at)` | выдачи; `returned_at IS NULL` значит «на руках» |

Решения и причины:

- **Выдача — отдельная таблица.** Флаг `on_hand` или `reader_id` в книге помнят только текущее состояние. Читатель берёт много книг, книгу берут много читателей, и нужна история: кто читал, сколько держал, сколько раз просрочил.
- **Авторы — таблица и связь многие ко многим.** У книги бывает несколько авторов, у автора много книг. Без таблицы авторов условие «книги Толкина» не сформулировать, а строка с именем в книге дублируется и пишется по-разному. Книга без автора — книга без строк в `book_authors`: так бывают сборники и народные сказки, и запросы обязаны это пережить.
- **Экземпляров нет.** Одна книга — один физический экземпляр, `loans.book_id` ссылается прямо на книгу. Так запросы короче и их легко читать. Когда спросят «а если несколько экземпляров», добавляется таблица `copies(id, book_id)`, `loans.copy_id` заменяет `book_id`, а частичный уникальный индекс переезжает на `copy_id`. Запросы по книге получают один лишний `JOIN`.
- **Даты — `date`, не `timestamptz`.** Библиотека считает дни. В выводе меньше шума, `due_at - issued_at` даёт дни.
- **Условное «сегодня» — 2026-11-20.** Данные заданы относительно этой даты, а запросы на других страницах пишут её литералом, а не `current_date`. Результаты не зависят от дня прогона.
- **Других индексов нет.** В схеме только то, что требуют ограничения: первичные ключи, составной ключ связи и один частичный уникальный индекс по открытым выдачам. Индексы под сценарии строятся на странице «[[Запросы и индексы библиотеки]]», там видно, что они дают.

## Схема

```sql title="schema.sql"
CREATE TABLE readers (
    id            integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name          text    NOT NULL,
    registered_at date    NOT NULL
);

CREATE TABLE authors (
    id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text    NOT NULL
);

CREATE TABLE books (
    id             integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title          text    NOT NULL,
    published_year integer
);

CREATE TABLE book_authors (
    book_id   integer NOT NULL REFERENCES books (id) ON DELETE CASCADE,
    author_id integer NOT NULL REFERENCES authors (id) ON DELETE RESTRICT,
    PRIMARY KEY (book_id, author_id)
);

CREATE TABLE loans (
    id          bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    reader_id   integer NOT NULL REFERENCES readers (id) ON DELETE RESTRICT,
    book_id     integer NOT NULL REFERENCES books (id)   ON DELETE RESTRICT,
    issued_at   date    NOT NULL,
    due_at      date    NOT NULL,
    returned_at date,
    CONSTRAINT loans_due_after_issue    CHECK (due_at >= issued_at),
    CONSTRAINT loans_return_after_issue CHECK (returned_at >= issued_at)
);

-- Книга на руках только у одного читателя: не больше одной открытой выдачи на книгу.
CREATE UNIQUE INDEX loans_one_open_per_book ON loans (book_id) WHERE returned_at IS NULL;
```

## Ограничения

**Частичный уникальный индекс.** Условие `WHERE returned_at IS NULL` вносит в индекс только открытые выдачи. Закрытых выдач одной книги может быть сколько угодно, открытая — одна. Индекс маленький и держит правило на уровне базы, а не приложения: два параллельных запроса «выдать книгу» не оба успеют, второй получит ошибку и должен показать «книга занята».

Книга 1 в наборе `small` уже у читателя. Вторая выдача:

```sql title="demo-open-twice.sql"
INSERT INTO loans (reader_id, book_id, issued_at, due_at)
VALUES (1, 1, DATE '2026-11-20', DATE '2026-12-04');
```

```text title="Вывод"
ERROR:  duplicate key value violates unique constraint "loans_one_open_per_book"
DETAIL:  Key (book_id)=(1) already exists.
```

**`CHECK` на даты.** Возврат раньше выдачи — ошибка данных. У открытой выдачи `returned_at` равен `NULL`, условие даёт `NULL`, и `CHECK` такую строку пропускает: `CHECK` отвергает только `false`.

```sql title="demo-check-return.sql"
UPDATE loans SET returned_at = DATE '2026-01-01' WHERE id = 1;
```

```text title="Вывод"
ERROR:  new row for relation "loans" violates check constraint "loans_return_after_issue"
DETAIL:  Failing row contains (1, 2, 4, 2026-01-10, 2026-01-24, 2026-01-01).
```

**Внешние ключи и удаление.** `ON DELETE RESTRICT` на читателе и книге: выдачи — история, терять её при удалении нельзя. Читателя с выдачами база не удалит:

```sql title="demo-delete-reader.sql"
DELETE FROM readers WHERE id = 2;
```

```text title="Вывод"
ERROR:  update or delete on table "readers" violates … "loans_reader_id_fkey" on table "loans"
DETAIL:  Key (id)=(2) is still referenced from table "loans".
```

Сообщение сокращено (`…`). Что делать на деле: читателя не удаляют, а обезличивают (имя заменяют, строку оставляют) или помечают неактивным. Связь `book_authors` каскадно уходит вместе с книгой, потому что она ничего не значит без неё. Автора с книгами `RESTRICT` не отпускает.

## Большой набор

Миллион случайных закрытых выдач, ещё 4000 закрытых у «прочитавших всего Толкина», около 20 тысяч открытых, сто тысяч книг, пятьдесят тысяч читателей. `setseed` фиксирует `random()`, так что набор одинаков при каждом `sql-up`. Правила, которые закладывает генерация:

- книги 1–40 написал Толкин (автор 1), у 1 % книг автора нет, у 4 % двое авторов;
- читатели 48001–48190 не получают случайных выдач: 50 читателей без выдач, 100 прочли все 40 книг Толкина, 20 держат на руках только Толкина, 20 — Толкина и другого автора. Так ответы на задачи про множества на `big` не пусты;
- популярность книг перекошена: `power(random(), 2)` даёт «хиты», на которых проверяется топ-K;
- закрытые выдачи разбросаны по трём годам, открытые — все на разных книгах (частичный индекс этого требует), срок 14 дней, часть просрочена.

```sql title="seed-big.sql"
SELECT setseed(0.42) AS seed \gset

INSERT INTO readers (name, registered_at)
SELECT 'Читатель ' || g, DATE '2023-01-01' + (random() * 700)::int
FROM generate_series(1, 50000) AS g;

INSERT INTO authors (name)
SELECT CASE WHEN g = 1 THEN 'Толкин' ELSE 'Автор ' || g END
FROM generate_series(1, 5000) AS g;

INSERT INTO books (title, published_year)
SELECT 'Книга ' || g, 1900 + (random() * 125)::int
FROM generate_series(1, 100000) AS g;

-- Каждая книга получает автора; книги 1-40 всегда Толкина, 1 % книг без автора.
INSERT INTO book_authors (book_id, author_id)
SELECT g,
       CASE WHEN g <= 40 THEN 1 ELSE 2 + (random() * 4997)::int END
FROM generate_series(1, 100000) AS g
WHERE g <= 40 OR g % 100 <> 0;

-- Второй автор у 4 % книг; автор отличается от первого.
INSERT INTO book_authors (book_id, author_id)
SELECT ba.book_id, 2 + ((ba.author_id + 1 + (random() * 4000)::int) % 4998)
FROM book_authors AS ba
WHERE ba.book_id > 40 AND ba.book_id % 20 = 0;

-- Закрытые выдачи: миллион, три года, популярность перекошена.
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
-- Случайный читатель: номера 1-48000 и 48191-50000 (r больше 48000 сдвигается на 190).
SELECT CASE WHEN r > 48000 THEN r + 190 ELSE r END, book_id,
       issued_at, issued_at + 14, issued_at + days
FROM (
    SELECT 1 + (random() * 49809)::int              AS r,
           1 + floor(100000 * power(random(), 2))::int AS book_id,
           DATE '2026-11-20' - 31 - (random() * 1064)::int AS issued_at,
           1 + (random() * 29)::int                  AS days
    FROM generate_series(1, 1000000)
) AS t;

-- Открытые выдачи: книги, номер которых кратен пяти (кроме 1-40), по одной на книгу.
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
SELECT CASE WHEN r > 48000 THEN r + 190 ELSE r END, g,
       DATE '2026-11-20' - issued, DATE '2026-11-20' - issued + 14, NULL
FROM (SELECT g, 1 + (random() * 49809)::int AS r, (random() * 30)::int AS issued
      FROM generate_series(45, 100000, 5) AS g) AS t;

-- Читатели 48001-48190 не получают случайных выдач, их выдачи заданы без random().
-- Читатели 48001-48050 без единой выдачи: ничего не вставляем.

-- 48051-48150 (100 читателей): брали все 40 книг Толкина, все возвращены.
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
SELECT r, b, DATE '2026-11-20' - 40 - (r * b) % 900, DATE '2026-11-20' - 26 - (r * b) % 900,
       DATE '2026-11-20' - 39 - (r * b) % 900
FROM generate_series(48051, 48150) AS r CROSS JOIN generate_series(1, 40) AS b;

-- 48151-48170: на руках только книга Толкина (книги 1-20, по одной на читателя).
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
SELECT 48150 + k, k, DATE '2026-11-20' - k, DATE '2026-11-20' - k + 14, NULL
FROM generate_series(1, 20) AS k;

-- 48171-48190: на руках книга Толкина (21-40) и книга другого автора (1001, 1006, ...).
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
SELECT 48170 + k, 20 + k, DATE '2026-11-20' - k, DATE '2026-11-20' - k + 14, NULL::date
FROM generate_series(1, 20) AS k
UNION ALL
SELECT 48170 + k, 1001 + 5 * k, DATE '2026-11-20' - k, DATE '2026-11-20' - k + 14, NULL::date
FROM generate_series(1, 20) AS k;
```

```sql title="big-counts.sql"
SELECT (SELECT count(*) FROM books)    AS books,
       (SELECT count(*) FROM loans)    AS loans,
       (SELECT count(*) FROM loans WHERE returned_at IS NULL) AS open_loans,
       (SELECT count(*) FROM books b
         WHERE NOT EXISTS (SELECT 1 FROM book_authors ba WHERE ba.book_id = b.id)) AS no_author;
```

```text title="Вывод"
 books  |  loans  | open_loans | no_author 
--------+---------+------------+-----------
 100000 | 1024052 |      20052 |      1000
(1 row)
```

Набор `big`.

## Что спросят дальше

- **Зачем частичный уникальный индекс, а не проверка в приложении.** Приложение проверяет «книга свободна» и потом вставляет: между двумя шагами вклинивается второй запрос. Индекс закрывает окно атомарно. Подробнее о гонках — [[Транзакции и уровни изоляции]].
- **А если несколько экземпляров.** Таблица `copies`, `loans.copy_id`, индекс по `copy_id WHERE returned_at IS NULL`. Вопрос «есть ли свободный экземпляр» становится подсчётом.
- **А если читателя надо удалить.** Обезличить, а не удалять: выдачи остаются, в них нет персональных данных.
- **Какие внешние ключи без индекса.** `loans.reader_id` и `loans.book_id` по умолчанию не индексируются: в схеме выше `book_id` покрыт частичным индексом только для открытых выдач. Что даст индекс по `reader_id` — на странице «[[Запросы и индексы библиотеки]]».
- **Почему `date`, а не `timestamptz`.** Срок считается в днях, время суток не нужно. Если понадобится время, `timestamptz` и сравнение с `now()`.
