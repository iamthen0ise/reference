Пять задач на множества поверх схемы «Библиотека»: у кого книги на руках, у кого только Толкин, кто прочёл всего Толкина, у кого две разные книги одного автора и какие ловушки ломают такие запросы. У каждой задачи два-три решения, сверка, что они дают одно и то же, и строка «что назвать первым на собеседовании». Схема и данные — на странице «[[Схема библиотеки]]».

Рядом: [[Схема библиотеки]], [[Запросы и индексы библиотеки]], [[JOIN и подзапросы]], [[UNION INTERSECT EXCEPT]], [[Агрегация]], [[Ловушки SQL]].

## Как читать страницу

- Читатели на `small` — по одному на каждый край: Анна (выдач нет), Борис (только возвращённые), Вера (на руках только Толкин), Глеб (Толкин и Азимов), Дарья (прочла всего Толкина), Егор (Солярис дважды), Жанна (прочла не всё). Книга 8 «Народные сказки» без автора. «Сегодня» — 2026-11-20, дат в запросах нет. Состав — на странице «[[Схема библиотеки]]».
- Решение оформлено как представление `t1_…`, `t2_…`: сверка и замер берут тот же текст. Представления нужны только прогону, в схему они не входят.
- Решения сравнивает функция `set_diff(a, b)`: `(A EXCEPT ALL B) UNION ALL (B EXCEPT ALL A)`, сколько строк различается. `EXCEPT ALL`, а не `EXCEPT`: он сравнивает мультимножества и видит дубль, который обычный `EXCEPT` схлопнул бы (читатель дважды в ответе — это тоже ошибка). Ноль строк значит, что решения совпали. Сверка на пустом ответе ничего не доказывает, поэтому рядом выводится число строк ответа.
- Функция `bench(q)` для замеров — со страницы «[[Запросы и индексы библиотеки]]», раздел [[Запросы и индексы библиотеки#Как читать страницу]]: три прогона после прогрева, медиана. Порядок запуска: на `big` сначала `bench-helper.sql` оттуда, потом `sets-helpers`, `sets-1…4-solutions`, `sets-traps-views`; остальные блоки по тексту, `sets-bench-index.sql` — до `sets-check.sql` на `big`.

```sql title="sets-helpers.sql"
CREATE VIEW tolkien_books AS
SELECT ba.book_id
FROM book_authors ba
JOIN authors a ON a.id = ba.author_id
WHERE a.name = 'Толкин';

CREATE FUNCTION rows_of(v regclass) RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE n bigint;
BEGIN
    EXECUTE format('SELECT count(*) FROM %s', v) INTO n;
    RETURN n;
END $$;

CREATE FUNCTION set_diff(a regclass, b regclass) RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE n bigint;
BEGIN
    EXECUTE format(
        'SELECT count(*) FROM ((SELECT * FROM %1$s EXCEPT ALL SELECT * FROM %2$s)
                         UNION ALL (SELECT * FROM %2$s EXCEPT ALL SELECT * FROM %1$s)) d',
        a, b) INTO n;
    RETURN n;
END $$;

CREATE VIEW solutions AS
SELECT relname AS name FROM pg_class WHERE relkind = 'v' AND relname ~ '^t[1-4]_';
```

Толкин — это `tolkien_books`: книги, у которых среди авторов есть Толкин. Книга без автора в него не входит, и это важно для задач 2 и 3.

## Задача 1. Читатели с книгами на руках и без

«На руках» — выдача с `returned_at IS NULL`. Нужны две выборки: у кого есть книги и у кого нет. У Анны выдач нет совсем, у Бориса и Жанны все выдачи возвращены: во вторую выборку попадают все трое.

```sql title="sets-1-solutions.sql"
-- есть книги на руках
CREATE VIEW t1_has_exists AS
SELECT r.id FROM readers r
WHERE EXISTS (SELECT 1 FROM loans l WHERE l.reader_id = r.id AND l.returned_at IS NULL);
CREATE VIEW t1_has_join AS
SELECT DISTINCT r.id FROM readers r
JOIN loans l ON l.reader_id = r.id
WHERE l.returned_at IS NULL;
CREATE VIEW t1_has_in AS
SELECT r.id FROM readers r
WHERE r.id IN (SELECT reader_id FROM loans WHERE returned_at IS NULL);

-- нет книг на руках
CREATE VIEW t1_none_notexists AS
SELECT r.id FROM readers r
WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.reader_id = r.id AND l.returned_at IS NULL);
CREATE VIEW t1_none_leftjoin AS
SELECT r.id FROM readers r
LEFT JOIN loans l ON l.reader_id = r.id AND l.returned_at IS NULL
WHERE l.id IS NULL;
CREATE VIEW t1_none_notin AS
SELECT r.id FROM readers r
WHERE r.id NOT IN (SELECT reader_id FROM loans WHERE returned_at IS NULL);

SELECT 'на руках' AS kind, string_agg(r.name, ', ' ORDER BY r.id) AS readers
FROM readers r WHERE r.id IN (SELECT id FROM t1_has_exists)
UNION ALL
SELECT 'без книг', string_agg(r.name, ', ' ORDER BY r.id)
FROM readers r WHERE r.id IN (SELECT id FROM t1_none_notexists);
```

```text title="Вывод"
   kind   |         readers         
----------+-------------------------
 на руках | Вера, Глеб, Дарья, Егор
 без книг | Анна, Борис, Жанна
(2 rows)
```

Решения:

- `EXISTS` и `NOT EXISTS` спрашивают «есть ли хоть одна такая строка» и не плодят дублей: читатель с двумя книгами на руках остаётся одной строкой.
- `JOIN` читателя с выдачами даёт строку на каждую выдачу, поэтому нужен `DISTINCT`. Без него Вера и Глеб идут по два раза (прогон в задаче 5).
- `LEFT JOIN … IS NULL` ищет читателя без пары. Условие `returned_at IS NULL` стоит в `ON`: из `WHERE` оно превратило бы запрос в другой (тоже в задаче 5).
- `NOT IN` тут работает, потому что `loans.reader_id` объявлен `NOT NULL`. Если в подзапросе окажется NULL, результат пуст (задача 5), поэтому ему не верят на колонке, у которой NULL возможен.

**Первым назвать:** `EXISTS` / `NOT EXISTS` — читается как условие, не размножает строки, не боится NULL.

## Задача 2. На руках только книги Толкина

Читатель с хотя бы одной книгой на руках, у которого нет книги на руках не Толкина. Книга без автора — тоже «не Толкин». На `small` ответ — одна Вера: у Глеба Азимов, у Дарьи и Егора Стругацкие.

```sql title="sets-2-solutions.sql"
CREATE VIEW t2_not_exists AS
SELECT r.id FROM readers r
WHERE EXISTS (SELECT 1 FROM loans l WHERE l.reader_id = r.id AND l.returned_at IS NULL)
  AND NOT EXISTS (
      SELECT 1 FROM loans l
      WHERE l.reader_id = r.id AND l.returned_at IS NULL
        AND NOT EXISTS (SELECT 1 FROM tolkien_books tb WHERE tb.book_id = l.book_id));
CREATE VIEW t2_bool_and AS
SELECT l.reader_id AS id
FROM loans l
LEFT JOIN tolkien_books tb ON tb.book_id = l.book_id
WHERE l.returned_at IS NULL
GROUP BY l.reader_id
HAVING bool_and(tb.book_id IS NOT NULL);
CREATE VIEW t2_except AS
SELECT reader_id AS id FROM loans WHERE returned_at IS NULL
EXCEPT
SELECT l.reader_id FROM loans l
WHERE l.returned_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM tolkien_books tb WHERE tb.book_id = l.book_id);

SELECT r.id, r.name FROM readers r WHERE r.id IN (SELECT id FROM t2_bool_and) ORDER BY r.id;
```

```text title="Вывод"
 id | name 
----+------
  3 | Вера
(1 row)
```

- `NOT EXISTS` в `NOT EXISTS`: «нет выдачи на руках, для которой нет Толкина». Читается тяжело, зато прямо повторяет условие.
- `bool_and` собирает «все книги читателя на руках — Толкина» в одну проверку в `GROUP BY`. `LEFT JOIN` обязателен: с `JOIN` книга без автора выпала бы из группы, и читатель с Толкином и сказками остался бы в ответе.
- `EXCEPT`: все, у кого есть книга на руках, минус те, у кого есть чужая. Условие «есть хоть одна» даёт левая часть.

**Первым назвать:** `bool_and` с `LEFT JOIN` — одна группировка, условие читается как «все»; про `LEFT JOIN` сказать вслух.

## Задача 3. Прочёл всех Толкина

Реляционное деление: читатели, у которых для каждой книги Толкина есть выдача, возвращённая или нет. На `small` ответ — Дарья (все три книги); Вера читала две из трёх, Жанна тоже две.

```sql title="sets-3-solutions.sql"
CREATE VIEW t3_count AS
SELECT l.reader_id AS id
FROM loans l
JOIN tolkien_books tb ON tb.book_id = l.book_id
GROUP BY l.reader_id
HAVING count(DISTINCT l.book_id) = (SELECT count(*) FROM tolkien_books);
CREATE VIEW t3_not_exists AS
SELECT r.id FROM readers r
WHERE NOT EXISTS (
    SELECT 1 FROM tolkien_books tb
    WHERE NOT EXISTS (
        SELECT 1 FROM loans l WHERE l.reader_id = r.id AND l.book_id = tb.book_id));
CREATE VIEW t3_except AS
SELECT id FROM readers
EXCEPT
SELECT missing.reader_id
FROM (SELECT r.id AS reader_id, tb.book_id
      FROM readers r CROSS JOIN tolkien_books tb
      EXCEPT
      SELECT reader_id, book_id FROM loans) AS missing;

SELECT r.id, r.name FROM readers r WHERE r.id IN (SELECT id FROM t3_count) ORDER BY r.id;
```

```text title="Вывод"
 id | name  
----+-------
  5 | Дарья
(1 row)
```

- `HAVING count(DISTINCT book_id) = число книг` считает, сколько разных книг Толкина читатель брал. `DISTINCT` обязателен: повторные выдачи одной книги иначе засчитались бы как разные.
- `NOT EXISTS` в `NOT EXISTS`: «нет книги Толкина, которой у читателя не было».
- `EXCEPT` внутри: книги Толкина минус книги читателя пусты.

**Первым назвать:** `HAVING count(DISTINCT …) = (SELECT count(*) …)`: короткий и понятный; про `DISTINCT` упомянуть. `NOT EXISTS` в `NOT EXISTS` — «классическое» деление, его называют вторым.

## Задача 4. Две разные книги одного автора

Пары читатель и автор, где читатель брал хотя бы две разные книги этого автора. Повторная выдача одной книги не считается.

```sql title="sets-4-solutions.sql"
CREATE VIEW t4_having AS
SELECT l.reader_id, ba.author_id
FROM loans l
JOIN book_authors ba ON ba.book_id = l.book_id
GROUP BY l.reader_id, ba.author_id
HAVING count(DISTINCT l.book_id) >= 2;
CREATE VIEW t4_minmax AS
SELECT l.reader_id, ba.author_id
FROM loans l
JOIN book_authors ba ON ba.book_id = l.book_id
GROUP BY l.reader_id, ba.author_id
HAVING min(l.book_id) <> max(l.book_id);
CREATE VIEW t4_selfjoin AS
SELECT DISTINCT l1.reader_id, a1.author_id
FROM loans l1
JOIN loans l2 ON l2.reader_id = l1.reader_id AND l2.book_id > l1.book_id
JOIN book_authors a1 ON a1.book_id = l1.book_id
JOIN book_authors a2 ON a2.book_id = l2.book_id AND a2.author_id = a1.author_id;

SELECT r.name AS reader, a.name AS author
FROM t4_having t
JOIN readers r ON r.id = t.reader_id
JOIN authors a ON a.id = t.author_id
ORDER BY r.id, a.id;
```

```text title="Вывод"
 reader | author 
--------+--------
 Борис  | Азимов
 Вера   | Толкин
 Глеб   | Азимов
 Дарья  | Толкин
 Жанна  | Толкин
(5 rows)
```

- `count(DISTINCT book_id) >= 2` — прямой перевод условия.
- `min <> max` — то же без `DISTINCT`: если все книги группы одинаковы, минимум равен максимуму. Не нужна сортировка уникальных значений.
- Самосоединение: две выдачи одного читателя разных книг с общим автором. Пара книг упорядочена по `book_id`, чтобы не считать её дважды; `DISTINCT` схлопывает читателей с несколькими такими парами.

Выдача Егора (Солярис дважды) в ответ не попала: книга одна. Решение с `count(*) >= 2` его бы добавило (задача 5).

**Первым назвать:** `HAVING count(DISTINCT …) >= 2`. `min <> max` — как приём, если спросят про сортировку; самосоединение — как «ещё один способ» (на `big` оно вдвое быстрее, но читается хуже).

## Задача 5. Ловушки

Ловушки показаны прогоном: неверное решение оформлено представлением `bad_…`, и `set_diff` ловит его там, где верное проходит. Без прогона, только текстом, дано правило про читателя без выдач и `count(l.id)` после `LEFT JOIN`.

### NOT IN и NULL

Условие `x NOT IN (…, NULL)` не истинно ни для какого `x`: сравнение с NULL даёт `UNKNOWN`. Если подзапрос возвращает NULL, `NOT IN` отдаёт пустой результат. У книги 8 год выхода NULL.

```sql title="sets-notin-null.sql"
-- книги, чей год не встречается среди книг без автора (у книги 8 год NULL)
WITH no_author AS (
    SELECT b.* FROM books b
    WHERE NOT EXISTS (SELECT 1 FROM book_authors ba WHERE ba.book_id = b.id))
SELECT
    (SELECT count(*) FROM books
      WHERE published_year NOT IN (SELECT published_year FROM no_author)) AS not_in_rows,
    (SELECT count(*) FROM books b
      WHERE NOT EXISTS (SELECT 1 FROM no_author n
                         WHERE n.published_year = b.published_year)) AS not_exists_rows;
```

```text title="Вывод"
 not_in_rows | not_exists_rows 
-------------+-----------------
           0 |              10
(1 row)
```

`NOT IN` вернул 0 строк, `NOT EXISTS` — все книги. Правило: `NOT EXISTS`, а если `NOT IN`, то колонка подзапроса `NOT NULL` или в подзапросе стоит `IS NOT NULL`.

```sql title="sets-traps-views.sql"
-- JOIN без DISTINCT: читатель по разу на каждую книгу на руках
CREATE VIEW bad_t1_dup AS
SELECT r.id FROM readers r
JOIN loans l ON l.reader_id = r.id
WHERE l.returned_at IS NULL;
-- условие по правой таблице в WHERE вместо ON
CREATE VIEW bad_t1_where AS
SELECT r.id FROM readers r
LEFT JOIN loans l ON l.reader_id = r.id
WHERE l.returned_at IS NULL;
-- INNER JOIN с авторами: книга без автора выпадает из группы
CREATE VIEW bad_t2_inner AS
SELECT l.reader_id AS id
FROM loans l
JOIN book_authors ba ON ba.book_id = l.book_id
JOIN authors a ON a.id = ba.author_id
WHERE l.returned_at IS NULL
GROUP BY l.reader_id
HAVING bool_and(a.name = 'Толкин');
-- count(*) вместо count(DISTINCT): повторные выдачи считаются разными книгами
CREATE VIEW bad_t3_count AS
SELECT l.reader_id AS id
FROM loans l
JOIN tolkien_books tb ON tb.book_id = l.book_id
GROUP BY l.reader_id
HAVING count(*) = (SELECT count(*) FROM tolkien_books);

CREATE VIEW bad_t4_count AS
SELECT l.reader_id, ba.author_id
FROM loans l
JOIN book_authors ba ON ba.book_id = l.book_id
GROUP BY l.reader_id, ba.author_id
HAVING count(*) >= 2;
```

```sql title="sets-traps-check.sql"
SELECT g.bad, rows_of(g.bad) AS bad_rows, rows_of(g.good) AS good_rows,
       set_diff(g.bad, g.good) AS diff
FROM (VALUES
    ('bad_t1_dup',    't1_has_exists'),
    ('bad_t1_where',  't1_none_notexists'),
    ('bad_t2_inner',  't2_bool_and'),
    ('bad_t3_count',  't3_count'),
    ('bad_t4_count',  't4_having')) AS g(bad, good);
```

```text title="Вывод"
     bad      | bad_rows | good_rows | diff 
--------------+----------+-----------+------
 bad_t1_dup   |        6 |         4 |    2
 bad_t1_where |        7 |         3 |    8
 bad_t2_inner |        1 |         1 |    0
 bad_t3_count |        1 |         1 |    0
 bad_t4_count |        6 |         5 |    1
(5 rows)
```

`bad_t1_dup` даёт лишние строки (дубли). `bad_t1_where` возвращает Анну и читателей с открытыми выдачами (7 строк с повторами), а Бориса и Жанну пропускает. `bad_t2_inner` и `bad_t3_count` на `small` совпали с верными, пока в данных нет нужного края: Веры с книгой без автора и читателя с повторной выдачей Толкина. Край добавляется в транзакции и откатывается:

```sql title="sets-edge.sql"
BEGIN;
-- Вера взяла книгу без автора, Жанна ещё раз взяла Властелина колец
INSERT INTO loans (reader_id, book_id, issued_at, due_at)
VALUES (3, 8, '2026-11-18', '2026-12-02');
INSERT INTO loans (reader_id, book_id, issued_at, due_at, returned_at)
VALUES (7, 1, '2026-04-01', '2026-04-15', '2026-04-10');

SELECT 'задача 2' AS task, string_agg(id::text, ',' ORDER BY id) AS bad_inner_ids,
       coalesce((SELECT string_agg(id::text, ',' ORDER BY id) FROM t2_bool_and), 'нет') AS right_ids
FROM bad_t2_inner
UNION ALL
SELECT 'задача 3', string_agg(id::text, ',' ORDER BY id),
       (SELECT string_agg(id::text, ',' ORDER BY id) FROM t3_count)
FROM bad_t3_count;
ROLLBACK;
```

```text title="Вывод"
   task   | bad_inner_ids | right_ids 
----------+---------------+-----------
 задача 2 | 3             | нет
 задача 3 | 5,7           | 5
(2 rows)
```

После вставки верное решение задачи 2 не находит никого (у Веры теперь на руках и сказки), а `bad_t2_inner` оставляет Веру: книга без автора для него просто не существует. Верное решение задачи 3 по-прежнему видит одну Дарью, а `count(*)` засчитал Жанне три выдачи Толкина за три книги.

Читатель без выдач (Анна) пропадает из обычного `JOIN` с `loans`: пары нет, строки нет. Нужен `LEFT JOIN`, а после него считают `count(l.id)`, а не `count(*)`: пустая строка пары тоже строка. Дубли после `JOIN` ловит `EXCEPT ALL` в `set_diff`: обычный `EXCEPT` их схлопнул бы.

**Первым назвать:** `NOT EXISTS`, не `NOT IN`; условие правой таблицы — в `ON`; решения сверять `EXCEPT ALL` в обе стороны.

## Сверка решений

Сначала число строк ответа, потом `set_diff` по каждой паре. На `big` сверка идёт после `CREATE INDEX`, который выполняет блок `sets-bench-index.sql` из раздела «Замер на big»: без этого индекса коррелированный `NOT EXISTS` задачи 3 не дождаться.

```sql title="sets-check.sql"
SELECT p.a, p.b, rows_of(p.a) AS rows_a, rows_of(p.b) AS rows_b, set_diff(p.a, p.b) AS diff
FROM (VALUES
    ('t1_has_exists',     't1_has_join'),
    ('t1_has_exists',     't1_has_in'),
    ('t1_none_notexists', 't1_none_leftjoin'),
    ('t1_none_notexists', 't1_none_notin'),
    ('t2_not_exists',     't2_bool_and'),
    ('t2_not_exists',     't2_except'),
    ('t3_count',          't3_not_exists'),
    ('t3_count',          't3_except'),
    ('t4_having',         't4_minmax'),
    ('t4_having',         't4_selfjoin')) AS p(a, b);
```

На `small`:

На `small` — 4 и 3, 1, 1 и 5. Во всех десяти парах `diff` равен 0 и на `small`, и на `big`: решения дают одни и те же мультимножества.

Медианы: сравниваем решения внутри одной таблицы. Разница в пределах 20 % считается шумом.
- **Задача 1.** Без индекса 5,29–5,52 мс (есть книги) и 4,67–4,97 мс (нет), с индексом 5,47–5,58 и 4,78–5,09 мс. Внутри каждой группы разброс не больше 7 %: разницы нет на 1 024 052 строках `loans`.
- **Задача 2.** `NOT EXISTS` 10,41 мс против `bool_and` 5,55 мс (на 88 % медленнее); с индексом 10,78 против 5,81 мс (на 86 %). `EXCEPT` 6,57 и 6,78 мс — от `bool_and` в пределах 20 % (18 % и 17 %), разницы нет.
- **Задача 3.** `HAVING count(DISTINCT …)` 28,15 мс, `EXCEPT` по парам 660,95 мс (в 23 раза медленнее). С индексом: 29,05 мс, коррелированный `NOT EXISTS` 68,93 мс (в 2,4 раза) и `EXCEPT` 648,65 мс.
- **Задача 4.** `count(DISTINCT)` 362,75 мс и `min <> max` 329,38 мс — разницы нет между ними на 1 024 052 строках (10 %); с индексом 435,50 и 450,61 мс (3 %). Но индекс замедлил оба решения: на 20 % и на 37 %. Самосоединение 183,06 мс быстрее вдвое, с индексом 173,82 мс — в 2,5 раза. План, снятый отдельно на `big` после `VACUUM ANALYZE` (на страницу не вынесен), показывает смену стратегии: без индекса `Hash Join` двух `Seq Scan`, с индексом `Nested Loop` с `Index Only Scan` по `ix_loans_reader_book` и `Memoize` над `Index Only Scan` по `book_authors_pkey`, и буферов читается в 53 раза больше: 421 061 против 7 970 (`shared hit`), хотя без индекса агрегация ещё уходит во временные файлы. Это согласуется с замедлением; других причин не проверяли.

Блок идёт с прогревом, чтобы первая строка таблицы не мерилась на холодном кэше. Отдельные повторы блока давали выбросы, поэтому сравниваются соотношения внутри таблицы, а не отдельные миллисекунды. Причины остальных разниц не разбираем: тема страницы — решения и их верность. Планы — на страницах [[EXPLAIN]] и «[[Запросы и индексы библиотеки]]».

## Что спросят дальше

- **А если у книги несколько авторов.** Задача 2 решается так же: Толкин — «среди авторов». Задача 4 считает пару читатель и автор отдельно по каждому автору, соавтор попадёт в свою пару.
- **Как сверить два решения.** `EXCEPT ALL` в обе стороны и число строк ответа.
