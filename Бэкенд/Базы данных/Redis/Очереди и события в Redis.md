Примеры снимались на Redis 8 (сервер 8.10.3) и redis-py 8.1.0, соединение `r = redis.Redis(port=6390, decode_responses=True)`.

## Суть

Redis умеет три разных механизма доставки, и они дают разные гарантии. Pub/Sub (публикация и подписка) — это рассылка «отправил и забыл» (fire-and-forget): сообщение получает тот, кто подписан в этот момент, и нигде не хранится. List (список) с командами `LPUSH` и `BRPOP` — простая очередь, но взятое из списка сообщение исчезает: если потребитель упал, не доделав, задача потеряна. Stream (поток) хранит сообщения, раздаёт их группам потребителей и ждёт подтверждения `XACK`; зависшие сообщения можно найти и передать другому потребителю. Если нужен полноценный брокер с маршрутизацией и сложными гарантиями, смотрите [[RabbitMQ]] и [[Kafka]]; Redis хорош, когда очередь простая и уже есть инфраструктура.

## Рецепт: pub/sub теряет сообщения

**Задача.** Разослать событие «обновился каталог» всем экземплярам сервиса.

`PUBLISH` возвращает число получателей, которым сообщение доставлено сейчас. Опубликуем сообщение, пока подписчика нет, потом подпишемся и опубликуем второе:

```python
print("PUBLISH, получателей:", await r.publish("news", "раз"))
ps = r.pubsub(); await ps.subscribe("news")
print("после подписки:", await ps.get_message(timeout=0.2))
print("PUBLISH, получателей:", await r.publish("news", "два"))
print("получено:", (await ps.get_message(timeout=0.5))["data"])
```

```text title="Вывод"
PUBLISH, получателей: 0
после подписки: {'type': 'subscribe', 'pattern': None, 'channel': 'news', 'data': 1}
PUBLISH, получателей: 1
получено: два
```

Сообщение «раз» ушло в никуда: получателей 0, и после подписки его уже не получить. Доставилось только «два». То же будет, если подписчик на секунду потерял соединение. Pub/Sub годится для сигналов, где потеря допустима (сбросить локальный кэш, обновить табло), и не годится для заказов и платежей.

**Грабли.** Подписчик, который читает медленнее, чем публикуют, копит сообщения в буфере соединения на стороне сервера, и по превышению лимита (`client-output-buffer-limit pubsub`) Redis его отключает: сообщения теряются без ошибки у издателя. Эта настройка запуском не проверялась.

## Рецепт: очередь на списке, BRPOP и BLMOVE

**Задача.** Раздать задачи воркерам так, чтобы упавший воркер не уносил задачу с собой.

Простейшая очередь: производитель делает `LPUSH`, воркер забирает командой `BRPOP` (блокирующее чтение: ждёт элемент, если список пуст). Беда в том, что `BRPOP` удаляет элемент, и если воркер упал, не доделав, задача исчезла:

```python
j = await r.brpop("jobs", 1)
print("взял:", j, "-> воркер упал, в jobs:", await r.lrange("jobs", 0, -1))
```

```text title="Вывод"
взял: ('jobs', 'job1') -> воркер упал, в jobs: ['job3', 'job2']
```

Задача `job1` нигде не осталась. Надёжный вариант — `BLMOVE`: он атомарно перекладывает элемент из списка задач в список «в обработке» и возвращает его воркеру. Закончив, воркер удаляет элемент из «в обработке» командой `LREM`; если воркер упал, элемент остаётся там, и его можно вернуть.

```python
for i in range(1, 4):
    await r.lpush("jobs", f"job{i}")
j = await r.blmove("jobs", "jobs:processing", 1, "RIGHT", "LEFT")
print("взял:", j)
print("jobs:", await r.lrange("jobs", 0, -1), "processing:", await r.lrange("jobs:processing", 0, -1))
# воркер упал, не вызвав LREM; сторож возвращает зависшую задачу
print("recover:", await r.lmove("jobs:processing", "jobs", "RIGHT", "RIGHT"))
print("jobs:", await r.lrange("jobs", 0, -1), "processing:", await r.lrange("jobs:processing", 0, -1))
```

```text title="Вывод"
взял: job1
jobs: ['job3', 'job2'] processing: ['job1']
recover: job1
jobs: ['job3', 'job2', 'job1'] processing: []
```

Задача `job1` во время обработки лежала в `jobs:processing` и после «падения» вернулась в очередь. Хуже, что у списка нет понятия времени и владельца: непонятно, какая задача в `processing` зависла, а какая просто выполняется. Придётся хранить рядом время взятия и самому писать сторожа.

**Грабли.** Возвращённая задача будет выполнена повторно, если воркер всё-таки доделал её, но упал перед `LREM`. Доставка здесь «хотя бы один раз» (at least once), поэтому обработчик должен быть идемпотентным ([[Идемпотентность в Redis]]).

## Рецепт: Streams и consumer groups

**Задача.** Те же задачи, но с учётом, кто что взял, и подтверждением обработки.

В Stream каждое сообщение получает идентификатор вида `время-номер`, добавляется командой `XADD` и хранится, пока его не обрежут. Consumer group (группа потребителей) — набор читателей, между которыми Redis раздаёт сообщения: каждое сообщение достаётся одному из них. Группа помнит, что выдано и не подтверждено, пока читатель не вызовет `XACK`.

```python
for i in range(1, 5):
    await r.xadd("orders", {"id": i, "sum": i * 100})
await r.xgroup_create("orders", "billing", id="0")
got = await r.xreadgroup("billing", "w1", {"orders": ">"}, count=3, block=500)
ids = [m[0] for m in got[0][1]]
print("w1 прочитал:", [(m[0], m[1]["id"]) for m in got[0][1]])
print("XACK первого:", await r.xack("orders", "billing", ids[0]))
print("XPENDING:", await r.xpending("orders", "billing"))
```

```text title="Вывод"
w1 прочитал: [('1795113557834-0', '1'), ('1795113557835-0', '2'), ('1795113557835-1', '3')]
XACK первого: 1
XPENDING: {'pending': 2, 'min': '1795113557835-0', 'max': '1795113557835-1', 'consumers': [{'name': 'w1', 'pending': 2}]}
```

Символ `>` в `XREADGROUP` значит «только новые, ещё никому не выданные». Воркер `w1` прочитал три сообщения и подтвердил первое; два остались в списке ожидающих (pending entries list, PEL) с пометкой `w1`. Идентификаторы в выводе зависят от часов сервера, у вас будут другие.

**Грабли.** Если не вызывать `XACK`, список ожидающих растёт бесконечно. `XREADGROUP` с идентификатором `0` вместо `>` вернёт собственные неподтверждённые сообщения воркера, это нужно делать при его старте, чтобы доделать то, что не успел до перезапуска.

## Рецепт: зависшие сообщения, XPENDING и XAUTOCLAIM

**Задача.** Воркер `w1` умер, не подтвердив два сообщения. Передать их живому воркеру.

`XPENDING` показывает ожидающие сообщения вместе с владельцем и числом доставок. `XAUTOCLAIM` забирает сообщения, которые простаивают без подтверждения дольше заданного времени, и передаёт новому владельцу.

```python
await asyncio.sleep(0.3)
print("XPENDING_RANGE:", [(p["message_id"], p["consumer"], p["times_delivered"])
                          for p in await r.xpending_range("orders", "billing", "-", "+", 10)])
res = await r.xautoclaim("orders", "billing", "w2", min_idle_time=200, start_id="0", count=10)
print("w2 XAUTOCLAIM забрал:", [(m[0], m[1]["id"]) for m in res[1]])
print("times_delivered:", [(p["message_id"], p["consumer"], p["times_delivered"])
                           for p in await r.xpending_range("orders", "billing", "-", "+", 10)])
for m in res[1]:
    await r.xack("orders", "billing", m[0])
```

```text title="Вывод"
XPENDING_RANGE: [('1795113557835-0', 'w1', 1), ('1795113557835-1', 'w1', 1)]
w2 XAUTOCLAIM забрал: [('1795113557835-0', '2'), ('1795113557835-1', '3')]
times_delivered: [('1795113557835-0', 'w2', 2), ('1795113557835-1', 'w2', 2)]
```

Владелец сменился с `w1` на `w2`, а счётчик доставок вырос до 2. Этот счётчик нужен для «ядовитых» сообщений (poison message): если сообщение доставлено, скажем, пять раз и каждый раз падает, его нужно переложить в отдельный поток-кладбище (dead letter, DLQ), а не крутить бесконечно. Само Redis этого не делает, логику пишет приложение. После подтверждения остаётся только то, что `w2` ещё не прочитал:

```python
new = await r.xreadgroup("billing", "w2", {"orders": ">"}, count=10, block=200)
print("новые для w2:", [(m[0], m[1]["id"]) for m in new[0][1]])
print("XPENDING после всего:", (await r.xpending("orders", "billing"))["pending"])
print("XINFO GROUPS:", [(g["name"], g["pending"], g["lag"]) for g in await r.xinfo_groups("orders")])
```

```text title="Вывод"
новые для w2: [('1795113557835-2', '4')]
XPENDING после всего: 1
XINFO GROUPS: [('billing', 1, 0)]
```

Прочитанное четвёртое сообщение ещё не подтверждено, поэтому в ожидающих осталась одна запись, а `lag` (сколько сообщений группа ещё не получила) равен нулю.

**Грабли.** `min_idle_time` нужно выбирать больше реального времени обработки, иначе `XAUTOCLAIM` отнимет сообщение у живого воркера, и оно обработается дважды. Как и в списке, доставка «хотя бы один раз»: идемпотентность обязательна.

## Рецепт: ограничение длины потока

**Задача.** Поток не должен расти бесконечно.

`XADD` принимает `MAXLEN`: при `~` (приблизительно) Redis обрезает пачками, что дешевле точной обрезки.

```python
for i in range(1000):
    await r.xadd("log", {"i": i}, maxlen=100, approximate=True)
print("XLEN log ~100:", await r.xlen("log"))
```

```text title="Вывод"
XLEN log ~100: 100
```

Длина осталась около 100 (в этом запуске ровно 100; из-за приближённой обрезки она может немного превышать лимит). Обрезка по длине стирает и ещё не обработанные сообщения, если потребители отстают, поэтому длину задают с запасом и следят за `lag`.

## Рецепт: отложенные задачи на sorted set

**Задача.** Отправить письмо через 5 минут.

В sorted set оценкой служит время выполнения; воркер периодически забирает всё, у чего время уже наступило (`ZRANGEBYSCORE 0 сейчас`).

```python
now = time.time()
await r.zadd("delayed", {"mail:1": now + 0.3, "mail:2": now + 5})
print("сразу:", await r.zrangebyscore("delayed", 0, time.time()))
await asyncio.sleep(0.4)
print("через 0.4 с:", await r.zrangebyscore("delayed", 0, time.time()))
```

```text title="Вывод"
сразу: []
через 0.4 с: ['mail:1']
```

Чтобы два воркера не взяли одну задачу, «забрать и удалить» нужно делать атомарно, Lua-скриптом или командой `ZREM` с проверкой её результата: удаление вернёт 1 только одному из них ([[Атомарность в Redis]]).

## Бизнес-кейс

- **Рассылка писем после заказа.** Redis-очередь допустима, если письмо можно потерять или отправить дважды без ущерба; для платежных событий нужен брокер с долговечностью и подтверждением ([[Kafka]], [[RabbitMQ]]) или outbox в базе.
- **Очередь фоновых задач [[Celery]] на Redis.** Брокер хранит задачи в списках; чтобы Redis при нехватке памяти не вытеснял очередь, для него задают `maxmemory-policy noeviction` ([[Персистентность и память Redis#Рецепт: политики вытеснения]]).

## Что спросят дальше

- Pub/Sub или Streams? Pub/Sub не хранит сообщения, и не подписанный в этот момент получатель их не увидит. Streams хранят, дают группы потребителей и подтверждения, а зависшие у упавшего потребителя сообщения передают другому командой `XAUTOCLAIM`.
- Чем Streams отличаются от Kafka? Нет разбиения на партиции с собственным порядком и масштабированием по ним, всё в памяти одного узла (либо шарда), ограничения по объёму и долговечности жёстче.
- Какая гарантия доставки у списка с `BLMOVE` и у Streams? «Хотя бы один раз»: возможны повторы, значит, обработчик идемпотентен.
