## Суть

Кэш хранит копию данных, которую дёшево читать, и поэтому почти всегда немного отстаёт от источника. Вся работа с кэшем сводится к вопросу, как часто и насколько допустимо показывать устаревшее, и к защите базы в те моменты, когда кэш пуст. Три классические беды — cache stampede («давка»: один популярный ключ истёк, и сотни запросов разом идут в базу), cache penetration («пробивание»: запросы к несуществующим ключам всегда доходят до базы) и cache avalanche («лавина»: много ключей истекают одновременно или падает сам Redis) — имеют разные лекарства, и ниже каждое проверено.

Redis подходит для кэша как хранилище в памяти (in-memory) с TTL (time to live, время жизни ключа: по истечении Redis удаляет ключ сам) и политиками вытеснения ([[Персистентность и память Redis#Рецепт: политики вытеснения]]).

## Рецепт: cache-aside

**Задача.** Читать карточку товара из кэша, а при промахе (cache miss) идти в базу и класть результат в кэш.

Cache-aside («кэш сбоку») — самый частый вариант: приложение само управляет кэшем, база о нём не знает. При чтении смотрим в кэш, при промахе читаем из базы и записываем результат с TTL.

```python
async def get_product(pid):
    key = f"product:{pid}"
    v = await r.get(key)
    if v is not None:
        return json.loads(v)
    row = await db_get(pid)                      # медленный запрос к базе
    await r.set(key, json.dumps(row), ex=60)     # TTL 60 секунд
    return row
```

Здесь и дальше `db_get` — заглушка с задержкой 0,2 с, которая считает обращения к «базе». Код корректен для одного запроса, но у него есть слабое место, которое видно сразу под нагрузкой (следующий рецепт).

**Грабли.** `None` как «в кэше пусто» нельзя путать с «в базе пусто»: без отдельной обработки несуществующий товар будет каждый раз ходить в базу (см. негативный кэш ниже). `ex=60` обязателен: ключ без TTL остаётся навсегда и при сбое инвалидации навсегда хранит неверное значение.

## Рецепт: запись и инвалидация

**Задача.** После обновления цены кэш не должен продолжать отдавать старую.

При записи сначала обновляем базу, затем удаляем ключ командой `DEL`, чтобы следующее чтение подтянуло свежее значение. Удаление выбирают, а не запись нового значения, потому что два параллельных обновления могли бы записать в кэш в обратном порядке, и кэш навсегда разошёлся бы с базой.

`DEL` тоже не идеален. Читатель, который промахнулся до записи и успел прочитать из базы старое значение, может положить его в кэш уже после `DEL`. Воспроизведём эту последовательность по шагам:

```python
await r.set("price:1", "100", ex=60)     # в кэше цена 100
stale = "100"                            # читатель A прочитал из базы старую цену и завис
await r.delete("price:1")                # писатель: в базе уже 120, ключ удалён
await r.set("price:1", stale, ex=60)     # читатель A дописывает устаревшее
print("DB=120, cache =", await r.get("price:1"))
```

```text title="Вывод"
DB=120, cache = 100
```

Кэш показывает 100, хотя в базе 120, и так будет до истечения TTL. Именно поэтому TTL нужен всегда: он ограничивает время, в течение которого неверное значение живёт. Для критичных данных дополнительно делают повторный `DEL` с небольшой задержкой (отложенное двойное удаление), который стирает запоздавшую запись читателя; полностью гонку это не закрывает (отложенное удаление запуском не проверялось, здесь показана только сама гонка).

**Грабли.** Если приложение упало между обновлением базы и `DEL`, кэш остаётся старым до TTL. Когда этого мало, инвалидацию отправляют событием через outbox (таблицу в базе, из которой отдельный процесс надёжно доставляет событие), а не из кода обработчика.

## Рецепт: cache stampede и single-flight

**Задача.** Популярный ключ истёк, и 100 запросов одновременно промахнулись. База должна получить один запрос, а не сто.

Сначала вариант из рецепта cache-aside, запущенный сотней задач на холодном ключе:

```python
await asyncio.gather(*[get_product(1) for _ in range(100)])
print("naive db calls:", db_calls)
```

Теперь вариант с single-flight («один полёт»): значение пересчитывает только тот запрос, который сумел взять короткую блокировку `SET ... NX PX`, остальные ждут и читают готовое из кэша. Блокировка снимается Lua-скриптом по токену ([[Распределённая блокировка в Redis#Рецепт: замок с токеном]]), а после захвата ключ проверяется ещё раз, потому что значение могли записать, пока мы ждали.

```python
async def get_single_flight(pid):
    key = f"product:{pid}"; lock = f"lock:{key}"
    for _ in range(50):
        v = await r.get(key)
        if v is not None:
            return json.loads(v)
        token = uuid.uuid4().hex
        if await r.set(lock, token, nx=True, px=5000):
            try:
                v = await r.get(key)             # двойная проверка
                if v is not None:
                    return json.loads(v)
                row = await db_get(pid)
                await r.set(key, json.dumps(row), ex=60)
                return row
            finally:
                await r.eval(RELEASE, 1, lock, token)
        await asyncio.sleep(0.05)                # не захватили, ждём и читаем кэш снова
    raise TimeoutError

await asyncio.gather(*[get_single_flight(1) for _ in range(100)])   # на очищенной базе, счётчик обнулён
print("single-flight db calls:", db_calls)
```

```text title="Вывод"
naive db calls: 100
single-flight db calls: 1
```

Сто запросов превратились в один. Другие меры против давки: случайный разброс TTL (см. ниже), фоновое обновление до истечения (значение живёт в кэше дольше «логического» срока, и один запрос обновляет его заранее), отдача слегка устаревшего значения, пока идёт пересчёт (stale-while-revalidate). Та же идея, что и с [[Повторные попытки при падении базы#Откуда берётся снежный ком|лавиной повторных попыток]]: нельзя дать всем одновременно ломиться в слабое место.

**Грабли.** TTL блокировки должен быть больше времени пересчёта, иначе замок истечёт и пересчёт пойдёт во втором запросе. Ожидающие запросы нужно ограничить по времени (здесь 50 попыток по 50 мс), иначе упавший владелец подвесит всех до конца TTL замка.

## Рецепт: негативный кэш и cache penetration

**Задача.** Бот перебирает несуществующие идентификаторы товаров. Такие запросы не оседают в кэше, потому что значения нет и в базе, и каждый доходит до базы.

Лечение — кэшировать и пустой ответ, но на короткое время, чтобы появившийся позже товар не прятался за ним дольше нескольких секунд.

```python
async def get_negative(pid):
    key = f"product:{pid}"
    v = await r.get(key)
    if v is not None:
        return json.loads(v)                   # строка "null" тоже попадание
    row = await db_get(pid)
    await r.set(key, json.dumps(row), ex=60 if row else 30)   # пустой ответ живёт меньше
    return row

for _ in range(50):
    await get_negative(999)
print("with negative cache db calls:", db_calls, "| ttl:", await r.ttl("product:999"), "| value:", await r.get("product:999"))
```

```text title="Вывод"
with negative cache db calls: 1 | ttl: 30 | value: null
```

Пятьдесят запросов к несуществующему идентификатору дали одно обращение к базе. Для перебора миллионов разных идентификаторов негативный кэш сам превратится в миллионы ключей, поэтому перед базой ставят фильтр Блума (Bloom filter) — компактную структуру, которая отвечает «такого ключа точно нет» или «возможно, есть». Запуском фильтр здесь не проверялся.

**Грабли.** Ключи, созданные по пользовательскому вводу, нужно ограничивать по длине и формату до обращения к кэшу, иначе атакующий забьёт память мусорными ключами.

## Рецепт: TTL с джиттером и cache avalanche

**Задача.** Тысячи ключей загрузили при старте или прогреве с одинаковым TTL, значит, истекут они в одну секунду, и база получит всю нагрузку разом.

Джиттер (jitter) — случайная добавка к времени жизни, чтобы ключи истекали в разное время:

```python
ttls = [int(3600 * random.uniform(0.9, 1.1)) for _ in range(5)]
print("ttl seconds:", ttls)
```

```text title="Вывод"
ttl seconds: [3460, 3910, 3441, 3673, 3431]
```

Разброс в плюс-минус 10% размазывает истечение по окну в 12 минут вместо одной секунды. От падения самого Redis джиттер не спасает; здесь нужен circuit breaker («предохранитель») на стороне приложения: после серии ошибок он на время прекращает слать запросы, давая базе восстановиться, а часть ответов отдаётся из резервного локального кэша.

**Грабли.** Джиттер должен считаться при каждой записи, а не один раз на старте процесса, иначе все ключи одной партии снова получат одинаковый срок.

## Write-through и write-behind

Write-through («сквозная запись») пишет в кэш и в базу синхронно, одной операцией: чтение всегда видит свежее, но запись медленнее, а при ошибке одной из двух записей нужен откат. Write-behind («отложенная запись») сначала пишет в кэш, а в базу данные попадают позже и асинхронно. Скорость выше, но если Redis упадёт до сброса в базу, данные потеряны, поэтому для денег и заказов этот вариант не годится.

## Бизнес-кейс

- **«Кэшируйте баланс для скорости».** Показать баланс из кэша с задержкой 5 секунд нормально. Решать по кэшу, хватит ли денег на списание, нельзя. Вопрос к продукту: где устаревшие данные допустимы и на сколько?
- **Распродажа в 12:00.** Карточка акционного товара истекает ровно в начале акции, и тысячи покупателей разом промахиваются. Прогрейте кэш заранее и поставьте single-flight, а не надейтесь, что база выдержит.

## Что спросят дальше

- Почему при записи `DEL`, а не `SET`? Два параллельных обновления могут записать в кэш в обратном порядке; `DEL` проще и безопаснее, а TTL ограничивает ущерб от гонок.
- Чем stampede отличается от avalanche? Stampede — один ключ и много запросов, avalanche — много ключей (или весь кэш) и обвал нагрузки на базу.
- Как не кэшировать ошибки? Ответ об ошибке в кэш не кладут, а пустой «не найдено» кладут на короткое время.
- Горячий ключ и большой ключ — отдельная тема: [[Репликация и кластер Redis#Горячие ключи и разбиение]] и [[Персистентность и память Redis#Большие ключи и UNLINK]].
