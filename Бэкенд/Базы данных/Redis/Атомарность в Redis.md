## Суть

Redis выполняет команды в одном потоке, одну за другой, поэтому каждая отдельная команда атомарна: чужая команда не вклинится в её середину. Но настоящие задачи редко умещаются в одну команду, обычно это «прочитать, решить, записать». Если разнести эти шаги по отдельным вызовам, между ними успеют вклиниться другие клиенты, и получится классическая гонка (race condition). Redis даёт три инструмента: транзакцию `MULTI`/`EXEC` (пачка команд подряд), оптимистичную блокировку `WATCH` (отмена, если данные изменились) и скрипты на Lua (всё решение выполняется на сервере). Pipeline от них отличается: он ускоряет передачу, но атомарности не даёт.

## Рецепт: счётчик, GET и SET против INCR

**Задача.** Сто параллельных клиентов увеличивают счётчик на единицу.

Плохой вариант читает значение, прибавляет в приложении и записывает обратно. Правильный — `INCR`, одна атомарная команда.

```python
async def inc_bad():
    v = int(await r.get("c1") or 0)
    await r.set("c1", v + 1)

await asyncio.gather(*[inc_bad() for _ in range(100)])
print("GET+SET:", await r.get("c1"))
await asyncio.gather(*[r.incr("c2") for _ in range(100)])
print("INCR:", await r.get("c2"))
```

```text title="Вывод"
GET+SET: 6
INCR: 100
```

Из ста увеличений в варианте `GET`+`SET` уцелело шесть: большинство клиентов прочитали одно и то же старое значение и записали его же плюс один. `INCR` дал ровно 100.

**Грабли.** Тот же дефект возникает с любым чтением «значение, решение, запись» (баланс, остаток, лимит), и там `INCR` уже не поможет: нужен Lua-скрипт или `WATCH`.

## Рецепт: MULTI и EXEC без отката

**Задача.** Выполнить несколько команд подряд так, чтобы чужие команды не перемешались с ними.

`MULTI` начинает очередь, команды ставятся в неё (ответ `QUEUED`), `EXEC` выполняет всю очередь. Это не транзакция в смысле SQL: отката нет. Если одна команда упала при выполнении (например, команда списка по строковому ключу), остальные всё равно выполняются. Подадим в `redis-cli` по порядку `MULTI`, `SET a 1`, `LPUSH a x`, `SET b 2`, `EXEC`:

```text title="Вывод"
OK
QUEUED
QUEUED
QUEUED
OK
WRONGTYPE Operation against a key holding the wrong kind of value
OK
```

Первые четыре строки — ответы на `MULTI` и три поставленные в очередь команды, дальше результаты `EXEC`: первая команда применилась, вторая вернула ошибку, третья снова применилась, и ключи `a` и `b` записаны. А вот ошибка при постановке команды в очередь (здесь неизвестная команда `SETT`) отменяет весь `EXEC`. Подаём `MULTI`, `SET a 1`, `SETT a`, `EXEC`, `GET a`:

```text title="Вывод"
OK
QUEUED
ERR unknown command 'SETT', with args beginning with: 'a' 

EXECABORT Transaction discarded because of previous errors.

```

Не выполнилось ничего: последний `GET a` вернул пустой ответ (`nil`), ключ не создан. Обратите внимание, что в клиенте redis-py `MULTI` и `EXEC` отправляются в одном соединении через `pipeline(transaction=True)`; обычные вызовы `r.execute_command("MULTI")` из пула могут уйти по разным соединениям и ничего не дадут, поэтому демонстрация сделана в `redis-cli`.

```python
p = r.pipeline(transaction=True)
p.set("a", 1); p.lpush("s", "x"); p.set("b", 2)
print(await p.execute(raise_on_error=False))
```

```text title="Вывод"
[True, server:ResponseError, True]
```

**Грабли.** Внутри `MULTI` нельзя прочитать значение и по нему решить, что писать дальше: ответы приходят только после `EXEC`. Для логики «прочитать, решить, записать» нужны `WATCH` или Lua.

## Рецепт: WATCH и оптимистичная блокировка

**Задача.** Списать часть баланса, если за время расчёта его никто не поменял.

`WATCH` — оптимистичная блокировка: `EXEC` отменяется, если за наблюдаемым ключом после `WATCH` кто-то записал. Тогда транзакцию повторяют с чтения.

```python
await r.set("bal", 100)
async with r.pipeline() as p:
    await p.watch("bal")
    v = int(await p.get("bal"))        # 100
    await r.set("bal", 50)             # чужая запись между чтением и EXEC
    p.multi(); p.set("bal", v - 30)
    try:
        await p.execute()
    except WatchError:
        print("WatchError, bal =", await r.get("bal"))
```

```text title="Вывод"
WatchError, bal = 50
```

Транзакция отменена, значение 50 от чужой записи сохранено. Приложение должно обернуть это в цикл повтора. При высокой конкуренции за один ключ повторы множатся; тогда Lua надёжнее.

**Грабли.** `WATCH` следит за ключами, а не за логикой: если решение зависит от нескольких ключей, наблюдать нужно все. В кластере все они должны лежать в одном слоте ([[Репликация и кластер Redis#Hash tags]]).

## Рецепт: Lua-скрипт и EVALSHA

**Задача.** Продать товар, только если остаток положительный. Пять штук, двадцать покупателей.

Сначала вариант без скрипта: прочитать остаток, проверить в приложении, записать уменьшенное значение.

```python
async def naive_buy():
    s = int(await r.get("stock"))
    if s > 0:
        await asyncio.sleep(0)            # сетевой обмен, в который вклиниваются другие
        await r.set("stock", s - 1)
        return 1
    return 0

res = await asyncio.gather(*[naive_buy() for _ in range(20)])
print("без Lua продано:", sum(res), "остаток:", await r.get("stock"))
```

Теперь Lua-скрипт: Redis выполнит его целиком, не пуская между командами чужие, поэтому «прочитать, проверить, уменьшить» атомарно.

```python
BUY = """local s = tonumber(redis.call('GET', KEYS[1]))
if s and s > 0 then redis.call('DECR', KEYS[1]); return 1 end
return 0"""
buy = r.register_script(BUY)
res = await asyncio.gather(*[buy(keys=["stock"]) for _ in range(20)])
print("с Lua продано:", sum(res), "остаток:", await r.get("stock"))
```

```text title="Вывод"
без Lua продано: 20 остаток: 4
с Lua продано: 5 остаток: 0
```

Без скрипта продано 20 штук при пяти на складе, а остаток показывает 4: почти все покупатели прочитали пятёрку и записали четвёрку. Со скриптом продано ровно пять.

`register_script` в redis-py сам вызывает `EVALSHA` по хешу текста скрипта и при ответе `NOSCRIPT` загружает его заново. `EVALSHA` вызывает скрипт по SHA1-хешу вместо отправки текста при каждом вызове, что экономит трафик. Но кеш скриптов на сервере живёт в памяти и сбрасывается при перезапуске и по `SCRIPT FLUSH`:

```python
sha = await r.script_load("return redis.call('INCR', KEYS[1])")
print("sha:", sha, "->", await r.evalsha(sha, 1, "k"))
await r.script_flush()
try:
    await r.evalsha(sha, 1, "k")
except NoScriptError as e:
    print("ошибка:", e)
```

```text title="Вывод"
sha: 61636018f4e6b5817b89791bbed242f93fa089e3 -> 1
ошибка: No matching script. Please use EVAL.
```

Поэтому ручной `EVALSHA` нужно оборачивать в обработку `NoScriptError` с повторной загрузкой, как делает `register_script`.

**Грабли.** Все ключи скрипт обязан получать через `KEYS`, а не строить внутри: иначе он не работает в кластере (там все ключи скрипта должны лежать в одном слоте). Скрипт блокирует сервер на время работы, поэтому цикл по миллиону элементов внутри скрипта недопустим (см. ниже).

## Рецепт: Redis Functions

Functions — развитие скриптов (с Redis 7.0): код хранится на сервере постоянно, как библиотека, переживает перезапуск вместе с данными и вызывается по имени командой `FCALL`, а не по хешу. Это снимает проблему `NOSCRIPT`, но библиотеки нужно выкатывать при деплое.

```python
lib = """#!lua name=mylib
redis.register_function('buy', function(keys, args)
  local s = tonumber(redis.call('GET', keys[1]))
  if s and s >= tonumber(args[1]) then return redis.call('DECRBY', keys[1], args[1]) end
  return -1
end)"""
print("FUNCTION LOAD:", await r.function_load(lib, replace=True))
await r.set("st2", 5)
print("FCALL buy 3:", await r.fcall("buy", 1, "st2", 3), "| buy 3:", await r.fcall("buy", 1, "st2", 3))
```

```text title="Вывод"
FUNCTION LOAD: mylib
FCALL buy 3: 2 | buy 3: -1
```

Первая покупка трёх штук оставила 2, вторая вернула `-1`, потому что остатка не хватает.

## Рецепт: pipeline быстрый, но не атомарный

**Задача.** Отправить 1000 команд, не ожидая ответа на каждую.

Pipeline — отправка нескольких команд одним пакетом без ожидания ответа на каждую. Он экономит сетевые обмены (round trip, «туда и обратно»), но не группирует команды атомарно: между ними могут выполниться команды других клиентов. `MULTI`/`EXEC` в redis-py включается параметром `transaction=True`, который по умолчанию для `pipeline()` включён, поэтому для чистого ускорения указывают `transaction=False`.

```python
t = time.perf_counter()
for i in range(1000):
    await r.set(f"k{i}", i)
one_by_one = time.perf_counter() - t

t = time.perf_counter()
p = r.pipeline(transaction=False)
for i in range(1000):
    p.set(f"k{i}", i)
await p.execute()
piped = time.perf_counter() - t
```

```text title="Вывод"
1000 SET по одному: 176 мс; pipeline: 7 мс
```

Ускорение примерно в 25 раз на локальной сети; на удалённом сервере с задержкой в миллисекунды разница больше. Чем отличается pipeline от транзакции и скрипта, сведено в таблице.

| Средство | Меньше сетевых обменов | Атомарность | Можно ветвиться по прочитанному |
| --- | --- | --- | --- |
| Pipeline без `MULTI` | да | нет | нет |
| `MULTI`/`EXEC` | да | да, без отката | нет (только с `WATCH`) |
| Lua или Functions | да | да | да |

## Долгий скрипт блокирует всех

Раз сервер однопоточный, долгий скрипт останавливает всех остальных клиентов. Порог, после которого Redis начинает отвечать `BUSY`, задаётся `busy-reply-threshold` (по умолчанию 5 секунд). Для демонстрации понижаем его до 200 мс и запускаем скрипт-цикл на полторы секунды, а второй клиент в это время шлёт `PING`:

```text title="Вывод"
PING во время скрипта: BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.
```

Пока скрипт не закончился, Redis отвечает на всё, кроме `SCRIPT KILL` и `SHUTDOWN NOSAVE`, ошибкой `BUSY`. `SCRIPT KILL` прервёт скрипт, только если он ещё ничего не записал. Поэтому в скрипте нет места циклам по большим данным и сетевым ожиданиям.

## Бизнес-кейс

- **Продажа ограниченного остатка (билеты, промокоды).** Остаток в Redis с Lua-скриптом защищает от перепродажи под нагрузкой, но после перезапуска Redis счётчик может оказаться устаревшим: источник правды по заказам остаётся в базе, а Redis служит быстрым фильтром.
- **Счётчик просмотров.** `INCR` без скриптов: точная атомарность здесь бесплатна, а потеря последних секунд при сбое допустима.

## Что спросят дальше

- Чем `MULTI`/`EXEC` отличается от транзакции в SQL? Нет отката и нет изоляции в смысле чтения внутри транзакции; команды просто выполняются подряд без чужих между ними.
- Чем Lua лучше `WATCH`? Нет повторов при конкуренции, логика ветвится по прочитанным данным и выполняется за один обмен; цена — блокировка сервера на время скрипта.
- Что такое `EVALSHA` и `NOSCRIPT`? Вызов скрипта по хешу; если кеш сервера сброшен, нужно загрузить скрипт заново.
- Чем Functions отличаются от скриптов? Хранятся на сервере постоянно и вызываются по имени.
