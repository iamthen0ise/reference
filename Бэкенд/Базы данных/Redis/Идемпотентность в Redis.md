Примеры снимались на Redis 8 (сервер 8.10.3) и redis-py 8.1.0, соединение `r = redis.Redis(port=6390, decode_responses=True)`.

## Суть

Идемпотентность (idempotency) — свойство операции: если её выполнить дважды с теми же данными, результат будет как после одного раза. Клиенты повторяют запросы при таймаутах и двойных нажатиях, поэтому платёж должен распознавать повтор. Для этого клиент присылает ключ идемпотентности (idempotency key) — уникальный идентификатор своего запроса, а сервер по нему решает, выполнять ли работу. Redis удобен как быстрая первая линия: `SET NX` атомарен, значит, из десяти одновременных повторов выиграет ровно один.

## Рецепт: ключ идемпотентности через SET NX

**Задача.** Пять одновременных запросов с одним ключом (двойной клик по кнопке «Оплатить») должны списать деньги один раз.

Сначала вариант «посмотреть, нет ли ключа; если нет, выполнить и записать». Между проверкой и записью проходит время работы, и все пять запросов успевают проверить пустой ключ:

```python
async def pay_naive(idem):
    if await r.get(f"idem:{idem}") is not None:
        return "duplicate"
    res = await charge(idem)                  # 0,1 с работы
    await r.set(f"idem:{idem}", json.dumps(res), ex=86400)
    return res

await asyncio.gather(*[pay_naive("p1") for _ in range(5)])
print("без NX:", len(charges), "списаний")
```

Правильный вариант сначала занимает ключ командой `SET idem:<key> in-progress NX EX 86400` (86400 секунд — сутки). Выигравший выполняет работу и перезаписывает ключ готовым ответом, остальные видят либо «в процессе», либо готовый ответ.

```python
async def pay(idem):
    key = f"idem:{idem}"
    if await r.set(key, "in-progress", nx=True, ex=86400):
        try:
            res = await charge(idem)
        except Exception:
            await r.delete(key)               # сбой: разрешаем повторить
            raise
        await r.set(key, json.dumps(res), ex=86400, xx=True)
        return res
    cur = await r.get(key)
    return "409 in-progress" if cur == "in-progress" else json.loads(cur)

res = await asyncio.gather(*[pay("p2") for _ in range(5)])
print("с NX:", len(charges), "списание;", res)
print("повтор позже:", await pay("p2"))
print("TTL ключа:", await r.ttl("idem:p2"))
```

```text title="Вывод"
без NX: 5 списаний
с NX: 1 списание; [{'status': 'paid', 'n': 1}, '409 in-progress', '409 in-progress', '409 in-progress', '409 in-progress']
повтор позже: {'status': 'paid', 'n': 1}
TTL ключа: 86400
```

Без `NX` деньги списаны пять раз. С `NX` списание одно: четыре повтора получили `409 in-progress` (HTTP 409 Conflict, «конфликт»; клиент может подождать и повторить), а повтор позже увидел готовый ответ. Сразу записать ответ через `NX` нельзя: ответа ещё нет, поэтому два этапа. Опция `xx=True` во втором `SET` перезаписывает ключ, только если он ещё существует: если TTL истёк посреди работы, ответ не создаст «воскресший» ключ.

**Грабли.** Ключ идемпотентности должен включать и ключ клиента, и идентификатор пользователя (`idem:<user>:<key>`), иначе один пользователь займёт ключ другого. Ответ нужно хранить только для успешных результатов; повтор запроса с другим телом при том же ключе — ошибка клиента, её нужно ловить, сравнивая хеш тела.

## Рецепт: сбой в середине обработки

**Задача.** Процесс упал после занятия ключа и до записи ответа. Ключ «в процессе» живёт сутки, и повтор получает `409` весь день.

Есть два варианта лечения. Короткий TTL у состояния «в процессе» (скажем, 60 секунд, дольше самой долгой обработки), после которого ключ освободится сам и повтор сможет пройти; тогда состояние и итог пишутся с разным временем жизни. Либо проверка по источнику правды: повтор проверяет в базе, была ли операция, и если была, достраивает ответ. Первый вариант проще, но при медленной обработке (дольше TTL) пропустит дубль, поэтому и второй нужен в системах с деньгами.

## Redis против ограничения UNIQUE

Redis хранит ключи в памяти, и при аварийном переключении на реплику последние записи можно потерять ([[Репликация и кластер Redis#Репликация и потеря записей]]): тогда ключ идемпотентности исчезнет, и повтор пройдёт. Поэтому источник правды для денег — ограничение `UNIQUE` на идентификатор операции в базе данных: вторая вставка получит нарушение уникальности независимо от состояния Redis. Redis при этом остаётся быстрым фильтром, который в 99% случаев отсекает повтор раньше обращения к базе ([[Блокировки#Общие понятия (для любой БД)]]).

```text
INSERT INTO payments (idempotency_key, ...) VALUES (...)
ON CONFLICT (idempotency_key) DO NOTHING
```

Этот SQL запуском не проверялся, он дан для сравнения подходов.

## Бизнес-кейс

- **Двойное нажатие «Оплатить».** Ключ идемпотентности генерируется на клиенте при открытии формы и отправляется заголовком `Idempotency-Key`; сервер отвечает на повтор тем же ответом, что и на первый запрос.
- **Повторная доставка сообщения из очереди.** Потребитель очереди «хотя бы один раз» ([[Очереди и события в Redis]]) пишет идентификатор сообщения в Redis и в базу и пропускает уже обработанные.

## Что спросят дальше

- Почему не `GET` и `SET`? Между ними проходит время обработки, и параллельные повторы все видят пустой ключ; `SET NX` атомарен.
- Что вернуть на повтор, пока первый запрос выполняется? `409` либо ожидание с повтором; на повтор после завершения — тот же ответ, что на первый.
- Нужен ли Redis, если есть `UNIQUE` в базе? Redis снижает нагрузку на базу и быстрее, `UNIQUE` надёжнее; в системах с деньгами нужны оба.
