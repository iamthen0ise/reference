## Суть

Redis держит все данные в оперативной памяти, а на диск пишет, чтобы пережить перезапуск. Есть два механизма: RDB (Redis Database) — периодический снимок всех данных, и AOF (Append Only File) — журнал каждой команды записи. Они решают разную задачу и часто работают вместе. Второй вопрос — что делать, когда память кончилась: Redis либо отказывает в записи, либо вытесняет ключи по выбранной политике. От этого выбора зависит, подходит ли Redis как кэш (потеря допустима) или как хранилище очереди (потеря недопустима). Источником правды для денег и заказов Redis быть не должен: данные в памяти можно потерять при сбое.

## Рецепт: RDB и AOF

**Задача.** Понять, сколько данных потеряется при падении, и включить нужный режим.

RDB делает снимок через `fork` (создание дочернего процесса): дочерний процесс пишет файл, а родитель продолжает работать. При падении теряем всё, что записано после последнего снимка. При активной записи действует copy-on-write (страница памяти копируется при первой записи в неё): возможен пик памяти до ×2 и всплески задержек. AOF — журнал команд, по которому Redis восстанавливается при старте. При `appendfsync everysec` (сброс на диск раз в секунду) теряем до секунды записей, при `always` — почти ничего, но запись медленнее.

Настройки по умолчанию у только что запущенного контейнера:

```text
> CONFIG GET save
save
3600 1 300 100 60 10000
> CONFIG GET appendonly
appendonly
no
> CONFIG GET appendfsync
appendfsync
everysec
```

Снимок делается, если за 3600 секунд изменился хотя бы 1 ключ, за 300 секунд — 100 ключей, за 60 секунд — 10000. AOF выключен. Принудительный снимок и включение AOF на лету:

```text
> BGSAVE
Background saving started
> INFO persistence
rdb_changes_since_last_save:0
rdb_last_bgsave_status:ok
aof_enabled:0
> CONFIG SET appendonly yes
OK
> INFO persistence
aof_enabled:1
aof_rewrite_in_progress:0
```

(в этом выводе оставлены только значимые строки команды `INFO`, а приглашения `>` добавлены для читаемости). После включения в каталоге данных появился каталог `appendonlydir` с базовым снимком (`appendonly.aof.1.base.rdb`), файлом журнала (`appendonly.aof.1.incr.aof`) и манифестом. Журнал содержит команды в текстовом протоколе Redis (RESP), например, после `SET b 2` в хвосте журнала:

```text title="Вывод"
*3
$3
set
$1
b
$1
2
```

Для надёжности обычно включают оба механизма: AOF даёт малую потерю, RDB — компактные копии для резервного копирования и быстрый старт.

**Грабли.** Если на хосте мало свободной памяти, `fork` при большом наборе данных и записи под нагрузкой может привести к нехватке памяти и убийству процесса системой (OOM killer), поэтому оставляют запас на copy-on-write. Диск должен успевать: при медленном диске `appendfsync always` тормозит все записи. Эти последствия запуском не проверялись.

## Рецепт: политики вытеснения

**Задача.** Redis дошёл до лимита `maxmemory`. Выбрать, что должно произойти.

Политика вытеснения (eviction policy) определяет поведение. `allkeys-lru` удаляет любой ключ, которым давно не пользовались (LRU, least recently used); `allkeys-lfu` удаляет редко используемые (LFU, least frequently used). Эти две подходят для кэша. `volatile-lru` и родственные трогают только ключи с TTL. `noeviction` не удаляет ничего и отвечает ошибкой на запись: нужна для данных, которые терять нельзя, например для очередей [[Celery]]. Проверим: лимит 20 МБ, значения по 1 КБ, пишем 40000 ключей (ключи с TTL только в варианте `volatile-lru`).

```python
await r.config_set("maxmemory", "20mb")
await r.config_set("maxmemory-policy", pol)
res = await fill("k", 40000, ex=3600 if pol == "volatile-lru" else None)
errs = sum(isinstance(x, Exception) for x in res)
info = await r.info("stats")
print(pol, "ключей:", await r.dbsize(), "ошибок OOM:", errs, "evicted_keys:", info["evicted_keys"])
```

```text title="Вывод"
noeviction   ключей:  17965  ошибок OOM:  22035  evicted_keys: 0  used: 19.87M
allkeys-lru  ключей:  18013  ошибок OOM:      0  evicted_keys: 21964  used: 20.00M
volatile-lru ключей:  17542  ошибок OOM:      0  evicted_keys: 22435  used: 20.00M
volatile-lru без TTL: ключей 18047 ошибок 21953 | пример: ["command not allowed when used memory > 'maxmemory'."]
```

При `noeviction` примерно 18 тысяч ключей поместились, остальные записи получили ошибку `OOM command not allowed when used memory > 'maxmemory'`. С `allkeys-lru` ошибок нет: старые ключи вытеснены (`evicted_keys` около 22 тысяч), память держится на лимите. Последняя строка показывает ловушку: `volatile-lru` без TTL у ключей вытеснять нечего, и Redis ведёт себя как `noeviction`, то есть отказывает в записи. Если выбрана политика `volatile-*`, каждому ключу нужен TTL. Точные числа плавают от запуска к запуску, важна разница в поведении.

**Грабли.** Значение `maxmemory` не включает накладные расходы на фрагментацию и буферы репликации, поэтому общее потребление процесса выше лимита; оставляйте запас. Очереди и кэш не стоит держать в одном экземпляре Redis: кэшу нужен `allkeys-lru`, очередям `noeviction`.

## SCAN против KEYS

**Задача.** Найти ключи по маске в боевом Redis с миллионом ключей.

`KEYS` обходит весь набор за один вызов и блокирует единственный поток Redis на всё время. `SCAN` обходит постепенно, порциями, возвращая курсор для продолжения; между вызовами Redis обслуживает других. Создадим 1 000 000 ключей вида `user:N:s` и сравним: параллельно клиент шлёт `PING` и фиксирует худшую задержку.

```python
ks = await r.keys("user:99999*")                       # блокирует
found = [k async for k in r.scan_iter(match="user:99999*", count=1000)]
cur, batch = await r.scan(0, match="user:99999*", count=1000)
```

```text title="Вывод"
DBSIZE: 1000000
KEYS: 11 ключей за 74 мс; худший PING параллельно: 70 мс
SCAN COUNT 1000: 11 ключей за 382 мс; худший PING параллельно: 1 мс
один вызов SCAN вернул: 0 ключей, курсор: 883712
```

`KEYS` нашёл 11 ключей за 74 мс, и всё это время другой клиент ждал ответа на `PING` (70 мс). `SCAN` потратил больше общего времени (382 мс), но задержка соседа была 1 мс: Redis не блокировался. Последняя строка — типичная неожиданность: один вызов `SCAN` может вернуть пустой список при ненулевом курсоре, потому что `MATCH` применяется после выборки порции (`COUNT` — размер порции, не число результатов). Цикл нужно вести до курсора `0`, а не до первого пустого ответа. На миллионе ключей 74 мс; на сотне миллионов блокировка будет в секундах (так не проверялось).

**Грабли.** `SCAN` может вернуть один ключ дважды и не гарантирует, что увидит ключи, добавленные во время обхода; обработку нужно делать идемпотентной. В кластере `SCAN` обходит один узел, а не весь кластер.

## Большие ключи и UNLINK

**Задача.** Удалить огромное множество (3 млн строк), не остановив Redis.

`DEL` освобождает память синхронно в главном потоке, и чем больше значение, тем дольше пауза. `UNLINK` отсоединяет ключ мгновенно, а память освобождает фоновый поток. Замерим то же множество двумя способами, с `PING` параллельно:

```text title="Вывод"
DEL: вызов занял 134 мс, худший PING 130 мс
UNLINK: вызов занял 0 мс, худший PING 1 мс
```

`DEL` остановил Redis на 134 мс, `UNLINK` вернул управление сразу. Такой же вред приносят `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` по большим структурам: они сериализуют весь ключ за один вызов и блокируют остальных. Большой ключ (100 МБ и больше) ещё и нагружает сеть и репликацию. Найти их помогают `redis-cli --bigkeys` (по каждому типу показывает самый большой ключ) и `MEMORY USAGE <ключ>`. Эти две утилиты здесь запуском не проверялись.

**Грабли.** Истечение TTL у большого ключа тоже освобождает память в главном потоке (на текущих версиях управляется настройкой `lazyfree-lazy-expire`), поэтому лучше не создавать огромные ключи, а дробить: `lb:2026-11:shard-0`.

## Истечение TTL и вытеснение

Это два разных механизма. Истечение срабатывает двумя способами: лениво (ключ проверяется и удаляется при обращении к нему) и активно (фоновая выборка ключей с TTL). Вытеснение (eviction) убирает ключи, когда достигнут `maxmemory`, независимо от их TTL. Поэтому ключ без TTL может быть вытеснен, а ключ с TTL может жить дольше срока, если Redis ещё не добрался до него фоновой выборкой, пока к нему не обратятся.

## Лицензия и форки

В 2024 году Redis сменил лицензию, и появился открытый форк Valkey (проект Linux Foundation); альтернативы — KeyDB и Dragonfly. В Redis 8 (2025) к лицензиям RSAL и SSPL (ограничивают коммерческое использование облачными провайдерами) добавили AGPLv3 (открытую лицензию), так что Redis снова open source, хотя и не под лицензией BSD (разрешающей почти всё), как до версии 7.4.

## Бизнес-кейс

- **Сессии пользователей в Redis.** Потеря последней секунды записей при сбое (AOF `everysec`) означает, что часть пользователей придётся залогинить заново: для сессий допустимо, для корзины заказа спорно, для платежа недопустимо.
- **Кэш и очередь на одном сервере.** Кэшу нужен `allkeys-lru`, очереди `noeviction`; при общем экземпляре политика вытеснит задачи или откажет в записи кэша. Разведите по разным экземплярам или базам с разными настройками.

## Что спросят дальше

- RDB или AOF? RDB компактнее и быстрее при старте, но теряет всё после последнего снимка; AOF теряет до секунды при `everysec`, но файл больше и восстановление дольше. Обычно включают оба.
- Что теряем при падении без настроенной персистентности? Всё содержимое; Redis при старте поднимется пустым.
- Чем `KEYS` отличается от `SCAN`? `KEYS` блокирует поток на весь обход, `SCAN` отдаёт порциями, но допускает повторы.
- Чем `UNLINK` отличается от `DEL`? Освобождает память в фоне.
