**Суть.** Событие — публичный контракт, как API: его читают сервисы, которых вы не видите. Схему держат в Schema Registry и меняют только совместимо. Отдельная тема — сжатие топика по ключу (compaction): топик хранит последнее значение каждого ключа и работает как таблица, а удаление ключа делается специальным сообщением со значением `null`.

## Событие как контракт

- **Формат.** Используют Avro или Protobuf вместе с **Schema Registry** (отдельным сервисом, который хранит схемы событий и проверяет их версии). Avro и Protobuf — бинарные форматы сообщений с заранее описанной схемой полей; они компактнее JSON. В самом сообщении лежит только id схемы, а не вся схема. Голый JSON без схемы — источник тихих поломок консюмеров.
- **Что кладут в событие:** `event_id` (для идемпотентности), тип события, версию схемы, время, ключ и версию агрегата.
- **Имена топиков** — `<домен>.<сущность>.<событие>`, без окружения и версии сервиса. Тип события — поле в самом событии, а не часть имени топика: так один топик на агрегат сохраняет порядок событий.

## Совместимость схем

Режимы совместимости определяют, какие изменения схемы Registry пропустит:

- `BACKWARD` — новый консюмер читает старые сообщения (дефолт Confluent Schema Registry);
- `FORWARD` — старый консюмер читает новые сообщения;
- `FULL` — выполняются оба условия сразу;
- варианты `*_TRANSITIVE` — проверка против всех прошлых версий схемы, а не только против последней.

Что безопасно: добавить необязательное поле с дефолтом. Что ломает: сделать поле обязательным без значения по умолчанию, переименовать поле, сменить тип. Удаление поля зависит от режима: при `BACKWARD` новый читатель просто не найдёт старого поля и справится, а вот при `FORWARD` старый читатель, которому поле нужно, сломается, если у поля не было значения по умолчанию. Поэтому для контракта, у которого потребителей много и вы их не контролируете, нужен `FULL`. Если изменение нельзя сделать совместимо, заводят новый тип события или новый топик, а старый живёт, пока все потребители не перейдут.

## Рецепт совместимости схем

Задача: на практике увидеть, какие правки схемы Avro проходят в каждую сторону. Сам Registry в рецепте не запускался, но правила чтения схем (schema resolution) — те же, на которых построены его проверки; вместо Registry используется библиотека `fastavro`: писатель кодирует запись своей схемой, читатель разбирает её своей.

```python
oid = {"name": "order_id", "type": "long"}
status = {"name": "status", "type": "string"}
v1 = S(oid, status)
v2 = S(oid, status, {"name": "currency", "type": "string", "default": "EUR"})
v3_nodef = S(oid, status, {"name": "currency", "type": "string"})            # без default
v4_drop = S(oid)                                                              # status удалён
v5_rename = S(oid, {"name": "state", "type": "string"})                       # status -> state
v6_alias = S(oid, {"name": "state", "type": "string", "aliases": ["status"]})
v7_type = S(oid, {"name": "status", "type": "int"})                           # string -> int

def roundtrip(writer, record, reader):
    buf = io.BytesIO(); schemaless_writer(buf, writer, record); buf.seek(0)
    return schemaless_reader(buf, writer, reader)
```

```text title="Вывод"
НОВЫЙ читатель читает СТАРЫЕ данные (BACKWARD):
  добавили поле с default            ok   {'order_id': 7, 'status': 'paid', 'currency': 'EUR'}
  добавили поле без default          FAIL SchemaResolutionError: No default value for field currency in OrderPaid
  удалили поле status                ok   {'order_id': 7}
  переименовали status -> state      FAIL SchemaResolutionError: No default value for field state in OrderPaid
  переименовали, но с aliases        ok   {'order_id': 7, 'state': 'paid'}
  сменили тип string -> int          FAIL SchemaResolutionError: Schema mismatch: string is not int
СТАРЫЙ читатель (v1) читает НОВЫЕ данные (FORWARD):
  писатель v2 (есть currency)        ok   {'order_id': 7, 'status': 'paid'}
  писатель v4 (нет status)           FAIL SchemaResolutionError: No default value for field status in OrderPaid
```

Видно, что для `BACKWARD` проходят добавление поля с дефолтом, удаление и переименование через `aliases`; не проходят поле без дефолта, обычное переименование и смена типа. Для `FORWARD` старый читатель переживает новое поле (лишнее он игнорирует), но не удаление поля, которое он ждёт. Грабли: переименование через `aliases` работает в Avro на уровне чтения, но старые читатели, не знающие алиаса, всё равно потеряют поле, поэтому безопасный путь — добавить новое поле рядом, дублировать значение на переходный период и только потом убрать старое.

## Log compaction

`cleanup.policy=compact` оставляет в топике последнее значение для каждого ключа, и топик работает как таблица: справочники, текущее состояние, служебный топик `__consumer_offsets`. Сжатие происходит не мгновенно: активный сегмент (файл, в который сейчас пишут) не трогается, и старые значения по ключу видны, пока не пройдёт фоновая очистка (cleaner).

**Tombstone** («надгробие», сообщение со значением `null`) удаляет ключ при сжатии. Он живёт `delete.retention.ms`: консюмер, отставший сильнее этого срока, удаление не увидит. Обработчик обязан разбирать `value is None`, а не падать на нём. Политика `compact,delete` объединяет сжатие и удаление старых сообщений по времени. Offset сообщений при сжатии не меняются: удалённые записи оставляют в нумерации «дырки», поэтому нельзя считать, что `offset` равен порядковому номеру записи.

## Рецепт compaction и tombstone

Задача: увидеть, что именно остаётся от топика после сжатия и когда исчезает tombstone. Чтобы сжатие случилось за секунды, топик создаётся с укороченными таймерами (а брокеру при запуске выставлено `log.cleaner.backoff.ms=2000`, иначе он проверяет «грязные» сегменты раз в 15 секунд): активный сегмент закрывается через три секунды, порог «грязности» минимальный, tombstone живёт 30 секунд.

```text title="Вывод"
$ kafka-topics.sh --create --topic cmp.users2 --partitions 1 --replication-factor 1 \
    --config cleanup.policy=compact --config segment.ms=3000 --config min.cleanable.dirty.ratio=0.01 \
    --config delete.retention.ms=30000 --config min.compaction.lag.ms=0
Created topic cmp.users2.
```

Записываются шесть сообщений: три значения ключа `u1`, одно значение `u2`, значение и tombstone для `u3`. Tombstone пишется консольным продюсером с `--property null.marker=NULL`. Чтобы закрыть активный сегмент, спустя `segment.ms` дописываются ещё два сообщения (`u4`, `u5`); без новых записей активный сегмент не закрывается, и сжимать нечего. После паузы топик читается снова:

```text title="Вывод"
--- сжатие прошло, tombstone ещё жив (delete.retention.ms=30 с)
Offset:1	u2	{"email":"b@x.io"}
Offset:4	u3	null
Offset:5	u1	{"email":"a3@x.io"}
Offset:6	u4	{"email":"d@x.io"}
Offset:7	u5	{"email":"e@x.io"}
```

До сжатия в топике лежали записи с offset 0 по 5: `u1` трижды (0, 3, 5), `u2` (1), `u3` дважды (значение с offset 2 и tombstone с offset 4). После сжатия остались только последние значения: `u1` с offset 5 (первые два значения исчезли), `u2` с offset 1, а у `u3` значение исчезло, но tombstone с offset 4 ещё на месте, чтобы читатели успели увидеть удаление. Номера offset не изменились: между 1 и 4 теперь «дыра». Затем спустя `delete.retention.ms` дописываются ещё два сообщения (чтобы снова закрыть сегмент и запустить очистку), и топик читается ещё раз:

```text title="Вывод"
--- после delete.retention.ms
Offset:1	u2	{"email":"b@x.io"}
Offset:5	u1	{"email":"a3@x.io"}
Offset:6	u4	{"email":"d@x.io"}
Offset:7	u5	{"email":"e@x.io"}
Offset:8	u6	{"email":"f@x.io"}
Offset:9	u7	{"email":"g@x.io"}
```

Tombstone (offset 4) исчез: ключ `u3` из топика удалён полностью. Консьюмер, который прочитал топик и собирает из него таблицу, обязан обрабатывать `None`:

```python
table = {}
while batch := await c.getmany(timeout_ms=2000):
    for ms in batch.values():
        for m in ms:
            if m.value is None:
                table.pop(m.key.decode(), None)        # tombstone: удалить ключ
            else:
                table[m.key.decode()] = json.loads(m.value)
```

```text title="Вывод"
u1 {'email': 'a3@x.io'}
u2 {'email': 'b@x.io'}
u4 {'email': 'd@x.io'}
u5 {'email': 'e@x.io'}
u6 {'email': 'f@x.io'}
u7 {'email': 'g@x.io'}
```

Грабли. Во-первых, сжатие не гарантирует момента: пока не закрыт активный сегмент и не накопилась «грязь», топик содержит все версии, поэтому код читателя не должен рассчитывать, что по ключу придёт ровно одно сообщение. Во-вторых, консьюмер, который был остановлен дольше `delete.retention.ms`, мог пропустить tombstone: после возвращения его локальная таблица содержит ключ, которого в топике уже нет; для таких читателей таблицу пересобирают с начала топика. В-третьих, в таблице хранят полное состояние в каждом сообщении, а не дельту: при сжатии теряются промежуточные значения, и дельты после него уже нельзя применить.

## Бизнес-кейс

Справочник тарифов публикуется в compacted-топик: каждый сервис при старте читает его целиком и держит в памяти актуальную таблицу, а после этого получает изменения. Отмена тарифа — tombstone. Вопросы к продукту и архитектуре: как долго может простоять сервис, чтобы не пропустить удаление (это и есть нижняя граница `delete.retention.ms`), кто владеет схемой справочника и что будет, когда в тариф добавится обязательное поле (по правилам выше — новый тип события или значение по умолчанию, а не «просто добавили поле»).

## Что спросят дальше

- Какой режим совместимости выбрать? Для публичного события с неизвестным числом читателей — `FULL` или `FULL_TRANSITIVE`, а не дефолт: `BACKWARD` защищает только читателей новой схемы, но не старых.
- Чем compaction отличается от удаления по сроку? Срок удаляет сообщения старше N; compaction оставляет последнее значение каждого ключа независимо от возраста. Вместе они дают `compact,delete`.
- Почему tombstone не исчезает сразу? Чтобы читатели, отставшие не больше `delete.retention.ms`, успели увидеть удаление и обновить свои таблицы.
- Можно ли использовать compacted-топик как источник правды? Для текущего состояния по ключу — да, при условии что сообщения содержат полное состояние, а не дельту, а читатель разбирает tombstone.
