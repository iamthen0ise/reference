Конспект к собеседованию по согласованности данных между сервисами: почему нельзя «записать в базу и отправить в Kafka» двумя вызовами, как это решает transactional outbox, чем сага отличается от 2PC и как выглядят компенсации. Выводы получены на Apache Kafka 4.1.0, `aiokafka` 0.15.0, Postgres 17 и `asyncpg` 0.32.0 (Python 3.13).

**Суть.** Когда одна бизнес-операция проходит через несколько сервисов с отдельными базами, обычной транзакции на всех нет. Выбирают между «всё или ничего» ценой блокировок (2PC) и цепочкой локальных транзакций с компенсациями (сага). Отдельная, более приземлённая задача внутри любой саги — надёжно связать запись в базу с публикацией события, и решается она таблицей outbox.

## Подходы

Для связанных операций в нескольких сервисах есть несколько подходов:

- **CAP и PACELC** — две теоремы о компромиссах распределённых систем. CAP: при сетевом разделении (одна часть системы не видит другую) приходится выбирать между консистентностью (все видят одни и те же данные) и доступностью (система отвечает всегда). PACELC дополняет её: пока разделения нет, выбирают между задержкой ответа (latency) и консистентностью.
- **2PC** (Two-Phase Commit, двухфазная фиксация) — координатор сначала спрашивает все сервисы, готовы ли они зафиксировать изменения, и только потом командует «фиксируй». Это даёт атомарность, но при падении координатора участники застревают в блокировке. В микросервисах почти не используется.
- **Сага** — цепочка локальных транзакций, у каждой из которых есть компенсирующее действие (операция, отменяющая результат шага, если дальше что-то пошло не так). Бывает два вида: хореография (сервисы сами реагируют на события друг друга) и оркестрация (центральный координатор ведёт процесс, например Temporal — платформа для надёжного исполнения таких процессов).

## Dual write и outbox

**Dual write** («двойная запись») — запись в две системы подряд без общей транзакции. Порядок «коммит в базу, затем отправка» теряет событие, если процесс упал между ними; порядок «отправка, затем коммит» публикует событие о том, чего не случилось, если коммит откатился. Первый вариант проще воспроизвести:

```python
async with pool.acquire() as db:
    await db.execute("INSERT INTO orders VALUES (104, 'paid')")        # commit в базу прошёл
    raise ConnectionError("процесс убит")                               # ...а до send не дошли
    await p.send_and_wait("orders.naive", b"OrderPaid 104")
```

```text title="Вывод"
сбой: процесс убит
в базе заказ 104: paid
orders.naive:0:0
```

Заказ оплачен, а события нет: последняя строка — конечный offset топика, он 0, топик пуст. Склад никогда не узнает об оплате. Решение — **transactional outbox**: событие пишется в таблицу `outbox` в той же транзакции базы, что и изменение данных, а отдельный процесс (релей) читает таблицу и публикует события в Kafka. Атомарность даёт транзакция базы; доставка в Kafka — по схеме «минимум один раз», поэтому потребитель идемпотентен.

## Рецепт outbox-релея на Postgres и aiokafka

Задача: оплатить заказ и гарантированно опубликовать `OrderPaid`, даже если релей падает в самый неудобный момент. Схема таблиц: `orders` и `outbox` с неотправленными строками в частичном индексе, потребитель хранит обработанные события в `processed_events`.

```sql
CREATE TABLE outbox (
  id bigserial PRIMARY KEY, event_id uuid NOT NULL DEFAULT gen_random_uuid(),
  aggregate_id text NOT NULL, type text NOT NULL, payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(), locked_at timestamptz, sent_at timestamptz);
CREATE INDEX outbox_unsent ON outbox (id) WHERE sent_at IS NULL;
CREATE TABLE processed_events (consumer text, event_id uuid, PRIMARY KEY (consumer, event_id));
```

Бизнес-операция пишет заказ и событие одной транзакцией. Релей берёт пачку короткой транзакцией: `UPDATE ... SET locked_at = now()` для строк, выбранных `FOR UPDATE SKIP LOCKED` (несколько релеев не берут одни и те же строки и не ждут друг друга, см. [[Блокировки#Техника: очередь задач на SKIP LOCKED]]), и сразу её закрывает. Сетевую отправку делает **вне** транзакции: открытая транзакция на время `send` держала бы соединение и блокировки. После отправки отдельным коротким `UPDATE` ставится `sent_at`. Строки с протухшим `locked_at` (релей умер) берутся снова.

```python
async def pay_order(pool, order_id):
    async with pool.acquire() as db, db.transaction():       # изменение данных и событие: одна транзакция
        await db.execute("INSERT INTO orders VALUES ($1, 'paid')", order_id)
        await db.execute("INSERT INTO outbox (aggregate_id, type, payload) VALUES ($1, 'OrderPaid', $2)",
                         str(order_id), json.dumps({"order_id": order_id, "status": "paid"}))

async def relay_once(pool, producer, batch=10, crash_after_send=False):
    async with pool.acquire() as db:
        async with db.transaction():                         # короткая транзакция: только забрать пачку
            rows = await db.fetch(f"""
                UPDATE outbox SET locked_at = now() WHERE id IN (
                  SELECT id FROM outbox WHERE sent_at IS NULL
                    AND (locked_at IS NULL OR locked_at < now() - interval '2 seconds')
                  ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED)
                RETURNING id, event_id, aggregate_id, payload""", batch)
        for r in sorted(rows, key=lambda r: r["id"]):        # публикация вне транзакции
            await producer.send_and_wait(TOPIC, key=r["aggregate_id"].encode(), value=r["payload"].encode(),
                                         headers=[("event_id", str(r["event_id"]).encode())])
        if crash_after_send:
            raise SystemExit("процесс упал после send, до sent_at")
        await db.execute("UPDATE outbox SET sent_at = now() WHERE id = ANY($1)", [r["id"] for r in rows])
```

Потребитель вставляет `event_id` в `processed_events` с `ON CONFLICT DO NOTHING` и применяет эффект, только если строка вставилась (проверка числа вставленных строк обязательна, иначе повтор выполнит эффект второй раз). Сценарий: три заказа оплачены; релей публикует пачку, но «падает» до `sent_at`; второй запуск сразу не берёт ничего (строки ещё заблокированы); третий, после истечения блокировки, публикует то же самое повторно.

```text title="Вывод"
3 заказа оплачены, в outbox: 3 неотправленных
релей, запуск 1 (падает после send):
  релей: отправил 3 событий, ids=[1, 2, 3]
  релей: процесс упал после send, до sent_at
  релей: отправил 0 событий, ids=[]
релей, запуск 2 сразу: строки ещё заблокированы -> 0 событий
релей, запуск 3 через 2.5 с: блокировка протухла
  релей: отправил 3 событий, ids=[1, 2, 3]
неотправленных в outbox: 0
потребитель:
  billing: offset 0 key=101 event_id=cb347659… -> применено
  billing: offset 1 key=102 event_id=db32df9b… -> применено
  billing: offset 2 key=103 event_id=7a58cb90… -> применено
  billing: offset 3 key=101 event_id=cb347659… -> дубль, пропущено
  billing: offset 4 key=102 event_id=db32df9b… -> дубль, пропущено
  billing: offset 5 key=103 event_id=7a58cb90… -> дубль, пропущено
  billing: прочитано 6, эффект применён 3
```

Строка «отправил 0 событий» перед заголовком «запуск 2» напечатана самим холостым вызовом релея, который не нашёл свободных строк. Ни одно событие не потеряно, но каждое доставлено дважды: это цена at-least-once. Идентификатор события, сгенерированный в outbox и лежащий в заголовке, отличает дубль, и потребитель отбросил три повтора, применив эффект ровно три раза. Грабли. Во-первых, порядок по агрегату релей сам не держит: `id` из sequence виден не в порядке `COMMIT`, а два релея разбирают соседние пачки вперемешку, поэтому нужен один релей на шард ключа либо версия агрегата в событии, по которой потребитель отбрасывает устаревшее (см. [[Порядок событий]]). Во-вторых, неотправленные строки надо мониторить: возраст старейшей (`now() - min(created_at) WHERE sent_at IS NULL`) растёт, когда публикация встала. В-третьих, отправленные строки чистят пачками по расписанию, иначе таблица растёт вечно. Вместо опроса таблицы можно читать журнал базы через CDC (Change Data Capture, захват изменений, например Debezium); тогда релея в приложении нет, а требования к идемпотентности потребителя те же.

## Хореография и оркестрация

В **хореографии** нет центра: сервис склада публикует `StockReserved`, платёжный сервис слушает его и публикует `PaymentCharged` или `PaymentFailed`, склад слушает `PaymentFailed` и снимает бронь. Плюс — слабая связность, каждый сервис знает только события. Минус — процесс «размазан» по сервисам, и по коду нельзя прочитать, как проходит заказ целиком; циклические зависимости между событиями находят поздно. В **оркестрации** есть один сервис-координатор (или платформа вроде Temporal): он хранит состояние процесса, шлёт командой следующий шаг и сам решает, что компенсировать. Процесс читается в одном месте и наблюдаем, но координатор — точка связности и надёжности: его состояние должно переживать падения. Практическое правило: для коротких линейных процессов из двух-трёх шагов хватает хореографии, для длинных, ветвящихся и с таймерами нужна оркестрация.

## Рецепт компенсаций

Задача: «забронировать товар, списать деньги, создать доставку». Сага из трёх шагов, у каждого есть компенсация; при ошибке выполняются компенсации уже сделанных шагов в обратном порядке. Рецепт показывает логику оркестратора без Kafka и базы (шаги — функции в одном процессе), поэтому демонстрирует порядок компенсаций, а не надёжность хранения состояния.

```python
SAGA = [Step("reserve", reserve, unreserve), Step("charge", charge, refund), Step("ship", ship, cancel_ship)]

async def run_saga(order):
    done = []
    try:
        for s in SAGA:
            await s.do(order); done.append(s)
        print(f"  итог: {order} COMPLETED")
    except Exception as e:
        print(f"  шаг упал ({e}); компенсируем в обратном порядке")
        for s in reversed(done):          # компенсации идемпотентны и выполняются с повторами до успеха
            await s.undo(order)
        print(f"  итог: {order} CANCELLED")
```

```text title="Вывод"
order-1
  [склад]    бронь товара для order-1
  [платежи]  списано по order-1
  [доставка] создана доставка для order-1
  итог: order-1 COMPLETED
order-2
  [склад]    бронь товара для order-2
  шаг упал (карта отклонена); компенсируем в обратном порядке
  [склад]    снята бронь для order-2
  итог: order-2 CANCELLED
```

У `order-2` упал шаг оплаты, и компенсировать пришлось только брони: упавший шаг в список выполненных не попал. Если бы падала доставка, компенсации прошли бы по оплате (возврат) и броне. Грабли. Компенсация — не откат, а новое бизнес-действие: возврат денег виден в выписке клиента, снятая бронь могла уже вызвать пересчёт остатков, поэтому компенсации тоже идемпотентны и выполняются с повторами, пока не пройдут. Шаги, которые нельзя отменить (отправленное письмо, физическая отгрузка), ставят в конец саги. Промежуточные состояния («заказ оформляется») видны пользователю, и продукт должен их продумать.

## Бизнес-кейс

Забронировать товар, затем списать деньги, затем создать доставку. Если оплата не прошла, срабатывает компенсация «снять бронь». Продукт должен решить, что пользователь видит в промежуточных состояниях («заказ оформляется»): eventual consistency (согласованность «в конце концов», данные в разных сервисах расходятся на короткое время) видна в интерфейсе. Дополнительные вопросы: сколько ждать ответа платёжного сервиса до компенсации, что делать, если компенсация сама не удалась (алерт и ручной разбор), и кто видит зависшие саги.

## Что спросят дальше

- Почему не отправить в Kafka прямо из обработчика запроса? Нет общей транзакции с базой: либо потеря события, либо событие о несостоявшемся. Поэтому outbox.
- Чем outbox с опросом отличается от CDC? Опрос проще и живёт в приложении, но даёт задержку и нагрузку на таблицу; CDC читает журнал базы без опроса, но требует инфраструктуры (Debezium, коннекторы). Гарантия доставки в обоих случаях «минимум один раз».
- Как сохранить порядок событий агрегата из outbox? Один релей на шард ключа либо версия агрегата в событии и отбрасывание устаревшего потребителем.
- Почему 2PC не любят в микросервисах? Блокировки при падении координатора, зависимость от доступности всех участников сразу; сага допускает промежуточные состояния, но не держит блокировок.
- Когда хореография, когда оркестрация? Короткие линейные процессы — хореография; длинные, ветвящиеся, с таймерами и компенсациями — оркестрация с хранимым состоянием.
