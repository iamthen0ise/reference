Конспект к собеседованию по отправке сообщений в Kafka: что значит «отправлено», зачем идемпотентный продюсер, как ключ выбирает партицию, чем пачки и сжатие меняют пропускную способность и что делать с ошибкой отправки. Выводы получены на Apache Kafka 4.1.0, `aiokafka` 0.15.0 и `confluent-kafka` 2.16.2 (Python 3.13).

Разделы: [[#Что значит отправлено]] · [[#acks и идемпотентный продюсер]] · [[#Ключ и выбор партиции]] · [[#Пачки, linger и сжатие]] · [[#Ошибка отправки]] · [[#Остановка и flush]] · [[#Бизнес-кейс]] · [[#Что спросят дальше]]

**Суть.** Продюсер (producer, отправитель) не пишет в Kafka сразу: `send` кладёт сообщение в буфер в памяти процесса, а фоновый поток собирает буфер в пачки и отправляет брокеру. Поэтому «вызвал `send`» не значит «сообщение сохранено». Сохранённым оно считается, когда брокер ответил подтверждением в нужном режиме `acks`, и дожидаться этого ответа должен код, для которого потеря недопустима. Остальные настройки продюсера — компромисс между надёжностью, порядком и пропускной способностью.

## Что значит отправлено

В `aiokafka` есть два вызова. `await producer.send_and_wait(...)` возвращает управление только после ответа брокера и отдаёт метаданные записи: партицию и offset. `await producer.send(...)` возвращает объект-обещание (future) сразу после постановки в буфер, и ошибка доставки придёт только в него. Если обещание никто не ждёт, сбой лидера или падение процесса теряют сообщение молча.

```python
import asyncio
from aiokafka import AIOKafkaProducer

async def main():
    producer = AIOKafkaProducer(bootstrap_servers="localhost:9094", acks="all", enable_idempotence=True)
    await producer.start()
    try:
        md = await producer.send_and_wait("orders", key=b"o-1", value=b'{"event":"OrderPaid"}')
        print(md.topic, md.partition, md.offset)

        # пакетная отправка: ставим в буфер много сообщений, затем ждём подтверждения всех
        futures = [await producer.send("orders", key=b"o-1", value=f"e{i}".encode()) for i in range(3)]
        for fut in futures:
            print((await fut).offset)
    finally:
        await producer.stop()          # stop() досылает буфер и закрывает соединения

asyncio.run(main())
```

Продюсер создаётся один на процесс (в старте приложения) и закрывается при остановке: на каждое сообщение он обходится соединением и потоком отправки. Для сообщений, которые нельзя терять, событие пишут не прямым `send` из обработчика запроса, а в таблицу outbox в той же транзакции базы, см. [[Распределённые транзакции и саги]].

> [!warning] Fire-and-forget
> `send` без ожидания годится только для некритичных событий (метрики, телеметрия) и с комментарием в коде: ошибка доставки в этом случае никому не видна.

## acks и идемпотентный продюсер

Настройка `acks` (acknowledgements, подтверждения) отвечает на вопрос «чьего ответа ждать»:

- `acks=0` — не ждать вообще, потеря не видна;
- `acks=1` — ждать записи на лидера: если лидер упал до копирования на реплики, сообщение потеряно, хотя продюсер получил «успех»;
- `acks=all` — ждать всех реплик из ISR, вместе с `min.insync.replicas=2` и replication factor 3 это стандарт для данных, которые нельзя терять.

Повтор отправки после таймаута сам по себе создаёт дубль: продюсер не знает, дошла ли первая попытка. **Идемпотентный продюсер** (`enable_idempotence=True`) решает это на стороне брокера: при старте он получает идентификатор `producerId`, нумерует записи по каждой партиции (`baseSequence`), и брокер отбрасывает запись с уже виденным номером. Заодно сохраняется порядок при нескольких запросах в полёте (`max.in.flight.requests.per.connection`, не больше 5). Это хорошо видно в журнале партиции: `kafka-dump-log.sh` печатает заголовок каждой пачки.

```python
# aiokafka: идемпотентность выключена по умолчанию
AIOKafkaProducer(bootstrap_servers=BOOT)
# aiokafka: включена явно, acks="all" обязателен
AIOKafkaProducer(bootstrap_servers=BOOT, enable_idempotence=True)
# confluent-kafka: идемпотентность тоже выключена по умолчанию
Producer({"bootstrap.servers": BOOT})
```

```text title="Вывод"
== idem.aio_default
baseOffset: 0 count: 1 baseSequence: 0 producerId: -1
== idem.aio_on
baseOffset: 0 count: 1 baseSequence: 0 producerId: 1
baseOffset: 1 count: 1 baseSequence: 1 producerId: 1
== idem.conf_default
baseOffset: 0 count: 2 baseSequence: -1 producerId: -1
```

Топик `idem.aio_default` написан `aiokafka` с настройками по умолчанию, `idem.aio_on` — `aiokafka` с `enable_idempotence=True` (два сообщения, две пачки), `idem.conf_default` — `confluent-kafka` по умолчанию (два сообщения уехали одной пачкой). `producerId: -1` и `baseSequence: -1` значат, что идемпотентности нет и брокер не отличит повтор от нового сообщения. При включённой идемпотентности `acks` должен быть `all`, иначе клиент откажется стартовать:

```text title="Вывод"
aiokafka: ValueError acks=1 not supported if enable_idempotence=True
confluent: KafkaException KafkaError{code=_INVALID_ARG,val=-186,str="Failed to create producer: `acks` must be set to `all` when `enable.idempotence` is true"}
```

> [!info] Дефолты клиентов расходятся
> В Java-клиенте идемпотентность включена по умолчанию начиная с Kafka 3.0. В `aiokafka` и `confluent-kafka` (librdkafka) на проверенных версиях она выключена, поэтому `enable_idempotence=True` и `acks="all"` нужно писать явно. Идемпотентность защищает от дублей одной сессии продюсера; после перезапуска процесс получает новый `producerId`, и повтор события «после сбоя» она не отсекает. Это забота идемпотентного консьюмера, см. [[Когда двигать offset]].

Про `max.in.flight`: без идемпотентности при значении больше 1 повтор неудавшегося запроса может обогнать следующий, и два сообщения одного ключа поменяются местами; с идемпотентностью брокер восстанавливает порядок по номерам. Это утверждение следует из протокола и в рецептах не воспроизводилось.

Потерю при `acks=1`, отказ записи при `acks=all` и `min.insync.replicas=2`, потерю при `acks=all` с `min.insync.replicas=1` и дубль от повтора отправки (с идемпотентным продюсером и без) можно воспроизвести в лабе: [[Стенд репликации Kafka#Потеря при acks=1]], [[Стенд репликации Kafka#Потеря при acks=all и min ISR 1]], [[Стенд репликации Kafka#Дубли при повторе отправки]].

## Ключ и выбор партиции

Порядок гарантирован только внутри партиции, поэтому ключ нужен, чтобы события одного агрегата (заказа, подписки, пользователя) попадали в одну партицию. Партиция считается как хеш ключа по модулю числа партиций, но алгоритм хеширования зависит от клиента. Тот же набор ключей на топике из 6 партиций:

```python
# aiokafka: murmur2, как в Java-клиенте
await producer.send_and_wait("keys.demo", key=k.encode(), value=b"x")

# confluent-kafka: partitioner по умолчанию consistent_random (CRC32), и отдельно с murmur2_random
Producer({"bootstrap.servers": BOOT})
Producer({"bootstrap.servers": BOOT, "partitioner": "murmur2_random"})
```

```text title="Вывод"
ключ        aiokafka   confluent (по умолчанию)   confluent murmur2_random
order-1            4                          1                          4
order-2            3                          3                          3
order-3            3                          5                          3
order-4            2                          2                          2
order-5            2                          4                          2
order-6            3                          0                          3
```

Если на один топик пишут два сервиса, один на Java или `aiokafka`, другой на `confluent-kafka` с настройкой по умолчанию, события одного заказа разъедутся по разным партициям и порядок пропадёт. Лечится одним партиционером на всех: `murmur2_random` в `confluent-kafka`. Сообщения без ключа раскладываются по партициям пачками (sticky-разбрасывание), порядка между ними нет. Последствия смены числа партиций разобраны в [[Эксплуатация Kafka и CLI]].

## Пачки, linger и сжатие

Фоновый поток отправляет не каждое сообщение отдельным запросом, а пачку на партицию. Размер пачки ограничивает `batch.size` (в `aiokafka` — `max_batch_size`), а ожидание пачки задаёт `linger.ms` (в `aiokafka` — `linger_ms`): сколько продюсер готов подержать неполную пачку в надежде, что подъедут ещё сообщения. Большая пачка означает меньше запросов, лучшее сжатие и более высокую пропускную способность ценой задержки до `linger.ms`.

Сначала цена ожидания подтверждения на каждое сообщение. Строка `one_by_one` — `send_and_wait` для каждого из 2000 сообщений, строка `linger20` — 20000 сообщений через `send` без ожидания, затем один `gather` по всем обещаниям (`linger_ms=20`); у обоих `acks="all"`, диск посчитан для разного числа сообщений:

```text title="Вывод"
one_by_one               2000 сообщений за  0.79 c  (    2533 сообщ/с)  на диске 3168 КиБ
linger20                20000 сообщений за  0.25 c  (   81098 сообщ/с)  на диске 6572 КиБ
```

Теперь влияние `linger.ms` и сжатия в `confluent-kafka`: 5000 JSON-сообщений около 250 байт, на живом потоке в несколько сотен сообщений в секунду (в строке «залпом» — без пауз). В последнем столбце — размер каталога топика на диске брокера, в предпоследнем — число запросов к брокеру, которые клиент насчитал в собственной статистике.

```text title="Вывод"
настройки                           время, с  запросов  на диске, КиБ
linger.ms=0 (≈700 сообщ/с)              6.80      1318           1268
linger.ms=50 (≈700 сообщ/с)             6.74       125           1196
linger.ms=0 (залпом)                    0.03         9           1196
linger.ms=50 (залпом)                   0.04         9           1196
gzip, linger.ms=50 (залпом)             0.05         4            292
lz4, linger.ms=50 (залпом)              0.06         4            468
zstd, linger.ms=50 (залпом)             0.06         4            280
```

Что видно из таблицы. При `linger.ms=0` на тонком потоке каждое сообщение уходит своим запросом (1318 запросов), при `linger.ms=50` те же сообщения едут пачками (125 запросов), а общее время то же, потому что его определяет сам поток. Когда сообщения идут залпом, пачки собираются сами, и `linger.ms` ничего не меняет. Сжатие работает на пачке, поэтому оно эффективно при больших пачках: JSON сжался в 4–5 раз (gzip и zstd лучше, lz4 быстрее и заметно хуже по размеру). Сжимает продюсер, брокер хранит пачку как есть, а консьюмер распаковывает, так что экономятся и сеть, и диск.

> [!info] Что осталось непроверенным
> Дефолт librdkafka для `linger.ms` (5 мс) и дефолты `batch.size` в клиентах взяты из документации, запуском не подтверждались. В таблице сравниваются только явно заданные значения.

## Ошибка отправки

Ошибку отправки нельзя глотать: `except: pass` теряет событие. Что именно прилетает, зависит от клиента.

```python
# aiokafka: исключение из send_and_wait
try:
    await producer.send_and_wait("err.demo", b"x" * 2_000_000)
except KafkaError as e:
    print(type(e).__name__, e)

# confluent-kafka: ошибка приходит в delivery callback, а слишком большое сообщение — исключением из produce
def on_delivery(err, msg):
    if err:
        print(err, err.retriable(), err.name())
producer.produce("err.demo", b"hello", on_delivery=on_delivery)
producer.flush(10)
```

```text title="Вывод"
1. MessageSizeTooLargeError - [Error 10] MessageSizeTooLargeError: The message is 2000088 bytes when serialized which is larger than the maximum request size you have configured with the max_request_size configuration
2. RequestTimedOutError - [Error 7] RequestTimedOutError
3. KafkaError{code=_MSG_TIMED_OUT,val=-192,str="Local: Message timed out"} | retriable: False | code: _MSG_TIMED_OUT
4. KafkaException - KafkaError{code=MSG_SIZE_TOO_LARGE,val=10,str="Unable to produce message: Broker: Message size too large"}
```

Строки 2 и 3 получены так: контейнер брокера поставили на паузу (`docker pause`), чтобы он перестал отвечать; `aiokafka` с `request_timeout_ms=3000` отдал `RequestTimedOutError`, а `confluent-kafka` с `message.timeout.ms=3000` через три секунды вернул в callback `_MSG_TIMED_OUT`. Решение зависит от типа ошибки. Слишком большое сообщение (1, 4) повторять бессмысленно: оно никогда не пройдёт, его нужно уменьшить или вынести тело наружу, а ссылку положить в событие. Таймаут (2, 3) — временный сбой: после истечения времени клиент уже перестал повторять, а сообщение неизвестно доставлено или нет. Здесь два рабочих пути: повторить отправку (идемпотентный продюсер не создаст дубль в рамках сессии) либо оставить событие в outbox и отправить позже. Что нельзя делать, так это молча отбросить событие.

## Остановка и flush

Сообщения, оставшиеся в буфере, при остановке процесса пропадают, если их не досылать. Эксперимент на `confluent-kafka`: 5 сообщений, `linger.ms=1000`, чтобы они гарантированно сидели в буфере, и три способа завершения.

```python
p = Producer({"bootstrap.servers": BOOT, "linger.ms": 1000})
for i in range(5):
    p.produce(topic, f"msg-{i}".encode())
if mode == "flush":
    p.flush()            # ждать, пока все сообщения будут доставлены
if mode == "hard":
    os._exit(0)          # процесс убит сразу после produce
# mode == "plain": скрипт просто закончился
```

```text title="Вывод"
flush.hard:0:0
flush.flush:0:5
%4|1795113710.536|TERMINATE|rdkafka#producer-1| [thrd:app]: Producer terminating with 5 messages (25 bytes) still in queue or transit: use flush() to wait for outstanding message delivery
flush.plain:0:0
```

Строки вида `топик:партиция:конечный offset` печатает `kafka-get-offsets.sh`: конечный offset 0 значит, что в партиции нет ни одного сообщения. Даже обычное завершение скрипта без `flush()` потеряло все пять сообщений: клиент только предупредил в логе. Поэтому в обработчике сигнала остановки сначала прекращают принимать работу, затем вызывают `flush()` (или `await producer.stop()` в `aiokafka`, который досылает буфер сам) и только после этого выходят. У `flush` есть таймаут: если за отведённое время буфер не опустел, он возвращает число недоставленных сообщений, и это число стоит залогировать и считать потерей или переотправкой из outbox.

## Бизнес-кейс

Платёжный сервис публикует событие «заказ оплачен». Потеря события означает, что склад не соберёт заказ, а дубль — что его соберут дважды. Решения здесь вытекают из страницы выше: событие пишется в outbox вместе с оплатой, релей отправляет его с `acks=all` и идемпотентным продюсером, ключ — идентификатор заказа, чтобы статусы заказа не менялись местами, а потребитель идемпотентен по `event_id`, потому что дубль после перезапуска релея неизбежен. Вопросы к продукту: допустима ли задержка события на минуты при сбое брокера (если да, outbox решает всё) и что хуже — дубль или потеря (для денег выбирают доставку «минимум один раз» плюс идемпотентность).

## Что спросят дальше

- Что произойдёт при `acks=all`, если в ISR осталась одна реплика? При `min.insync.replicas=2` запись отклоняется ошибкой `NotEnoughReplicas`, при `min.insync.replicas=1` принимается, но живёт на единственной копии. Поэтому для важных данных комбинация `acks=all` с `min.insync.replicas=2` и RF=3: потеря одного брокера не останавливает запись, а потеря двух останавливает её, но не данные.
- Чем идемпотентный продюсер отличается от транзакционного? Идемпотентный отсекает дубли одной сессии в одной партиции. Транзакционный (см. [[Транзакции Kafka и exactly-once]]) дополнительно делает атомарной запись в несколько партиций вместе с фиксацией offset консьюмера.
- Почему нельзя выбирать ключ случайным UUID? Порядок событий одного агрегата пропадёт, потому что они разъедутся по партициям. Ключ — идентификатор агрегата.
- Что делать с «горячим» ключом? Измельчить ключ (id заказа вместо id мерчанта), если порядок по мерчанту не нужен: см. [[Порядок событий]].
