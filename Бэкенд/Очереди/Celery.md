Конспект к собеседованию по Celery: архитектура, надёжная задача, типичные ошибки, составные задачи (канвасы) и альтернативы. Брокер под Celery — [[RabbitMQ]] или [[Redis]].

Разделы: [[#Архитектура]] · [[#Техника: надёжная задача]] · [[#Типичные ошибки]] · [[#Канвасы: составные задачи]] · [[#Альтернативы]] · [[#Бизнес-кейсы]] · [[#Что спросят дальше]]

**Суть.** Celery — фреймворк фоновых задач для Python. Он работает поверх брокера (broker: посредника, который хранит очереди сообщений; это RabbitMQ или Redis). Приложение кладёт описание задачи в очередь брокера, воркеры (worker: отдельные процессы, которые берут задачи из очереди и выполняют их) исполняют её, а результат при желании записывается в result backend (хранилище результатов). По умолчанию Celery подтверждает задачу брокеру **до** её выполнения. Это называется early ack («раннее подтверждение») и даёт гарантию at-most-once («не более одного раза»): если воркер упал посреди задачи, она потеряна. Противоположная гарантия — at-least-once («как минимум один раз»): задача не теряется, но может выполниться повторно. Про это чаще всего спрашивают на собеседовании.

## Архитектура

| Компонент | Роль | На что смотреть |
| --- | --- | --- |
| Broker | хранит очереди задач | RabbitMQ надёжнее. Redis проще, но у него есть visibility timeout (см. ниже) и риск потери задач, если Redis вытеснит ключи при нехватке памяти (eviction) или переключится на реплику (failover) |
| Worker | исполняет задачи | Выбирают pool (способ параллельной работы): `prefork` (отдельные процессы, для задач с вычислениями, CPU-bound), `gevent` или `eventlet` («зелёные» потоки, для задач с ожиданием сети и диска, I/O-bound), `threads` (потоки), `solo` (один поток, без параллелизма) |
| Result backend | статус и результат задачи | Часто не нужен: ставят `ignore_result=True`, иначе результаты копятся и засоряют Redis |
| Beat | планировщик периодических задач | Экземпляр должен быть **ровно один**, иначе задачи по расписанию будут дублироваться |
| Flower | веб-интерфейс мониторинга | Дополняют метрикой длины очередей в Prometheus (системе сбора метрик) |

Что значат термины из таблицы:

- Visibility timeout («время невидимости») — механизм Redis-брокера. Когда воркер берёт задачу, она остаётся в Redis, но невидима для других. Если воркер не подтвердил задачу за visibility timeout (по умолчанию 1 час), Redis считает воркера упавшим и отдаёт задачу другому. Для долгой задачи это значит дубль: первый воркер ещё работает, а второй уже начал то же самое.
- Eviction (вытеснение) — удаление ключей Redis при нехватке памяти (см. [[Redis#Персистентность, память, масштабирование]]). Если вытеснены ключи очереди, задачи пропадают.
- CPU-bound — задача упирается в процессор; от Python-потоков тут мало толку из-за GIL (Global Interpreter Lock: блокировка, из-за которой байт-код Python в один момент исполняет только один поток), поэтому берут процессы. I/O-bound — задача большую часть времени ждёт ответа сети или диска.

## Техника: надёжная задача

```python
@app.task(
    bind=True,
    acks_late=True,                   # ack ПОСЛЕ выполнения → at-least-once
    reject_on_worker_lost=True,       # воркер убит (OOM) → вернуть в очередь
    autoretry_for=(OperationalError, ConnectionError),  # только временные ошибки
    retry_backoff=True,               # 1, 2, 4, 8 … сек (потолок — retry_backoff_max)
    retry_backoff_max=600,
    retry_jitter=True,                # дефолт; случайная пауза от 0 до backoff
    max_retries=8,
    soft_time_limit=60, time_limit=90,
    ignore_result=True,
)
def charge_bonus(self, purchase_id: int) -> None:
    with transaction.atomic():
        # идемпотентность держит UNIQUE(purchase_id): exists() + create() две копии задачи пройдут обе
        Bonus.objects.get_or_create(purchase_id=purchase_id, defaults={...})

# Вызов — ТОЛЬКО после коммита транзакции, создавшей покупку
transaction.on_commit(lambda: charge_bonus.delay(purchase.id))
```

Что делает каждая настройка:

- `acks_late=True` — подтверждать задачу брокеру после выполнения, а не до. Если воркер упал посреди задачи, брокер не получил подтверждения и отдаст задачу другому воркеру. Это at-least-once. Цена: задача может выполниться дважды, поэтому она должна быть идемпотентной.
- Идемпотентность (idempotency) — повторный запуск с теми же входными данными не меняет результат. Здесь её обеспечивает ограничение `UNIQUE(purchase_id)` в базе: проверка `exists()` с последующим `create()` не защищает, потому что две копии задачи могут пройти проверку одновременно, а уникальный индекс пропустит только одну.
- `reject_on_worker_lost=True` — если процесс воркера убит снаружи (например, ядро завершило его из-за нехватки памяти, OOM, out of memory), вернуть задачу в очередь. Без этого флага даже при `acks_late` такая задача была бы потеряна.
- `autoretry_for=(...)` — автоматически повторять задачу при этих исключениях. Перечисляют только временные ошибки: недоступность базы или сети. Ошибка в коде повторами не лечится.
- `retry_backoff=True` — задержка между попытками растёт экспоненциально: 1, 2, 4, 8 секунд и так далее (backoff, «отступление»), чтобы не добивать упавшую зависимость. Потолок задаёт `retry_backoff_max=600` (десять минут).
- `retry_jitter=True` — джиттер (jitter): к паузе добавляется случайность (от 0 до рассчитанного backoff), чтобы сотни упавших задач не пошли повторять в один и тот же момент. Включён по умолчанию.
- `max_retries=8` — после восьми повторов задача окончательно падает с ошибкой.
- `soft_time_limit=60`, `time_limit=90` — мягкий и жёсткий лимит времени выполнения в секундах (разница — в разделе «Что спросят дальше»).
- `ignore_result=True` — не писать результат в result backend.
- `transaction.on_commit(...)` — функция Django: выполнить переданный код только после успешной фиксации (COMMIT) текущей транзакции. Если поставить задачу в очередь до коммита, воркер может стартовать раньше и не найти запись, которая ещё не видна, а при откате транзакции задача уже будет в очереди.

`reject_on_worker_lost` вместе с `acks_late` вернёт в очередь и ту задачу, которая сама роняет воркер (например, OOM на огромном файле). Такая задача будет возвращаться бесконечно. Поэтому ограничивай размер входных данных и следи за повторными доставками.

Настройки воркера:

- `worker_prefetch_multiplier=1` для долгих задач. Воркер по умолчанию заранее забирает у брокера пачку задач (prefetch); с долгими задачами один воркер наберёт пачку и будет держать её, пока другие простаивают.
- `worker_max_tasks_per_child` — перезапускать дочерний процесс после N задач, как защита от утечек памяти.

## Типичные ошибки

| Ошибка | Чем опасна | Лечение |
| --- | --- | --- |
| `delay()` внутри транзакции | Воркер стартует раньше COMMIT и не находит запись; либо транзакция откатилась, а задача уже ушла | `transaction.on_commit`; для надёжной гарантии — [[Когда двигать offset#Смежное: transactional outbox (таблица исходящих событий)\|outbox]] (задача сначала пишется в таблицу в той же транзакции, а отдельный процесс затем отправляет её в брокер) |
| Передача ORM-объекта в задачу | К моменту выполнения данные устарели; есть проблемы с сериализацией | Передавать id, свежие данные читать внутри задачи |
| Ранний ack по умолчанию | Падение или деплой во время выполнения: задача потеряна | `acks_late` плюс идемпотентность |
| Redis-брокер, долгие задачи или ETA | После `visibility_timeout` (1 час) задача отдаётся другому воркеру, получается дубль | Увеличить timeout; не ставить ETA на часы вперёд |
| `countdown` или `eta` на дни вперёд | Задачи висят в памяти воркера, при его перезапуске возможны сюрпризы | Таблица расписания в базе плюс периодический поллер (процесс, который опрашивает таблицу) |
| Одна очередь на всё | Массовая рассылка забивает очередь, и письмо сброса пароля ждёт час | Разные очереди по критичности (`task_routes`) и свои воркеры на каждую |
| Синхронное ожидание `.get()` внутри задачи | Взаимная блокировка (deadlock) пула воркеров: все воркеры ждут результатов задач, которым негде выполниться | Составные задачи: `chain`, `group`, `chord` |
| Повторы на любое исключение (`autoretry_for=(Exception,)`) | Баг в коде повторится 8 раз, добавив нагрузку на базу | Повторять только временные ошибки (см. [[Повторные попытки при падении базы]]) |

Пояснения: ETA (Estimated Time of Arrival) и `countdown` — параметры, которые откладывают запуск задачи на указанное время или на заданное число секунд. ORM-объект — запись базы данных в виде объекта (например, модель Django). `task_routes` — настройка, по которой задачи разных типов уходят в разные очереди.

## Канвасы: составные задачи

Канвас (canvas) — набор примитивов Celery, из которых собирается сложный процесс из нескольких задач.

```python
chain(download.s(url), parse.s(), save.s()).delay()             # последовательно
group(resize.s(img, size) for size in SIZES).delay()            # параллельно
chord(group(fetch.s(s) for s in shops), build_report.s()).delay()  # fan-out + сбор
```

- `chain` запускает задачи по очереди и передаёт результат каждой следующей.
- `group` запускает задачи параллельно.
- `chord` запускает группу задач параллельно (fan-out, «веер»), а когда все закончились, вызывает итоговую задачу и передаёт ей собранные результаты.
- `.s(...)` создаёт signature («подпись»): описание вызова задачи, который ещё не запущен.

Для `chord` нужен result backend: без него Celery не соберёт результаты. Длинные бизнес-процессы с компенсациями (откатом уже сделанных шагов при сбое) в Celery делать больно; для них есть движки управления процессами, например Temporal.

## Альтернативы

- **RQ, Dramatiq, arq** — более простые очереди задач. Dramatiq по умолчанию подтверждает задачу после выполнения. arq рассчитан на asyncio.
- **Temporal** — движок для долгих процессов с сохраняемым состоянием, таймерами на дни и сагами (цепочками шагов с компенсацией).
- **Очередь в PostgreSQL** ([[Блокировки#Техника: очередь задач на SKIP LOCKED|SKIP LOCKED]], библиотека procrastinate). Задача создаётся в той же транзакции, что и данные, поэтому проблемы dual write (двойной записи в два хранилища, из которых одно может не сохраниться) нет вообще.

## Бизнес-кейсы

- **«Клиент оплатил, а чек не пришёл».** Типичные причины: ранний ack и деплой во время выполнения задачи, либо `delay()` до коммита. Для фискальных чеков (это требование закона) нужны outbox, `acks_late`, идемпотентность по id оплаты и ночная сверка «оплаты без чека».
- **Массовая рассылка на 1 млн пользователей.** Нельзя ставить миллион задач разом. Лучше задача-нарезчик, которая ставит пачки по 1000 в отдельную очередь с ограничением скорости. `rate_limit='100/s'` в Celery действует на **каждый воркер**, а не на всех сразу: десять воркеров дадут 1000 задач в секунду. Общий лимит провайдера держат через счётчик в Redis ([[Redis#Техника: ограничитель частоты запросов (rate limiter)]]). Иначе письма сброса пароля и транзакционные уведомления встанут в очередь за маркетинговой рассылкой, а провайдер заблокирует отправителя за превышение лимита.
- **Ночной отчёт по beat выполнился дважды.** Причина: после релиза работали два пода (pod: минимальная единица запуска в Kubernetes, обычно один контейнер) с beat. Защита: один экземпляр beat (отдельный deployment с `replicas: 1`) плюс сама задача берёт advisory lock (программную блокировку PostgreSQL по числовому ключу) или проверяет, нет ли уже отчёта за эту дату.

## Что спросят дальше

- Чем отличается `soft_time_limit` от `time_limit`? Soft бросает исключение `SoftTimeLimitExceeded` внутри задачи, и она может прибраться: закрыть файлы, откатить изменения. Hard (`time_limit`) просто убивает процесс воркера, без возможности прибраться.
- Prefork или gevent? Prefork подходит для задач с тяжёлыми вычислениями: отдельные процессы обходят GIL. Gevent подходит для сотен параллельных HTTP-вызовов, где задачи в основном ждут ответа.
- Что будет с задачами при деплое? Kubernetes посылает воркеру сигнал SIGTERM (вежливая просьба завершиться), и воркер начинает warm shutdown («мягкая остановка»): перестаёт брать новые задачи и доделывает текущие. Kubernetes ждёт `terminationGracePeriodSeconds` (по умолчанию 30 секунд) и затем убивает процесс, так что долгие задачи прервутся. С `acks_late` они вернутся в очередь, без него пропадут. Grace period ставят больше самой долгой задачи.
- Как масштабировать? По длине очереди и времени ожидания (автомасштабирование через KEDA: Kubernetes Event-Driven Autoscaling), отдельные пулы воркеров на разные очереди. Помнить про лимит соединений к базе: каждый воркер открывает свои.
