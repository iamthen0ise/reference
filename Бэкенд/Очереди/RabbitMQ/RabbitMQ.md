**Суть.** RabbitMQ — брокер сообщений (посредник, который принимает сообщения от одних программ и передаёт другим) на протоколе AMQP 0-9-1 (Advanced Message Queuing Protocol). Сильные стороны RabbitMQ — гибкая маршрутизация и очереди задач с поштучным подтверждением. Главное отличие от Kafka в том, что сообщение здесь живёт до подтверждения, а не до истечения срока хранения: консюмер прочитал, подтвердил, и брокер забыл о сообщении.

## Модель AMQP 0-9-1

Путь сообщения состоит из четырёх шагов.

1. Продюсер (программа-отправитель) пишет сообщение не в очередь, а в **exchange** («обменник»): точку входа, которая сама ничего не хранит, а только решает, куда сообщение направить.
2. Exchange раскладывает сообщение по **очередям** (queue) согласно правилам привязки — **binding**. Binding связывает exchange с очередью и содержит ключ или шаблон. Сообщение при отправке несёт **routing key** («ключ маршрутизации», строка вроде `order.created`), и exchange сравнивает её с binding. Подробно — в [[Exchange и маршрутизация]].
3. Консюмер (программа-получатель) получает сообщения из очереди «пушем»: брокер сам отправляет их, консюмеру не нужно опрашивать очередь. Сколько сообщений брокер может отдать вперёд, регулирует **prefetch** ([[Конкурентность и порядок в RabbitMQ#Prefetch и равномерная нагрузка]]).
4. Консюмер подтверждает каждое сообщение — **ack** (acknowledgement, «принято и обработано»). После ack брокер удаляет сообщение. Что происходит без ack, разобрано в [[Надёжная доставка в RabbitMQ]].

Ещё три понятия нужны, чтобы читать остальные страницы. **Соединение** (connection) — одно TCP-соединение с брокером; внутри него открывают лёгкие **каналы** (channel), по которым и идут публикации и подтверждения. **Virtual host** (vhost) — изолированное «пространство имён» брокера со своими exchange и очередями; по умолчанию это `/`. **Свойства сообщения** (properties) — `delivery_mode`, `message_id`, `correlation_id`, `reply_to`, `expiration`, `headers` и другие поля, которые едут вместе с телом.

## Как запускать примеры

Все примеры на этих страницах выполнялись на реальном брокере, вывод в блоках «Вывод» снят запуском, а не написан по памяти.

- RabbitMQ 4.4.1 (Erlang/OTP 29), образ `rabbitmq:4-management`, порты 5673 (AMQP) и 15673 (management).
- Python-клиент — `aio-pika` 10.2.3 (асинхронная обёртка над AMQP, строится на `aiormq`).

```bash
docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:4-management
docker exec rabbit rabbitmq-plugins enable rabbitmq_consistent_hash_exchange   # нужен для одной страницы
uv run --with aio-pika python script.py
```

> [!warning] Ловушка версии
> В версиях 4.x часть привычного поведения выключена по умолчанию. Очередь, которая не durable и не exclusive, объявить нельзя: брокер закрывает соединение ошибкой `Feature transient_nonexcl_queues is deprecated`. Глобальный `basic.qos` (`global=True`) тоже запрещён, а зеркалируемые classic-очереди удалены. Старые примеры с `auto_delete=True` и без `durable=True` на новом брокере не заработают.

Сам `aio_pika` ведёт себя не так, как можно ожидать: `exchange.publish()` по умолчанию вызывается с `mandatory=True`, а `channel.set_qos()` без вызова оставляет prefetch неограниченным. Об этом — в соответствующих страницах.

## Kafka vs RabbitMQ

|  | Kafka | RabbitMQ |
| --- | --- | --- |
| Модель | распределённый лог, консюмер сам запрашивает данные (pull) | брокер с очередями, брокер сам отправляет сообщения (push) |
| После чтения | сообщение остаётся на срок хранения (retention), его можно перечитать | удаляется после ack (кроме Streams) |
| Подтверждение | offset (номер позиции в логе) на партицию | ack на каждое сообщение |
| Порядок | в пределах партиции | в очереди при одном консюмере |
| Маршрутизация | по топику и ключу | exchange, шаблоны, заголовки |
| Отложенные сообщения, приоритеты | нет из коробки | TTL и DLX, priority queues (очереди с приоритетом), плагин delayed |
| Пропускная способность | сотни тысяч – миллионы сообщений в секунду | десятки тысяч сообщений в секунду на очередь |
| Когда брать | потоковая передача событий (event streaming), CDC (Change Data Capture, трансляция изменений из базы), аналитика, event sourcing (хранение состояния как цепочки событий), несколько независимых читателей | очереди задач, RPC (вызов удалённой процедуры через сообщения), сложная маршрутизация, поштучные повторы |

Смежное: **RabbitMQ Streams** — append-only лог (запись только в конец) с чтением по offset. Это значит, что внутри RabbitMQ появилась семантика, похожая на Kafka: сообщения не удаляются после ack, а читаются с любой позиции ([[Типы очередей RabbitMQ#Stream]]).

Практические различия видны в повседневных вещах. Подтверждение в Kafka — это сдвиг offset ([[Когда двигать offset]]), и один «ядовитый» message блокирует партицию, пока его не обойдут; в RabbitMQ ack относится к одному сообщению, и повтор с паузой, перекладывание в DLQ или параллельная обработка соседних сообщений — штатные приёмы. Зато в Kafka легко перечитать историю, а в RabbitMQ после ack сообщения нет.

## Бизнес-кейсы

- **Генерация PDF-счетов и отправка писем.** Классическая очередь задач: у задач разная длительность, повтор нужен для каждой отдельно, масштабируется воркерами, порядок не важен. Rabbit подходит лучше Kafka. Одно «тяжёлое» сообщение в Kafka тормозит всю партицию (head-of-line blocking, блокировка головой очереди), а в Rabbit занят только один воркер. Воркер (worker) здесь — процесс-консюмер, который берёт задачи из очереди и выполняет их.
- **VIP-клиенты должны получать уведомления раньше.** Отдельная очередь с выделенными воркерами надёжнее, чем priority queue: приоритеты перестают работать при большом prefetch, потому что консюмер уже набрал пачку сообщений без учёта приоритета.
- **«Напомни об оплате через 24 часа».** TTL с DLX или плагин delayed (он не реплицируется и не работает с quorum queues) работают, но держат миллионы сообщений в брокере сутками и плохо отменяются. Для долгих задержек надёжнее таблица `scheduled_jobs` в базе данных и поллер (процесс, который периодически опрашивает таблицу) с `SKIP LOCKED` (запрос пропускает строки, уже взятые другим процессом; [[Блокировки#Техника: очередь задач на SKIP LOCKED]]). Задачу в такой таблице можно отменить, перенести и посмотреть. Короткие задержки (секунды и минуты) удобно делать лестницей очередей ([[Повторы и DLQ в RabbitMQ#Лестница задержек]]).
- **«Заказ оплачен — надо обновить склад, отправить письмо и выставить событие аналитике».** Один exchange типа topic и по очереди на каждого получателя: каждая служба читает свою копию независимо, а новую можно добавить без правок публикующего кода ([[Exchange и маршрутизация#Topic]]).

## Что спросят дальше

- Что будет, если консюмеры не успевают? Очередь растёт в памяти и на диске, срабатывает memory alarm или disk alarm (сигнал о нехватке памяти или места), и брокер блокирует продюсеров (flow control, управление потоком). Защита: `x-max-length` (предел длины очереди) вместе с `overflow: reject-publish` (при переполнении отклонять новые публикации) и мониторинг длины очереди. Подробно — [[Эксплуатация RabbitMQ#Алармы и flow control]] и [[Типы очередей RabbitMQ#Лимиты длины и x-overflow]].
- Как сделать RPC через Rabbit? Клиент указывает в запросе `reply_to` (имя очереди для ответа, либо встроенный direct reply-to) и `correlation_id` (идентификатор, по которому клиент сопоставит ответ со своим запросом). Оговорки и грабли — [[RPC через RabbitMQ]].
- Почему долгая задача «вернулась» в очередь через полчаса? Из-за `consumer_timeout` (по умолчанию 30 минут): если за это время нет ack, брокер закрывает канал и возвращает сообщение в очередь. Для долгих задач поднимают таймаут на очереди либо подтверждают раньше, сохраняя прогресс в базе ([[Эксплуатация RabbitMQ#Таймаут подтверждения]]).
- Exactly-once («ровно один раз»)? Нет, такой гарантии нет. Используют at-least-once плюс идемпотентность по `message_id`: обработчик запоминает идентификаторы уже обработанных сообщений и пропускает дубль ([[Конкурентность и порядок в RabbitMQ#Идемпотентный консьюмер]]). То же верно для [[Когда двигать offset|Kafka и базы данных]].
- Как не потерять сообщение при публикации из обработчика запроса? Нельзя записать в базу и отправить в брокер «одной транзакцией»; пишут событие в таблицу outbox в той же транзакции и отправляют отдельным воркером ([[Надёжная доставка в RabbitMQ#Transactional outbox для публикации]]).
- Как сохранить порядок и масштабироваться? Порядок даёт одна очередь с одним активным консюмером; по ключу — consistent hash exchange или single active consumer на очередь каждого шарда ([[Конкурентность и порядок в RabbitMQ#Порядок по ключу]]).
