## Суть

Ошибки обработки бывают двух видов. **Временные** (база недоступна, таймаут апстрима) проходят сами, и повтор с паузой их лечит. **Постоянные** (битый JSON, нарушен инвариант) повтором не лечатся, и сообщение надо сразу отложить на ручной разбор. Если сбой затрагивает все сообщения (упала база), отправлять их в DLQ не нужно: туда уедет весь поток. Консюмер лучше остановить (прекратить брать сообщения) и ждать с нарастающей паузой, а DLQ оставить для ошибок, привязанных к конкретному сообщению ([[Повторные попытки при падении базы]]).

В RabbitMQ нет встроенного «повторить через 30 секунд». Её собирают из двух механизмов. **DLX** (dead letter exchange, «обменник мёртвых писем») — exchange, куда брокер сам перенаправляет сообщения, которые не удалось обработать: их отклонили через `nack` или `reject` с `requeue=False`, у них истёк TTL, очередь переполнилась или превышен `delivery-limit` у quorum. **TTL** (time to live) — время жизни сообщения в очереди; по его истечении оно считается «мёртвым». Из них собирается схема: сообщение умирает в очереди ожидания и тем самым возвращается в рабочую очередь.

## Защита от бесконечного цикла

Самая частая ошибка начинающих: `nack(requeue=True)` на любую ошибку. Сообщение мгновенно возвращается в очередь, консюмер получает его снова, падает, и круг замыкается. Процессор и сеть заняты, остальные сообщения ждут, а логи забиты одной и той же ошибкой.

**Задача.** Измерить, что делает «ядовитое» сообщение с возвратом без паузы.

```python
async def run(kind, args):
    name = f"demo.poison.{kind}"
    q = await ch.declare_queue(name, durable=True, arguments=args)
    await ch.default_exchange.publish(Message(b"bad", delivery_mode=2), routing_key=name)
    n = 0
    async def h(m):
        nonlocal n
        n += 1
        await m.nack(requeue=True)      # неправильный вариант: возврат без паузы
    await q.consume(h)
    # ... ждём 3 секунды и печатаем n

await run("classic", {})
await run("quorum", {"x-queue-type": "quorum"})
await run("quorum5", {"x-queue-type": "quorum", "x-delivery-limit": 5})
```

```text title="Вывод"
classic  доставок за 3.0 с: 10543; в очереди осталось: 0
quorum   доставок за 3.0 с: 267; в очереди осталось: 0
quorum5  доставок за 3.0 с: 238; в очереди осталось: 0
```

Одно сообщение было доставлено более 10 тысяч раз за три секунды на classic-очереди. «В очереди осталось: 0» не значит, что сообщение исчезло: оно в этот момент как раз выдано консюмеру (unacked), счётчик показывает только готовые к выдаче. На quorum цикл медленнее (репликация), но не остановился: `x-delivery-limit: 5` не сработал, потому что `basic.nack(requeue=True)` не увеличивает счётчик доставок ([[Типы очередей RabbitMQ#Delivery-limit у quorum]]).

Защита состоит из нескольких слоёв, и каждый закрывает свою дыру.

1. Сообщение не возвращают в очередь немедленно: временную ошибку отправляют на повтор через очередь ожидания (ниже), а не `requeue=True`.
2. Число попыток ограничено: счётчик берут из `x-death` либо из собственного заголовка `attempt`; после последней попытки сообщение уходит в parking lot.
3. Постоянные ошибки (валидация, неизвестный тип события) сразу в parking, без повторов.
4. На quorum-очередях задают `x-delivery-limit` и DLX: это страховка на случай, когда консюмер падает (процесс убит) раньше, чем успел решить судьбу сообщения. Потеря консюмера и `reject(requeue=True)` в лимит засчитываются.
5. Консюмер ловит исключение на границе сообщения и не завершает цикл потребления.

> [!warning] Грабли
> `nack(requeue=True)` допустим для одного случая: консюмер сам не может обработать (останавливается, получил SIGTERM) и честно возвращает сообщение другому. Для ошибок обработки он вреден.

## Повтор с задержкой через DLX и TTL

Схема из трёх очередей:

```text
work.queue     x-dead-letter-exchange = retry.dlx
               (nack requeue=False → сообщение уходит в DLX)

retry.queue    x-message-ttl = 1000
               x-dead-letter-exchange = work.exchange
               (никто не читает; через 1 с TTL истёк → назад в work)

parking.queue  сюда после N попыток
```

Как это работает по шагам. Консюмер не смог обработать сообщение из `work.queue` и делает `nack(requeue=False)`, брокер отправляет сообщение в `retry.dlx`, а оттуда в `retry.queue`. В `retry.queue` у сообщения TTL, и никто эту очередь не читает: это и есть пауза перед повтором. Когда TTL истёк, сообщение умирает, а DLX у `retry.queue` указывает на `work.exchange`, так что оно возвращается в рабочую очередь. Брокер при каждом перенаправлении дописывает в `x-death` запись со счётчиком, по которому консюмер понимает, сколько попыток уже было.

**Задача.** Две задачи: одна успешна на третьей попытке, вторая падает всегда и должна уехать в parking после трёх.

```python
MAX_ATTEMPTS = 3
work = await ch.declare_queue("work.queue", durable=True, arguments={
    "x-queue-type": "quorum",
    "x-dead-letter-exchange": "retry.dlx", "x-dead-letter-routing-key": "retry"})
retry = await ch.declare_queue("retry.queue", durable=True, arguments={
    "x-queue-type": "quorum", "x-message-ttl": 1000,
    "x-dead-letter-exchange": "work.exchange", "x-dead-letter-routing-key": "work"})
park = await ch.declare_queue("parking.queue", durable=True, arguments={"x-queue-type": "quorum"})
await work.bind(work_ex, "work"); await retry.bind(retry_ex, "retry")

def attempts(m):
    deaths = m.headers.get("x-death") or []
    return sum(d["count"] for d in deaths if d["queue"] == "work.queue")

async def worker(m):
    n = attempts(m)
    if m.body == b"ok-on-3" and n >= 2:
        await m.ack(); return                                  # успех
    if n + 1 >= MAX_ATTEMPTS:
        await ch.default_exchange.publish(                    # лимит: в parking
            Message(m.body, headers={"reason": "max attempts", "attempts": n + 1}, delivery_mode=2),
            routing_key="parking.queue")
        await m.ack(); return
    await m.nack(requeue=False)                                # ошибка: в DLX -> retry
```

```text title="Вывод"
[ 0.0 с] ok-on-3: попытка 1, x-death count по work.queue = 0
[ 0.0 с]   ошибка -> nack(requeue=False) -> DLX
[ 0.1 с] always-bad: попытка 1, x-death count по work.queue = 0
[ 0.1 с]   ошибка -> nack(requeue=False) -> DLX
[ 1.1 с] ok-on-3: попытка 2, x-death count по work.queue = 1
[ 1.1 с]   ошибка -> nack(requeue=False) -> DLX
[ 1.1 с] always-bad: попытка 2, x-death count по work.queue = 1
[ 1.1 с]   ошибка -> nack(requeue=False) -> DLX
[ 2.2 с] ok-on-3: попытка 3, x-death count по work.queue = 2
[ 2.2 с]   успех -> ack
[ 2.2 с] always-bad: попытка 3, x-death count по work.queue = 2
[ 2.2 с]   лимит -> в parking.queue, ack оригинала
parking.queue: b'always-bad' {'attempts': 3, 'reason': 'max attempts'}
```

Пауза между попытками около секунды (TTL у `retry.queue`), счётчик растёт на единицу при каждом круге, а ядовитое сообщение после третьей попытки лежит в `parking.queue` с причиной. Порядок действий при отправке в parking важен: сначала публикация (с подтверждением) и только потом `ack` оригинала. Если сделать наоборот и упасть между ними, сообщение потеряется.

> [!warning] Грабли
> У `retry.queue` не должно быть консюмеров: любой из них заберёт сообщение до истечения TTL, и пауза пропадёт. Второе: TTL — общий для очереди, и менять его для каждой попытки нельзя (см. лестницу ниже). Третье: если DLX указывает на несуществующий exchange, сообщения при смерти исчезнут без ошибки.

## Заголовок x-death

Каждый раз, когда сообщение умирает и перенаправляется, брокер ведёт запись в заголовке `x-death`: это список словарей, по одному на пару «очередь и причина». В записи есть `queue`, `reason` (`rejected`, `expired`, `maxlen`, `delivery_limit`), `exchange`, `routing-keys`, `time` и `count` — сколько раз сообщение умирало именно по этой паре. В примере выше сообщение, уезжающее из `work.queue` по `nack`, попадает в запись `{queue: work.queue, reason: rejected, count: N}`, а истёкшее в `retry.queue` — в запись `{queue: retry.queue, reason: expired, count: N}`. Поэтому число попыток считают, суммируя `count` по записям нужной очереди, как в `attempts()`.

```text title="Вывод"
[{'count': 1, 'reason': 'delivery_limit', 'queue': 'demo.w', 'time': datetime.datetime(2026, 11, 19, 18, 40, 45, tzinfo=datetime.timezone.utc), 'exchange': '', 'routing-keys': ['demo.w']}]
```

Это `x-death` сообщения, которое вылетело из quorum-очереди по `delivery-limit` ([[Типы очередей RabbitMQ#Delivery-limit у quorum]]); у сообщения, умершего по `nack`, будет `reason: rejected`.

> [!warning] Грабли
> Опираться на `x-death` как на единственный счётчик опасно: заголовок хранится у сообщения, а если консюмер перепубликует копию (как в лестнице ниже), он начнётся заново. Поэтому при ручной перепубликации счётчик ведут в собственном заголовке `attempt`.

## Лестница задержек

Одна `retry.queue` даёт одну паузу, а на практике нужна нарастающая: 5 секунд, 30 секунд, 5 минут. TTL задаётся на очереди, поэтому делают несколько очередей ожидания, по одной на ступень, и консюмер сам выбирает, в какую отправить: ступень равна номеру попытки.

**Задача.** Три ступени (в бою 5 с, 30 с, 5 мин; в примере 0.5 с, 1 с, 2 с), после последней сообщение уходит в parking.

```python
LADDER = [0.5, 1.0, 2.0]
for i, delay in enumerate(LADDER):
    q = await ch.declare_queue(f"retry.{i}", durable=True, arguments={
        "x-queue-type": "quorum", "x-message-ttl": int(delay * 1000),
        "x-dead-letter-exchange": "work.exchange", "x-dead-letter-routing-key": "work"})
    await q.bind(retry_ex, f"retry.{i}")

async def worker(m):
    attempt = int(m.headers.get("attempt", 0))
    # ... обработка упала
    if attempt >= len(LADDER):
        await ch.default_exchange.publish(
            Message(m.body, headers={"attempt": attempt, "reason": "ladder exhausted"}),
            routing_key="parking.queue")
        await m.ack(); return
    # сначала публикуем в retry (confirm), потом ack оригинала
    await retry_ex.publish(Message(m.body, headers={"attempt": attempt + 1}, delivery_mode=2),
                           routing_key=f"retry.{attempt}")
    await m.ack()
```

```text title="Вывод"
[ 0.0 с] попытка 1: падаем
[ 0.6 с] попытка 2: падаем
[ 1.6 с] попытка 3: падаем
[ 3.6 с] попытка 4: падаем
   лестница кончилась -> parking
parking: b'job' {'attempt': 3, 'reason': 'ladder exhausted'}
```

Интервалы между попытками растут (0.6, 1.0, 2.0 секунды), после четвёртой сообщение лежит в parking. В этой схеме консюмер сам решает судьбу сообщения (повтор, ступень, parking), поэтому он различает временные и постоянные ошибки: постоянную сразу в parking, временную по лестнице.

> [!warning] Грабли
> Перепубликация и `ack` оригинала — два действия, и между ними возможен сбой. Порядок «сначала publish с confirm, потом ack» даёт дубль при сбое, а обратный порядок — потерю. Дубль безопаснее, поэтому консюмер идемпотентен ([[Конкурентность и порядок в RabbitMQ#Идемпотентный консьюмер]]). Ещё одна ловушка: сообщение, ушедшее в retry, выпадает из порядка, и следующие события того же ключа обработаются раньше ([[Конкурентность и порядок в RabbitMQ#Порядок по ключу]]).

## Parking lot

Parking lot («парковка») — очередь, куда складывают сообщения, которые не получилось обработать автоматически. Она нужна не для обработки, а для разбора человеком: у неё есть владелец, алерт на размер и порядок действий. В сообщение при парковке кладут причину, число попыток и исходные exchange и routing key, чтобы его можно было вернуть в работу. Вернуть сообщение после исправления бага можно скриптом, который читает `parking.queue` и публикует в исходный exchange, либо shovel-ом; выбросить стоит осознанно, с записью причины.

DLQ в смысле «DLX с очередью на конце» и parking lot — одно и то же по сути, различие в способе попадания: в DLQ сообщение попадает автоматически по DLX, а в parking консюмер кладёт его осознанно после решения. Для нужд разбора разница несущественна, главное, чтобы очередь не росла незамеченной.

## Задержка на уровне сообщения и очередь голов

Вместо `x-message-ttl` у очереди TTL можно задать у каждого сообщения полем `expiration`. Тогда можно было бы одной очередью обслужить разные задержки, но это не работает: брокер проверяет истечение только у сообщения, стоящего первым в очереди. Сообщение с коротким TTL, которое стоит за сообщением с длинным TTL, будет ждать, пока умрёт первое.

**Задача.** Опубликовать подряд сообщение с TTL 3 секунды и с TTL 0.5 секунды в одну очередь.

```python
q = await ch.declare_queue("demo.hol", durable=True, arguments={
    "x-dead-letter-exchange": "", "x-dead-letter-routing-key": "demo.dead"})
await ch.default_exchange.publish(Message(b"long TTL 3s", expiration=3), routing_key="demo.hol")
await ch.default_exchange.publish(Message(b"short TTL 0.5s", expiration=0.5), routing_key="demo.hol")
```

```text title="Вывод"
[3.0 с] в dead: long TTL 3s
[3.0 с] в dead: short TTL 0.5s
```

Короткое сообщение должно было умереть через полсекунды, а умерло через три, одновременно с головным. Вот почему лестницу делают отдельными очередями с TTL на очереди, где все сообщения ждут одинаково и порядок смерти совпадает с порядком поступления.

> [!warning] Грабли
> Per-message TTL подходит только как верхний предел «сообщение не нужно, если не взято за N секунд», а не как точный таймер. Для задержек его не используют.

## Плагин delayed message

Плагин `rabbitmq_delayed_message_exchange` (тип exchange `x-delayed-message`) принимает заголовок `x-delay` в миллисекундах и доставляет сообщение в очереди по истечении этого времени. Удобно тем, что одна схема подходит для любых задержек и нет лестницы очередей. Ограничения серьёзные: плагин сторонний и в образ `rabbitmq:4-management` не входит (на стенде его нет, поэтому примера с выводом здесь нет), отложенные сообщения хранятся на одном узле, не реплицируются и теряются вместе с узлом, масштабируется плагин плохо, а отменить отложенное сообщение нельзя. Поэтому для платежей и долгих задержек (часы и сутки) надёжнее таблица `scheduled_jobs` в базе с поллером на `SKIP LOCKED` ([[RabbitMQ#Бизнес-кейсы]]). Для задержек в секунды и минуты хватает лестницы очередей.

## Бизнес-кейс

Сервис отправки писем зовёт внешний SMTP-провайдер, который временами отвечает 503. Консюмер при временной ошибке отправляет письмо по лестнице 5 секунд, 30 секунд, 5 минут. На битом адресе (постоянная ошибка) письмо сразу уходит в `emails.parking`. Если провайдер лежит целиком, все сообщения не должны идти в parking: консюмер видит серию подряд идущих ошибок, останавливает потребление на минуту и пробует снова, а parking остаётся для отдельных писем. На размер `emails.parking` настроен алерт, а раз в день ответственный разбирает его: чинит адреса и возвращает письма в работу.

## Что спросят дальше

- Как реализовать повтор через 30 секунд? Очередь ожидания с `x-message-ttl: 30000` и DLX обратно в рабочий exchange; консюмер делает `nack(requeue=False)` или сам публикует в очередь ожидания.
- Как не зациклить сообщение? Не возвращать его с `requeue=True` без паузы, ограничить число попыток по `x-death` или собственному счётчику, на quorum задать `x-delivery-limit` и DLX.
- Что такое x-death? Заголовок, куда брокер записывает каждую смерть сообщения (очередь, причина, число раз, время).
- Чем DLQ отличается от parking lot? По назначению ничем: очередь для сообщений, которые нужно разобрать вручную; в DLQ они попадают автоматически через DLX, в parking консюмер кладёт их сам.
- Почему сообщение с коротким TTL не умирает вовремя? Брокер проверяет только голову очереди; отдельные задержки делают отдельными очередями.
- Когда нужен плагин delayed? Для произвольных коротких задержек, если приемлемы его ограничения (нет репликации, нельзя отменить). Для долгих и критичных задержек — таблица в базе и поллер.
