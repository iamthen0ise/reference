## Суть

Масштабировать обработку очереди просто: запустить ещё консюмеров. Брокер раздаёт сообщения по очереди (round-robin), каждое получает один консюмер. Это называют competing consumers («конкурирующие потребители»). Но две вещи подстерегают: сколько сообщений брокер выдаёт консюмеру вперёд (prefetch) и что порядок обработки перестаёт совпадать с порядком публикации.

- Одна очередь и один консюмер дают строгий порядок, но не масштабируются.
- Несколько консюмеров на одной очереди дают масштаб, но порядка нет.
- Порядок по ключу при масштабе дают только схемы с несколькими очередями или single active consumer.

## Prefetch и равномерная нагрузка

**Prefetch** (`basic.qos`, «предвыборка») — сколько неподтверждённых сообщений брокер даёт консюмеру одновременно. Без этого лимита брокер вываливает в первого же консюмера всю очередь, остальные простаивают. Prefetch — главный рычаг backpressure (обратного давления: медленный консюмер получает меньше, а не захлёбывается) и равномерной нагрузки. Обратите внимание на две особенности. У aio-pika prefetch по умолчанию не ограничен (0 значит «без лимита»), пока вы сами не вызовете `set_qos`. В RabbitMQ 4.x глобальный `basic.qos` (`global=True`, лимит на весь канал) запрещён: лимит действует на каждого консюмера отдельно.

**Задача.** Два консюмера: A медленный (0.2 с на сообщение) и подключается первым, B быстрый (0.02 с) и подключается через 0.3 с. В очереди 20 сообщений.

```python
async def start(name, delay, join_delay):
    await asyncio.sleep(join_delay)
    ch = await conn.channel(); await ch.set_qos(prefetch_count=prefetch)
    q = await ch.declare_queue("demo.jobs", durable=True, arguments={"x-queue-type": "quorum"})
    async def h(m):
        await asyncio.sleep(delay); counts[name] += 1
        await m.ack()
    await q.consume(h)

await start("A (медленный)", 0.2, 0)
await start("B (быстрый)", 0.02, 0.3)
# prefetch = 0, затем 1, затем 5
```

```text title="Вывод"
prefetch=0 (без лимита): {'A (медленный)': 20}
prefetch=1             : {'A (медленный)': 4, 'B (быстрый)': 16}
prefetch=5             : {'A (медленный)': 10, 'B (быстрый)': 10}
```

Без лимита A забрал все двадцать сообщений до появления B и один обрабатывал их по 0.2 секунды, а быстрый B простоял. С `prefetch=1` каждый консюмер получает следующее сообщение только после подтверждения предыдущего, поэтому быстрый B обработал 16 из 20. С `prefetch=5` картина промежуточная: A успел набрать пачку из пяти и «потащил» её.

Как выбирать значение. Для долгих, неоднородных задач ставят маленький prefetch (1–10), чтобы нагрузка уравновешивалась. Для коротких однородных задач prefetch увеличивают (десятки и сотни): иначе каждое сообщение ждёт сетевого круга «ack, затем следующее», и пропускная способность упирается в задержку сети. Prefetch также ограничивает память консюмера: все выданные сообщения лежат у него.

> [!warning] Грабли
> Prefetch и приоритеты несовместимы: консюмер уже набрал пачку без учёта приоритета, поэтому высокоприоритетное сообщение ждёт, пока он её разберёт. Для VIP делают отдельную очередь. И ещё: если консюмер обрабатывает сообщения параллельно (много задач на один канал), prefetch должен быть не меньше числа параллельных задач, иначе часть из них будет простаивать.

## Порядок и конкурирующие консюмеры

Порядок ломается в двух случаях.

**Несколько консюмеров.** Быстрый консюмер заканчивает более позднее сообщение раньше. Порядок публикации не равен порядку завершения.

**Возврат сообщения.** `nack(requeue=True)` или потеря консюмера возвращают сообщение на прежнее место очереди, но следующие сообщения консюмер к этому моменту мог уже получить и обработать.

**Задача.** Показать оба случая. В первом два консюмера с `prefetch=1`, и `m1` обрабатывается долго. Во втором консюмер один, и `m1` при первой попытке возвращается через `nack`.

```python
delays = {"m1": 0.4}   # m1 обрабатывается долго, остальные по 0.05 с
async def h(m):
    await asyncio.sleep(delays.get(m.body.decode(), 0.05)); order.append(m.body.decode()); await m.ack()
# два консюмера A и B на одной очереди, prefetch=1

# второй случай: один консюмер, nack(requeue=True) при первой доставке m1
```

```text title="Вывод"
два консюмера, prefetch=1, порядок завершения: ['m2', 'm3', 'm4', 'm5', 'm6', 'm1']
один консюмер, prefetch=3, m1 вернули через nack(requeue=True): ['m1(nack)', 'm2', 'm3', 'm1', 'm4', 'm5', 'm6']
один консюмер, prefetch=1, m1 вернули через nack(requeue=True): ['m1(nack)', 'm1', 'm2', 'm3', 'm4', 'm5', 'm6']
```

В первом случае `m1` обрабатывался у консюмера A, пока B разобрал остальные пять: в результате `m1` последний. Во втором случае с `prefetch=3` консюмер уже держал `m2` и `m3` на руках, когда `m1` вернулся, и обработал `m1` после них. С `prefetch=1` возврат сохранил порядок: следующее сообщение не выдаётся, пока не подтверждено текущее.

Отсюда практический вывод: порядок не гарантируется ничем, кроме «один активный консюмер и prefetch=1 (или обработка строго по одному)». Если порядок нужен, не опираться на «обычно получается», а проектировать схему.

> [!warning] Грабли
> Приём «prefetch=1 ради порядка» работает только при одном консюмере на очередь и без параллельной обработки внутри него. Любой параллелизм (несколько воркеров, `asyncio.gather` внутри хендлера) порядок ломает. Ещё одно следствие: сообщение, ушедшее в retry или DLQ, выпадает из порядка ([[Повторы и DLQ в RabbitMQ#Лестница задержек]]), поэтому для событий одного агрегата консюмер использует версию агрегата и отбрасывает устаревшее. Те же правила, что и для [[Порядок событий|Kafka]].

## Single active consumer

**Single active consumer** (SAC, «единственный активный консюмер») — режим очереди `x-single-active-consumer: true`: на очередь может быть подписано несколько консюмеров, но сообщения получает только один, а остальные ждут на случай его падения. Так получают порядок и отказоустойчивость одновременно: если активный консюмер упал, брокер сам передаёт очередь следующему.

**Задача.** Три консюмера на одной SAC-очереди; пять сообщений; затем активный консюмер «падает»; ещё пять сообщений.

```python
args = {"x-queue-type": "quorum", "x-single-active-consumer": True}
await ch.declare_queue("demo.sac", durable=True, arguments=args)
# три соединения A, B, C, у каждого консюмер на эту очередь с prefetch=1
# публикуем m1..m5, закрываем соединение активного, публикуем m6..m10
```

```text title="Вывод"
после 5 сообщений : {'A': ['m1', 'm2', 'm3', 'm4', 'm5']}
упал A; после ещё 5: {'A': ['m1', 'm2', 'm3', 'm4', 'm5'], 'B': ['m6', 'm7', 'm8', 'm9', 'm10']}
```

Все пять сообщений получил один A, хотя консюмеров трое. После падения A очередь перешла к B, и порядок на всём отрезке сохранился.

SAC даёт порядок на одну очередь, но не масштабирует: обрабатывает всегда один консюмер. Чтобы масштабироваться и сохранить порядок по ключу, нужна не одна очередь, а несколько.

> [!warning] Грабли
> Порядок при переключении между консюмерами не абсолютный: unacked-сообщения упавшего консюмера возвращаются в очередь и достаются новому активному, а он мог уже получить следующие. Это тот же случай возврата, что выше. Кроме того, SAC не помогает, если обработка внутри консюмера параллельная.

## Порядок по ключу

Чтобы масштабироваться и сохранить порядок внутри ключа (заказа, клиента), сообщения нужно раскладывать так, чтобы все события одного ключа попадали в одну очередь, а очередей было несколько. Это аналог партиций Kafka (партиция — независимая часть топика со своим порядком сообщений). В RabbitMQ это делает плагин **consistent hash exchange** (exchange типа `x-consistent-hash`): он по хешу routing key (или заголовка, или свойства) выбирает одну из привязанных очередей. Routing key в binding здесь означает **вес** очереди (`"1"`, `"2"`), а не шаблон. На каждую очередь потом ставят одного консюмера (или SAC).

Плагин включают командой `rabbitmq-plugins enable rabbitmq_consistent_hash_exchange`.

**Задача.** Три очереди-шарда, восемь клиентов, по пять событий у каждого.

```python
ex = await ch.declare_exchange("orders.sharded", "x-consistent-hash", durable=True)
for i in range(3):
    q = await ch.declare_queue(f"orders.shard.{i}", durable=True, arguments={"x-queue-type": "quorum"})
    await q.bind(ex, routing_key="1")        # вес очереди
for n in range(5):
    for c in range(1, 9):
        await ex.publish(Message(f"c{c}-e{n}".encode(), delivery_mode=2), routing_key=f"customer-{c}")
```

```text title="Вывод"
orders.shard.0 -> {'c1': '01234', 'c4': '01234', 'c5': '01234', 'c6': '01234'}
orders.shard.1 -> {'c3': '01234', 'c7': '01234'}
orders.shard.2 -> {'c2': '01234', 'c8': '01234'}
```

Каждый клиент целиком попал в одну очередь, и его события шли подряд (`01234`). Между клиентами порядка нет, он и не нужен. Распределение по очередям неравномерное (4, 2 и 2 клиента): хеш не обещает равномерности на малом числе ключей.

> [!warning] Грабли
> Добавление или удаление очереди-шарда перераскладывает часть ключей: на время перехода порядок по этим ключам нарушен, поэтому число шардов выбирают с запасом сразу. Плагин не включён по умолчанию, и в `rabbitmq-plugins list` его надо смотреть отдельно.

## Идемпотентный консьюмер

Брокер даёт at-least-once, поэтому дубль приходит неизбежно: консюмер упал после эффекта и до `ack`, сработал возврат, retry продублировал сообщение, outbox отправил событие дважды. Консюмер должен выдержать повтор без повторного эффекта. Для этого нужен идентификатор сообщения (`message_id`, который проставляет продюсер, а не консюмер при приёме) и уникальный ключ в базе, а проверка «видел ли я это» должна быть **не** отдельным `SELECT`: две копии сообщения обрабатываются параллельно, обе не видят записи и обе делают эффект. Отметка об обработке и эффект выполняются в **одной транзакции**: упала середина, откатилось всё.

**Задача.** Консюмер применил эффект (прибавил бонус 50) и «упал» до ack, брокер доставил сообщение второй раз. Сравним консюмер без дедупликации и с таблицей inbox. Таблицы лежат в sqlite для компактности; в PostgreSQL логика та же (`INSERT ... ON CONFLICT DO NOTHING`).

```python
def naive(db, mid, amount):
    with db: db.execute("UPDATE accounts SET balance = balance + ? WHERE id = 1", (amount,))

def idempotent(db, mid, amount):
    with db:   # одна транзакция: отметка + эффект
        cur = db.execute("INSERT OR IGNORE INTO inbox VALUES ('billing', ?)", (mid,))
        if cur.rowcount == 0: return "дубль, пропускаем"
        db.execute("UPDATE accounts SET balance = balance + ? WHERE id = 1", (amount,))
```

```text title="Вывод"
  доставка 1 (redelivered=False): эффект применён
  доставка 2 (redelivered=True): эффект применён
без дедупликации: баланс = 200 (ожидали 150)
  доставка 1 (redelivered=False): эффект применён
  доставка 2 (redelivered=True): дубль, пропускаем
с inbox: баланс = 150 (ожидали 150)
```

Без дедупликации бонус начислен дважды, и баланс 200 вместо 150. С inbox второй раз уникальный ключ не дал вставить отметку, `rowcount` равен нулю, и эффект пропущен.

В PostgreSQL это выглядит так:

```sql
BEGIN;
INSERT INTO processed_messages (consumer, message_id) VALUES (:consumer, :message_id) ON CONFLICT DO NOTHING;
-- rowcount 0 → дубль: приложение пропускает эффект и коммитит; иначе выполняем его:
UPDATE accounts SET balance = balance + :amount WHERE user_id = :u;
COMMIT;
-- и только после COMMIT: ack сообщения
```

Ключ отметки — `(consumer, message_id)`, если одно событие читают несколько обработчиков. Старые строки чистят по сроку, не короче возможного окна повторной доставки (например, периода хранения очередей и retry), иначе таблица растёт вечно. Эффект вне базы (HTTP-вызов, письмо) в одну транзакцию с отметкой не положить: его делают идемпотентным у получателя (ключ идемпотентности равен `message_id`) либо превращают в команду через outbox. Общая схема та же, что в [[Когда двигать offset#Техника: идемпотентный консьюмер с таблицей inbox]] для Kafka.

> [!warning] Грабли
> `ack` после `COMMIT`, а не до: подтверждение до коммита превращает сбой в потерянное сообщение. Если же упасть между `COMMIT` и `ack`, брокер доставит сообщение повторно, и inbox его отсеет: именно поэтому отметка и эффект лежат в одной транзакции.

## Бизнес-кейс

Сервис баланса принимает события `bonus.accrued`. Событий много, поэтому очередь делится на 8 шардов через consistent hash exchange по `user_id`: события одного пользователя идут строго друг за другом, а разные пользователи обрабатываются параллельно. На каждый шард по одному активному консюмеру (SAC, чтобы запасной подхватил очередь при падении) и `prefetch=1`. Каждый обработчик пишет в таблицу `processed_messages` в одной транзакции с изменением баланса: повторы после падений никому не начисляют бонус дважды. Устаревшие по версии события отбрасываются.

## Что спросят дальше

- Что делает prefetch? Ограничивает число неподтверждённых сообщений у консюмера; регулирует равномерность и backpressure.
- Почему один консюмер получил всё? Нет prefetch (в aio-pika он по умолчанию неограничен): брокер отдал всю очередь первому подключившемуся.
- Гарантирует ли RabbitMQ порядок? Только для одной очереди с одним консюмером при `prefetch=1` и без возвратов; с несколькими консюмерами и при requeue порядок не гарантируется.
- Как сохранить порядок по ключу при масштабировании? Consistent hash exchange по ключу в несколько очередей, на каждую один консюмер; либо single active consumer при небольшой нагрузке.
- Чем single active consumer отличается от обычной очереди с одним консюмером? Запасные консюмеры уже подключены и подхватывают очередь автоматически, если активный упал.
- Как сделать обработчик идемпотентным? Уникальный ключ по `message_id` в одной транзакции с эффектом; `ack` после коммита.
