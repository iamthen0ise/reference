## Суть

RPC (Remote Procedure Call, «вызов удалённой процедуры») через брокер выглядит так. Клиент отправляет запрос в очередь сервера и в свойствах сообщения указывает, куда прислать ответ: `reply_to` — имя очереди для ответа, и `correlation_id` — идентификатор, по которому клиент потом сопоставит ответ со своим запросом (ответов от разных запросов в одной очереди приходит много, и порядок не гарантирован). Сервер обрабатывает запрос, публикует ответ в `reply_to` с тем же `correlation_id`, клиент по нему находит нужный запрос и завершает ожидание.

Для очереди ответа есть два варианта. Первый: клиент объявляет свою очередь (exclusive, на время соединения) и слушает её. Второй: **direct reply-to** — встроенная псевдоочередь `amq.rabbitmq.reply-to`: ничего объявлять не надо, брокер сам подставляет в `reply_to` временный адрес, и ответ доставляется на то же соединение. Второй вариант дешевле: нет затрат на создание очереди на каждый вызов. Условие — клиент должен читать псевдоочередь в режиме без ack (`no_ack=True`) на том же канале, на котором публикует запрос.

## Рецепт: RPC с direct reply-to

**Задача.** Сложить два числа через сервис по RPC, проверить поведение при таймауте и увидеть, что происходит с запросом, на который никто не ответил вовремя.

```python
async def server(conn):
    ch = await conn.channel(); await ch.set_qos(prefetch_count=10)
    q = await ch.declare_queue("rpc.sum", durable=True)
    async def h(m: aio_pika.IncomingMessage):
        async with m.process():
            a, b = map(int, m.body.split(b","))
            print(f"  сервер: correlation_id={m.correlation_id[:8]} reply_to={m.reply_to!r}")
            await ch.default_exchange.publish(
                Message(str(a + b).encode(), correlation_id=m.correlation_id),
                routing_key=m.reply_to)                      # ответ в default exchange по reply_to
    await q.consume(h); return ch

async def call(conn, payload, timeout):
    ch = await conn.channel()
    pending = {}
    async def on_reply(raw):
        m = aio_pika.IncomingMessage(raw, no_ack=True)
        fut = pending.pop(m.correlation_id, None)
        if fut: fut.set_result(m.body)
    # direct reply-to: очередь не объявляется, чтение без ack
    await (await ch.get_underlay_channel()).basic_consume(
        "amq.rabbitmq.reply-to", on_reply, no_ack=True)
    cid = str(uuid.uuid4()); fut = asyncio.get_running_loop().create_future(); pending[cid] = fut
    await ch.default_exchange.publish(
        Message(payload, correlation_id=cid, reply_to="amq.rabbitmq.reply-to"),
        routing_key="rpc.sum")
    try:
        return await asyncio.wait_for(fut, timeout)
    except asyncio.TimeoutError:
        return "TIMEOUT"
    finally:
        await ch.close()
```

```text title="Вывод"
1) сервера нет, клиент ждёт 1 с:
  результат: TIMEOUT
  запрос остался в очереди: 1
2) сервер стартует и обрабатывает старый запрос (клиента уже нет):
  сервер: correlation_id=e4419259 reply_to='amq.rabbitmq.reply-to.g1h2AA5yZXBseUA0MTU1MTMzNwAACe0AAAAAav9CWw==.sh/wsnDVQ2KpoZkJbke71A=='
3) нормальный вызов:
  сервер: correlation_id=8c556f7f reply_to='amq.rabbitmq.reply-to.g1h2AA5yZXBseUA0MTU1MTMzNwAACfYAAAAAav9CWw==.IKAne2ldRGiGvDCWMwe1NA=='
  результат: b'42'
```

Нормальный вызов отработал и вернул `42`, а `reply_to` оказался длинным временным адресом, который выдал брокер. Интереснее первые два пункта. Сервера не было, клиент по таймауту отказался ждать, но сообщение осталось в очереди `rpc.sum`. Когда сервер потом поднялся, он честно обработал запрос, о котором клиент уже забыл, и опубликовал ответ в адрес, которого больше нет: ответ пропал, а побочный эффект запроса (если он был) произошёл.

## Оговорки

RPC через брокер даёт развязку, но не даёт того, что привычно ждать от вызова функции.

- **Таймаут клиента не отменяет запрос.** Клиент перестаёт ждать, а сообщение остаётся в очереди и будет обработано позже. Для запросов, которые нельзя выполнять с опозданием, ставят у сообщения срок `expiration`: по истечении брокер выбросит его сам (учтите оговорку про голову очереди в [[Повторы и DLQ в RabbitMQ#Задержка на уровне сообщения и очередь голов]]). Для запросов с побочным эффектом это не помогает: нужна идемпотентность по `correlation_id` или ключу запроса.
- **At-least-once действует и здесь.** Запрос может быть доставлен серверу дважды (упал до `ack`), и ответов тоже может быть два. Клиент обязан игнорировать ответ с неизвестным `correlation_id`.
- **Потерянный ответ не отличим от потерянного запроса.** Клиент видит только таймаут и не знает, выполнено ли действие. Для денежных операций повтор безопасен лишь при идемпотентном запросе.
- **Ответ в никуда пропадает молча.** Если клиент исчез вместе с соединением, ответ без `mandatory` никуда не попадёт. Сервер такой ошибки не видит и не должен падать.
- **Сервер не должен блокироваться.** Долгий запрос занимает консюмера, и очередь запросов растёт. Для долгих операций RPC не подходит: клиент получает номер задачи и потом спрашивает статус или принимает webhook.
- **Прямой HTTP или gRPC проще**, если нужен синхронный ответ с чётким таймаутом и кодом ошибки. RPC через брокер оправдан, когда нужны очереди (сглаживание нагрузки, балансировка по воркерам, повтор), а не просто транспорт.
- **Масштабирование.** Несколько серверов на одной очереди запросов делят нагрузку как обычные конкурирующие консюмеры ([[Конкурентность и порядок в RabbitMQ#Prefetch и равномерная нагрузка]]).

> [!warning] Грабли
> Если очередь ответа создавать для каждого вызова (не exclusive и без `auto_delete`), очереди копятся; в 4.4 non-durable неэксклюзивные очереди вообще запрещены. Либо одна exclusive-очередь на клиента с таблицей `correlation_id`, либо direct reply-to. Direct reply-to читают только с `no_ack=True` и только на том же канале, где публикуется запрос: на другом канале или с ack брокер ответит ошибкой. Последнее правило взято из документации RabbitMQ, на стенде как отдельный случай не проверялось.

## Бизнес-кейс

Интернет-магазин при оформлении заказа синхронно запрашивает у сервиса расчёта цену со скидками. Сервис расчёта масштабируется воркерами на очереди запросов, нагрузку на него выравнивает prefetch, а клиент ждёт ответ не дольше 2 секунд и при таймауте показывает пользователю цену без скидки. Запрос расчёта не имеет побочных эффектов, поэтому поздняя обработка безвредна; для надёжности у запроса стоит `expiration` 5 секунд, чтобы очередь не копила устаревшие. А вот резервирование товара на складе делают не RPC, а командой с идемпотентным ключом и событием о результате.

## Что спросят дальше

- Как сделать RPC через Rabbit? Запрос с `reply_to` и `correlation_id`, ответ публикуется по `reply_to` с тем же `correlation_id`; клиент сопоставляет ответы.
- Зачем `correlation_id`? Ответы в одной очереди приходят вперемешку; по идентификатору клиент находит свой запрос.
- Что такое direct reply-to? Псевдоочередь `amq.rabbitmq.reply-to`, которая не требует создавать очередь ответа; читается без ack на том же канале.
- Что будет, если клиент отвалился по таймауту? Запрос остаётся в очереди и обрабатывается позже, ответ уходит в никуда; поэтому нужны `expiration` и идемпотентность.
- Когда не стоит использовать RPC через брокер? Когда нужен простой синхронный вызов с чётким контрактом ошибок (HTTP, gRPC) или операция длится долго.
