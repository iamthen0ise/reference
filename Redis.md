**Суть.** Redis — in-memory key-value хранилище с богатыми структурами данных. Команды выполняются в одном потоке, поэтому каждая команда атомарна. Типичные роли: кэш, сессии, счётчики и rate limit, распределённые блокировки, лидерборды, простые очереди и pub/sub. Не источник правды для денег и заказов.

## Структуры данных и задачи

| Структура | Команды | Задача |
| --- | --- | --- |
| String | `GET`, `SET EX NX`, `INCR` | кэш, счётчики, блокировки, idempotency key |
| Hash | `HSET`, `HGETALL`, `HINCRBY` | объект (профиль, корзина) без сериализации целиком |
| List | `LPUSH`, `BRPOP`, `LMOVE` | простая очередь, лента последних N |
| Set | `SADD`, `SISMEMBER`, `SINTER` | уникальные посетители, теги |
| Sorted Set | `ZADD`, `ZRANGE`, `ZRANGEBYSCORE` | лидерборд, sliding window rate limit, отложенные задачи по времени |
| Stream | `XADD`, `XREADGROUP`, `XACK` | очередь с consumer groups и ack (мини-Kafka) |
| HyperLogLog | `PFADD`, `PFCOUNT` | приблизительный подсчёт уникальных (12 КБ на ключ, ошибка ~0.8%) |
| Bitmap | `SETBIT`, `BITCOUNT` | активность пользователей по дням |
| Pub/Sub | `PUBLISH`, `SUBSCRIBE` | оповещения без гарантий (подписчик офлайн = сообщение потеряно) |

## Паттерны кэширования

- **Cache-aside** (самый частый): читаем из кэша → промах → БД → пишем в кэш с TTL. При записи — сначала БД, потом `DEL` ключа.
- **Write-through**: пишем в кэш и БД синхронно. **Write-behind**: сначала кэш, в БД асинхронно — риск потери.
- Почему `DEL`, а не `SET` нового значения: два параллельных апдейта могут записать в кэш в обратном порядке, и кэш навсегда разойдётся с БД. `DEL` тоже не идеален: читатель, промахнувшийся до записи, может положить в кэш старое значение уже после `DEL` — поэтому TTL обязателен всегда, а для критичного — повторный `DEL` с задержкой.
- Проблемы: **stampede** (популярный ключ истёк → тысяча промахов сразу в БД; лечение — single-flight или lock на пересчёт, рандомный TTL, фоновое обновление; та же идея, что и с [[Kafka#Откуда берётся снежный ком|лавиной ретраев]]), **penetration** (запросы к несуществующим ключам → кэшировать пустой ответ или Bloom filter), **avalanche** (массовое истечение или падение Redis → джиттер TTL, circuit breaker на БД).
- **Горячий ключ / большой ключ**: один ключ на миллион RPS упирается в один шард; ключ на 100 МБ блокирует поток при `DEL` (использовать `UNLINK`).

## Техника: распределённая блокировка

```text
# Захват: атомарно, с TTL и уникальным токеном владельца
SET lock:order:42 <uuid> NX PX 30000

# Освобождение: только свой замок (Lua атомарен)
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:42 <uuid>
```

Оговорки, которые ждут на собеседовании: замок может истечь, пока процесс в GC-паузе, и два владельца будут работать одновременно. Для корректности нужен **fencing token** (монотонный номер, который проверяет целевое хранилище). Redlock на 5 узлах эту проблему не решает — так считает Мартин Клеппман; автор Redis antirez с ним спорит, но про fencing на собеседовании спросят в любом случае. Если ошибка стоит денег — блокировка в БД ([[PostgreSQL#Блокировки]]: `FOR UPDATE`, advisory lock, UNIQUE).

## Техника: rate limiter

```text
# Fixed window: 100 запросов в минуту на пользователя
INCR rl:user:42:202611191530
EXPIRE rl:user:42:202611191530 60 NX     # если > 100 → 429
# NX (Redis 7.0+) на каждом запросе: упал процесс между INCR и EXPIRE — TTL поставит следующий

# Sliding window на sorted set (точнее, нет всплеска на стыке окон) — одним Lua-скриптом
ZREMRANGEBYSCORE rl:user:42 0 <now-60000>
ZCARD rl:user:42                          # ≥ 100 → 429, отклонённый запрос в окно не пишем
ZADD rl:user:42 <now> <request_id>
PEXPIRE rl:user:42 60000                  # неактивный ключ исчезнет сам
```

Token bucket допускает короткие всплески и чаще всего реализуется Lua-скриптом.

## Атомарность и транзакции

- Одна команда атомарна. `MULTI/EXEC` — пачка без перемешивания с чужими командами, но **без отката**: если команда упала при выполнении (не тот тип ключа), остальные выполнятся. Синтаксическая ошибка в очереди отменит весь EXEC.
- `WATCH` — оптимистичная блокировка: EXEC отменяется, если ключ изменился.
- **Lua-скрипты / Functions** — атомарный read-modify-write на сервере. Долгий скрипт блокирует весь Redis.

## Персистентность, память, масштабирование

| Тема | Что знать |
| --- | --- |
| RDB | снапшот через fork; при падении теряем данные с последнего снапшота. Fork + copy-on-write при активной записи — пик памяти (до ×2) и задержек |
| AOF | лог команд; `appendfsync everysec` — потеря до ~1 секунды |
| maxmemory-policy | `allkeys-lru`/`allkeys-lfu` для кэша; `noeviction` для данных, которые нельзя терять (очереди [[Celery]]!) |
| Репликация | асинхронная; при failover последние записи можно потерять (`WAIT` и `min-replicas-to-write` сужают окно, но не закрывают) |
| Истечение TTL | ленивое (при обращении к ключу) + активное (фоновая выборка ключей с TTL). Это не eviction: eviction вытесняет ключи при достижении `maxmemory` |
| Sentinel | автоматический failover для одного master |
| Cluster | 16384 hash slot по шардам; мульти-ключевые операции только в одном слоте — hash tags `{user:42}:cart` |
| Антипаттерны | `KEYS *` на проде (блокирует, используйте `SCAN`), ключи без TTL, огромные коллекции |

Смежное: в 2024 году Redis сменил лицензию, появился открытый форк Valkey (Linux Foundation); альтернативы — KeyDB, Dragonfly. В Redis 8 (2025) к RSAL и SSPL добавили AGPLv3 — Redis снова open source, хотя и не под BSD, как до 7.4.

## Бизнес-кейсы

- **«Кэшируйте баланс для скорости».** Показать баланс из кэша с задержкой 5 секунд — нормально. Решать по кэшу, хватит ли денег на списание, — нельзя. Вопрос к продукту: где устаревшие данные допустимы и на сколько?
- **Ограничение попыток ввода OTP.** 5 попыток за 15 минут на номер телефона — `INCR` + `EXPIRE ... NX` (или Lua). Если Redis недоступен: fail-open (пускаем всех, риск брутфорса) или fail-closed (никто не войдёт)? Это решение бизнеса и безопасности, а не разработчика.
- **Лидерборд игры на миллион игроков.** Sorted set: `ZINCRBY` и `ZREVRANK` за O(log N) — в SQL это оконная функция по всей таблице на каждый запрос.
- **Идемпотентность API.** `SET idem:<key> in-progress NX EX 86400` до обработки, после — перезаписать ключ готовым ответом. Повтор видит либо «в процессе» (409 или подождать), либо готовый ответ — быстрая защита от двойного нажатия «Оплатить». Ставить ответ сразу через `NX` нельзя: его ещё нет. Но источник правды — UNIQUE в БД: при failover Redis ключ может потеряться.

## Что спросят дальше

- Почему однопоточный Redis быстрый? — данные в памяти, нет блокировок и переключений контекста, мультиплексирование I/O (epoll); с версии 6 сетевой I/O может быть многопоточным. Узкое место — сеть, лечится pipelining.
- Pub/Sub vs Streams? — Pub/Sub — fire-and-forget; Streams хранят сообщения, есть consumer groups, ack и передача зависших (`XAUTOCLAIM`).
- Redis или Memcached? — Memcached проще и многопоточный, но только строки и без персистентности.
