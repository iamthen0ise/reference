Конспект к собеседованию по Redis: структуры данных под задачи, кэширование, распределённые блокировки, ограничение частоты запросов, сохранение данных на диск и масштабирование.
Рядом: [[PostgreSQL]] · [[SQL-задачи]] · [[Kafka]] · [[RabbitMQ]] · [[Celery]] · [[Чек-лист бэкенда]] (быстрые ответы на 30 секунд).
Разделы: [[#Структуры данных и задачи]] · [[#Паттерны кэширования]] · [[#Техника: распределённая блокировка]] · [[#Техника: ограничитель частоты запросов (rate limiter)]] · [[#Атомарность и транзакции]] · [[#Персистентность, память, масштабирование]] · [[#Бизнес-кейсы]] · [[#Что спросят дальше]]

**Суть.** Redis — хранилище «ключ → значение», которое держит все данные в оперативной памяти (in-memory key-value store). Значением может быть не только строка, но и список, множество, хеш и другие структуры, поэтому многие задачи решаются одной командой. Команды выполняются в одном потоке, одна за другой, так что каждая отдельная команда атомарна: другая команда не вклинится в её середину. Типичные роли Redis: кэш, сессии, счётчики и ограничение частоты запросов, распределённые блокировки, таблицы лидеров, простые очереди и рассылка сообщений подписчикам (pub/sub). Источником правды для денег и заказов Redis быть не должен: данные в памяти можно потерять при сбое (подробнее в разделе про персистентность).

## Структуры данных и задачи

| Структура | Команды | Задача |
| --- | --- | --- |
| String (строка) | `GET`, `SET EX NX`, `INCR` | кэш, счётчики, блокировки, ключ идемпотентности (idempotency key, см. ниже) |
| Hash (хеш) | `HSET`, `HGETALL`, `HINCRBY` | объект (профиль, корзина), поля которого читаются и меняются по отдельности, без сериализации целиком |
| List (список) | `LPUSH`, `BRPOP`, `LMOVE` | простая очередь, лента последних N записей |
| Set (множество) | `SADD`, `SISMEMBER`, `SINTER` | уникальные посетители, теги |
| Sorted Set (упорядоченное множество) | `ZADD`, `ZRANGE`, `ZRANGEBYSCORE` | таблица лидеров, ограничитель частоты со скользящим окном, отложенные задачи по времени |
| Stream (поток) | `XADD`, `XREADGROUP`, `XACK` | очередь с группами потребителей (consumer groups) и подтверждением обработки, «мини-Kafka» |
| HyperLogLog | `PFADD`, `PFCOUNT` | приблизительный подсчёт уникальных значений: 12 КБ на ключ, ошибка около 0,8% |
| Bitmap (битовая карта) | `SETBIT`, `BITCOUNT` | активность пользователей по дням: один бит на день |
| Pub/Sub (публикация и подписка) | `PUBLISH`, `SUBSCRIBE` | оповещения без гарантий: если подписчик был офлайн, сообщение для него потеряно |

Пояснения к таблице:

- `SET EX NX` — запись значения, которая срабатывает, только если ключа ещё нет (`NX`, not exists), и сама удаляет ключ через заданное число секунд (`EX`, expire).
- `INCR` — атомарно увеличить число в ключе на единицу; `HINCRBY` делает то же для поля хеша.
- Идемпотентность (idempotency) — свойство операции: если её выполнить дважды с теми же данными, результат будет как после одного раза. Ключ идемпотентности — уникальный идентификатор запроса, по которому повтор можно распознать.
- Consumer group — группа читателей потока: Redis раздаёт сообщения между ними, а читатель подтверждает обработку командой `XACK` (ack, acknowledge, «подтверждено»).
- `LMOVE` атомарно перекладывает элемент из одного списка в другой, `BRPOP` ждёт элемент, если список пуст.

## Паттерны кэширования

- **Cache-aside** («кэш сбоку», самый частый вариант). Приложение само управляет кэшем. При чтении: 1) смотрим в кэш; 2) если там пусто (промах, cache miss), читаем из базы данных; 3) кладём результат в кэш с TTL (time to live, время жизни ключа: по его истечении Redis удаляет ключ сам). При записи: сначала обновляем базу, затем удаляем ключ командой `DEL`, чтобы следующее чтение подтянуло свежее значение.
- **Write-through** («сквозная запись»): запись идёт в кэш и в базу синхронно, одной операцией. **Write-behind** («отложенная запись»): сначала пишем в кэш, а в базу данные попадают позже и асинхронно. Скорость выше, но если Redis упадёт до сброса в базу, данные потеряны.
- Почему при записи `DEL`, а не `SET` нового значения. Два параллельных обновления могут записать в кэш в обратном порядке, и кэш навсегда разойдётся с базой. `DEL` тоже не идеален: читатель, который промахнулся до записи и успел прочитать из базы старое значение, может положить его в кэш уже после `DEL`. Поэтому TTL нужен всегда, а для критичных данных ещё делают повторный `DEL` с небольшой задержкой.
- Три классические проблемы кэша:
  - **Cache stampede** («давка»): популярный ключ истёк, и тысячи запросов одновременно промахиваются и идут в базу. Лечение: пересчитывать значение только в одном запросе, остальные ждут (single-flight, «один полёт»; либо блокировка на пересчёт), случайный разброс TTL, фоновое обновление до истечения. Та же идея, что и с [[Kafka#Откуда берётся снежный ком|лавиной повторных попыток]].
  - **Cache penetration** («пробивание»): запросы к ключам, которых нет ни в кэше, ни в базе, всегда доходят до базы. Лечение: кэшировать и пустой ответ (на короткое время) либо поставить перед базой фильтр Блума (Bloom filter) — компактную структуру, которая быстро отвечает «такого ключа точно нет» или «возможно, есть».
  - **Cache avalanche** («лавина»): много ключей истекают одновременно или падает сам Redis, и вся нагрузка разом обрушивается на базу. Лечение: джиттер (jitter) TTL, то есть случайная добавка к времени жизни, чтобы ключи истекали в разное время; и circuit breaker («предохранитель») на стороне базы: после серии ошибок он на время прекращает слать запросы, давая базе восстановиться.
- **Горячий ключ и большой ключ.** Если один ключ получает миллион запросов в секунду, он упирается в один шард (одну часть кластера). Ключ размером 100 МБ блокирует единственный поток Redis при удалении командой `DEL`; вместо неё используют `UNLINK`, которая освобождает память в фоне.

## Техника: распределённая блокировка

Блокировка нужна, чтобы из нескольких процессов (возможно, на разных серверах) одну работу выполнял только один.

```text
# Захват: атомарно, с TTL и уникальным токеном владельца
SET lock:order:42 <uuid> NX PX 30000

# Освобождение: только свой замок (Lua атомарен)
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:42 <uuid>
```

Как это работает:

- `SET ... NX PX 30000` записывает ключ, только если его ещё нет (`NX`), и ставит время жизни 30 000 миллисекунд (`PX`). Кто успел записать, тот и владеет замком. TTL нужен, чтобы замок снялся сам, если владелец упал.
- В значение пишут уникальный токен (`<uuid>`), чтобы процесс мог снять только свой замок. Иначе процесс, у которого замок уже истёк и достался другому, удалит чужой.
- Проверка токена и удаление выполняются Lua-скриптом (Lua — встроенный в Redis язык скриптов): Redis выполняет скрипт целиком, не пуская между командами чужие, поэтому «прочитать токен, сравнить, удалить» атомарно.

Оговорки, которые ждут на собеседовании. Замок может истечь, пока процесс стоит в паузе сборщика мусора (GC, garbage collection) или завис на сети. Тогда замок достанется второму процессу, и первый, очнувшись, продолжит работать одновременно с ним. Для корректности нужен **fencing token** («токен-ограждение»): монотонно растущий номер, который выдаётся при каждом захвате, а целевое хранилище отвергает операции с номером меньше уже виденного. **Redlock** — алгоритм захвата замка сразу на нескольких независимых узлах Redis (обычно пяти), по большинству. Мартин Клеппман считает, что Redlock эту проблему не решает (он не выдаёт fencing token, а корректность опирается на часы и паузы); автор Redis antirez с ним спорит, но про fencing на собеседовании спросят в любом случае. Если ошибка стоит денег, блокировку надёжнее держать в базе данных, см. [[PostgreSQL#Блокировки]]: `FOR UPDATE`, advisory lock (программная блокировка по числовому ключу) или ограничение уникальности `UNIQUE`.

## Техника: ограничитель частоты запросов (rate limiter)

Ограничитель считает запросы пользователя за период и отклоняет лишние. Два основных способа:

```text
# Fixed window (фиксированное окно): 100 запросов в минуту на пользователя
INCR rl:user:42:202611191530
EXPIRE rl:user:42:202611191530 60 NX     # если счётчик > 100 → ответить 429
# NX (Redis 7.0+) на каждом запросе: упал процесс между INCR и EXPIRE — TTL поставит следующий

# Sliding window (скользящее окно) на sorted set — точнее, нет всплеска на стыке окон. Одним Lua-скриптом
ZREMRANGEBYSCORE rl:user:42 0 <now-60000>
ZCARD rl:user:42                          # ≥ 100 → 429, отклонённый запрос в окно не пишем
ZADD rl:user:42 <now> <request_id>
PEXPIRE rl:user:42 60000                  # неактивный ключ исчезнет сам
```

Как это читать:

- Фиксированное окно: ключ содержит номер минуты (`202611191530` — это 2026-11-19, 15:30), `INCR` считает запросы в этой минуте, `EXPIRE` стирает ключ через 60 секунд. `429` — HTTP-статус «Too Many Requests» (слишком много запросов). Слабое место: пользователь может сделать 100 запросов в конце одной минуты и ещё 100 в начале следующей, то есть 200 запросов за пару секунд.
- Опция `NX` у `EXPIRE` (доступна с Redis 7.0) выставляет TTL, только если его ещё нет. Её вызывают при каждом запросе: если процесс упал между `INCR` и `EXPIRE`, ключ без TTL остался бы навсегда, а так следующий запрос поставит TTL.
- Скользящее окно: каждый запрос — элемент sorted set, где оценка (score) — время запроса в миллисекундах. Сначала удаляем элементы старше 60 секунд (`ZREMRANGEBYSCORE`), потом считаем оставшиеся (`ZCARD`). Если их уже 100 или больше, запрос отклоняем и в окно не записываем, иначе отклонённые запросы продлевали бы блокировку. Все четыре команды выполняют одним Lua-скриптом, чтобы между ними не вклинился другой запрос.
- Token bucket («ведро с токенами») допускает короткие всплески: в ведро с постоянной скоростью добавляются токены, каждый запрос забирает один. Чаще всего его реализуют Lua-скриптом.

## Атомарность и транзакции

- Одна команда атомарна. `MULTI` / `EXEC` — пачка команд, которую Redis выполнит подряд, не перемешивая с чужими, но **без отката**: если какая-то команда упала при выполнении (например, применили команду списка к строке), остальные всё равно выполнятся. Синтаксическая ошибка при постановке команды в очередь отменит весь `EXEC`.
- `WATCH` — оптимистичная блокировка: `EXEC` отменяется, если за наблюдаемым ключом после `WATCH` кто-то записал. Тогда транзакцию повторяют с чтения.
- **Lua-скрипты и Functions** (постоянно хранимые на сервере функции, развитие скриптов) дают атомарный цикл «прочитать, посчитать, записать» прямо на сервере. Долгий скрипт блокирует весь Redis, потому что поток один.

## Персистентность, память, масштабирование

| Тема | Что знать |
| --- | --- |
| RDB | Снимок всех данных на диск (RDB, Redis Database), который делается через `fork` (создание дочернего процесса). При падении теряем всё, что записано после последнего снимка. При активной записи действует copy-on-write (страница памяти копируется при первой записи в неё): возможен пик памяти до ×2 и всплески задержек |
| AOF | Журнал всех команд записи (AOF, Append Only File), по которому Redis восстанавливается при старте. При `appendfsync everysec` (сброс на диск раз в секунду) теряем до секунды записей |
| maxmemory-policy | Политика вытеснения (eviction policy): что делать, когда память дошла до лимита `maxmemory`. `allkeys-lru` удаляет любой ключ, которым давно не пользовались (LRU, least recently used); `allkeys-lfu` удаляет редко используемые (LFU, least frequently used). Эти две подходят для кэша. `noeviction` не удаляет ничего и отвечает ошибкой на запись: нужна для данных, которые терять нельзя, например для очередей [[Celery]] |
| Репликация | Реплика — копия данных на другом узле. Репликация асинхронная: при аварийном переключении (failover) на реплику последние записи можно потерять. `WAIT` и `min-replicas-to-write` сужают окно потери, но не закрывают его |
| Истечение TTL | Срабатывает двумя способами: лениво (ключ проверяется и удаляется при обращении к нему) и активно (фоновая выборка ключей с TTL). Это не eviction: eviction вытесняет ключи, когда достигнут `maxmemory`, независимо от их TTL |
| Sentinel | Служба наблюдения за одним главным узлом (master) и его репликами: следит за их здоровьем и автоматически переключает на реплику при падении master |
| Cluster | Redis Cluster делит ключи на 16384 слота (hash slot) и раздаёт слоты по шардам. Слот ключа считается от хеша его имени. Команды с несколькими ключами работают, только если все ключи в одном слоте. Чтобы попасть в один слот, в имя добавляют hash tag: хешируется только часть в фигурных скобках, например `{user:42}:cart` и `{user:42}:profile` лежат вместе |
| Антипаттерны | `KEYS *` в боевой системе блокирует единственный поток: вместо неё используют `SCAN` (постепенный обход небольшими порциями). Ключи без TTL копятся и съедают память. Огромные коллекции в одном ключе становятся большими и горячими ключами (см. выше) |

Смежное: в 2024 году Redis сменил лицензию, и появился открытый форк Valkey (проект Linux Foundation); альтернативы — KeyDB и Dragonfly. В Redis 8 (2025) к лицензиям RSAL и SSPL (ограничивают коммерческое использование облачными провайдерами) добавили AGPLv3 (открытую лицензию), так что Redis снова open source, хотя и не под лицензией BSD (разрешающей почти всё), как до версии 7.4.

## Бизнес-кейсы

- **«Кэшируйте баланс для скорости».** Показать баланс из кэша с задержкой 5 секунд нормально. Решать по кэшу, хватит ли денег на списание, нельзя. Вопрос к продукту: где устаревшие данные допустимы и на сколько?
- **Ограничение попыток ввода одноразового кода (OTP, one-time password).** 5 попыток за 15 минут на номер телефона: счётчик `INCR` плюс `EXPIRE ... NX` (или Lua-скрипт). Если Redis недоступен, есть два варианта. Fail-open: пускаем всех, риск подбора кода. Fail-closed: не пускаем никого, никто не войдёт. Это решение бизнеса и безопасности, а не разработчика.
- **Таблица лидеров игры на миллион игроков.** Sorted set: `ZINCRBY` (добавить очки) и `ZREVRANK` (место игрока) работают за O(log N) (время растёт с логарифмом числа игроков, то есть почти не замедляется). В SQL то же потребует оконной функции по всей таблице на каждый запрос.
- **Идемпотентность API.** До обработки запроса пишем `SET idem:<key> in-progress NX EX 86400` (86400 секунд — сутки), после обработки перезаписываем ключ готовым ответом. Повторный запрос увидит либо «в процессе» (вернуть ошибку 409 Conflict, «конфликт», или подождать), либо готовый ответ. Это быстрая защита от двойного нажатия «Оплатить». Сразу записать ответ через `NX` нельзя: ответа ещё нет. Но источник правды — ограничение `UNIQUE` в базе: при аварийном переключении Redis ключ может потеряться.

## Что спросят дальше

- Почему однопоточный Redis быстрый? Данные лежат в памяти, нет блокировок между потоками и переключений контекста, а сетевой ввод-вывод мультиплексируется (одним потоком обслуживается много соединений через механизм `epoll`). С версии 6 сетевой ввод-вывод может быть многопоточным. Узкое место — сеть; лечится pipelining, то есть отправкой нескольких команд одним пакетом без ожидания ответа на каждую.
- Pub/Sub или Streams? Pub/Sub — «отправил и забыл» (fire-and-forget): не подписанный в этот момент получатель сообщение не увидит. Streams хранят сообщения, дают группы потребителей и подтверждения, а зависшие у упавшего потребителя сообщения можно передать другому командой `XAUTOCLAIM`.
- Redis или Memcached? Memcached проще и многопоточный, но хранит только строки и не умеет сохранять данные на диск.
