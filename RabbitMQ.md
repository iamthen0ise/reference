**Суть.** RabbitMQ — брокер сообщений (AMQP 0-9-1): продюсер пишет в **exchange**, тот по правилам (**binding**) раскладывает в **очереди**, консюмер получает push и подтверждает каждое сообщение (**ack**). После ack сообщение удаляется. Сильные стороны — гибкая маршрутизация и очереди задач с поштучным подтверждением.

## Типы exchange

| Exchange | Маршрутизация | Пример |
| --- | --- | --- |
| direct | routing key совпадает с binding key точно | `email`, `sms` → свои очереди воркеров |
| topic | шаблон `*` (одно слово) и `#` (ноль или больше) | `order.*.paid`, `logs.#.error` |
| fanout | во все привязанные очереди | инвалидация кэшей во всех инстансах |
| headers | по заголовкам (`x-match: all/any`) | редко нужен |
| default (`""`) | имя очереди = routing key | простая очередь задач |

## Надёжность: что надо включить

- **На продюсере**: publisher confirms (брокер подтверждает приём), `mandatory` флаг или alternate exchange — иначе сообщение без подходящей очереди молча теряется.
- **На брокере**: durable-очереди + persistent-сообщения; **quorum queues** (Raft, репликация на 3 узла) — стандарт; classic mirrored queues удалены в RabbitMQ 4.0.
- **На консюмере**: manual ack после обработки (аналог коммита offset после БД). Консюмер упал без ack → сообщение вернётся другому (at-least-once).
- **prefetch (`basic.qos`)** — сколько неподтверждённых сообщений держит консюмер. Без него брокер вывалит всю очередь в один консюмер. Это главный рычаг backpressure и равномерной нагрузки.

## Техника: retry с задержкой через DLX + TTL

```text
work.queue   x-dead-letter-exchange = retry.dlx
             (nack/reject requeue=false → сообщение уходит в DLX)

retry.queue  x-message-ttl = 30000
             x-dead-letter-exchange = work.exchange
             (никто не читает; через 30 с TTL истёк → назад в work)

parking.queue  сюда после N попыток (счётчик в заголовке x-death)
```

> [!warning] Ловушка
> `nack(requeue=true)` без задержки — сообщение тут же вернётся, и консюмер будет крутить его в горячем цикле на 100% CPU. Это тот же [[Kafka#Откуда берётся снежный ком|снежный ком повторов]], что и в Kafka. В quorum queues есть `delivery-limit` (по умолчанию 20 с 4.0): считаются все возвраты — nack с requeue и потеря консюмера. После лимита сообщение уходит в DLX, а если DLX не настроен — молча удаляется.

## Порядок сообщений в RabbitMQ

- Одна очередь + один консюмер = строгий порядок (prefetch на него не влияет, ломает requeue), но без масштабирования.
- Несколько консюмеров (competing consumers) и requeue порядок ломают.
- Порядок по ключу — consistent hash exchange (плагин): шардирует по ключу в N очередей, аналог партиций Kafka; или Single Active Consumer.

## Kafka vs RabbitMQ

|  | Kafka | RabbitMQ |
| --- | --- | --- |
| Модель | распределённый лог, pull | брокер с очередями, push |
| После чтения | сообщение остаётся (retention), можно перечитать | удаляется после ack (кроме Streams) |
| Подтверждение | offset на партицию | ack на каждое сообщение |
| Порядок | в партиции | в очереди при одном консюмере |
| Маршрутизация | по топику и ключу | exchanges, шаблоны, заголовки |
| Отложенные сообщения, приоритеты | нет из коробки | TTL + DLX, priority queues, плагин delayed |
| Пропускная способность | сотни тысяч – миллионы msg/s | десятки тысяч msg/s на очередь |
| Когда брать | event streaming, CDC, аналитика, event sourcing, несколько независимых читателей | очереди задач, RPC, сложная маршрутизация, поштучные повторы |

Смежное: **RabbitMQ Streams** — append-only лог с чтением по offset, внутри Rabbit появилась Kafka-подобная семантика.

## Бизнес-кейсы

- **Генерация PDF-счетов и отправка писем.** Классическая очередь задач: разная длительность, поштучный retry, масштабирование воркерами, порядок не важен — Rabbit подходит лучше Kafka. Одно «тяжёлое» сообщение в Kafka тормозит всю партицию (head-of-line blocking), в Rabbit — только один воркер.
- **VIP-клиенты должны получать уведомления раньше.** Отдельная очередь с выделенными воркерами надёжнее priority queue: приоритеты сломаются при большом prefetch.
- **«Напомни об оплате через 24 часа».** TTL+DLX или delayed-плагин (он не реплицируется и не работает с quorum queues) работают, но держат миллионы сообщений в брокере сутками и плохо отменяются. Для долгих задержек надёжнее таблица `scheduled_jobs` в БД + поллер с `SKIP LOCKED` ([[PostgreSQL#Техника: очередь задач на SKIP LOCKED]]): можно отменить, перенести, посмотреть.

## Что спросят дальше

- Что будет, если консюмеры не успевают? — очередь растёт в памяти и на диске, срабатывает memory/disk alarm, брокер блокирует продюсеров (flow control). Защита: `x-max-length` + `overflow: reject-publish`, мониторинг длины очереди.
- Как сделать RPC через Rabbit? — `reply_to` (временная очередь или direct reply-to) + `correlation_id`.
- Почему долгая задача «вернулась» в очередь через полчаса? — `consumer_timeout` (по умолчанию 30 минут): нет ack за это время — брокер закрывает канал и возвращает сообщение. Для долгих задач — поднять таймаут на очереди или ack раньше с сохранением прогресса в БД.
- Exactly-once? — нет; at-least-once + идемпотентность по `message_id`, как и с [[Kafka#Когда двигать offset|Kafka → DB]].
