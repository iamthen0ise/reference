## Inode и ссылки

У файла в файловой системе есть inode: запись с метаданными (тип, владелец, права, размер, время, число жёстких ссылок) и с указателем на данные. По [inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html) номер inode уникален только внутри одной файловой системы. Имени в inode нет: имя — это запись в каталоге, которая ведёт на inode.

- Жёсткая ссылка — ещё одно имя того же inode. По [link(2)](https://man7.org/linux/man-pages/man2/link.2.html) оба имени ведут на один и тот же файл, и отличить «оригинал» от ссылки нельзя. Поэтому жёсткая ссылка не пересекает файловые системы (там `EXDEV`).
- Символическая ссылка — отдельный файл со своим inode, внутри которого записан путь. Размер такого файла — длина этого пути (inode(7)). Если по пути ничего нет, ссылка называется висячей ([symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)).
- `rm` вызывает `unlink`: убирает имя. По [unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html) данные освобождаются, когда убрано последнее имя и файл никто не держит открытым.

«Всё есть файл» в этом смысле значит, что у обычного файла, каталога, символической ссылки, трубы, сокета и устройства есть тип в `st_mode` (список в inode(7)), а доступ к открытому объекту идёт через одинаковые дескрипторы. На странице это видно в `/proc/<pid>/fd`: файл, труба и сокет лежат в одной таблице.

```sh title="links.sh"
d=$(mktemp -d)
trap 'rm -rf "$d"' EXIT
cd "$d"
echo hello > orig
ln orig hard
ln -s orig soft
echo "== до удаления =="
ls -li orig hard soft
stat -c '%n: inode=%i links=%h %F, size=%s' orig hard soft
rm orig
echo "== после rm orig =="
ls -li hard soft
echo -n "hard: "; cat hard
echo -n "soft: "; cat soft 2>&1 || true
```

```text title="Вывод"
== до удаления ==
1269767 -rw-r--r-- 2 root root 6 Nov 21 08:34 hard
1269767 -rw-r--r-- 2 root root 6 Nov 21 08:34 orig
1269769 lrwxrwxrwx 1 root root 4 Nov 21 08:34 soft -> orig
orig: inode=1269767 links=2 regular file, size=6
hard: inode=1269767 links=2 regular file, size=6
soft: inode=1269769 links=1 symbolic link, size=4
== после rm orig ==
1269767 -rw-r--r-- 1 root root 6 Nov 21 08:34 hard
1269769 lrwxrwxrwx 1 root root 4 Nov 21 08:34 soft -> orig
hard: hello
soft: cat: soft: No such file or directory
```

Номера inode, время и PID у вас будут другими. У `orig` и `hard` один inode и счётчик ссылок 2, а у `soft` свой inode, тип `symbolic link` и размер 4: это длина строки `orig`. После `rm orig` счётчик у `hard` стал 1, данные на месте и читаются. `soft` остался на месте, но его путь теперь указывает в пустоту, и `cat` отвечает «No such file or directory».

### Частые ошибки в ответе

- «Удалил оригинал, значит ссылка сломалась». Для жёсткой ссылки «оригинала» нет: она осталась и читается, как показал прогон. Ломается символическая: она хранит путь, а не файл.
- «Жёсткая ссылка — копия файла». Это второе имя того же inode, данные одни, а не две копии.
- «Символическая и жёсткая ссылки одинаково переживают удаление». Нет, см. прогон выше.
- «`rm` стирает данные файла». `rm` убирает имя; данные освобождаются, только когда имён не осталось и файл никто не держит открытым (подробнее — в [разделе про удалённый файл](#удалённый-файл-держит-место)).

## Дескрипторы и fork

Открытый файл для процесса — число, дескриптор: индекс в таблице открытых файлов этого процесса. По [open(2)](https://man7.org/linux/man-pages/man2/open.2.html) `open` возвращает наименьший свободный номер. За записью в таблице стоит «описание открытого файла» в ядре, и в нём живут смещение и флаги; поэтому два дескриптора, ведущие на одно описание, делят смещение.

`/proc/<pid>/fd` показывает эту таблицу: по записи на каждый открытый файл, символические ссылки на реальный объект. Для трубы и сокета ссылка выглядит как `тип:[inode]` ([proc_pid_fd(5)](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html)).

По [fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html) ребёнок получает копию таблицы дескрипторов, и каждая её запись ведёт на то же описание открытого файла, что и у родителя: смещение общее. Блок ниже открывает файл и сокет, вызывает `fork`, показывает таблицу родителя и ребёнка, а затем читает по 4 байта сначала в ребёнке, потом в родителе. В Python дескрипторы по умолчанию не наследуются при `exec`, но при `fork` наследуются ([документация Python](https://docs.python.org/3/library/os.html#fd-inheritance)), поэтому демонстрация честная для `fork`.

```python title="fd-table.py"
import os
import socket
import tempfile


def table(label):
    print(label)
    for fd in sorted(map(int, os.listdir("/proc/self/fd"))):
        try:
            target = os.readlink(f"/proc/self/fd/{fd}")
        except OSError:
            continue
        if target.startswith("/proc/"):
            continue  # дескриптор самого listdir
        print(f"  fd {fd} -> {target}")


with tempfile.TemporaryDirectory() as d:
    path = f"{d}/data.txt"
    with open(path, "w") as f:
        f.write("0123456789")
    fd = os.open(path, os.O_RDONLY)
    srv = socket.socket()
    srv.bind(("127.0.0.1", 0))
    srv.listen()
    table("родитель")

    pid = os.fork()
    if pid == 0:
        table("ребёнок сразу после fork")
        print("  ребёнок прочитал", os.read(fd, 4))
        os._exit(0)
    os.waitpid(pid, 0)
    print("родитель читает дальше", os.read(fd, 4))
```

```text title="Вывод"
родитель
  fd 0 -> pipe:[3093476]
  fd 1 -> pipe:[3093477]
  fd 2 -> pipe:[3093478]
  fd 3 -> /tmp/tmpe_asjee7/data.txt
  fd 4 -> socket:[3094128]
ребёнок сразу после fork
  fd 0 -> pipe:[3093476]
  fd 1 -> pipe:[3093477]
  fd 2 -> pipe:[3093478]
  fd 3 -> /tmp/tmpe_asjee7/data.txt
  fd 4 -> socket:[3094128]
  ребёнок прочитал b'0123'
родитель читает дальше b'4567'
```

Номера inode, имя временного каталога и PID у вас будут другими. Таблица ребёнка совпадает с таблицей родителя запись в запись: те же fd 0, 1, 2, файл на fd 3 и сокет на fd 4. Ребёнок прочитал `0123`, а родитель продолжил с `4567`: смещение общее, ребёнок не получил «свою копию» файла с начала. На `fd 0`–`2` стоят трубы, потому что блок запущен через `docker exec` без терминала; в интерактивной оболочке там был бы `/dev/pts/N`.

### Частые ошибки в ответе

- «Дескриптор — это файл». Это номер в таблице процесса, а таблица у каждого процесса своя.
- «После `fork` ребёнок читает файл с начала». Описание открытого файла общее, смещение общее: прогон показал, что родитель продолжил после ребёнка.
- «`exec` закрывает все дескрипторы». Только те, у которых стоит флаг close-on-exec (`O_CLOEXEC`, open(2)): по умолчанию дескриптор переживает `exec`. Python ставит этот флаг сам, в C его нужно запросить.
- «Если удалить файл, дескриптор перестанет работать». Он продолжит работать, пока открыт (см. раздел про удалённый файл).

## Стандартные потоки и перенаправления

По proc_pid_fd(5) дескриптор 0 — стандартный ввод, 1 — стандартный вывод, 2 — стандартный поток ошибок. Оболочка настраивает дескрипторы ребёнка до `exec`, так что программа получает уже готовые 0, 1 и 2 (см. [[Процессы в Linux#fork и exec]]). `2>&1` означает «пусть fd 2 смотрит туда же, куда fd 1 смотрит сейчас», и поэтому порядок записи важен: по [bash(1)](https://man7.org/linux/man-pages/man1/bash.1.html) перенаправления обрабатываются в порядке записи, слева направо.

```sh title="redirects.sh"
d=$(mktemp -d)
trap 'rm -rf "$d"' EXIT
ls -l /proc/self/fd 0</dev/null 1>"$d/out" 2>"$d/err"
echo "== fd процесса ls, как их выстроила оболочка =="
awk 'NR > 1 && $9 ~ /^[0-3]$/ { print "fd", $9, $10, $11 }' "$d/out"
echo "== 2>&1 после >файл: ошибка уехала в файл =="
ls /nonexistent >"$d/o1" 2>&1
echo "в файле: $(wc -c < "$d/o1") байт; на экран не попало ничего"
echo "== 2>&1 до >файл: ошибка пошла в канал =="
ls /nonexistent 2>&1 >"$d/o2" | sed 's/^/в канале: /'
echo "в файле: $(wc -c < "$d/o2") байт"
```

```text title="Вывод"
== fd процесса ls, как их выстроила оболочка ==
fd 0 -> /dev/null
fd 1 -> /tmp/tmp.e3tFfGCbOg/out
fd 2 -> /tmp/tmp.e3tFfGCbOg/err
fd 3 -> /proc/416/fd
== 2>&1 после >файл: ошибка уехала в файл ==
в файле: 60 байт; в канал не попало ничего
== 2>&1 до >файл: ошибка пошла в канал ==
в канале: ls: cannot access '/nonexistent': No such file or directory
в файле: 0 байт
```

Имя временного каталога и номер процесса у вас будут другими. У `ls` дескриптор 0 ведёт в `/dev/null`, 1 и 2 — в два разных файла, а `fd 3` — каталог `/proc/<pid>/fd`, который `ls` открыл сам, чтобы его прочитать. В первом случае `2>&1` стоит после `>файл`, поэтому fd 2 попал в файл вместе с fd 1. Во втором `2>&1` выполнено раньше: fd 2 скопировал fd 1, который тогда ещё смотрел в канал, и лишь потом fd 1 ушёл в файл. Сообщение об ошибке попало в канал, а файл остался пустым.

### Частые ошибки в ответе

- «`>f 2>&1` и `2>&1 >f` — одно и то же». Порядок важен, прогон показал разный результат.
- «`2>&1` пишет ошибки в файл `1`». Это не имя файла, а копия дескриптора: fd 2 начинает смотреть туда же, куда сейчас смотрит fd 1.

## Лимит дескрипторов

У процесса есть лимит на число открытых дескрипторов — `RLIMIT_NOFILE`. По [getrlimit(2)](https://man7.org/linux/man-pages/man2/getrlimit.2.html) это значение на единицу больше максимального номера дескриптора, который процесс может открыть; при превышении `open`, `pipe`, `dup` и другие вызовы возвращают `EMFILE` (errno 24, текст «Too many open files»). Другая ошибка, `ENFILE`, значит, что исчерпан общий лимит на всю систему (open(2)).

Лимитов два. Мягкий — тот, что ядро применяет. Жёсткий — потолок для мягкого: обычный процесс может поднимать мягкий лимит до жёсткого и необратимо понижать жёсткий, а менять жёсткий свободно может только привилегированный процесс с `CAP_SYS_RESOURCE` (getrlimit(2)). Лимит — свойство процесса, и по тому же man его наследует ребёнок после `fork` и сохраняет `exec`.

Блок проверяет это на подоболочке с лимитом 64. В bash `ulimit` без `-S` и `-H` выставляет и мягкий, и жёсткий лимит ([bash(1)](https://man7.org/linux/man-pages/man1/bash.1.html), встроенная команда `ulimit`), `-Sn` — только мягкий.

```sh title="limit.sh"
echo "оболочка: мягкий $(ulimit -Sn), жёсткий $(ulimit -Hn)"
grep 'Max open files' /proc/self/limits
(
  ulimit -n 64
  echo "в подоболочке: мягкий $(ulimit -Sn), жёсткий $(ulimit -Hn)"
  python3 -u - <<'PY'
import os
files = []
try:
    while True:
        files.append(open("/dev/null"))
except OSError as e:
    print(f"открыто {len(files)}, затем {type(e).__name__}: {e}")
    print("errno =", e.errno, "=", os.strerror(e.errno))
PY
)
echo "после подоболочки: мягкий $(ulimit -Sn)"
(
  ulimit -Sn 64
  echo "ulimit -Sn 64: мягкий $(ulimit -Sn), жёсткий $(ulimit -Hn)"
  ulimit -Sn 128 && echo "поднять мягкий до 128 можно: $(ulimit -Sn)"
)
```

```text title="Вывод"
оболочка: мягкий 1048576, жёсткий 1048576
Max open files            1048576              1048576              files     
в подоболочке: мягкий 64, жёсткий 64
открыто 61, затем OSError: [Errno 24] Too many open files: '/dev/null'
errno = 24 = Too many open files
после подоболочки: мягкий 1048576
ulimit -Sn 64: мягкий 64, жёсткий 1048576
поднять мягкий до 128 можно: 128
```

Значения лимитов зависят от окружения. 1048576 — это лимит в этой песочнице (Docker Desktop), на вашем сервере, в systemd-юните или в другом контейнере число будет другим: в Docker его задают при запуске, `docker run --ulimit nofile=<мягкий>:<жёсткий>`. Узнать лимит работающего процесса можно в строке `Max open files` файла `/proc/<pid>/limits`.

Python открыл 61 файл, а потом получил `OSError` с errno 24: 61 плюс три стандартных дескриптора (0, 1 и 2) дают 64, то есть дескрипторы 0–63, как и описывает getrlimit(2). После подоболочки лимит оболочки прежний: `ulimit` менял только процесс подоболочки. Мягкий лимит, понижённый через `-Sn`, можно вернуть выше (до жёсткого), а `ulimit -n` понизил оба.

Что делать, когда в проде «Too many open files». Сначала понять, утечка это или нормальная нагрузка: посмотреть, какие записи копятся в `ls -l /proc/<pid>/fd` и сколько их (`ls /proc/<pid>/fd | wc -l`). Если растёт число одинаковых сокетов или файлов, причина в коде (не закрывают соединения), и поднятие лимита лишь отложит падение. Если нагрузка законна (много соединений), лимит поднимают осознанно, в конфигурации сервиса или контейнера.

### Частые ошибки в ответе

- «Лимит дескрипторов один на систему». Есть лимит на процесс (`RLIMIT_NOFILE`, ошибка `EMFILE`) и общий лимит системы (`ENFILE`); на странице показан первый.
- «Мягкий и жёсткий лимиты — одно и то же». Мягкий ядро применяет, жёсткий — потолок для него. Прогон: `ulimit -Sn 64` оставил жёсткий прежним.
- «`ulimit -n 1000000` в скрипте лечит утечку». Лимит отодвигает падение; утечку чинят закрытием дескрипторов.
- «Лимит в контейнере такой же, как на хосте». Он задаётся при запуске контейнера и может отличаться; смотрят `ulimit -n` внутри и `/proc/<pid>/limits`.

## Удалённый файл держит место

По [unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html) если имя было последней ссылкой на файл, но какой-то процесс всё ещё держит его открытым, файл существует, пока не закроют последний дескриптор. Это классика: служба пишет в лог, лог удалили, а `df` показывает прежнее занятое место, и `du` его не находит, потому что имени в каталоге уже нет.

Демонстрация на собственной tmpfs (предсказуемые числа). Файл в 10 МиБ открыт на чтение в самой оболочке (`exec 3<`), потом удалён. `lsof +L1` выбирает открытые файлы с числом ссылок меньше 1, то есть удалённые ([man lsof](https://lsof.readthedocs.io/en/latest/manpage/)); `-a -p $$` оставляет в списке только нашу оболочку, чтобы не разбирать чужие процессы песочницы. Читается блок так: `df` до записи, после записи, после `rm`, пока дескриптор открыт, и после закрытия.

```sh title="deleted-open.sh"
m=$(mktemp -d)
mount -t tmpfs -o size=20M tmpfs "$m"
trap 'exec 3<&-; umount "$m"; rmdir "$m"' EXIT
used() {
  df -k --output=used,avail "$m" | tail -n 1 |
    awk '{ print $1 / 1024 " МиБ занято, " $2 / 1024 " МиБ свободно" }'
}
echo "пустая tmpfs:        $(used)"
dd if=/dev/zero of="$m/big" bs=1M count=10 status=none
echo "после записи 10 МиБ: $(used)"
exec 3< "$m/big"
rm "$m/big"
echo "после rm, fd открыт: $(used)"
echo "файлов в каталоге:   $(ls -A "$m" | wc -l); du: $(du -sk "$m" | cut -f1) КиБ"
echo "== lsof -a +L1 -p оболочки =="
lsof -a +L1 -p $$ 2>/dev/null | awk '{ print $1, $2, $4, $8, $10, $11 }'
echo "== readlink /proc/PID/fd/3 =="
readlink /proc/$$/fd/3
exec 3<&-
echo "после закрытия fd:   $(used)"
```

```text title="Вывод"
после записи 10 МиБ: 10 МиБ занято, 10 МиБ свободно
после rm, fd открыт: 10 МиБ занято, 10 МиБ свободно
файлов в каталоге:   0; du: 0 КиБ
== lsof -a +L1 -p оболочки ==
COMMAND PID FD NLINK NAME 
bash 477 3r 0 /tmp/tmp.Z1BiSLo8bT/big (deleted)
== readlink /proc/PID/fd/3 ==
/tmp/tmp.Z1BiSLo8bT/big (deleted)
после закрытия fd:   0 МиБ занято, 20 МиБ свободно
```

PID, имя каталога и объёмы у вас будут другими. Место вернулось только после `exec 3<&-`: пока дескриптор был открыт, `df` показывал те же 10 МиБ занятыми, хотя каталог пуст, а `du` видел 0 КиБ. `lsof` нашёл строку с `NLINK 0` и пометкой `(deleted)`, а `/proc/<pid>/fd/3` показал тот же путь с этой пометкой: дескриптор по-прежнему вёл на живой inode, у которого нет имени.

Освободить место можно, только закрыв дескриптор: перезапустить процесс или заставить его переоткрыть лог.

### Частые ошибки в ответе

- «Удалил файл, значит место свободно». Данные живут, пока есть имя или открытый дескриптор; прогон показал 10 МиБ занятыми при пустом каталоге.
- «`du` и `df` должны совпадать». Это разные измерения, и прогон показал расхождение: `du` по каталогу дал 0 КиБ, а `df` — 10 МиБ занято.
- «Освободит место `lsof` или `rm` ещё раз». `lsof` только показывает; имени уже нет, остаётся закрыть дескриптор.
- «Можно просто убить процесс-виновник в проде». Сначала выясняют, что это за процесс; перезапуск службы ради лога — решение с последствиями.

## Кончились inode

Свободное место и свободные inode — два разных ресурса. В tmpfs число inode задаётся параметром `nr_inodes` ([tmpfs(5)](https://man7.org/linux/man-pages/man5/tmpfs.5.html)); `df -i` показывает inode вместо блоков. Блок монтирует tmpfs на 10 МиБ со ста inode и создаёт пустые файлы, пока `touch` не откажет.

```sh title="inodes.sh"
m=$(mktemp -d)
mount -t tmpfs -o size=10M,nr_inodes=100 tmpfs "$m"
trap 'umount "$m"; rmdir "$m"; rm -f "$m.err"' EXIT
echo "== до =="
df -i "$m" | awk '{ print $1, $2, $3, $4, $5 }'
df -k "$m" | awk '{ print $1, $2, $3, $4, $5 }'
n=0
while touch "$m/f$n" 2>"$m.err"; do n=$((n + 1)); done
echo "== создано файлов: $n; ошибка: $(sed 's/.*: //' "$m.err")"
df -i "$m" | awk '{ print $1, $2, $3, $4, $5 }'
df -k "$m" | awk '{ print $1, $2, $3, $4, $5 }'
```

```text title="Вывод"
== до ==
Filesystem Inodes IUsed IFree IUse%
tmpfs 100 1 99 1%
Filesystem 1K-blocks Used Available Use%
tmpfs 10240 0 10240 0%
== создано файлов: 99; ошибка: No space left on device
Filesystem Inodes IUsed IFree IUse%
tmpfs 100 100 0 100%
Filesystem 1K-blocks Used Available Use%
tmpfs 10240 0 10240 0%
```

Создано 99 файлов: `df -i` до создания показывал 1 занятый inode из 100, после — 100 из 100. `touch` отказал с `No space left on device` (`ENOSPC`, open(2)), хотя `df -k` показывает все 10240 КиБ свободными: пустые файлы блоков не занимают, а inode кончились. Диагностика: `df -h` вместе с `df -i`.

### Частые ошибки в ответе

- «`No space left on device` — значит кончилось место». Это может быть и нехватка inode; `df -i` отвечает на это за секунду.
- «Если `df` показывает свободное место, писать можно». Для создания файла нужен свободный inode, прогон показывает пример.

## Права и umask

Права файла — это биты `rwx` для владельца, группы и остальных, они хранятся в inode (inode(7)). Когда программа создаёт файл, она передаёт желаемый режим, а ядро вычитает из него `umask`: по open(2) режим создаваемого файла равен `mode & ~umask`. По [umask(2)](https://man7.org/linux/man-pages/man2/umask.2.html) маска наследуется ребёнком при `fork` и сохраняется при `execve`.

Обычно программа просит 666 для файла и 777 для каталога; из них вычитается маска. Блок создаёт файл и каталог в подоболочках с `umask 022` и `077`. Дальше он проверяет, что `root` игнорирует права: файл с режимом 000 `root` читает, а процесс от `nobody` (`setpriv`) получает отказ.

```sh title="umask.sh"
d=$(mktemp -d)
trap 'rm -rf "$d"' EXIT
chmod 755 "$d"
cd "$d"
echo "umask по умолчанию: $(umask)"
for u in 022 077; do
  (
    umask "$u"
    touch "file-$u"
    mkdir "dir-$u"
    echo "umask $u: $(stat -c '%a %n' "file-$u" "dir-$u" | tr '\n' ' ')"
  )
done
ls -l
echo secret > locked
chmod 000 locked
echo "== файл с режимом 000 =="
echo -n "root: "; cat locked
echo -n "nobody: "
setpriv --reuid=65534 --regid=65534 --clear-groups cat locked 2>&1 || true
```

```text title="Вывод"
umask по умолчанию: 0022
umask 022: 644 file-022 755 dir-022 
umask 077: 600 file-077 700 dir-077 
total 8
drwxr-xr-x 2 root root 4096 Nov 21 08:34 dir-022
drwx------ 2 root root 4096 Nov 21 08:34 dir-077
-rw-r--r-- 1 root root    0 Nov 21 08:34 file-022
-rw------- 1 root root    0 Nov 21 08:34 file-077
== файл с режимом 000 ==
root: secret
nobody: cat: locked: Permission denied
```

Время и имя временного каталога у вас будут другими. Результат совпадает с `666 & ~022 = 644` и `777 & ~022 = 755` для 022, и с 600 и 700 для 077: маска только отнимает биты. `umask` по умолчанию в песочнице равна 0022. Файл с режимом 000 `root` прочитал, `nobody` получил `Permission denied`.

Почему процесс в контейнере не должен работать от root. `root` обходит проверки прав на файлы (способность `CAP_DAC_OVERRIDE`, [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)), и прогон выше это показал. Если приложение взломали, у атакующего внутри контейнера те же возможности; под обычным пользователем (`USER` в Dockerfile) ему приходится считаться с правами.

Про setuid: по [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html) если на исполняемом файле стоит бит set-user-ID, при запуске эффективный пользователь процесса становится владельцем файла. Поэтому такие файлы владельца `root` стоит учитывать при разборе образа.

### Частые ошибки в ответе

- «`umask 077` разрешает только владельцу». Маска отнимает биты у запрошенного режима: она сработала на новых файлах и каталогах, а на существующие не влияет.
- «`umask` добавляет права». Маска только выключает биты (umask(2)).
- «Права 000 защищают файл от всех». Для `root` права не помеха, как показал прогон.
- «`USER root` в контейнере безопасен, он же внутри контейнера». `root` в контейнере по-прежнему обходит проверки прав на файлы: в прогоне выше он прочитал файл с режимом 000.
