## Процесс и поток для ядра

Для ядра и процесс, и поток — задача (`task_struct`), и создаются они одним системным вызовом `clone`. Разница в том, что новая задача делит с создателем. С флагом `CLONE_VM` у них общее адресное пространство; `CLONE_THREAD` помещает новую задачу в ту же группу потоков. Без этих флагов получается отдельная копия, то есть обычный процесс.

Идентификаторов два. TID уникален для каждой задачи. PID, который видит пользователь и возвращает `getpid()`, — это идентификатор группы потоков (TGID), общий для всех её потоков. Поэтому в `/proc/<pid>/task/` лежит по каталогу на каждый поток, а у главного потока TID равен PID.

```python title="threads.py"
import os
import threading
import time

t = threading.Thread(target=time.sleep, args=(2,))
t.start()
time.sleep(0.2)
pid = os.getpid()
tids = sorted(os.listdir(f"/proc/{pid}/task"))
print("pid =", pid, "задачи в /proc/<pid>/task:", tids)
for tid in tids:
    with open(f"/proc/{pid}/task/{tid}/status") as f:
        d = dict(line.split(":", 1) for line in f if ":" in line)
    print(f"tid={tid:<6} Tgid={d['Tgid'].strip()} Name={d['Name'].strip()}")
t.join()
```

```text title="Вывод"
pid = 312 задачи в /proc/<pid>/task: ['312', '313']
tid=312    Tgid=312 Name=python3
tid=313    Tgid=312 Name=python3
```

PID и TID у вас будут другими.

Про GIL, выбор между потоками, процессами и asyncio — на странице [[Потоки и процессы]]. Здесь только то, что видит ядро.

### Частые ошибки в ответе

- «Поток — это что-то принципиально другое». Для планировщика это такая же задача, отличается набором общих ресурсов.
- «У потока свой PID». У потока свой TID, а PID один на группу.

## fork и exec

`fork` создаёт копию вызывающего процесса: тот же код, те же открытые файлы, та же память на момент вызова. Различаются возвращаемым значением (0 в ребёнке, PID ребёнка в родителе) и идентификаторами. `exec` не создаёт процесс: он заменяет программу в текущем процессе, PID остаётся прежним. Оболочка запускает команду как `fork`, а затем `exec` в ребёнке; между двумя вызовами ребёнок успевает настроить перенаправления и каналы. Поэтому вызовов два.

```sh title="fork-exec.sh"
show() { tr '|' ' ' | fold -s -w 78 | sed 's/ *$//'; }
echo "== bash запускает ls =="
strace -f -qq -e trace=clone,clone3,execve bash -c 'ls /; true' 2>&1 >/dev/null |
  grep -E 'clone|execve\(.*"ls"' |
  sed -E 's/.*flags=([A-Z_|]+).*/clone flags=\1/; s/(execve\("[^"]*").*/\1, …)/' | show
echo "== Python создаёт поток =="
strace -f -qq -e trace=clone,clone3 python3 -c '
import threading
threading.Thread(target=lambda: None).start()' 2>&1 |
  sed -E 's/.*flags=([A-Z_|]+).*/clone flags=\1/' | show
```

```text title="Вывод"
== bash запускает ls ==
clone flags=CLONE_CHILD_CLEARTID CLONE_CHILD_SETTID SIGCHLD
[pid   344] execve("/usr/bin/ls", …)
== Python создаёт поток ==
clone flags=CLONE_VM CLONE_FS CLONE_FILES CLONE_SIGHAND CLONE_THREAD
CLONE_SYSVSEM CLONE_SETTLS CLONE_PARENT_SETTID CLONE_CHILD_CLEARTID
```

В первом случае `clone` без `CLONE_VM` — это `fork`, и сразу за ним `execve` в ребёнке. Во втором есть `CLONE_VM` и `CLONE_THREAD` — это поток. Из `clone` оставлены только флаги, аргументы `execve` обрезаны до `…`.

### Частые ошибки в ответе

- «`exec` создаёт новый процесс». Он заменяет программу в существующем, PID не меняется.
- «`fork` запускает другую программу». Ребёнок — копия родителя, пока не вызовет `exec`.

## Copy-on-write, память после fork

`fork` не копирует память процесса сразу. Копируются таблицы страниц и структура задачи, а сами страницы остаются общими. Записи одного процесса другому не видны: после записи у процессов своё содержимое. Прогон ниже показывает, как общая память становится приватной. Цена `fork` — время и память на таблицы страниц и структуру задачи, а не на всю память процесса.

В `/proc/<pid>/smaps_rollup` видно, чья память чья. `Rss` — сколько резидентно в RAM, включая общие страницы, поэтому у ребёнка он сразу почти как у родителя. `Pss` делит общие страницы поровну между владельцами. `Shared_*` — страницы, на которые ссылается больше одного процесса, `Private_*` — только этот процесс.

```python title="cow.py"
import os
import time

SIZE = 200 * 1024 * 1024
FIELDS = ("Rss", "Pss", "Shared_Dirty", "Private_Dirty")


def mem(pid):
    out = {}
    with open(f"/proc/{pid}/smaps_rollup") as f:
        for line in f:
            key, _, rest = line.partition(":")
            if key in FIELDS:
                out[key] = int(rest.split()[0]) // 1024
    return out


def show(label, pid):
    m = mem(pid)
    print(f"{label:<24}" + "".join(f"{m[k]:>14}" for k in FIELDS))


print(f"{'МиБ':<24}" + "".join(f"{k:>14}" for k in FIELDS))
buf = bytearray(b"x") * SIZE
show("родитель до fork", os.getpid())

r, w = os.pipe()
child = os.fork()
if child == 0:
    os.read(r, 1)
    for i in range(0, SIZE, 4096):
        buf[i] = 1
    show("ребёнок после записи", os.getpid())
    os._exit(0)
time.sleep(0.5)
show("ребёнок после fork", child)
show("родитель после fork", os.getpid())
os.write(w, b"go")
os.waitpid(child, 0)
```

```text title="Вывод"
МиБ                                Rss           Pss  Shared_Dirty Private_Dirty
родитель до fork                   207           206             0           202
ребёнок после fork                 205           102           202             0
родитель после fork                207           104           202             0
ребёнок после записи               205           202             2           200
```

Объёмы у вас будут другими. Сразу после `fork` у ребёнка `Rss` около 200 МиБ, но почти всё это `Shared_Dirty`, а `Pss` вдвое меньше: память не продублирована. После записи в каждую страницу общее превращается в `Private_Dirty`: теперь у ребёнка свои 200 МиБ.

Это же объясняет, почему рост памяти после `fork` бывает неожиданным. Пока оба процесса только читают, лишней памяти нет. Как только один из них пишет, платит за копии страниц. Так работают воркеры с предзагруженными данными: общий объём растёт по мере изменения этих данных.

### Частые ошибки в ответе

- «`fork` копирует всю память сразу». Копируются таблицы страниц, сами страницы остаются общими до первой записи.
- «Rss ребёнка равен тому, сколько он занимает отдельно». В `Rss` входят общие страницы; для разделения смотрят `Pss` и `Private_*`.

## Дерево процессов и proc

У каждого процесса есть родитель (PPID). Все процессы образуют дерево с корнем PID 1. `ps` читает `/proc`: каждый каталог `/proc/<pid>/` — окно в состояние процесса. Там `status` (имя, состояние, PID, PPID, число потоков), `cmdline` (аргументы, разделённые нулевыми байтами), `exe` (символическая ссылка на выполняемый файл), `cwd` (ссылка на текущий каталог), `fd/` (по записи на каждый открытый файл).

```sh title="proc-tree.sh"
sleep 30 &
child=$!
ps -eo pid,ppid,stat,comm --forest
echo "---"
grep -E '^(Name|State|Tgid|PPid|Threads):' /proc/$child/status
echo "---"
echo "exe -> $(readlink /proc/$child/exe)"
echo "cwd -> $(readlink /proc/$child/cwd)"
printf 'cmdline: %s\n' "$(tr '\0' ' ' < /proc/$child/cmdline | sed 's/ $//')"
kill "$child"
```

```text title="Вывод"
  PID  PPID STAT COMMAND
  388     0 Ss   timeout
  394   388 S     \_ bash
  395   394 S         \_ sleep
  396   394 R         \_ ps
    1     0 Ss   tini
    7     1 S    sleep
---
Name:	sleep
State:	S (sleeping)
Tgid:	395
PPid:	394
Threads:	1
---
exe -> /usr/bin/sleep
cwd -> /root
cmdline: sleep 30
```

PID у вас будут другими. `tini` в корне — PID 1 песочницы, `sleep infinity` держит её живой. `timeout` и `bash` — обвязка прогона блока (`make linux-block`), `sleep 30` — ребёнок `bash`.

### Частые ошибки в ответе

- «`ps` — отдельная база процессов». Это чтение `/proc`, которым пользуются и `top`, и `lsof`.
- «PPID процесса всегда тот, кто его запустил». У процесса, переживающего родителя, он меняется (см. [раздел про сирот](#сироты-и-усыновление)).

## Состояния процесса

`ps` показывает состояние буквой в колонке `STAT`.

- **R** — выполняется или готов выполняться и ждёт CPU в очереди. Процесс с бесконечным циклом.
- **S** — спит и может быть разбужен сигналом или событием: ждёт данные из сокета, таймер, `sleep`. Большинство процессов большую часть времени здесь.
- **D** — непрерываемый сон, обычно ждёт ввода-вывода. Сигнал его не будит, поэтому такой процесс не убить даже `kill -9`, пока операция не вернётся. Типичные причины: медленный диск, зависшая сетевая файловая система.
- **Z** — зомби: процесс завершён, а родитель ещё не прочитал статус завершения (см. [раздел про зомби](#зомби)).
- **T** — остановлен сигналом управления заданиями (`SIGSTOP`, `Ctrl-Z`). Ещё есть `t` — остановка отладчиком при трассировке. Продолжить остановленный можно `SIGCONT`.

Колонка `WCHAN` показывает, в какой функции ядра процесс спит; название функции зависит от версии ядра.

```sh title="states.sh"
yes > /dev/null &
r=$!
sleep 60 &
s=$!
sleep 60 &
t=$!
sleep 0.3
kill -STOP "$t"
sh -c '(exit 0) & exec sleep 60' &
z=$!
sleep 0.5
ps -o pid,stat,wchan:16,comm -p "$r,$s,$t"
echo "--- зомби: потомок процесса sleep, который его не ждёт ---"
ps -o pid,ppid,stat,comm --ppid "$z"
kill -CONT "$t"
kill "$r" "$s" "$t" "$z" 2>/dev/null
wait 2>/dev/null
```

```text title="Вывод"
  PID STAT WCHAN            COMMAND
  423 R    -                yes
  424 S    hrtimer_nanoslee sleep
  425 T    do_signal_stop   sleep
--- зомби: потомок процесса sleep, который его не ждёт ---
  PID  PPID STAT COMMAND
  429   427 Z    sh
```

Строки по порядку: `yes` в R (если свободное ядро есть, оно выполняется), первый `sleep` в S, второй `sleep` остановлен и стоит в T. Зомби — потомок, чей родитель превратился в `sleep` и никогда его не ждёт.

D за секунду не поймать «из ничего», но на записи с синхронизацией на диск он виден. Поведение зависит от файловой системы и ядра, поэтому поймать D удаётся не на каждой выборке.

```sh title="state-d.sh"
dd if=/dev/zero of=/root/dd.bin bs=4k count=30000 oflag=dsync 2>/dev/null &
p=$!
for i in 1 2 3 4 5 6; do
  ps -o pid,stat,wchan:22,comm -p "$p" | tail -n 1
  sleep 0.3
done
kill "$p" 2>/dev/null
wait 2>/dev/null
rm -f /root/dd.bin
```

```text title="Вывод"
  452 D    folio_wait_bit_common  dd
  452 D    jbd2_log_wait_commit   dd
  452 D    jbd2_log_wait_commit   dd
  452 D    jbd2_log_wait_commit   dd
  452 D    jbd2_log_wait_commit   dd
  452 D    jbd2_log_wait_commit   dd
```

Чаще всего `dd` стоит в D и ждёт записи на диск, иногда успевает попасть в R. Строки у вас могут отличаться, как и имя функции в `WCHAN`.

### Частые ошибки в ответе

- «Процесс в D надо убить через `kill -9`». Сигнал доставится только когда процесс выйдет из этого состояния. Искать надо причину: диск или сетевую файловую систему, а не сигнал.
- «Процесс в D грузит CPU». Он ждёт ввода-вывода; смотреть надо диск или сетевую файловую систему.
- «`T` — это зависший процесс». Он остановлен намеренно и продолжится по `SIGCONT`.

## Зомби

Когда процесс завершается, ядро оставляет запись в таблице процессов с кодом завершения: родитель должен его прочитать системным вызовом `wait`. Пока родитель не вызвал `wait`, ребёнок — зомби (`Z`). Он занимает запись в таблице процессов и держит PID, а PID конечны.

Зомби уже завершён, поэтому сигнал, в том числе `kill -9`, его не убирает: в прогоне ниже статус `Z` после `SIGKILL` не меняется. Убирает его только `wait` родителя; если родитель умер, зомби усыновляет PID 1, который обязан сделать `wait`.

```python title="zombie.py"
import os
import signal
import subprocess
import time


def ps(pid):
    subprocess.run(["ps", "-o", "pid,ppid,stat,comm", "-p", str(pid)])


child = os.fork()
if child == 0:
    os._exit(0)
time.sleep(0.5)
print("ребёнок вышел, родитель не вызывал wait:")
ps(child)

os.kill(child, signal.SIGKILL)
time.sleep(0.5)
print("после SIGKILL:")
ps(child)

os.waitpid(child, 0)
print("после waitpid (осталась только шапка):")
ps(child)
```

```text title="Вывод"
ребёнок вышел, родитель не вызывал wait:
  PID  PPID STAT COMMAND
  492   491 Z    python3
после SIGKILL:
  PID  PPID STAT COMMAND
  492   491 Z    python3
после waitpid (осталась только шапка):
  PID  PPID STAT COMMAND
```

PID у вас будут другими. Статус `Z` не изменился после `SIGKILL` и пропал после `waitpid`.

На практике зомби копятся, когда родитель их игнорирует: например, процесс запускает дочерние и не вызывает `wait` или `waitpid`. Смотреть надо родителя (`PPID` зомби), а не зомби. Лечение — исправить код родителя или перезапустить родителя: когда он умрёт, зомби усыновит PID 1 и уберёт. Перезапускать нужно обычным завершением (`SIGTERM`); `kill -9` родителя — крайняя мера, потому что он не успеет закрыть соединения и дописать данные.

### Частые ошибки в ответе

- «Зомби убивают через `kill -9`». Процесс уже завершён; сигнал запись не убирает. Запись уберёт `wait` родителя или смерть родителя.
- «Зомби — это работающий процесс, который надо остановить». Это только запись в таблице процессов; опасны тем, что копятся и держат PID.
- «Зомби и сирота — одно и то же». Зомби завершился, а родитель его не прочитал. Сирота жив, а родитель умер.

## Сироты и усыновление

Если родитель умирает раньше потомка, тот остаётся без родителя. Ядро передаёт его PID 1 (в своём пространстве имён PID) или ближайшему предку, объявившему себя субреапером через `prctl`. PPID сироты меняется на PID усыновителя.

```python title="orphan.py"
import os
import subprocess
import time

child = os.fork()
if child == 0:
    print("ребёнок: PPID до =", os.getppid())
    time.sleep(1)
    print("ребёнок: PPID после =", os.getppid())
    subprocess.run(["ps", "-o", "pid,ppid,comm", "-p", f"{os.getppid()},{os.getpid()}"])
    os._exit(0)
time.sleep(0.3)
os._exit(0)
```

```text title="Вывод"
ребёнок: PPID до = 515
ребёнок: PPID после = 1
  PID  PPID COMMAND
    1     0 tini
  516     1 python3
```

PID у вас будут другими. После смерти родителя PPID ребёнка стал 1, и это `tini`. А теперь то же внутри нового пространства имён PID: `unshare --pid --fork --mount-proc` запускает `sh` как PID 1 нового пространства, и сироту усыновляет он.

```sh title="orphan-ns.sh"
unshare --pid --fork --mount-proc sh -c 'python3 -u - <<PY
import os, subprocess, time
if os.fork() == 0:
    time.sleep(1)
    subprocess.run(["ps", "-e", "-o", "pid,ppid,comm"])
    os._exit(0)
os._exit(0)
PY
sleep 2'
```

```text title="Вывод"
  PID  PPID COMMAND
    1     0 sh
    3     1 python3
    4     1 sleep
    5     3 ps
```

PID 1 здесь — `sh`, `sleep` с PID 4 — его `sleep 2`. Родитель сироты (первый `python3`) умер, а сирота (`python3` с PID 3) получила PPID 1.

### Частые ошибки в ответе

- «Сироты умирают вместе с родителем». Они продолжают жить и получают нового родителя.
- «Усыновляет всегда PID 1 хоста». PID 1 своего пространства имён PID или ближайший субреапер.

## PID 1 в контейнере

PID 1 особенный. Он усыновляет сирот и обязан делать `wait` для чужих потомков. Кроме того, сигнал, для которого у PID 1 нет обработчика, другие процессы пространства ему доставить не могут. Про сигналы подробнее на странице про них.

Приложение, запущенное в контейнере как PID 1, часто не готово к этой роли: если оно запускает подпроцессы и не вызывает `wait` для сирот, зомби копятся. Покажем это. Один и тот же скрипт: процесс порождает ребёнка, ребёнок порождает внука и сразу выходит, внук становится сиротой и умирает позже. Сначала скрипт сам PID 1, потом PID 1 — `tini`.

```sh title="pid1-zombies.sh"
cat > /tmp/spawn.py <<'PY'
import os
import subprocess
import time

for _ in range(3):
    child = os.fork()
    if child == 0:
        if os.fork() == 0:
            time.sleep(0.5)
            os._exit(0)
        os._exit(0)
    os.waitpid(child, 0)
time.sleep(1.5)
subprocess.run(["ps", "-e", "-o", "pid,ppid,stat,comm"])
PY
echo "== PID 1 не вызывает wait для сирот =="
unshare --pid --fork --mount-proc python3 /tmp/spawn.py
echo "== PID 1 — tini =="
unshare --pid --fork --mount-proc tini -- python3 /tmp/spawn.py
rm -f /tmp/spawn.py
```

```text title="Вывод"
== PID 1 не вызывает wait для сирот ==
  PID  PPID STAT COMMAND
    1     0 S    python3
    3     1 Z    python3
    5     1 Z    python3
    7     1 Z    python3
    8     1 R    ps
== PID 1 — tini ==
  PID  PPID STAT COMMAND
    1     0 S    tini
    2     1 S    python3
    9     2 R    ps
```

PID у вас будут другими. В первом случае внуки остались зомби (`Z`) с PPID 1: PID 1 их усыновил, но не вызвал `wait`. Во втором `tini` усыновил и сразу убрал их, остался только приложение под ним.

`tini` — крошечный init для контейнера: усыновляет и собирает зомби и пересылает полученные сигналы приложению. В Docker его включают флагом `docker run --init`. В образе можно прописать `ENTRYPOINT ["tini", "--"]`. Эта песочница сама запускается под `tini`: `tini -- sleep infinity`.

Если процесс не запускает подпроцессов, зомби не появятся и без init. Но сигналы в любом случае приходят PID 1 особым образом, поэтому init в контейнере безопаснее.

### Частые ошибки в ответе

- «Приложению в контейнере init не нужен». Нужен, если оно порождает процессы и не собирает сирот или не обрабатывает `SIGTERM`.
- «`tini` ускоряет или лечит приложение». Он только собирает зомби и передаёт сигналы.
- «Чтобы убрать зомби, перезапустить контейнер всегда правильно». Это лечение симптома: причина в том, что PID 1 не делает `wait`.
