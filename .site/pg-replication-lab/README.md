# pg-replication-lab

PostgreSQL 17: primary и три потоковые реплики со слотами, фоновая нагрузка и HTML-дашборд лага репликации в реальном времени.

```sh
docker compose up -d --build
open http://localhost:8088
```

| Сервис | Порт на хосте | Что это |
|---|---|---|
| primary | 15432 | `postgres` / `postgres`, БД `lab` |
| replica1, replica2 | 15433, 15434 | обычные async-реплики |
| replica3 | 15435 | отложенная: `recovery_min_apply_delay` = `REPLICA3_APPLY_DELAY` (5s) |
| loader | — | `pgbench -i -s 20`, затем бесконечный pgbench: tpcb-like + вставки в `events`, `LOADER_RATE` TPS (300) |
| dashboard | 8088 | Python + psycopg, SSE раз в секунду |

Реплика при пустом томе сама снимает `pg_basebackup` со слотом `<имя>_slot`, `cluster_name` становится `application_name` в `pg_stat_replication`.

## Что показывает дашборд

- **heartbeat** — дашборд 10 раз в секунду пишет `clock_timestamp()` в `heartbeat` на primary, на реплике читается `clock_timestamp() - ts`.
  Это сквозной лаг «запись на primary → видна на реплике». Он включает и остановки самого primary (fsync, checkpoint):
  если у всех реплик лаг одинаковый, сравни его с «возрастом heartbeat на primary».
- **отставание в байтах** — `pg_current_wal_lsn() - replay_lsn` из `pg_stat_replication`, а также sent / write / flush по отдельности.
- **write / flush / replay lag** — время из `pg_stat_replication`. Когда нагрузки нет, PostgreSQL показывает в этих полях NULL.
- **принято, но не применено** — `receive_lsn - replay_lsn` на самой реплике. У отложенной и поставленной на паузу реплики он растёт.
- **WAL держит слот** (строка таблицы в карточке реплики, не график) — сколько WAL primary хранит ради слота реплики.

## Сценарии

- **Пауза replay** на реплике (`pg_wal_replay_pause()`): WAL продолжает приходить, но не применяется. Лаг растёт линейно, после «возобновить» реплика догоняет.
- **Залп** — `INSERT ... SELECT generate_series` на 100k / 1M / 3M строк одной транзакцией: всплеск WAL.
- **Доп. вставка, строк/с** — постоянная нагрузка поверх pgbench.
- **Синхронная реплика** — `ALTER SYSTEM SET synchronous_standby_names = 'FIRST 1 (replicaN)'`: TPS на primary падает, `sync_state` = sync.
  Если остановить эту реплику (`docker compose stop replica1`), коммиты на primary встанут: так и задумано. Сними sync в дашборде.
- Остановить реплику целиком: `docker compose stop replica2`. Слот станет неактивным, и строка «WAL держит слот» начнёт расти.

## Управление контейнерами

`POST /api/services/<сервис>/<действие>`: сервисы `replica1..3` и `loader`, действия `start`, `stop` (SIGTERM, 10 с), `kill` (SIGKILL), `restart`.
Primary с дашборда не управляется. Docker API доступен только через `docker-proxy` (wollomatic/socket-proxy:1.14.0, порт не публикуется, клиент — только `dashboard`). Прокси пропускает `GET /containers/json` и `POST /containers/<id>/(start|stop|restart|kill)`; create, DELETE, exec и прочее — 403/405. Regex-прокси выбран вместо tecnativa/docker-socket-proxy: в v0.5.0 флаги `ALLOW_START/STOP/RESTARTS` работают только с `POST=1`, а он открывает create и другие записи. Флаг `:ro` на docker.sock от записи через Docker API не защищает; защищает только фильтр прокси.

Кнопки в дашборде:

| Кнопка | Где | Действие |
|---|---|---|
| stop / kill | карточка реплики | `stop` (SIGTERM, до 10 с) и `kill` (SIGKILL); обе спрашивают подтверждение |
| start / restart | карточка реплики | доступность зависит от состояния контейнера: `start` только у остановленного |
| обрыв связи / восстановить связь | карточка реплики | iptables DROP в обе стороны между primary и репликой (цепочка `LAB-PARTITION` в netns primary), бейдж «обрыв» |
| start / stop | панель «Нагрузка», `loader` | останов и запуск фоновой нагрузки pgbench |

Остановленная реплика показывается как «контейнер остановлен (<статус Docker>)», а не как ошибка подключения. Бейдж «обрыв» берётся из состояния агента netem:
после `docker compose restart netem` правила сбрасываются, и бейдж пропадает сам, без перезагрузки страницы.

`kill` оставляет контейнер в `exited` (код 137): `restart: unless-stopped` его не поднимает, потому что остановка командой Docker API считается ручной. Поднять — действием `start`.

## Сценарии управления

- **Падение реплики (kill).** Нажми `kill` на replica2. Карточка: «контейнер остановлен (Exited (137) ...)», сама реплика не поднимется, нужен `start`.
  На primary слот `replica2_slot` станет неактивным, строка «WAL держит слот» растёт, пока реплика лежит. После `start` реплика дочитывает WAL
  по слоту и догоняет; на время запуска карточка показывает «недоступна: database system is not yet accepting connections».
- **Аккуратный останов (stop).** То же через SIGTERM: Postgres завершается штатно (код 0, `Exited (0)`), слот так же неактивен и держит WAL.
  Если replica1 синхронная, а ты её остановил, коммиты на primary встанут (см. выше); сними sync в дашборде.
- **Обрыв связи.** Нажми «обрыв связи» на replica1: контейнер жив, но пакеты не ходят. Сразу виден бейдж «обрыв», heartbeat-лаг линейно растёт
  (замер: 8 с через 8 с после обрыва, 16 с через 16 с). Через `wal_sender_timeout` / `wal_receiver_timeout` = 10 с primary закрывает walsender,
  реплика пропадает из `pg_stat_replication` («не стримит», слот неактивен, WAL копится). «Восстановить связь» (или `docker compose restart netem`)
  возвращает стриминг, реплика догоняет.

## Docker API и docker-proxy

На Linux сокет Docker принадлежит `root:docker`, а `docker-proxy` работает под uid 65534: передай GID группы сокета, иначе кнопки управления не заработают:
`DOCKER_GID=$(stat -c %g /var/run/docker.sock) docker compose up -d` (или строкой `DOCKER_GID=...` в `.env`). На Docker Desktop значение по умолчанию (0) подходит.

POST дашборда (`/api/...`) требуют заголовок `X-Lab-Request: 1`, а присланный `Origin` должен совпадать с `Host`: так чужая страница в браузере не сможет остановить контейнеры. Без заголовка ответ 403.

`docker.sock` напрямую дашборду не отдан: доступ к нему равен root на хосте (create контейнера с bind-mount, exec), а `:ro` на сокете запись через API не ограничивает.
Поэтому между дашбордом и сокетом стоит `docker-proxy` с allowlist по регулярным выражениям: только `GET /containers/json` и
`POST /containers/<id>/(start|stop|restart|kill)`. Всё остальное получает 403/405. Дополнительно дашборд сам проверяет сервис и действие по белому списку.

## Ограничения

- Запись WAL в Docker Desktop упирается в fsync тома внутри VM: на залпе бэкенды ждут `WALWrite`, и TPS проседает. Это свойство стенда, а не PostgreSQL.
- **netem и таймауты:** `wal_sender_timeout` / `wal_receiver_timeout` = 10 с, поэтому `delay` ограничен 5000 мс: при большей задержке репликация рвалась бы по таймауту, а не из-за задержки.
- **Обрыв остановленной реплики:** если у реплики нет IP (контейнер остановлен), обрыв запоминается, бейдж показывает «ждёт IP реплики», а правила ставятся, как только IP появится.
- **netem** задерживает только исходящий трафик primary → реплика (WAL); обратный поток (ответы реплики) идёт без задержки,
  так что RTT = заданная задержка + собственное время ответа. Задержка 300 мс на фоновой нагрузке даёт heartbeat-лаг 0,3-0,6 с и не растёт.
- **netem и jitter:** netem с jitter сам переупорядочивает пакеты (у каждого своё время отправки), и TCP primary это не переживает:
  `reordering:300`, спурионные ретрансмиты, `cwnd` в единицы, лаг растёт без предела (замер: 300 мс + 20 мс jitter, лаг 118 с за 120 с).
  Агент поэтому добавляет к netem с jitter `rate 10gbit`: очередь становится FIFO, переупорядочивания нет, на скорость это не влияет.
  Проверено: 300 мс + 20 мс jitter держит лаг 0,37-0,47 с, как и без jitter. Если задан свой `rate_mbit`, он и так сохраняет порядок.
  Дашборд сам даёт нагрузку, которая может подпереть лаг: после большого залпа pgbench догоняет расписание на полной скорости,
  и лаг всех реплик растёт независимо от netem. Перед замером задержки дождись, пока лаг без netem вернётся к норме (при необходимости `docker compose restart loader`).
- Пароли и порты — только для локального стенда (порты слушают 127.0.0.1).

```sh
docker compose down -v   # снести стенд вместе с данными
```
