Разбор типовых SQL-задач с live-coding собеседований бэкенд-разработчика. Диалект — PostgreSQL 15 и новее, все запросы прогнаны на PostgreSQL 17 на одной общей схеме из первого раздела. В каждой задаче: что просят, идея решения словами, сам запрос, почему он работает, где обычно ошибаются, какая есть альтернатива и сколько она стоит, какой нужен индекс.

> [!note] Термины, которые встретятся в заметке
> Каждый подробно разобран там, где применяется; здесь — короткая расшифровка.
> - **Оконная функция** — функция, которая считает значение для каждой строки, глядя на соседние строки, но не склеивает строки в одну, как это делает `GROUP BY`. Записывается как `функция() OVER (...)`.
> - **`PARTITION BY`** — часть `OVER`, которая делит строки на независимые группы («окна»): функция считается внутри каждой группы отдельно.
> - **`ROW_NUMBER`, `RANK`, `DENSE_RANK`** — оконные функции нумерации строк; отличаются тем, как ведут себя при равных значениях ([[#ROW_NUMBER, RANK и DENSE_RANK: три способа пронумеровать строки]]).
> - **CTE (Common Table Expression, общее табличное выражение)** — подзапрос с именем, записанный через `WITH имя AS (...)` перед основным запросом. Читается как временная таблица, которая живёт только на время запроса.
> - **`LATERAL`** — слово перед подзапросом в `FROM`, которое разрешает подзапросу ссылаться на столбцы таблиц, стоящих левее. Подзапрос выполняется заново для каждой строки левой таблицы.
> - **Anti-join (анти-соединение)** — выбрать строки из A, для которых нет пары в B («клиенты без заказов»).
> - **Semi-join (полусоединение)** — выбрать строки из A, для которых пара в B есть, но не размножать строку по числу пар («клиенты, у которых есть хотя бы один оплаченный заказ»).
> - **Gaps and islands («пропуски и острова»)** — класс задач про серии подряд идущих значений («острова») и дыры между ними («пропуски»).
> - **Keyset pagination (пагинация по ключу)** — постраничный вывод, где следующая страница запрашивается словами «строки после такого-то ключа», а не «пропусти N строк» ([[#OFFSET на больших смещениях]]).
> - **Tie-breaker (разрешение ничьей)** — дополнительный столбец в `ORDER BY` (обычно уникальный `id`), чтобы порядок равных строк был однозначным.
> - **`NULL`** — «значение неизвестно», а не ноль и не пустая строка. Любое сравнение с `NULL` даёт не «истина» и не «ложь», а «неизвестно», и `WHERE` такие строки отбрасывает ([[#= NULL]]).

> [!tip] Как выбрать приём
> Читай условие и ищи ключевую фразу.
> - «топ-N в каждой группе» — `ROW_NUMBER` или `DENSE_RANK` ([[#Топ-N в каждом отделе]]). Если групп мало, в каждой много строк и есть подходящий индекс, быстрее `LATERAL` с `LIMIT` ([[#LATERAL как топ-N в группе]])
> - «N-я по величине» — `DENSE_RANK` или `OFFSET` ([[#N-я по величине зарплата]])
> - «N дней подряд», «серии», «непрерывные периоды» — gaps and islands ([[#Дни подряд]])
> - «есть в A, нет в B» — `NOT EXISTS` ([[#Клиенты без заказов]])
> - «есть в A и в B, но без дублей» — `EXISTS`, а не `JOIN` с `DISTINCT`
> - «по месяцам, включая пустые» — `generate_series` (генератор рядов значений) и `LEFT JOIN` ([[#Выручка по месяцам с пустыми месяцами]])
> - «иерархия любой глубины», «все подчинённые» — рекурсивный CTE ([[#Все подчинённые любой глубины]])
> - «рост к прошлому периоду», «разница с предыдущей строкой» — `LAG` и `LEAD` (значение из предыдущей и следующей строки)
> - «нарастающий итог», «скользящее среднее» — агрегат с `OVER (ORDER BY ...)` и рамкой окна
> - «доля от итога» — `sum() OVER ()`
> - «последняя или первая запись по ключу» — `DISTINCT ON` или `ROW_NUMBER`
> - «медиана», «перцентиль» — `percentile_cont`
> - «пропуски в id» — `LEAD` или `generate_series` с `LEFT JOIN`
> - «удалить дубли» — `ROW_NUMBER` по ключу дубля, удалять строки с номером больше 1

## Схема для примеров

Все задачи ниже решаются на этой схеме. Данные подобраны так, чтобы подвохи проявлялись на деле: `NULL` в `manager_id` и `amount`, ничья в зарплатах, пропущенный день в `logins`, пустой март в `orders`, клиент без заказов, отдел без сотрудников, два отдела с одинаковой средней зарплатой.

- `departments` — отделы; `employees` — сотрудники со ссылкой на отдел и на менеджера (у топ-менеджера `manager_id` равен `NULL`).
- `customers` — клиенты; `orders` — заказы со статусом и суммой (сумма может быть `NULL`); `logins` — дни, в которые клиент заходил.
- `emails` и `tickets` — вспомогательные таблицы для задач про дубли и пропуски в нумерации.

```sql
CREATE TABLE departments (
    id   int PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE employees (
    id            int PRIMARY KEY,
    name          text NOT NULL,
    department_id int REFERENCES departments (id),
    manager_id    int REFERENCES employees (id),   -- NULL у топ-менеджера
    salary        int NOT NULL
);

CREATE TABLE customers (
    id   int PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE orders (
    id          int PRIMARY KEY,
    customer_id int NOT NULL REFERENCES customers (id),
    amount      numeric(10, 2),                    -- может быть NULL
    status      text NOT NULL,                     -- new (новый) / paid (оплачен) / cancelled (отменён)
    created_at  timestamptz NOT NULL
);

CREATE TABLE logins (
    user_id int  NOT NULL REFERENCES customers (id),
    day     date NOT NULL,
    PRIMARY KEY (user_id, day)
);

-- вспомогательные таблицы для двух задач
CREATE TABLE emails  (id serial PRIMARY KEY, email text NOT NULL);
CREATE TABLE tickets (id int PRIMARY KEY);
```

## Порядок выполнения запроса

База выполняет части запроса не в том порядке, в котором они написаны. Логический порядок такой:

1. `FROM` и `JOIN` собирают исходные строки.
2. `WHERE` отфильтровывает строки до группировки.
3. `GROUP BY` объединяет оставшиеся строки в группы.
4. `HAVING` отфильтровывает группы.
5. Оконные функции считаются по строкам, которые прошли шаги 1–4.
6. `SELECT` вычисляет выражения и задаёт псевдонимы (алиасы, `AS ...`).
7. `DISTINCT` убирает повторяющиеся строки результата.
8. `ORDER BY` сортирует.
9. `LIMIT` и `OFFSET` отрезают нужный кусок.

Из этого следуют два вопроса, которые задают на каждом собеседовании.

### Алиас из SELECT в WHERE

Условие: можно ли в `WHERE` пользоваться псевдонимом, объявленным в `SELECT`? Нельзя. `WHERE` выполняется раньше `SELECT`, и на этом шаге псевдонима ещё не существует.

```sql
SELECT salary * 12 AS yearly FROM employees WHERE yearly > 3000;
-- ERROR: column "yearly" does not exist
```

Повтори выражение в `WHERE` или вынеси вычисление в подзапрос или CTE. Псевдоним работает в `ORDER BY`, потому что сортировка идёт после `SELECT`. В PostgreSQL он работает и в `GROUP BY` (можно написать `GROUP BY d` для `department_id AS d`), но не в `HAVING`.

### Оконная функция в WHERE

Оконные функции считаются после `WHERE` и `HAVING`, поэтому условие по ним в `WHERE` запрещено: на этом шаге значения ещё нет.

```sql
SELECT name FROM employees WHERE row_number() OVER (ORDER BY salary) = 1;
-- ERROR: window functions are not allowed in WHERE
```

Решение — посчитать окно во вложенном подзапросе (или в CTE), а отфильтровать снаружи:

```sql
SELECT name, salary FROM (
    SELECT name, salary, row_number() OVER (ORDER BY salary DESC) AS rn
    FROM employees
) t
WHERE rn <= 3;   -- Anna, Egor, Dina
```

> [!tip] Следствие
> Фильтр в `WHERE` уменьшает набор строк, который попадает в окно или агрегат, а фильтр снаружи окна его не уменьшает: окно уже посчитано по всем строкам. Например, `WHERE status = 'paid'` перед `sum() OVER ()` изменит итог, а внешний фильтр после окна — нет.

## JOIN и подзапросы

Виды соединений:

- `INNER JOIN` оставляет только пары строк, у которых есть совпадение.
- `LEFT JOIN` оставляет все строки левой таблицы; если пары справа нет, столбцы правой таблицы заполняются `NULL`.
- `FULL JOIN` оставляет все строки обеих таблиц.
- `CROSS JOIN` даёт декартово произведение: каждая строка левой с каждой строкой правой.
- `RIGHT JOIN` почти не нужен: поменяй таблицы местами и используй `LEFT`.

### Условие на правую таблицу в WHERE

Условие: вывести клиентов с их оплаченными заказами. Типичная ошибка — написать условие на правую таблицу в `WHERE`.

```sql
-- Ловушка: Cat исчезла, LEFT JOIN стал INNER
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';
```

У Cat заказов нет, поэтому после `LEFT JOIN` её `o.status` равен `NULL`. Условие `NULL = 'paid'` не истинно, и `WHERE` выбрасывает строку. Получилось, что `LEFT JOIN` повёл себя как `INNER JOIN`. Чтобы условие не убивало строки без пары, кладут его в `ON`: тогда оно участвует в поиске пары, а не в фильтрации готового результата.

```sql
SELECT c.name, count(o.id) AS paid_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
GROUP BY c.id, c.name
ORDER BY c.id;   -- Ann 2, Bob 2, Cat 0, Dan 2
```

Для `INNER JOIN` разницы между `ON` и `WHERE` нет. Для `LEFT JOIN` она принципиальная.

### Клиенты без заказов

Условие: клиенты, у которых нет ни одного заказа. Это anti-join.

Идея: для каждого клиента проверить, существует ли хотя бы один его заказ, и оставить тех, у кого такого нет.

```sql
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);   -- Cat
```

`NOT EXISTS (подзапрос)` истинно, когда подзапрос не вернул ни одной строки. Что именно выбирается в подзапросе (`SELECT 1`), неважно: проверяется только наличие строк.

Альтернатива — `LEFT JOIN ... WHERE o.id IS NULL`: присоединить заказы и оставить клиентов, к которым ничего не присоединилось. Планировщик строит из обоих вариантов один и тот же план (Anti Join), результат одинаков. `NOT EXISTS` читается как условие на человеческом языке, а не как трюк с `NULL`.

> [!warning] NOT IN и NULL
> `x NOT IN (подзапрос)` возвращает пустой результат, если в подзапросе есть хотя бы один `NULL`. Причина: `x <> NULL` даёт «неизвестно», и условие для всех строк оказывается не истинным.
> ```sql
> -- сотрудники, которые не являются менеджерами; у Anna manager_id IS NULL
> SELECT name FROM employees WHERE id NOT IN (SELECT manager_id FROM employees);   -- 0 строк
>
> SELECT name FROM employees e
> WHERE NOT EXISTS (SELECT 1 FROM employees s WHERE s.manager_id = e.id);          -- Vera, Gleb, Egor, Zoya, Ivan
> ```
> Для клиентов без заказов `NOT IN` случайно работает, пока на `orders.customer_id` стоит `NOT NULL`. Это хрупко: через год колонку сделают допускающей `NULL`, и запрос молча начнёт возвращать пустой результат. Поэтому всегда `NOT EXISTS`.

Индекс: `orders (customer_id)`. Без него `NOT EXISTS` для каждого клиента сканирует всю таблицу `orders`.

### Клиенты с оплаченным заказом (semi-join)

Условие: клиенты, у которых есть хотя бы один оплаченный заказ, каждый клиент один раз.

```sql
SELECT c.name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'paid');
-- Ann, Bob, Dan по одному разу
```

Обычный `JOIN orders` вернул бы Ann дважды, по числу её оплаченных заказов. `EXISTS` останавливается на первом найденном совпадении и не размножает строки клиента. Вариант с `DISTINCT` после `JOIN` даёт тот же ответ, но работает хуже: сначала строит все пары, потом убирает повторы.

### Сотрудники, получающие больше своего менеджера

Условие: найти сотрудников, чья зарплата больше зарплаты их непосредственного менеджера.

Идея: self-join (самосоединение). Таблица `employees` присоединяется сама к себе: одна копия (`e`) играет сотрудника, вторая (`m`) — его менеджера; пары находятся по условию `m.id = e.manager_id`.

```sql
SELECT e.name, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;   -- Egor 260 > Dina 250
```

`INNER JOIN` сам отбрасывает топ-менеджеров: у них `manager_id` равен `NULL`, и пары не находится. Если в условии сказано «вывести всех сотрудников и имя менеджера (если он есть)», нужен `LEFT JOIN`.

### Размножение строк при JOIN двух «один-ко-многим»

Условие: суммарная выручка и число дней активности по каждому клиенту. И у `orders`, и у `logins` связь с клиентом «один-ко-многим»: у одного клиента много заказов и много дней входа.

```sql
-- Ловушка: Ann получает 1100 вместо 220
SELECT c.name, sum(o.amount) AS total, count(l.day) AS days
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN logins l ON l.user_id = c.id
GROUP BY c.id, c.name ORDER BY c.id;
-- сумма / число дней: Ann 1100.00 / 15, Bob 800.00 / 6, Dan 1800.00 / 12
```

Что произошло: у Ann 3 заказа и 5 входов. `JOIN` строит все сочетания заказа и входа, то есть 15 строк, и каждый заказ повторяется 5 раз. Сумма и количество считаются по размноженным строкам, поэтому оба числа завышены.

Решение: свернуть каждую сторону до одной строки на клиента ещё до соединения, и тогда соединяются по одной строке с каждой стороны.

```sql
SELECT c.name, o.total, l.days
FROM customers c
JOIN (SELECT customer_id, sum(amount) AS total FROM orders GROUP BY customer_id) o ON o.customer_id = c.id
JOIN (SELECT user_id, count(*) AS days FROM logins GROUP BY user_id) l ON l.user_id = c.id
ORDER BY c.id;
-- сумма / число дней: Ann 220.00 / 5, Bob 400.00 / 2, Dan 450.00 / 4
```

Альтернатива — коррелированные подзапросы в `SELECT` (подзапрос, который ссылается на строку внешнего запроса). Писать проще, но подзапрос выполняется заново для каждой строки внешнего запроса. Признак этого бага: итоги получаются во столько раз больше ожидаемых, во сколько размножились строки.

## Агрегация

Агрегатные функции (`count`, `sum`, `avg`, `min`, `max`) сворачивают много строк в одно значение.

### GROUP BY и HAVING

`WHERE` фильтрует строки до группировки, `HAVING` фильтрует группы после неё. Условие по агрегату (`count(*) > 2`) в `WHERE` писать нельзя: на этом шаге групп ещё нет.

```sql
SELECT customer_id, count(*) AS n, sum(amount) AS s
FROM orders
GROUP BY customer_id
HAVING count(*) > 2;   -- клиенты 1, 2, 4
```

Всё, что есть в `SELECT` и не завёрнуто в агрегатную функцию, должно быть перечислено в `GROUP BY`. Исключение: столбцы, однозначно определяемые первичным ключом, который указан в `GROUP BY` (`GROUP BY c.id` разрешает выбирать `c.name`). Я всё равно перечисляю оба столбца: так запрос переносимее между СУБД (системами управления базами данных: PostgreSQL, MySQL и другими).

### COUNT(*), COUNT(col), COUNT(DISTINCT col)

```sql
SELECT count(*) AS all_rows,                       -- 9: все строки
       count(amount) AS non_null,                  -- 8: только строки, где amount не NULL
       count(DISTINCT customer_id) AS customers    -- 3: число разных клиентов, NULL не считается
FROM orders;
```

Ловушка: `count(col)` пропускает `NULL`, а `count(*)` считает строки целиком. После `LEFT JOIN` считай `count(o.id)`, а не `count(*)`: для клиента без заказов `count(*)` вернёт 1 (одна строка, в которой справа `NULL`), а `count(o.id)` вернёт 0, как и должно быть.

### Условная агрегация и FILTER

Условие: по каждому клиенту число заказов по статусам и сумма оплаченных. Такую раскладку называют pivot (сводная таблица: значения статуса превращаются в столбцы).

```sql
SELECT customer_id,
       count(*) FILTER (WHERE status = 'paid')      AS paid,
       count(*) FILTER (WHERE status = 'new')       AS new,
       count(*) FILTER (WHERE status = 'cancelled') AS cancelled,
       sum(amount) FILTER (WHERE status = 'paid')   AS paid_sum
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
-- порядок значений: paid / new / cancelled / paid_sum
-- клиент 1: 2 / 0 / 1 / 150.00,  клиент 2: 2 / 1 / 0 / 320.00,  клиент 4: 2 / 1 / 0 / 450.00
```

`FILTER (WHERE ...)` после агрегата говорит: учитывай только строки, подходящие под условие. Это один проход по таблице вместо трёх отдельных `GROUP BY`, склеенных через `JOIN`.

Классический вариант без `FILTER` — `sum(CASE WHEN status = 'paid' THEN amount END)`. Результат тот же, он работает в любой СУБД, но выглядит шумнее. Для `count` через `CASE` пиши `THEN 1` без `ELSE 0`: иначе `count` посчитает и нули, ведь он пропускает только `NULL`.

### NULL в агрегатах

- `sum`, `avg`, `min`, `max` игнорируют `NULL`.
- `sum` по пустому набору строк возвращает `NULL`, а не 0.
- `avg(col)` делит на число ненулевых значений, а не на число строк.

```sql
SELECT sum(amount) FROM orders WHERE status = 'refunded';                 -- NULL
SELECT coalesce(sum(amount), 0) FROM orders WHERE status = 'refunded';    -- 0

-- у Dan три заказа, у одного amount равен NULL
SELECT avg(amount)               AS avg_skip_null,   -- 225: (300 + 150) / 2
       sum(amount) / count(*)    AS sum_over_all,    -- 150: (300 + 150) / 3
       avg(coalesce(amount, 0))  AS avg_zero         -- 150
FROM orders WHERE customer_id = 4;
```

`coalesce(x, 0)` подставляет 0 вместо `NULL`. Что считать «средним заказом», когда есть заказ без суммы, — вопрос к бизнесу, и решение должно быть осознанным. `coalesce` ставь снаружи агрегата, если нужен результат для пустой группы. Внутрь агрегата его ставь, если `NULL` по смыслу означает ноль.

### Доля и целочисленное деление

Условие: процент оплаченных заказов.

```sql
SELECT count(*) FILTER (WHERE status = 'paid') / count(*)                     AS bad,    -- 0
       round(100.0 * count(*) FILTER (WHERE status = 'paid') / count(*), 1)   AS pct     -- 66.7
FROM orders;
```

`count` возвращает `bigint` (целое число), и `6 / 9` для целых — целочисленное деление, то есть 0. Домножь на `100.0` или приведи значение к `numeric` до деления. Порядок важен: выражение `count(*) FILTER (...) / count(*) * 100.0` даст 0, потому что деление уже выполнилось над целыми.

## Оконные функции

Обычный агрегат с `GROUP BY` схлопывает группу строк в одну. Оконная функция считает значение для каждой строки, но строки при этом остаются на месте. Окно описывается в скобках после `OVER`:

- `PARTITION BY` делит строки на независимые группы; без него все строки образуют одну группу;
- `ORDER BY` задаёт порядок строк внутри группы;
- рамка (`ROWS`, `RANGE` или `GROUPS`) говорит, какие именно строки группы видит функция для текущей строки: например, «от начала до текущей» или «шесть предыдущих и текущая».

### ROW_NUMBER, RANK и DENSE_RANK: три способа пронумеровать строки

Все три присваивают строкам номера по порядку сортировки и различаются только поведением при ничьей (равных значениях). Пример — отдел 1, ничья у Boris и Vera:

```sql
SELECT name, salary,
       row_number() OVER w AS rn,
       rank()       OVER w AS rnk,
       dense_rank() OVER w AS drnk
FROM employees
WHERE department_id = 1
WINDOW w AS (ORDER BY salary DESC)
ORDER BY salary DESC, id;
```

`WINDOW w AS (...)` даёт окну имя, чтобы не повторять его три раза.

| name | salary | rn | rnk | drnk |
| --- | --- | --- | --- | --- |
| Anna | 300 | 1 | 1 | 1 |
| Boris | 200 | 2 | 2 | 2 |
| Vera | 200 | 3 | 2 | 2 |
| Gleb | 150 | 4 | 4 | 3 |

- `ROW_NUMBER` даёт каждой строке уникальный номер. На ничьей порядок равных строк произвольный, поэтому добавляй tie-breaker в `ORDER BY` (например, `id`).
- `RANK` даёт равным значениям одинаковый ранг, а следующий ранг пропускает: после двух вторых мест идёт четвёртое.
- `DENSE_RANK` тоже даёт равным значениям одинаковый ранг, но без пропусков: после двух вторых мест идёт третье.

Как выбирать: если нужно ровно N строк, бери `ROW_NUMBER`. Если нужны все строки, равные граничной (например, все, кто делит последнее место), бери `RANK` или `DENSE_RANK`.

### Топ-N в каждом отделе

Условие: двое самых высокооплачиваемых сотрудников в каждом отделе.

Идея: пронумеровать сотрудников внутри каждого отдела по убыванию зарплаты и оставить тех, чей номер не больше 2. Нумерация идёт в окне с `PARTITION BY department_id`, поэтому для каждого отдела она начинается заново. Фильтр по номеру нельзя писать в том же запросе (оконная функция в `WHERE` запрещена), поэтому окно считается во вложенном подзапросе.

```sql
SELECT department_id, name, salary
FROM (
    SELECT department_id, name, salary,
           dense_rank() OVER (PARTITION BY department_id ORDER BY salary DESC) AS dr
    FROM employees
) t
WHERE dr <= 2
ORDER BY department_id, salary DESC, name;
```

В отделе 1 вернутся трое: Anna, а также Boris и Vera, которые делят второе место. С `ROW_NUMBER` одна из двух (Vera) пропала бы случайно, поэтому на интервью уточни, что делать с ничьей.

Индекс `employees (department_id, salary DESC)` позволяет читать каждую группу уже отсортированной, но окно всё равно считается по всей таблице. Для «топ-N из очень многих строк в немногих группах» лучше `LATERAL` ([[#LATERAL как топ-N в группе]]).

### N-я по величине зарплата

Условие: вторая по величине зарплата. Если такой нет, вернуть `NULL`. «Вторая по величине» значит второе уникальное значение: две одинаковые максимальные зарплаты не занимают места первой и второй.

Идея первого решения: `DENSE_RANK` нумерует разные значения без пропусков, останется взять значение с номером 2. Идея второго: отсортировать уникальные значения по убыванию и пропустить первое (`OFFSET 1`).

```sql
-- DENSE_RANK: ничья не сдвигает номер
SELECT salary
FROM (SELECT salary, dense_rank() OVER (ORDER BY salary DESC) AS dr FROM employees) t
WHERE dr = 2
GROUP BY salary;                                           -- 260

-- OFFSET: скалярный подзапрос сам превращает «нет строки» в NULL
SELECT (SELECT DISTINCT salary FROM employees
        ORDER BY salary DESC OFFSET 1 LIMIT 1) AS second_salary;       -- 260
SELECT (SELECT DISTINCT salary FROM employees
        ORDER BY salary DESC OFFSET 99 LIMIT 1) AS salary_99;          -- NULL
```

`GROUP BY salary` в первом запросе схлопывает несколько сотрудников с одинаковой зарплатой в одну строку. Скалярный подзапрос — подзапрос в скобках, который используется как одно значение; если он не вернул строк, значением становится `NULL`.

Подвохи:

- Вариант с окном при `dr = 99` вернёт ноль строк, а не `NULL`. Если нужен именно `NULL`, оберни запрос во внешний `SELECT (...)`.
- Для второго максимума можно написать `max(salary) WHERE salary < (SELECT max(salary) ...)`, но для N больше 2 это не масштабируется.
- `OFFSET 1` без `DISTINCT` вернёт вторую строку, а не второе значение: если на первом месте дубль, получится то же число, что и на первом.

### Нарастающий итог

Условие: для оплаченных заказов в порядке времени вывести накопленную сумму. Идея: `sum` как оконная функция с `ORDER BY` внутри `OVER` суммирует строки от начала до текущей.

```sql
SELECT id, created_at::date AS day, amount,
       sum(amount) OVER (ORDER BY created_at, id) AS running
FROM orders
WHERE status = 'paid'
ORDER BY created_at;      -- running по строкам: 100, 150, 350, 470, 770, 920

-- по клиентам: добавь PARTITION BY
SELECT customer_id, id, amount,
       sum(amount) OVER (PARTITION BY customer_id ORDER BY created_at, id) AS running
FROM orders WHERE status = 'paid';
```

Если в `OVER` есть `ORDER BY`, а рамка не задана, по умолчанию действует `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` («от самой первой строки до текущей»). Режим `RANGE` считает все строки с одинаковым ключом сортировки одним моментом, и они получают одинаковый итог. Поэтому `id` в `ORDER BY` служит tie-breaker: без него два заказа в одну секунду получили бы одинаковый «нарастающий» итог, а не последовательно растущий.

### Скользящее среднее за 7 дней

Условие: средняя дневная выручка за текущий день и 6 предыдущих.

Идея: сначала свернуть заказы в выручку по дням (в CTE `daily`), потом посчитать `avg` по окну из последних дней. Окно можно задать двумя способами: через `ROWS` (считать строки) и через `RANGE` (считать значения ключа сортировки).

```sql
WITH daily AS (
    SELECT created_at::date AS day, sum(amount) AS revenue
    FROM orders WHERE status = 'paid' GROUP BY 1
)
SELECT day, revenue,
       round(avg(revenue) OVER (ORDER BY day
             RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW), 2) AS avg_range,
       round(avg(revenue) OVER (ORDER BY day
             ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2)                  AS avg_rows
FROM daily ORDER BY day;
```

`GROUP BY 1` значит «сгруппировать по первому столбцу `SELECT`».

Подвох проявляется, когда в данных есть пустые дни. Возьмём 20 января: `avg_range` равен 50.00, потому что в диапазоне «последние 6 дней» только сам этот день. А `avg_rows` равен 75.00, потому что `ROWS` взял предыдущую строку, то есть 5 января, а это уже не «предыдущие 6 дней», а просто «предыдущая строка». Итог: `ROWS` считает строки, `RANGE` считает значения ключа.

Для календарного окна при пропусках нужен `RANGE` с интервалом (поддерживается с PostgreSQL 11, ключ сортировки должен быть `date` или `timestamp`) либо добавление пустых дней через `generate_series` ([[#Выручка по месяцам с пустыми месяцами]]) с последующим `ROWS`.

### Ловушка LAST_VALUE

`last_value(name)` должна вернуть «последнее» значение в окне, но по умолчанию возвращает не то, что ожидаешь.

```sql
SELECT name, salary,
       last_value(name) OVER (ORDER BY salary) AS lv_default,
       last_value(name) OVER (ORDER BY salary
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS lv_full
FROM employees WHERE department_id = 2 ORDER BY salary;
-- lv_default: Zoya, Dina, Egor (всегда сама строка)   lv_full: Egor, Egor, Egor
```

Рамка по умолчанию заканчивается на текущей строке (вместе со строками, равными ей по ключу сортировки), поэтому «последняя» строка рамки — это сама текущая строка. Для `last_value` и `nth_value` (значение с заданным номером в окне) всегда задавай рамку явно, как в `lv_full`, либо переверни порядок сортировки и бери `first_value`.

### Рост выручки месяц к месяцу

Условие: выручка по месяцам и её изменение в процентах к предыдущему месяцу.

Идея: свернуть заказы в выручку по месяцам (CTE `m`), затем функцией `lag(revenue)` взять значение из предыдущей строки и сравнить с текущим.

```sql
WITH m AS (
    SELECT date_trunc('month', created_at)::date AS month, sum(amount) AS revenue
    FROM orders WHERE status = 'paid' GROUP BY 1
)
SELECT month, revenue,
       lag(revenue) OVER (ORDER BY month) AS prev,
       round(100.0 * (revenue - lag(revenue) OVER (ORDER BY month))
             / lag(revenue) OVER (ORDER BY month), 1) AS growth_pct
FROM m ORDER BY month;
-- 2025-01: 350, NULL   2025-02: 420, +20.0   2025-04: 150, -64.3
```

У первой строки предыдущей нет, поэтому она получает `NULL`. Можно было бы написать `lag(x, 1, 0)`, подставив 0 вместо `NULL`, но тогда деление на 0 упадёт с ошибкой; лучше оставить `NULL`. `LEAD` делает то же самое в обратную сторону: берёт значение из следующей строки.

Подвох: марта в данных нет, поэтому `lag` для апреля возьмёт февраль, а не пустой март. Если нужно сравнение с календарным предыдущим месяцем, сначала дополни список месяцев пустыми ([[#Выручка по месяцам с пустыми месяцами]]).

### Доля от итога

Условие: доля зарплаты каждого сотрудника в зарплате всей компании и в зарплате его отдела.

```sql
SELECT name, salary,
       round(100.0 * salary / sum(salary) OVER (), 1)                         AS pct_company,
       round(100.0 * salary / sum(salary) OVER (PARTITION BY department_id), 1) AS pct_dept
FROM employees ORDER BY id;
```

Пустое `OVER ()` означает окно из всех строк, поэтому `sum(salary) OVER ()` — общий итог, выданный в каждой строке. Так можно обойтись без самосоединения с подзапросом `(SELECT sum(...))`, и таблица читается один раз.

### Первый заказ каждого клиента

Условие: по одному первому заказу на каждого клиента. Есть два способа: специфичный для PostgreSQL `DISTINCT ON` и переносимый вариант с `ROW_NUMBER`.

```sql
-- PostgreSQL-специфично: лаконично, и на индексе (customer_id, created_at) быстро
SELECT DISTINCT ON (customer_id) customer_id, id, created_at
FROM orders
ORDER BY customer_id, created_at, id;

-- переносимо
SELECT customer_id, id, created_at
FROM (SELECT *, row_number() OVER (PARTITION BY customer_id ORDER BY created_at, id) AS rn FROM orders) t
WHERE rn = 1;
```

`DISTINCT ON (customer_id)` оставляет по одной строке на каждое значение `customer_id`, и это первая строка группы в порядке `ORDER BY`. `ORDER BY` обязан начинаться с тех же столбцов, что и `DISTINCT ON`. Без `ORDER BY` выбор «первой» строки произволен.

`ROW_NUMBER` нужен, когда требуется топ-N (а не только одна строка) или когда запрос должен работать не только в PostgreSQL.

## Классические задачи

### Найти дубли и удалить

Условие: в таблице `emails` повторяются адреса. Найти повторы и оставить по одной строке на адрес, с наименьшим `id`.

Идея: внутри каждой группы одинаковых адресов пронумеровать строки по `id`. Строка с номером 1 остаётся, все строки с номером больше 1 — дубли, их и удаляем.

```sql
SELECT email, count(*) FROM emails GROUP BY email HAVING count(*) > 1;   -- a@x.io 3, b@x.io 2

DELETE FROM emails
WHERE id IN (
    SELECT id FROM (
        SELECT id, row_number() OVER (PARTITION BY email ORDER BY id) AS rn
        FROM emails
    ) t
    WHERE rn > 1
);   -- DELETE 3, остаются id 1, 2, 4
```

Первый запрос только показывает дубли. Второй удаляет: внутренний подзапрос выбирает `id` всех строк с номером больше 1 внутри своего адреса, внешний `DELETE` удаляет их.

Альтернатива — `DELETE ... USING`: `DELETE FROM emails a USING emails b WHERE a.email = b.email AND a.id > b.id;`. Результат тот же (удаляется строка, если есть строка с таким же адресом и меньшим `id`), но самосоединение квадратично растёт с размером группы дублей, и на больших группах оно медленнее.

Если нет уникального ключа, строку можно идентифицировать по `ctid` — физическому адресу строки в таблице:

```sql
DELETE FROM t
WHERE ctid IN (
    SELECT ctid FROM (
        SELECT ctid, row_number() OVER (PARTITION BY email) AS rn FROM t
    ) s WHERE rn > 1
);
```

> [!warning] ctid
> `ctid` меняется при `UPDATE` и при `VACUUM FULL` (полной перезаписи таблицы), поэтому это не идентификатор, а адрес. Используй его только внутри одного оператора. После очистки добавь ограничение `UNIQUE (email)`, иначе дубли вернутся. На больших таблицах удаляй пачками (по диапазонам `ctid` или `id`): одна долгая транзакция раздувает таблицу мёртвыми версиями строк и мешает работе `VACUUM` (фоновой очистке этих версий).

### Дни подряд

Условие: найти пользователей, которые входили три дня подряд и больше. Это задача типа gaps and islands.

Идея. Внутри каждого пользователя пронумеруем дни по возрастанию: 1, 2, 3 и так далее. У подряд идущих дней разность «дата минус номер» одинакова: например, 1 марта минус 1, 2 марта минус 2 и 3 марта минус 3 дают одну и ту же дату, 28 февраля. Когда в датах появляется пропуск, номер растёт на 1, а дата на 2 и более, поэтому разность сдвигается и начинается новая серия. Эта разность и служит идентификатором серии. Остаётся сгруппировать по пользователю и идентификатору серии, взять первый и последний день серии и их количество.

```sql
SELECT user_id, min(day) AS from_day, max(day) AS to_day, count(*) AS days
FROM (
    SELECT user_id, day,
           day - (row_number() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
    FROM logins
) t
GROUP BY user_id, grp
ORDER BY user_id, from_day;
-- пользователь: период (число дней).  1: 03-01..03-03 (3)   1: 03-05..03-06 (2)   2: 03-01..03-02 (2)   4: 03-10..03-13 (4)
```

Для условия «не меньше 3 дней» замени внешний `SELECT` на `SELECT DISTINCT user_id ... GROUP BY user_id, grp HAVING count(*) >= 3`: в ответе пользователи 1 и 4. Выражение `date - int` даёт `date` (число отнимается как количество дней). Вариант `day - row_number() * interval '1 day'` тоже работает (получится `timestamp`) и нужен, когда ключ сам имеет тип `timestamp`.

Если длина серии известна заранее, короче решается через `LEAD`: берём дату, стоящую на две строки впереди, и проверяем, что она ровно на 2 дня позже текущей.

```sql
SELECT DISTINCT user_id
FROM (SELECT user_id, day, lead(day, 2) OVER (PARTITION BY user_id ORDER BY day) AS d2 FROM logins) t
WHERE d2 - day = 2;   -- 1 и 4
```

Этот способ работает, пока в `(user_id, day)` нет дублей: `lead` смотрит на строку, а не на значение. Для серии переменной длины или для поиска самой длинной серии подходит только способ с `row_number`. Если дубли дней возможны, сначала сделай `SELECT DISTINCT user_id, day`. Индекс: первичный ключ `(user_id, day)` уже отдаёт данные в нужном порядке.

### Пропуски в последовательности id

Условие: какие `id` пропущены в `tickets`, где лежат 1, 2, 3, 6, 7, 10.

Есть два способа: найти диапазоны пропусков или перечислить каждое отсутствующее значение.

```sql
-- диапазоны пропусков
SELECT id + 1 AS gap_from, next_id - 1 AS gap_to
FROM (SELECT id, lead(id) OVER (ORDER BY id) AS next_id FROM tickets) t
WHERE next_id - id > 1;       -- 4..5, 8..9

-- каждое отсутствующее значение
SELECT g AS missing
FROM generate_series((SELECT min(id) FROM tickets), (SELECT max(id) FROM tickets)) g
LEFT JOIN tickets t ON t.id = g
WHERE t.id IS NULL;            -- 4, 5, 8, 9
```

Первый способ: для каждого `id` смотрим следующий (`lead`); если разница больше 1, между ними дыра, и её границы — `id + 1` и `next_id - 1`. Второй способ: `generate_series` создаёт ряд всех чисел от минимума до максимума, `LEFT JOIN` присоединяет существующие `id`, и там, где пары нет (`t.id IS NULL`), число отсутствует в таблице.

Первый способ быстрее на разреженных данных: `generate_series` порождает строку на каждое возможное значение. Оба способа видят только пропуски внутри диапазона; пропуск в начале (например, нет `id = 1`) придётся добавить отдельно. Пропуски в значениях `serial` (автоувеличиваемый счётчик) — норма: счётчик не откатывается вместе с откатом транзакции. Это не баг данных.

### Выручка по месяцам с пустыми месяцами

Условие: оплаченная выручка по месяцам за январь–апрель, при этом март должен быть в результате с нулём.

Идея: обычная группировка по месяцу вернёт только месяцы, в которых есть заказы. Поэтому сначала строим календарь из всех нужных месяцев (`generate_series`), а заказы присоединяем к нему через `LEFT JOIN`. Месяц без заказов остаётся в результате, потому что календарь стоит слева.

```sql
SELECT m::date AS month,
       coalesce(sum(o.amount), 0) AS revenue,
       count(o.id) AS orders
FROM generate_series('2025-01-01'::date, '2025-04-01'::date, interval '1 month') AS m
LEFT JOIN orders o
       ON o.status = 'paid'
      AND o.created_at >= m
      AND o.created_at <  m + interval '1 month'
GROUP BY m
ORDER BY m;
-- месяц: выручка / число заказов:  01: 350.00/3   02: 420.00/2   03: 0/0   04: 150.00/1
```

Почему работает и где подвохи:

- Без календаря `GROUP BY date_trunc('month', created_at)` вернёт три строки: марта в результате нет вовсе.
- Календарь стоит слева, а все условия на `orders` лежат в `ON`. Иначе `LEFT JOIN` превратится в `INNER` ([[#Условие на правую таблицу в WHERE]]).
- Условие `>= m AND < m + interval` — диапазон по столбцу, он использует индекс `orders (created_at)`. Запись `date_trunc('month', created_at) = m` индекс не использует, потому что функция применена к столбцу.
- `count(o.id)`, а не `count(*)`: иначе в пустом месяце будет 1.
- `sum` для пустого месяца даёт `NULL`, поэтому он обёрнут в `coalesce(..., 0)`.

### Медиана

Условие: медиана зарплат по компании и по отделам. Медиана — значение посередине упорядоченного набора, в отличие от среднего её не искажают выбросы.

```sql
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY salary) AS median,   -- 200
       percentile_disc(0.5) WITHIN GROUP (ORDER BY salary) AS disc,     -- 200
       avg(salary) AS avg                                                -- 209.44
FROM employees;

SELECT department_id, percentile_cont(0.5) WITHIN GROUP (ORDER BY salary)
FROM employees GROUP BY department_id;   -- 1: 200, 2: 250, 3: 212.5
```

`percentile_cont(0.5)` — непрерывный перцентиль 50%: если посередине два значения, он интерполирует между ними (в отделе 3 из 200 и 225 получилось 212.5). `percentile_disc(0.5)` — дискретный: возвращает реально существующее значение из набора. Запись `WITHIN GROUP (ORDER BY ...)` указывает, по какому порядку искать.

Агрегат сортирует всю группу, поэтому на больших таблицах он дорогой. Приближённая медиана для больших данных — отдельная тема (структура `tdigest` в расширениях). Вручную через `row_number` медиану пишут только на СУБД, где нет `percentile_cont`.

### Удержание (retention) и когорты

Условие: доля клиентов, сделавших заказ в месяц, следующий за месяцем их первого заказа. Когорта — группа клиентов, сделавших первый заказ в одном месяце. Удержание (retention) — какая часть когорты вернулась в следующий период.

Идея в три шага:

1. Для каждого клиента найти месяц первого заказа: это его когорта.
2. Составить список пар «клиент и месяц, в котором он делал заказы».
3. Для каждой когорты посчитать, сколько её клиентов есть в этом списке в месяце «когорта плюс один месяц».

```sql
WITH first_month AS (
    SELECT customer_id, min(date_trunc('month', created_at)) AS cohort
    FROM orders GROUP BY customer_id
), active AS (
    SELECT DISTINCT customer_id, date_trunc('month', created_at) AS month
    FROM orders
)
SELECT f.cohort::date,
       count(*) AS size,
       count(a.customer_id) AS returned,
       round(100.0 * count(a.customer_id) / count(*), 1) AS retention_pct
FROM first_month f
LEFT JOIN active a
       ON a.customer_id = f.customer_id
      AND a.month = f.cohort + interval '1 month'
GROUP BY f.cohort
ORDER BY f.cohort;
-- 2025-01: size 2, returned 2, 100.0   2025-02: size 1, returned 0, 0.0
```

Почему так:

- В `active` стоит `DISTINCT`: иначе два заказа клиента в одном месяце дали бы две строки и клиент посчитался бы дважды.
- `LEFT JOIN` сохраняет когорты, в которых никто не вернулся (получаем ноль, а не пропажу строки).
- `count(a.customer_id)`, а не `count(*)`, по той же причине, что в разделе про `COUNT`: строка без пары не должна считаться вернувшимся клиентом.
- Для кривой по нескольким месяцам добавь столбец «сдвиг в месяцах» (`month_offset`) и группируй по `cohort, offset`.

### Отдел с максимальной средней зарплатой

Условие: отдел (или отделы) с максимальной средней зарплатой. Средние: Backend 212.5, Ops 212.5, Data 203.3, то есть у двух отделов ничья.

Идея: посчитать среднюю зарплату по отделам, пронумеровать отделы по ней через `RANK` и оставить тех, у кого ранг 1. `RANK` даёт обеим ничьим первый ранг.

```sql
SELECT name, avg_salary
FROM (
    SELECT d.name, avg(e.salary) AS avg_salary,
           rank() OVER (ORDER BY avg(e.salary) DESC) AS rnk
    FROM departments d
    JOIN employees e ON e.department_id = d.id
    GROUP BY d.id, d.name
) t
WHERE rnk = 1;   -- Backend и Ops
```

Подвохи:

- `ORDER BY avg DESC LIMIT 1` вернёт одного из двух (какого именно, зависит от плана запроса) и тихо потеряет ничью.
- Оконная функция над агрегатом допустима: сначала выполняется `GROUP BY`, затем окно считается по получившимся группам.
- Отдел без сотрудников (Design) выпал из-за `INNER JOIN`. Если он нужен в результате с нулём, используй `LEFT JOIN` и `coalesce(avg(...), 0)`.

## CTE и LATERAL

### CTE и ключевое слово MATERIALIZED

`WITH имя AS (...)` создаёт CTE — именованный подзапрос, на который можно ссылаться в основном запросе. С PostgreSQL 12 нерекурсивный CTE без побочных эффектов, на который ссылаются один раз, встраивается в основной запрос как обычный подзапрос, и фильтры внешнего запроса спускаются внутрь. Этим поведением управляют ключевые слова: `MATERIALIZED` («вычисли CTE отдельно и сохрани результат») и `NOT MATERIALIZED` («встрой в запрос»).

```sql
-- встроится: Seq Scan с обоими условиями (по умолчанию для одной ссылки)
WITH paid AS NOT MATERIALIZED (SELECT * FROM orders WHERE status = 'paid')
SELECT count(*) FROM paid WHERE customer_id = 1;

-- посчитается отдельно и сохранится: в плане CTE Scan
WITH paid AS MATERIALIZED (SELECT * FROM orders WHERE status = 'paid')
SELECT count(*) FROM paid WHERE customer_id = 1;
```

Seq Scan — последовательное чтение всей таблицы, CTE Scan — чтение сохранённого результата CTE. В первом случае фильтр `customer_id = 1` объединяется с условием внутри CTE, во втором CTE сначала целиком выбирает оплаченные заказы, и только потом фильтруется.

- `MATERIALIZED` нужен, когда CTE дорогой и на него несколько ссылок (чтобы не считать дважды), либо когда нужен барьер оптимизации: запретить спуск условий внутрь или зафиксировать порядок вычисления.
- `NOT MATERIALIZED` принудительно встраивает CTE, даже если на него несколько ссылок.
- До PostgreSQL 12 CTE всегда материализовался, и утверждение «CTE — барьер оптимизации» осталось в головах. Сегодня по умолчанию это неверно.
- `WITH` с `INSERT`, `UPDATE` или `DELETE ... RETURNING` всегда выполняется ровно один раз и не встраивается.

### Все подчинённые любой глубины

Условие: найти всех прямых и непрямых подчинённых менеджера 1 с уровнем вложенности.

Идея: рекурсивный CTE. Он состоит из двух частей, склеенных `UNION ALL`: якорь (стартовая строка: сам менеджер 1) и шаг (найти сотрудников, чей менеджер уже попал в результат). База повторяет шаг по уровням: каждый раз применяет его к строкам, найденным на предыдущем шаге, и останавливается, когда шаг вернул пусто.

```sql
WITH RECURSIVE team AS (
    SELECT id, name, manager_id, 1 AS depth          -- якорь
    FROM employees WHERE id = 1
    UNION ALL
    SELECT e.id, e.name, e.manager_id, t.depth + 1   -- шаг: сотрудники, чей менеджер уже в team
    FROM employees e
    JOIN team t ON e.manager_id = t.id
)
SELECT id, name, depth FROM team WHERE id <> 1 ORDER BY depth, id;
-- 2, 3, 5 (depth 2); 4, 6, 7 (depth 3)
```

`UNION ALL` дешевле `UNION`: второй дедуплицирует результат на каждом шаге. Сам менеджер (id 1) исключён из результата условием `WHERE id <> 1`.

Обратная задача — цепочка начальников вверх. Поменяй условие соединения в шаге на `e.id = c.manager_id`, где `c` — имя рекурсивного CTE (в примере выше он назван `team`): для Gleb получится Gleb, Boris, Anna.

Индекс: `employees (manager_id)`. Без него на каждом шаге таблица сканируется целиком.

> [!warning] Циклы
> Если в данных есть цикл (Anna подчиняется Gleb, а Gleb через цепочку подчиняется Anna), рекурсия не остановится. Защита с PostgreSQL 14 — предложение `CYCLE`: оно запоминает пройденные значения и помечает строку, которая встретилась второй раз.
> ```sql
> WITH RECURSIVE team AS (
>     SELECT id, name, manager_id FROM emp_loop WHERE id = 2
>     UNION ALL
>     SELECT e.id, e.name, e.manager_id
>     FROM emp_loop e JOIN team t ON e.manager_id = t.id
> ) CYCLE id SET is_cycle USING path
> SELECT id, name, is_cycle FROM team;
> -- строка Boris встречается второй раз с is_cycle = true, и обход дальше не идёт
> ```
> До версии 14 путь копили массивом и отсекали уже посещённые узлы вручную.
> ```sql
> WITH RECURSIVE team AS (
>     SELECT id, name, manager_id, ARRAY[id] AS path FROM emp_loop WHERE id = 2
>     UNION ALL
>     SELECT e.id, e.name, e.manager_id, t.path || e.id
>     FROM emp_loop e JOIN team t ON e.manager_id = t.id
>     WHERE e.id <> ALL (t.path)
> )
> SELECT id, name, path FROM team;
> ```
> `emp_loop` — копия `employees`, где `manager_id` у Anna заменён на 4. `CYCLE` помечает повторный заход в узел и не идёт дальше, массив просто не пускает повторный узел в результат.

### LATERAL как топ-N в группе

Условие: два последних заказа каждого клиента.

Идея: `LATERAL` разрешает подзапросу в `FROM` ссылаться на столбцы таблицы, стоящей левее. Поэтому подзапрос выполняется отдельно для каждого клиента: берёт заказы именно этого клиента, сортирует от новых к старым и отрезает два через `LIMIT 2`.

```sql
SELECT c.name, o.id, o.amount, o.created_at::date
FROM customers c
CROSS JOIN LATERAL (
    SELECT id, amount, created_at
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY created_at DESC, id DESC
    LIMIT 2
) o
ORDER BY c.id, o.created_at DESC;
-- Ann: 4, 2   Bob: 7, 5   Dan: 9, 8   (Cat пропала: CROSS JOIN)
```

`CROSS JOIN` отбрасывает клиента, для которого подзапрос вернул пусто. Чтобы клиент без заказов остался в результате, используй `LEFT JOIN LATERAL (...) o ON true`: Cat вернётся со `NULL` в столбцах заказа. (`ON true` нужен потому, что синтаксис `LEFT JOIN` требует условие, а вся фильтрация уже внутри подзапроса.)

Индекс: `CREATE INDEX ON orders (customer_id, created_at DESC, id DESC)`. План для каждого клиента: `Index Only Scan ... Index Cond: (customer_id = c.id)` под `Limit`, то есть читаются только нужные две записи индекса. Это выигрыш перед `ROW_NUMBER`, который пронумеровал бы все заказы.

Когда `LATERAL` не нужен: на небольшой таблице окно проще и не хуже. `LATERAL` выигрывает, когда групп мало (или внешний список мал), а строк в каждой много. Если групп много, а в каждой по паре строк, цикл из тысяч отдельных проходов (nested loop, вложенный цикл) проиграет одному сканированию таблицы.

## Ловушки

### = NULL

`NULL` означает «неизвестно». Любое сравнение с ним даёт не «истина» и не «ложь», а `NULL`, а `WHERE` пропускает только истину.

```sql
SELECT count(*) FROM orders WHERE amount = NULL;                  -- 0, всегда
SELECT count(*) FROM orders WHERE amount IS NULL;                 -- 1
SELECT count(*) FROM orders WHERE amount <> 100;                  -- 7: заказ с NULL не вошёл
SELECT count(*) FROM orders WHERE amount IS DISTINCT FROM 100;    -- 8: NULL учтён
```

Для проверки на `NULL` существует `IS NULL`. Операторы `IS DISTINCT FROM` и `IS NOT DISTINCT FROM` сравнивают значения, считая `NULL` обычным значением. Тот же корень у ловушки с `NOT IN` ([[#Клиенты без заказов]]) и у того, что `count(col)` пропускает `NULL`.

### NOT IN с NULL

Подробно разобрано выше: [[#Клиенты без заказов]]. Правило: всегда `NOT EXISTS`, а `NOT IN` только с литеральным списком значений.

### BETWEEN и конец дня

`BETWEEN a AND b` включает обе границы. Для `timestamp` запись `'2025-01-31'` означает полночь начала 31 января, поэтому заказ из 31 января 23:30 в диапазон не попадёт.

```sql
SELECT count(*) FROM orders WHERE created_at BETWEEN '2025-01-01' AND '2025-01-31';          -- 2: потерян заказ 3
SELECT count(*) FROM orders WHERE created_at >= '2025-01-01' AND created_at < '2025-02-01';  -- 3
```

Правило: для времени всегда используй полуинтервал «с границы включительно, до границы не включая». Он не требует угадывать `23:59:59.999999`, стыкуется с соседними периодами без пересечений и пропусков и работает с индексом по `created_at`.

### Пагинация: нестабильный ORDER BY

Запрос `ORDER BY salary DESC LIMIT 3 OFFSET 2` при ничьей по `salary` не гарантирует порядок равных строк. Между запросами порядок может измениться, и один и тот же сотрудник попадёт на две страницы, а другой не попадёт ни на одну. Всегда добавляй уникальный ключ последним в сортировку: `ORDER BY salary DESC, id`.

### OFFSET на больших смещениях

`OFFSET 100000 LIMIT 20` читает и выбрасывает 100 000 строк, поэтому время растёт линейно вместе с номером страницы. Замена — keyset-пагинация: запомни ключ последней строки текущей страницы и в следующем запросе потребуй строки строго «после» этого ключа. Ключ сравнивается кортежем из двух столбцов: `(created_at, id)`.

```sql
SELECT id, created_at
FROM orders
WHERE (created_at, id) < ('2025-04-15 13:00+00', 8)   -- ключ последней строки прошлой страницы
ORDER BY created_at DESC, id DESC
LIMIT 3;                                               -- 7, 6, 5
```

Нужен индекс `(created_at DESC, id DESC)` и уникальный хвост ключа (`id`), иначе при равных `created_at` строки потеряются или повторятся. Цена такого подхода: нельзя перейти сразу на страницу N, можно только «дальше» и «назад». Подробнее и про фильтры — [[PostgreSQL#Бизнес-кейс: фильтры в каталоге]].

### DISTINCT как лечение размножения

Если после `JOIN` строк оказалось больше, чем должно быть, и ты ставишь `DISTINCT`, значит, соединение построено неверно.

```sql
SELECT DISTINCT c.name FROM customers c JOIN logins l ON l.user_id = c.id;                    -- работает, но платит за все пары
SELECT c.name FROM customers c WHERE EXISTS (SELECT 1 FROM logins l WHERE l.user_id = c.id);  -- тот же результат
```

`DISTINCT` маскирует проблему: пары уже построены, а дедупликация — это дополнительная сортировка или хеширование. И он не спасает суммы: после размножения строк `sum` уже посчитан неверно ([[#Размножение строк при JOIN двух «один-ко-многим»]]). Если нужны только значения левой таблицы, используй `EXISTS`. Если нужны агрегаты, агрегируй каждую сторону до `JOIN`.
