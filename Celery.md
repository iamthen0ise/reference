**Суть.** Celery — фреймворк фоновых задач для Python поверх брокера (RabbitMQ или Redis). Приложение кладёт задачу в очередь, воркеры её исполняют, результат (опционально) пишется в result backend. По умолчанию задача подтверждается **до** выполнения (at-most-once) — это самый частый вопрос-ловушка.

## Архитектура

| Компонент | Роль | На что смотреть |
| --- | --- | --- |
| Broker | хранит очереди задач | RabbitMQ надёжнее; Redis проще, но есть visibility timeout и риск потери при eviction/failover |
| Worker | исполняет задачи | pool: `prefork` (процессы, CPU-bound), `gevent`/`eventlet` (I/O-bound), `threads`, `solo` |
| Result backend | статус и результат | часто не нужен: `ignore_result=True`, иначе Redis засоряется |
| Beat | планировщик периодических задач | должен быть **ровно один** экземпляр, иначе задачи дублируются |
| Flower | мониторинг | + метрики длины очередей в Prometheus |

## Техника: надёжная задача

```python
@app.task(
    bind=True,
    acks_late=True,                   # ack ПОСЛЕ выполнения → at-least-once
    reject_on_worker_lost=True,       # воркер убит (OOM) → вернуть в очередь
    autoretry_for=(OperationalError, ConnectionError),  # только временные ошибки
    retry_backoff=True,               # 1, 2, 4, 8 … сек (потолок — retry_backoff_max)
    retry_backoff_max=600,
    retry_jitter=True,                # дефолт; случайная пауза от 0 до backoff
    max_retries=8,
    soft_time_limit=60, time_limit=90,
    ignore_result=True,
)
def charge_bonus(self, purchase_id: int) -> None:
    with transaction.atomic():
        # идемпотентность держит UNIQUE(purchase_id): exists() + create() две копии задачи пройдут обе
        Bonus.objects.get_or_create(purchase_id=purchase_id, defaults={...})

# Вызов — ТОЛЬКО после коммита транзакции, создавшей покупку
transaction.on_commit(lambda: charge_bonus.delay(purchase.id))
```

`reject_on_worker_lost` с `acks_late` вернёт в очередь и задачу, которая сама роняет воркер (OOM на огромном файле), — она будет крутиться бесконечно; ограничивай размер входа и следи за повторными доставками.

Настройки воркера: `worker_prefetch_multiplier=1` для долгих задач (иначе один воркер наберёт пачку и держит её, пока другие простаивают), `worker_max_tasks_per_child` против утечек памяти.

## Типичные ошибки

| Ошибка | Чем опасна | Лечение |
| --- | --- | --- |
| `delay()` внутри транзакции | воркер стартует раньше COMMIT и не находит запись; или транзакция откатилась, а задача уже ушла | `transaction.on_commit`, для гарантий — [[Kafka#Смежное: transactional outbox|outbox]] |
| Передача ORM-объекта в задачу | устаревшие данные, проблемы сериализации | передавать id, читать свежее в задаче |
| Дефолтный early ack | краш/деплой во время выполнения = задача потеряна | `acks_late` + идемпотентность |
| Redis-брокер + долгие задачи / ETA | после `visibility_timeout` (1 час) задача отдаётся другому воркеру — дубль | увеличить timeout, не делать ETA на часы вперёд |
| `countdown`/`eta` на дни вперёд | задачи висят в памяти воркера, при рестарте сюрпризы | таблица расписания в БД + периодический поллер |
| Одна очередь на всё | массовая рассылка забивает очередь, сброс пароля ждёт час | разные очереди по критичности (`task_routes`) и свои воркеры |
| Синхронное ожидание `.get()` внутри задачи | deadlock пула воркеров | canvas: `chain`, `group`, `chord` |
| Ретраи на всё (`autoretry_for=(Exception,)`) | баг в коде повторяется 8 раз, нагрузка на БД | ретраить только временные ошибки (см. [[Kafka#Ретраи при падении базы]]) |

## Канвасы: составные задачи

```python
chain(download.s(url), parse.s(), save.s()).delay()             # последовательно
group(resize.s(img, size) for size in SIZES).delay()            # параллельно
chord(group(fetch.s(s) for s in shops), build_report.s()).delay()  # fan-out + сбор
```

Для `chord` нужен result backend. Длинные бизнес-процессы с компенсациями в Celery делать больно: для них есть workflow-движки (Temporal).

## Альтернативы

- **RQ, Dramatiq, arq** — проще; Dramatiq по умолчанию делает ack после выполнения; arq — для asyncio.
- **Temporal** — долгие воркфлоу с состоянием, таймерами на дни, саги.
- **Очередь в PostgreSQL** ([[PostgreSQL#Техника: очередь задач на SKIP LOCKED|SKIP LOCKED]], procrastinate) — задача создаётся в той же транзакции, что и данные: dual write нет вообще.

## Бизнес-кейсы

- **«Клиент оплатил, а чек не пришёл».** Типичная причина — early ack + деплой во время выполнения, или `delay()` до коммита. Для фискальных чеков (законодательное требование) нужны outbox, `acks_late`, идемпотентность по id оплаты и ночная сверка «оплаты без чека».
- **Массовая рассылка на 1 млн пользователей.** Не ставить 1 млн задач разом: задача-нарезчик ставит пачки по 1000 в отдельную очередь с rate limit. `rate_limit='100/s'` в Celery — на **каждый воркер**, а не на всех: 10 воркеров дадут 1000/s; общий лимит провайдера держат через Redis-счётчик ([[Redis#Техника: rate limiter]]). Иначе письма сброса пароля и транзакционные уведомления встанут в очередь за маркетингом, а провайдер забанит за превышение лимита.
- **Ночной отчёт по beat выполнился дважды.** Два пода с beat после релиза. Защита: один инстанс beat (отдельный deployment с `replicas: 1`) + сама задача берёт advisory lock или проверяет «отчёт за дату уже есть».

## Что спросят дальше

- Чем отличается `soft_time_limit` от `time_limit`? — soft бросает исключение внутри задачи (можно прибраться), hard убивает процесс.
- Prefork или gevent? — prefork для CPU-задач (обход GIL процессами), gevent для сотен параллельных HTTP-вызовов.
- Что будет с задачами при деплое? — SIGTERM даёт warm shutdown: воркер перестаёт брать новое и доделывает текущее. Kubernetes ждёт `terminationGracePeriodSeconds` (30 с по умолчанию) и убивает — долгие задачи прервутся; с `acks_late` они вернутся в очередь, без него пропадут. Grace period ставят больше самой долгой задачи.
- Как масштабировать? — по длине очереди и времени ожидания (KEDA), отдельные пулы воркеров на очереди; помнить про лимит соединений к БД.
