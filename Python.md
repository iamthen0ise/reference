## Короткие ответы

**Декоратор.** Функция, которая принимает функцию и возвращает обёртку; `@d` над `def f` — это `f = d(f)`, выполняется один раз при импорте. Обёртке всегда ставят `functools.wraps`, иначе теряются имя, документация и сигнатура (ломаются логи, FastAPI, Celery). Декоратор с параметрами — лишний уровень вложенности. Для `async def` нужна асинхронная обёртка с `await`, иначе декоратор работает с корутиной, а не с выполнением. → [[Python-протоколы#Декораторы]]

**Повтор с задержкой (retry).** Ловить только переданные временные ошибки, задержка растёт экспоненциально с потолком и случайным разбросом (jitter), на последней попытке — голый `raise`. Не ловить `BaseException`, чтобы не глушить отмену. Повторять только идемпотентные операции. → [[Python-протоколы#Декоратор с параметрами: повтор при ошибках с экспоненциальной задержкой]]

**Итератор и генератор.** Итерируемый объект отдаёт итератор через `__iter__`; итератор отдаёт элементы через `__next__` и одноразовый. Генератор — функция с `yield`, самый короткий способ написать итератор: состояние хранится в замороженном кадре функции. Ленивый, держит в памяти один элемент. Асинхронный вариант — `__aiter__`/`__anext__` или `async def` с `yield`, обходится через `async for`. → [[Python-протоколы#Итераторы и генераторы]]

**Контекстный менеджер.** `__enter__` на входе, `__exit__` на выходе при любом исходе; `True` из `__exit__` глотает исключение. Если упал `__enter__`, `__exit__` не вызовется. Асинхронный — `__aenter__`/`__aexit__` и `async with`. → [[Python-протоколы#Контекстные менеджеры]]

**contextlib.** `@contextmanager` превращает генератор с одним `yield` в менеджер; очистку обязательно оборачивать в `try/finally`, иначе при исключении она не выполнится. `ExitStack` — когда число ресурсов заранее неизвестно. Ещё `suppress`, `closing`/`aclosing`, `nullcontext`. → [[Python-протоколы#contextlib]]

**`__new__`, `__init__`, `__call__`.** `C()` вызывает `type.__call__`, тот — `__new__` (создать объект), потом `__init__` (заполнить), если `__new__` вернул экземпляр `C`. `__new__` нужен для наследования от неизменяемых типов и контроля числа экземпляров. `__call__` делает объект вызываемым как функцию. → [[Python-классы#Как создаётся объект]]

**MRO и C3.** Порядок, в котором ищутся методы при наследовании. C3: потомок раньше родителей, порядок родителей сохраняется, порядок у родителя не ломается у потомка. Считается слиянием MRO родителей: берём первую голову списка, которой нет ни в одном хвосте. `super()` идёт к следующему классу в MRO объекта, а не к родителю. → [[Python-классы#Порядок разрешения методов (MRO)]]

**`__slots__`.** Фиксированный набор атрибутов вместо `__dict__`: меньше памяти (с 3.11 выигрыш около 40%, а не в разы), опечатка в имени атрибута сразу даёт ошибку. Ловушки: подкласс без слотов возвращает `__dict__`, два родителя со слотами несовместимы, `cached_property` не работает. Удобно — `@dataclass(slots=True)`. → [[Python-классы#__slots__]]

**Виды параллелизма.** Потоки — для блокирующего ввода-вывода; процессы — для вычислений; asyncio — для тысяч соединений в одном потоке; субинтерпретаторы и сборка без GIL — новые способы считать параллельно в одном процессе. → [[Python-конкурентность#Виды параллелизма]]

**GIL.** Блокировка в CPython: Python-байткод в каждый момент выполняет один поток. Отпускается на вводе-выводе и в C-расширениях, поэтому потоки ускоряют ожидание, но не вычисления. Не делает код потокобезопасным: «проверить, потом действовать» ломается. С 3.14 есть официально поддерживаемая сборка без GIL, но не по умолчанию. → [[Python-конкурентность#GIL]]

**GC.** Основной механизм — подсчёт ссылок: счётчик дошёл до нуля — объект удалён сразу. Циклы находит поколенческий сборщик: он смотрит только контейнеры и удаляет группы, на которые нет ссылок снаружи. Утечки в Python — это почти всегда забытые ссылки (кэши, глобальные списки), а не баг сборщика. → [[Python-конкурентность#Сборка мусора (GC)]]

**Синхронизация потоков и процессов.** Потоки: `Lock`, `RLock`, `Semaphore`, `Event`, `Condition`, а лучше всего — `queue.Queue` вместо общего состояния. Блокировки всегда в одном порядке, чтобы избежать deadlock. Процессы: `Queue`/`Pipe`, `Value` с `get_lock()`, общая память. Между независимыми процессами и серверами — база, Redis или брокер сообщений. → [[Python-конкурентность#Синхронизация потоков]]

**Async под капотом.** Корутина — функция, которая умеет приостанавливаться на `await`, устроена как генератор. Future — обещание результата с колбэками. Task — ведёт корутину и продолжает её, когда готов Future, которого она ждёт. Цикл событий — однопоточный планировщик: выполняет готовые колбэки, ждёт сокеты через `epoll`/`kqueue` и срабатывание таймеров. Блокирующий вызов в корутине останавливает всех. → [[Python-конкурентность#Async под капотом]]

## Python против других языков

### Сильные стороны

- **Скорость разработки и читаемость.** Мало шаблонного кода, рабочий прототип за часы, код легко читать новому человеку. Для бизнеса это часто важнее скорости выполнения: время разработчика дороже серверов.
- **Экосистема.** Веб и API (Django, FastAPI, SQLAlchemy, pydantic, Celery), данные и ML (numpy, pandas, PyTorch, scikit-learn), автоматизация, DevOps-скрипты. В ML и работе с LLM Python — стандарт де-факто.
- **Язык-«клей».** Узкие места легко вынести в нативный код: Cython, расширения на Rust через PyO3, C через cffi. numpy и PyTorch — Python-интерфейс к C, C++ и CUDA, поэтому «медленный Python» в ML обычно не узкое место.
- **Постепенная типизация.** Аннотации типов и проверка mypy/pyright добавляются по мере роста проекта; pydantic проверяет данные в рантайме на границе с внешним миром.
- **Найм и порог входа.** Много разработчиков, язык учат в вузах, легко перейти из аналитики и QA.

### Слабые стороны

- **Скорость CPython на вычислениях.** Интерпретатор, динамическая типизация, каждое число — объект в куче. На циклах с арифметикой Python в десятки раз медленнее Go, Java и Rust. Что смягчает: специализирующий интерпретатор (PEP 659, с 3.11 в среднем на четверть быстрее), экспериментальный JIT с 3.13, PyPy, вынос горячего кода в нативные расширения.
- **Параллелизм.** Из-за GIL потоки не ускоряют вычисления, процессы дороги по памяти и требуют сериализации. Ситуация меняется (сборка без GIL, субинтерпретаторы), но библиотеки догоняют годами.
- **Память.** Объект с тремя полями — около 100 байт, `int` — 28 байт. Миллионы объектов в памяти обходятся дорого.
- **Ошибки типов — в рантайме.** Аннотации не проверяются при выполнении; опечатка в имени атрибута или `None` там, где не ждали, вылезет в проде, если не настроены тайпчекер и тесты.
- **Деплой.** Нет единого бинарника, как у Go: нужен интерпретатор, зависимости, виртуальное окружение; образы контейнеров больше, холодный старт медленнее. Пакетный менеджмент долго был больным местом; сейчас его в основном закрывает uv.
- **Два мира: sync и async.** Асинхронная функция «заражает» всех, кто её вызывает (проблема «цветных функций»). Многие библиотеки существуют в двух версиях, а один синхронный вызов в асинхронном сервисе тормозит всех.

### Как ответить на собеседовании

«Python беру, когда важны скорость разработки и экосистема, а узкое место — ввод-вывод: база, сеть, очереди. Большинство бэкендов именно такие, и там время ответа определяет SQL-запрос, а не язык. Когда узкое место — вычисления, есть варианты: numpy или нативное расширение, процессы, задачи в очереди. Если весь сервис упирается в CPU или нужна гарантированно низкая задержка с высокой конкурентностью (шлюз, стриминг, обработка миллионов событий в секунду), такой сервис пишу на Go или Rust рядом с Python-сервисами, а не переписываю всё».
