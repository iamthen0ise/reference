# SQL-рецепты — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Добавить группу меню «Базы данных → SQL-рецепты»: сквозная задача «Библиотека» (схема, сценарии с индексами, множества), три служебные страницы (эффективность индексов, пожар, отладка) и указатель. Каждый вывод — из прогона на PostgreSQL 17 через инструмент в репозитории.

**Architecture:** Страницы — заметки Obsidian в `Бэкенд/Базы данных/SQL-рецепты/` и пункты `sidebar` в `.site/astro.config.mjs`. SQL живёт только в `.md`. Каждый запускаемый блок имеет уникальный на странице `title="<имя>.sql"`. Скрипт `.site/scripts/sql-pg.sh` поднимает Postgres в Docker, загружает схему и данные из блоков страницы «Схема библиотеки» и прогоняет блок любой страницы по его `title`. Вывод вставляется в страницу вручную.

**Tech Stack:** Obsidian markdown, Astro Starlight, Docker (`postgres:17-alpine` или `postgres:17`), `psql` внутри контейнера, bash.

**Spec:** `docs/superpowers/specs/2026-11-20-sql-cookbook-design.md` — исполнитель читает его целиком: состав каждой страницы перечислен там, здесь не повторяется.

## Review Focus

1. **План на маленьких таблицах выдан за доказательство индекса.** На 20 строках планировщик берёт Seq Scan при любом индексе, а на `big` без `ANALYZE` оценки неверны. Задача 1: `up big` выполняет `VACUUM ANALYZE`. Задачи 2–6: каждый план показан на `big`, и это подписано.
2. **Запрос верен на «удобных» данных, но ломается на краевых:** читатель без единой выдачи, книга без автора, NULL в подзапросе `NOT IN`, повторная выдача той же книги. Задача 1 закладывает эти строки в `small` (список ниже). Задача 3 показывает, что каждое из решений даёт одинаковый результат и на `small`, и на `big` (сверка через `EXCEPT` в обе стороны, ожидается 0 строк).
3. **Совет удалить индекс, который держит ограничение.** Задача 4: запрос неиспользуемых индексов исключает индексы под `PRIMARY KEY`, `UNIQUE` и ограничения из `pg_constraint`. Вывод показывает, что частичный уникальный индекс из задачи 1 с нулём сканирований не попал в кандидаты.
4. **Сессии демонстрации пожара остаются висеть.** У каждой фоновой сессии есть верхняя граница жизни (≤ 60 с). После задачи 5 `make sql-down` и `docker ps --filter name=reference-pg -q` пусто.
5. **Замер, где разница — шум.** Задачи 2 и 3 прогоняют каждый вариант 3 раза и публикуют медиану. Если варианты в пределах 20 % друг от друга, на странице написано «разницы нет на N строках».

  - `make sql-up SEED=small|big` (по умолчанию `small`) — пересоздаёт контейнер `reference-pg`, база `library`, пользователь `postgres`. Загружает блоки `schema.sql`, затем `seed-small.sql` или `seed-big.sql` со страницы «Схема библиотеки», затем `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` и `VACUUM ANALYZE`. ### Task 5: Пожар в PostgreSQL

Риск: высокий — конкурентность и действия на живой базе.

**Files:** Create `Бэкенд/Базы данных/SQL-рецепты/Пожар в PostgreSQL.md`; Modify `.site/scripts/sql-pg.sh`, `.site/scripts/sql-pg.test.sh`, `Makefile`, `.site/astro.config.mjs`.

**Interfaces:**
- Consumes — задача 1.
- Produces: `make sql-bg PAGE="…" TITLE="<имя>.sql"` — запускает блок в фоновой сессии с `application_name` = имя блока без `.sql` и возвращается, когда блок начал работу: сессия в `pg_stat_activity` вышла за ведущие `SET` и `BEGIN` и держит транзакцию, выполняет запрос или ждёт блокировку; блок, успевший завершиться, — по коду выхода `psql` (не дольше 10 с, иначе выход 1; сессия с тем же именем уже есть — выход 1 сразу). Подход: блок копируется в контейнер, `psql -f` запускается через `docker exec -d`.

**Обязательно на странице:**
- Чек-лист порядка действий в начале страницы.
- Сценарий: сессия держит строку в открытой транзакции (`idle in transaction`, ≤ 60 с), вторая ждёт ту же строку, третья — `ALTER TABLE` встаёт в очередь за второй и блокирует всех следующих. Диагностика прогоном: `pg_stat_activity`, `pg_blocking_pids`, цепочка до корня рекурсивным запросом.
- `pg_cancel_backend` ожидающей сессии и `pg_terminate_backend` корня — вывод и что стало с транзакцией.
- Соединения: число по `state` против `max_connections`.
- `lock_timeout` и `statement_timeout` — ошибка из прогона. `idle_in_transaction_session_timeout` — сессию закрывает сервер, показать прогоном.

- [ ] **Тест до кода:** в `sql-pg.test.sh` — `bg` блока `SELECT pg_sleep(5)` → код 0, и `application_name` найден в `pg_stat_activity`; несуществующий блок → код 1. Запуск — падает.
- [ ] **Реализовать `bg`**, `make sql-test` — проходит.
